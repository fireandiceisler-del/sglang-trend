# SGLang 技术趋势周报 — 2026-W33

> 周期：2026-08-10 ～ 2026-08-16  
> 范围：KV Cache / Prefill-Decode Disaggregation / Scheduler / Speculative Decoding  
> 过滤：纯模型适配、普通小修、机械重构；仅保留能体现架构演进、性能边界或跨特性组合问题的变化。

## 一句话结论

本周 SGLang 的核心变化不是继续堆叠独立 feature，而是开始**把异步执行、状态生命周期和跨特性组合的 contract 显式化**：P/D 从粗粒度的 phase split 向 layer-wise compute/transfer pipeline 演进；Scheduler 把 CUDA stream 上的读结束点、对象生命周期和写入顺序拆成不同的同步契约；KV Cache 逐渐从“保存 attention KV”扩展为 Full/SWA/Mamba/DSA indexer/spec draft 等多组件状态系统；Speculative Decoding 的优化重点也从单纯提高 acceptance length，扩展到显存容量、verify 数据搬运、状态回滚/恢复与调度公平性。

## 1. 本周最重要的架构变化

### 1.1 P/D 正从 phase-level disaggregation 走向 layer-wise pipeline

**PR #34905 — Layer-wise KV transfer for P/D disaggregation**  
https://github.com/sgl-project/sglang/pull/34905

传统 P/D 路径大致是：

```text
Prefill 全部层计算完成
        ↓
KV / state 整体传输
        ↓
Decode 开始
```

#34905 开始把这个边界拆成：

```text
Layer group 0 compute ──► transfer group 0
Layer group 1 compute ──► transfer group 1
Layer group 2 compute ──► transfer group 2
               ...
```

也就是让**后续层计算与前面层的 KV/state 传输重叠**。实现不只是给 MHA KV 做分层传输，而是建立了 `layer_id -> buffer handle` 的映射，覆盖 MHA/MLA、DSA、SWA、Mamba、DeepSeek-V4 state，并继续向 EAGLE/DSpark 的 draft state 透传。

这意味着 P/D 的抽象正在变化：它不再只是“两个实例之间搬 KV”，而逐渐变成一个**带状态依赖的 pipeline runtime**。

性能上，Qwen3.5-35B-A3B-FP8 在 4×RTX 5090 上，TTFT 下降约 **15.9%～35.3%**；DeepSeek-V4-Flash 在 8×H100、8K prompt 的中高并发场景中，TTFT 下降约 **4.4%～16.9%**。同时 TPOT 基本没有明显收益，符合预期：这个优化主要缩短的是 Prefill 完成到 Decode 可开始之间的 critical path。

值得注意的是，高 cache-hit 或极长 prompt 场景下收益会变小，因为可与传输重叠的 Prefill compute window 缩短，或者 TTFT 已经主要被排队时间支配。

### 1.2 Scheduler 开始显式描述 CUDA Graph metadata 的“读结束点”

**PR #34982 — SharedReadEnds**  
https://github.com/sgl-project/sglang/pull/34982

Overlap Scheduler 的危险点是：Scheduler 想尽早准备下一批 metadata，而上一批 forward 可能仍在另一个 CUDA stream / CUDA Graph 中读取相同的共享状态。

本周这一套同步逻辑进一步被抽象为明确的读结束语义：

```text
PRE_REPLAY
IN_REPLAY
POST_REPLAY
UNKNOWN
```

并且 wrapper backend 不再自己声明一个粗略边界，而要根据真正读取 metadata 的 child backend 聚合出最晚读结束点。

这看似只是 fence API 重构，实际上反映了一个很重要的 runtime 设计方向：

> **Scheduler 与 Attention Backend 之间需要显式的异步内存访问 contract，而不能依赖“forward 函数返回了，所以应该读完了”这样的同步直觉。**

本周多个问题都在强化同一件事：

- #34076：tensor 的 Python 生命周期结束，但 forward stream kernel 仍在读取；
- #34077：旧 request 的 forward-tail relay write 可以晚于新 request 的 staging write；
- #34319：`record_stream()` 能保护 allocator lifetime，却不能阻止 persistent buffer 被下一次 forward 原地覆盖；
- #34449：跨 rank collective 顺序需要精确 CUDA Event，而不是整条 forward stream 的粗粒度 barrier；
- #34816 / #34890：DSPARK / EAGLE 的 WAR read-done 继续向 CUDA Graph 内部更精确的位置推进。

这些变化共同说明，SGLang 的 overlap scheduler 正逐渐形成三套分离的概念：

```text
1. lifetime       —— 这块显存什么时候可以被 allocator 复用？
2. mutation       —— 谁还能修改这个 persistent buffer？
3. happens-before —— 两个 stream 上的读写到底谁先发生？
```

三者不能互相替代。

### 1.3 KV Cache 正从 token cache 变成 multi-component state manager

本周 KV Cache 相关变化的共同点是：系统越来越少用一个“token 数”来抽象所有状态，而更关注**真正的物理 page、组件和状态版本**。

**PR #34958 — exact page demand for paged prefill eviction**  
https://github.com/sgl-project/sglang/pull/34958

旧逻辑在 paged allocation 前用“extend token 数 + batch_size × page_size”估算需求，可能为了一个实际只缺 32 token/page-capacity 的请求，按 353 token 的 shortfall 去 eviction。新逻辑直接通过 allocator 的 `get_num_new_pages()` 计算真实 page demand。

这里的重要思想是：

> admission / eviction 应该基于 allocator 的真实物理资源单位，而不是逻辑 token 的保守近似。

**PR #34801 — P/D retraction through HiCache host pool**  
https://github.com/sgl-project/sglang/pull/34801

P/D Decode request 被 retract 时，以前会走一套独立的 per-request CPU tensor backup；现在开始复用 HiCache host pool，并同时保存 target KV 与 speculative draft sidecar KV。

这说明 HiCache 正逐渐成为统一的**状态连续性层**：不仅服务 prefix reuse，还负责 P/D retraction、Spec draft state、Full/SWA 等组件的恢复。

**PR #34870 — SWA eviction frontier for EAGLE bigram key**  
https://github.com/sgl-project/sglang/pull/34870

EAGLE bigram key 的 key length 与它代表的 token span 并不相同。如果 SWA eviction 仍按 raw-token key 的假设计算 frontier，会只留下半个 sliding window，最终造成匹配失败并错误释放 tree 已经拥有的 KV。

这类问题说明在 Unified Radix Cache 中，下面几个长度已经不能混为一谈：

```text
logical token depth
radix key depth
physical page depth
SWA live window depth
speculative key encoding depth
```

### 1.4 Speculative Decoding 的瓶颈已经从 acceptance 扩展到“状态成本”

本周几项性能变化很有代表性。

**#34290：动态 Spec capacity**  
历史上 Spec 的 `max_running_requests` 存在较保守的固定上限；改为结合 Decode CUDA Graph / 显存容量推导后，8×H200 的 GLM-5.2 + MTP 测试报告吞吐达到约 **2.375×**。这说明 speculative throughput 不只是由 acceptance 决定，也可能长期被 runtime capacity ceiling 限制。

**#30967：MTP recurrent state 从 snapshot 转向 replay/recompute**  
https://github.com/sgl-project/sglang/pull/30967

GDN/Mamba 类 draft state 如果每个 speculative token 都保存完整 recurrent state，显存和 copy 成本会随 draft width 增长。新的方向是只保存能够重放的输入，并对 accepted state 做异步 recomputation。BS=512 的测试中吞吐从 **19,879.96 → 23,407.08 tok/s（约 +17.7%）**。

**#34775：DSA cache relocation 批量化**  
多层 DSA speculative cache relocation 从 78 层 × 多次 launch 的约 **234 次 GPU 操作**压缩为 **2 次 full-cache launch**，microbenchmark 报告约 **12×～76×** 的提升。

**#34847：prefetch policy 必须跟 batch geometry 变化**  
固定 4-block prefetch 在高 batch 下会让 prefetch 自身成为 critical path；改成 one-block-per-request 后，BS=54 相比旧异步策略报告 **+245.8%**，同时重新比同步 swap-in 快约 10%。

**#34846：draft correctness 与 final correctness 不是同一个指标**  
EPLB 后，DSpark draft MoE 如果仍把 logical expert id 当 physical slot，target model 最终仍可能生成正确输出，但 draft quality 会显著下降：报告中的 accept length 从约 3.38 掉到 1.61；修复后 output throughput 从 **161.64 → 313.24 tok/s（约 +93.8%）**。

因此评估 speculative decoding 不能只看最终 accuracy，需要至少同时看：

```text
final model correctness
acceptance length / acceptance rate
draft-state correctness
verify latency
state-copy / cache-relocation cost
runtime capacity
```

## 2. 四个方向的本周演进

### KV Cache

本周最明显的趋势是 **“精确物理记账 + 多组件状态统一”**。

- #34958：eviction 从保守 token estimate 转向 exact page demand。
- #34801：P/D retraction 开始复用 HiCache host pool，并保护 target + draft KV。
- #34870：SWA eviction 开始正确区分 raw key 与 EAGLE bigram key 的长度语义。
- #34653 / #34924：Unified Cache 更积极释放 out-of-window SWA slot，同时补齐 DFLASH/DSPARK 的 eviction bookkeeping。
- #34899 Roadmap：开始建设 bit-exact cache restore correctness oracle。

**Roadmap #34899 — Bit-exact correctness coverage**  
https://github.com/sgl-project/sglang/issues/34899

这是本周最值得长期关注的 cache 方向之一。目标是让 deterministic path 下的 prefill/decode logprob 完全一致，使：

> 任意非零 KL 都可以直接视为 KV/state reuse bug。

当前已经覆盖 base cache、Mamba `extra_buffer`、HiCache multi-turn；下一阶段明确指向 MTP、DSpark/DFlash 和 Unified Memory。

### Prefill / Decode Disaggregation

本周 P/D 的重点从“能不能分离”转到**分离后的执行粒度与状态协议**。

- #34905：layer-wise KV/state transfer，把 compute 与 transfer pipeline 化。
- #34191：Prefill role 不再为只在 target-verify 使用的 speculative state 分配显存，Qwen3.5-397B 测试可减少约 **4.31 GB/rank** dead state；更深 PP 场景报告可到约 **24 GB/rank**。
- #33584：Prefill-side PP 与 EAGLE 开始组合，说明 P/D prefill worker 正变成独立可扩展的执行拓扑，而不只是单一 TP engine。
- #34289：NIXL endpoint 增加 process-generation identity，处理 Prefill Pod 替换后的 stale endpoint 问题。
- #34077：P/D bootstrap staging 与旧 forward tail write 的跨 stream 顺序被显式 fence。
- #34977：Mooncake / NIXL 开始补统一 P/D protocol 的 wire-semantics truth table。

总体趋势可以概括为：

```text
过去：P/D = KV transport feature
现在：P/D = role-specific runtime + state protocol + pipeline execution
```

### Scheduler

Scheduler 本周有两个明显方向。

第一是**更精确的异步同步 contract**，典型就是 `SharedReadEnds`、immutable snapshot、stream event/fence、tensor lifetime pin。

第二是**从单纯吞吐优先转向 QoS / fairness**。

#34623 把 chunked-prefill 的“全局 batch budget”与“单请求 service quantum”拆开，允许多个 long prompt 同时 mid-prefill，也允许后续短请求绕过已占满的 long-prefill slot，直接针对 HOL blocking 和 TTFT tail。

新 PR #35017 则进一步处理 DP-attention 下的 decode starvation：一次 EXTEND 后，可以强制后续 N 个 scheduler round 优先给 running batch decode。AgentX 3600 秒测试中，8×B200、TP8/DP8/EP8、MTP3、interval=16 的结果为：

- concurrency 56：23,559 tok/s/GPU，interactivity 30.76 tok/s/user；
- concurrency 84：26,110 tok/s/GPU，interactivity 23.24 tok/s/user。

这说明 scheduler optimization 开始越来越关注**用户交互速率、prefill/decode 公平性和跨 DP rank 的一致决策**，而不只是最大 batch throughput。

### Speculative Decoding

本周 Spec 的主线是**“组合正确性 + 状态成本优化”**。

- #34290：Spec capacity 不再依赖历史固定上限。
- #30967：recurrent draft state 从 snapshot 走向 replay/recompute。
- #34775：DSA relocation 从逐层小操作改成 bulk operation。
- #34847：prefetch 策略开始 batch-aware。
- #34846：EPLB 后 draft expert mapping 的 correctness 直接影响 acceptance/perf。
- #34924：修复 SWA eviction bookkeeping 后，长 decode output throughput **2240.55 → 2835.66 tok/s（+26.6%）**，Mean TPOT **8.01 → 4.42 ms（-44.8%）**，accept length 基本不变——收益来自 KV 生命周期，而不是 draft quality。
- #34478：DSpark 开始支持 output logprobs，为 #34899 的 exact-KL correctness 测试铺路。

同时，Issue #34959 暴露了 DeepSeek-V4-Flash 多位置 DSPARK verify 在 heterogeneous concurrent batch 下仍可能出现 silent corruption；这也是为什么“最终文本看起来正常”已经不足以作为 Spec + Cache 的 correctness gate。

## 4. 哪些设计正在成为主流

### 4.1 Role-specialized resource allocation

Prefill、Decode、Target Verify 不再默认拥有完全相同的 state/CUDA Graph/显存结构。#34191 是很典型的信号：**根据 execution role 决定哪些 state reachable，再做 allocation**。

这比统一分配后再“尽量不用”更适合大模型推理，因为一个 rank 上几 GB 的 dead state 乘上多 rank 后代价非常大。

### 4.2 Pipeline everything

过去的 overlap 主要是 Scheduler CPU ↔ GPU forward；现在进一步变成：

```text
Prefill layer compute ↔ KV/state network transfer
Scheduler metadata prep ↔ CUDA graph replay
Spec verify ↔ state prefetch / relocation
```

未来 runtime 优化越来越像一个 dataflow scheduling 问题，而不仅是 kernel optimization。

### 4.3 Explicit asynchronous ownership

本周最重要的工程思想之一：

```text
record_stream ≠ immutable snapshot ≠ CUDA event ≠ stream fence
```

- `record_stream`：延长 allocator lifetime；
- snapshot：防止 producer 后续原地 mutation；
- CUDA event：建立一个精确执行点的依赖；
- stream fence/wait：建立跨 stream happens-before。

这些概念正在从隐含经验变成 runtime API contract。

### 4.4 “KV Cache”正在演变成 State Cache

Full attention KV、SWA KV、Mamba recurrent state、DSA indexer K、compressor state、Spec draft KV 都要一起经历：

```text
allocate
commit
cache
move
retract
restore
rollback / discard
```

因此未来很多 KV Cache 设计问题，本质已经不是简单的 `K/V tensor` 生命周期，而是**多组件事务状态管理**。

### 4.5 Correctness 从 benchmark 走向 exact oracle

Accuracy benchmark 能发现大问题，但 silent cache corruption 可能仍生成流畅文本；#34899 的 zero-KL 路线是非常重要的变化：先构造 bit-exact baseline，再让每一个 cache/save/restore feature 都证明等价性。

这会比“GSM8K 没掉多少，所以应该没问题”更适合作为 cache runtime 的 CI gate。

### 4.6 Composability 成为一等指标

当前 Roadmap 中仍然明确未完成的组合包括：

- DCP × DSpark × HiCache × P/D；
- PP + Spec + P/D；
- Unified Memory × Spec / P/D / HiCache；
- general DCP × DFlash / EAGLE。

这意味着判断一个推理系统是否成熟，不能只问：

> “这个 feature 支不支持？”

而要问：

> “这个 feature 和另外三到四个生产 feature 同时开启时，状态语义是否仍然成立？”

## 5. 对 AI Infra 面试和项目实践的启发

### 5.1 面试题：为什么 `record_stream()` 不能解决所有 overlap race？

建议能清楚回答：`record_stream()` 只告诉 caching allocator 某 tensor 仍被另一个 stream 使用，避免显存 block 被过早复用；如果这个 tensor 是 persistent buffer，下一次 forward 仍然可以对同一地址做原地写，这时需要 snapshot 或读写 fence，而不是 `record_stream()`。

### 5.2 面试题：Layer-wise P/D 为什么能降低 TTFT？什么时候收益会消失？

核心是把：

```text
T_prefill_compute + T_KV_transfer
```

尽量变成：

```text
max(T_prefill_compute, T_KV_transfer) + pipeline bubble
```

但如果 prefix cache hit 很高，Prefill compute 变短，transfer 更容易暴露到 critical path；如果队列等待本身已经占 TTFT 大头，compute-transfer overlap 也无法解决排队延迟。

### 5.3 面试题：Speculative Decoding 为什么需要“optimistic state”与“committed state”？

Draft/verify 会提前产生多个 candidate token，对应 KV/SWA/Mamba/indexer state；只有 accepted prefix 能真正 commit。系统必须支持：

```text
produce optimistic state
verify
commit accepted prefix
rollback / discard rejected suffix
```

这也是 #34189、#34870、#34924 等问题背后的共同本质。

### 5.4 面试题：为什么 KV eviction 应该按 physical page demand，而不是 token count？

paged allocator 的真实资源单位是 page。一个 request 可能只需要补一部分新 page，token 级保守估计会造成过度 eviction，既损失 prefix cache 命中率，也增加后续 recompute/restore 成本。

### 5.5 项目实践：建立“组合矩阵”而不是单 feature 单测

如果自己做推理引擎项目，建议至少设计这样的 CI 维度：

```text
Cache:  Radix / HiCache / Unified
Spec:   Off / EAGLE / DSpark
Serve:  Unified / P-D
Par:    TP / DP / DCP / PP
Sched:  Normal / Overlap
```

不需要穷举所有笛卡尔积，但要明确哪些交叉点是高风险状态边界，并针对它们做 differential / exact-logprob 测试。

## 6. 下周值得继续关注

1. **#34905 是否推进合入，以及 layer-wise P/D 是否扩展到 NIXL / MORI。** 当前核心实现仍以 Mooncake 为主；如果抽象真正稳定，transfer backend 应该只负责数据搬运，不拥有上层 pipeline semantics。
2. **统一 P/D protocol (#33861) 与 #34977 的 wire conformance。** Mooncake/NIXL/MORI 是否能共享 control/state machine，将决定后续 P/D backend 的维护成本。
3. **Issue #34959 + Roadmap #34899。** DSpark silent corruption 是否能被 exact-logprob / zero-KL 测试稳定复现并进入 CI，是 Spec correctness 是否真正生产化的重要信号。
4. **SharedReadEnds / EAGLE WAR contract 是否继续收敛。** 重点看 #34982、#34890 以及更多 backend 是否能从 UNKNOWN/POST_REPLAY 审计到更早的安全 read-end。
5. **HiCache concurrent load-back。** #35009 正在把 load-back pin 从 node-global 约束细化到 component/transfer scope；这会直接影响 Full/SWA/Mamba 多组件并行恢复能力。
6. **#35017 decode starvation policy 是否从固定 interval 走向自适应。** 固定 N 是很好的第一步，但更长期可能需要根据 waiting/running、TTFT/TPOT SLO、DP rank 状态动态调整。
7. **三组 Roadmap 未完成组合：** DCP × DSpark × HiCache × P/D、PP + Spec + P/D、Unified Memory × Spec/P-D/HiCache。
