# SGLang 技术趋势周报 — 2026-W32

> 时间范围：2026-08-03 ～ 2026-08-09  
> 关注范围：**KV Cache / Prefill-Decode Disaggregation / Scheduler / Speculative Decoding**  
> 筛选原则：只保留会改变架构边界、组合能力、性能上限或 correctness contract 的工作；过滤普通模型适配、机械重构和小修复。

## 一、本周结论

本周最明显的趋势不是某一个孤立 kernel 变快，而是 SGLang 在把此前“单点可用”的能力推向 **可组合、可推理、可验证的生产级状态**：

1. **KV Cache 的正确性边界继续从“缓存命中”扩展到“完整状态恢复”**。HiCache 已开始同时恢复 target KV、draft KV、DSA indexer、SWA state；DCP 下则进一步明确 Q 与 K/V 的不同分片语义。缓存系统正在从“token -> KV”演进为一组具有共同 slot/lifetime 的 inference state。
2. **P/D 的核心问题逐渐从“能传 KV”转向“缓存命中、异构 TP、DCP、Spec 同时存在时还能正确传”**。Staging Buffer 与 RadixCache 的兼容合入是这一转变的代表；新 RFC #33861 更进一步，准备把 Mooncake/NIXL/MORI 的控制协议统一，只让 backend 负责真正的数据移动。
3. **Scheduler 的优化重点从算法层转向 CPU hot path 与异步执行 contract**。批量 free、复用 batched metadata、显式声明 CUDA Graph 中 scheduler-shared buffer 的最后读取边界，都说明 overlap scheduler 正在从“靠约定避免 race”转向“把 ownership / WAR boundary 写进接口”。
4. **Speculative Decoding 已经进入“组合性 + backend specialization”阶段**。DSpark 本周同时补齐 AMD、Unified KV、DP/EP、HiCache、长上下文 verify backend 等路径；真正的瓶颈不再只是 acceptance length，而是 verify 阶段如何读 KV、如何与 cache/PD/scheduler 的状态机组合。
5. **v0.5.17 于 2026-08-08 发布**。这一版本把 Kimi K3 的 DCP、DSpark、KDA-aware prefix caching、HiCache L2 等组合能力作为正式 highlight，说明这些方向已经从实验 PR 进入版本级能力。

## 二、本周最重要的新增能力

### 1. KV Cache：从单一 KV 状态走向“多状态一致恢复”

#### ⭐ #30393 HiCache 支持 MTP/EAGLE/DSpark 的 draft cache

PR: https://github.com/sgl-project/sglang/pull/30393

这是本周 KV Cache 方向最值得精读的 PR 之一。

**问题**

过去 HiCache 只恢复 target model 的 KV 并不够。Speculative Decoding 可能额外持有：

- draft KV
- DSA indexer cache
- SWA state

如果只恢复 target KV，Radix/HiCache 仍然可以报告“prefix hit”，但 draft 侧状态缺失或 slot mapping 不一致，最终会表现为 acceptance length 明显下降，而不是直接报错。

**核心设计**

PR 引入两种路径：

- `Packed`：draft KV/indexer/SWA 作为 target host pool 的尾部层，共享 host slot。
- `Sidecar`：为 standalone EAGLE/EAGLE3、DFlash、部分 DSpark 建立独立 `DRAFT / DRAFT_INDEXER / DRAFT_SWA` host pool，但仍与 target KV/SWA 保持一一对应的 host index。

本质上是在建立一个重要 invariant：

> **一次 prefix cache 命中必须恢复该 prefix 所依赖的全部推理状态，而不只是 target KV。**

**效果**

DeepSeek-V4-Flash-0731 + DSpark 的 L3 replay：

- upstream/main：cold accept length `3.317`，replay 降到 `2.660`
- 本 PR：cold `3.285`，replay `3.323`

accept rate 也从 replay 的 `33.57%` 恢复到 `46.86%`，基本回到 cold-run 水平。

这类问题很适合用来理解：**cache correctness 不一定表现为错误答案，也可能首先表现为 speculative efficiency 下降。**

#### ⭐ #32858 修复 DCP 下 GQA 的 KV head mapping

PR: https://github.com/sgl-project/sglang/pull/32858

**问题**

DCP 沿 token/sequence 维度切分 KV。一个 DCP group 内不同 rank 处理不同 token shard，但这些 token 必须由**相同的 K/V projection**产生。

原 TP-only GQA layout 可能让同一 DCP group 中不同 rank 使用不同 KV head，最终不是 crash，而是 silent numerical corruption。

**核心改动**

- Q 继续按 attention TP 切分。
- K/V 的 TP layout 改为由 `attn_tp_size / dcp_size` 推导。
- DCP group 内复制 K/V projection，不需要 runtime KV communication。
- KV pool/backend metadata 根据实例化后的 local KV-head layout 重新 sizing。

**性能 / 正确性**

Qwen3.5-397B-A17B-NVFP4-V2，TP4/DCP4，200 GSM8K：

- Triton accuracy：`0.880 -> 0.980`
- TRTLLM MHA：`0.920 -> 0.975`

16×GB300、TP16、ISL=8192、OSL=1024、concurrency=1024：

- DCP1 total TPS/GPU：`733.56`
- DCP4 total TPS/GPU：`1025.13`
- output throughput：`+39.75%`
- duration：`-28.44%`

**值得记住的面试点**：DCP 切的是 token 维度，所以不能简单把“TP 的 KV head sharding”原封不动复用到 DCP。

#### #34067 修复 deferred KV free 的 tensor aliasing

PR: https://github.com/sgl-project/sglang/pull/34067

**问题**

Batch free 为了减少 allocator 操作，会延迟真正的 free。但如果队列里保存的是指向可变 req-to-token row 的 tensor view，那么在 Radix rematch 后，该 row 已经可能被改写成新的 cache/tree index。

于是发生很危险的状态：

- 逻辑上：旧 KV 已 eviction
- 物理 allocator：实际 free 的可能是新的 slot

最终会造成“逻辑空间还有，但 allocator 认为没有”的容量泄漏，甚至错误回收。

**改动**

在 allocator boundary 对 deferred free 输入做 ownership snapshot（clone/owned copy），覆盖 paged/SWA/NPU/HiSparse/unified cache 路径。

这是一个很典型的系统设计原则：

> **异步/延迟操作不能持有指向可变元数据的借用引用，必须持有稳定 ownership snapshot。**

### 2. P/D Disaggregation：从传输后端走向统一协议层

#### ⭐ #30545 Staging Buffer 正式兼容 RadixCache hit

PR: https://github.com/sgl-project/sglang/pull/30545

**问题**

异构 TP 的 P/D staging buffer 原先隐含假设 transfer chunk 是均匀固定网格。但 Prefix/Radix Cache 命中后，prefill 实际需要发送的是“cached prefix + newly computed suffix”的非均匀布局。

如果继续按固定 chunk index 推导位置，可能导致：

- ring/staging slot 越界
- decode scatter 到错误 offset
- cached-prefix 请求在 P/D 下输出错误

**核心改动**

- Prefill：按 staging grid slot 拆分 send；重新支持 cached-prefix 的 early send。
- Decode：改成 arrival-driven scatter；最后 chunk 显式发送 `CHUNK_READY`。
- transfer 完成条件变成：所有 rank 成功且所有 scatter 都结束。
- decode scatter offset 显式计入 cached prefix。
- timeout / transfer failure 进入统一失败状态，而不是继续等待。

**验证**

128K needle-in-haystack、约 127.5K shared cached prefix：

- 修复前：`2/128`
- 修复后：`128/128`

8×GB300 AgentX 256K context：DEP4→TP4 staging 在 concurrency 192 下，相比 TP4→TP4 concurrency 128：

- output TPS/user：`+9.61%`
- total TPS/GPU：约 `-0.16%`

这说明 staging 不只是 correctness patch，也能在异构资源配置下保持几乎相同的 GPU efficiency。

#### #31477 Spec + PD 下的 DSA TopK/IndexShare 融合

PR: https://github.com/sgl-project/sglang/pull/31477

在 P/D 中，target/draft 的 index-share seed 需要经过 wire 传输，然后 decode 侧转换成 local physical slot。该 PR 让这一转换与 fused DSA TopK 路径兼容，去掉大量 page-table transform 和 unfused TopK。

4 nodes / 32 H20、prefill TP16、decode TP16、131K+ 长上下文：

- TPOT：`11.60 -> 11.22 ms`（-3.28%）
- ITL：`34.37 -> 33.31 ms`（-3.08%）
- decode forward：约 -3.11%
- output throughput：+1.11%
- MTP acceptance：约 66%，基本不变

这里体现的趋势是：**P/D 已经开始优化 speculative-specific state transfer，而不仅仅是 target KV。**

#### ⭐ RFC #33861：统一 P/D protocol，backend 只负责 transport

RFC: https://github.com/sgl-project/sglang/issues/33861

Mooncake、NIXL、MORI 目前分别复制了一整套：

- bootstrap
- ZMQ loop
- room/session lifecycle
- staging
- TP/DCP slice orchestration
- timeout / heartbeat
- failure propagation

三套实现已经产生行为漂移。例如部分 backend 缺 heartbeat、部分不传播 prefill transfer failure，甚至 transfer-info 的 frame 顺序存在差异。

RFC 的目标边界是：

```text
PD Protocol Layer
  ├─ bootstrap / room / timeout / heartbeat
  ├─ staging / chunking
  ├─ TP/DCP slice mapping
  └─ failure semantics
            │
            ▼
Transport Interface
  ├─ register_memory
  ├─ open_peer
  ├─ submit(src, dst, len)
  └─ poll(handle)
            │
      ┌─────┼─────┐
   Mooncake NIXL  MORI
```

这是本周最重要的架构 RFC 之一：**控制面决定传什么、什么时候传；backend 只负责怎么搬 bytes。**

### 3. Scheduler：CPU hot path 与异步读写边界显式化

#### ⭐ #34052 用 SharedReadBoundary 统一 overlap scheduler 的 WAR contract

PR: https://github.com/sgl-project/sglang/pull/34052

过去不同 attention/spec backend 通过多个独立 bool 和 if-chain 描述“CUDA Graph replay 的哪个阶段还会读取 scheduler-shared metadata”。这种做法在新组合增加时非常容易漏分支。

本 PR 引入统一声明：

```text
SharedReadBoundary
  PRE_REPLAY
  IN_REPLAY
  POST_REPLAY
  UNKNOWN
```

并把责任分层：

- Attention backend：声明自己的最后 shared-read 边界。
- Spec algorithm：声明哪个 phase 是 WAR publish phase。
- CUDA Graph runner：根据 declaration 机械地 record event。
- Scheduler：只消费这个 event，不再理解 backend 特例。

这是典型的“把并发约定变成接口 contract”。虽然 PR 自身宣称 behavior-equivalent，但它为后续 P/D、Spec、不同 attention backend 安全使用 overlap scheduler 提供了更清晰的组合边界。

---

#### ⭐ #33475 批量化 scheduler cache free

PR: https://github.com/sgl-project/sglang/pull/33475

Scheduler 在大 batch 下逐请求 free SWA/cache，会重复执行 mapping expand、gather、mask、allocator free、mapping clear。

PR 将 prefill result processing 与 SWA maintenance 中的 free 统一进入 free-group，并增加 SWA free queue。

约 1000 running requests 的 10-step profile：

- `get_next_batch_to_run` CPU：`38.75 ms -> 15.08 ms`，**-61%**
- `aten::_unique2` launch：`111 -> 40`，**-64%**

这类优化非常关键：GPU kernel 已越来越快后，Scheduler 的 Python/C++ metadata bookkeeping 会直接暴露到 TPOT/ITL。

---

#### #33477 复用 batched Mamba boundary mask

PR: https://github.com/sgl-project/sglang/pull/33477

`prepare_for_decode` 已经 vectorized 地算出了 Mamba boundary mask，但 result processing 过去又逐 request 重算一次。

优化后：

- `_mamba_check_track_boundary`：10174 次 / 18.20 ms -> 0
- `_mamba_prefix_cache_update`：10174 次 / 31.47 ms -> 22–34 次 / 0.07–0.09 ms
- `process_batch_result_decode`：27.11 -> 24.19 ms，约 **-10.8%**
- bs=1024 的 method benchmark：per-step CPU 约 **-18%**

重点不是 Mamba 本身，而是一个通用思路：**Scheduler 不应在 result phase 重新推导已经在 batch-prep phase 计算好的状态。**

---

#### #33404 SWA eviction 从“全局 scheduler 时钟”改为“每个 KV handle 的单调进度”

PR: https://github.com/sgl-project/sglang/pull/33404

过去 eviction 依赖 decode batch index，request retract/re-enter extend 后计数会 reset，可能导致某些 request 长期错过 eviction phase。

现在 eviction 由：

```text
current out-of-window tokens
    >= last evicted progress + eviction interval
```

触发。

这使维护逻辑绑定到 KV handle 自己的单调 progress，而不是 scheduler iteration。这种设计对 retraction / resume 场景更健壮，也自然打散了大 batch 中 eviction 的同步尖峰。

### 4. Speculative Decoding：组合性与 verify backend 成为核心瓶颈

#### ⭐ #30964 DSpark 在 AMD/HIP 上支持 Unified KV + ragged verify CUDA Graph

PR: https://github.com/sgl-project/sglang/pull/30964

该 PR 不只是“AMD 支持”，而是一次较完整的 composability 落地：

- HIP ragged verify CUDA Graph
- Unified KV 中 draft KV store/injection
- SWA ring slot addressing
- commit masking
- DP Attention 配合

Kimi/DeepSeek V4 风格 workload 中，DSpark 不再要求独立的非 unified-KV 路径。

**性能**

TP8、8K/1K：

- Triton，conc=1：TTT `548.65 -> 1607.02 tok/s`，**2.93x**
- Unified KV Triton，conc=8：TTT `3801.30 -> 7796.98`，**2.05x**；TPOT `17.33 -> 7.51 ms`
- Unified KV Triton，conc=32：TTT `9164.07 -> 14753.85`，**1.61x**

TP8DP8、conc=256、Unified KV：

- total TTT：`29294.55 -> 40089.16`，**1.37x**
- mean TTFT：`18427.91 -> 7607.62 ms`，约 **2.42x** 改善
- mean TPOT：`60.05 -> 47.18 ms`，约 **1.27x**

这说明 speculative 的收益会随着 concurrency 上升而下降，但在高并发下仍能提供可观收益。

#### ⭐ #33650 长上下文 DSpark verify 切到 `cutedsl_mla`，900K context 约 2x

PR: https://github.com/sgl-project/sglang/pull/33650

K3 DSpark verify 的 q_len=8。旧路径回退到 `trtllm_mla`，会对每个 query row 重读 KV；在超长 context 下，verify attention 成为严重 memory-traffic bottleneck。

flashinfer 的 `fold_sq` 允许 CuTe DSL MLA 把多个 verify query 折进 head/MMA tile，使 shared KV 只需更有效地加载。

Kimi-K3，TP8，8×B300，bf16 KV，bs=1，ISL=900K，OSL=2048：

- decode ITL：`10.18 -> 5.07 ms`
- output throughput：`98.2 -> 197.4 tok/s`
- per spec step：约 `44 -> 22 ms`
- acceptance length：`4.34 -> 4.26`，基本不变

isolated MLA kernel：约 `1.263 ms -> 0.320 ms`，接近 **3.9x**。

这给出了一个非常重要的结论：

> **Speculative Decoding 的速度不只由 acceptance length 决定；长上下文下 verify 阶段的 KV memory traffic 可能更重要。**

PR 中甚至给出了 `(TP, q_len, context, KV dtype)` 相关的 backend crossover，说明未来可能需要 context-aware backend selection，而不是固定一个 attention backend。

#### #33981 AMD K3 新增专用 MLA verify kernel

PR: https://github.com/sgl-project/sglang/pull/33981

旧 `verify_splitkv` 面向普通 MHA，每个 query head 独立读取同一个 MLA latent，TP8 下大约产生 12x redundant load。

新 kernel 改为一个 program 处理一组 query heads，并复用 shared latent tile。

Kimi-K3 8K/1K，concurrency 2–32：

- total token throughput：**1.37x ～ 1.77x**
- ITL：**1.45x ～ 2.42x**
- conc=32：`7652.96 tok/s`，accept length 约 `7.02`

再次说明 verify attention 已经成为一个独立优化方向，而不是 speculative runtime 的附属代码。

#### #34026 修复 DFlash + overlap scheduler 的异步 state capture 丢失

PR: https://github.com/sgl-project/sglang/pull/34026

Overlap 模式下 state capture 返回 deferred GPU->CPU handle。DFlash 构建新的 `GenerationBatchResult` 时没有把这些 handle 往上传，导致 scheduler 不会 finalize captured state，host cache 最终保留 0/stale entry。

修复方式不是“再 copy 一次”，而是把 capture handle 沿标准 result path 传播，让 Scheduler 的 normal result processor 统一等待并 finalize。

这体现了本周多次出现的架构原则：

> **异步结果必须把 completion ownership 沿调用链显式传递，不能仅传最终 tensor/value。**

## 三、正在成为主流的设计方向

### 1. “Composability” 正在取代“单功能支持”成为主要验收标准

当前 Roadmap 明确保留：

```text
DCP × DSpark × HiCache × PD Disaggregation
```

的组合性工作：

- DCP Roadmap: https://github.com/sgl-project/sglang/issues/29736
- Kimi K3 Roadmap: https://github.com/sgl-project/sglang/issues/32607

一个 feature 仅在 `TP-only + no-cache + no-PD` 下通过，已经越来越不够。

未来更常见的测试矩阵会是：

```text
Parallelism × Cache × Spec × Serving topology

DCP/DP/TP/PP
  × Radix/HiCache/Unified KV
  × EAGLE/DFlash/DSpark
  × Unified/P-D
```

---

### 2. Cache 正从“内存池”变成具有 ownership/lifecycle 的状态系统

本周多个 PR 都指向同一方向：

- #30393：一次 cache hit 必须同时恢复 target/draft/indexer/SWA。
- #34067：deferred free 必须 snapshot ownership，不能借用可变 row view。
- #32858：DCP 改变的是 KV layout 语义，而不仅是 allocator 容量。

因此理解 KV Cache，已经不能只停留在 `block/page + eviction`；还要理解：

- logical slot vs physical slot
- target/draft shared mapping
- host/device/L3 的 state correspondence
- deferred operation 的 tensor lifetime
- prefix hit 后各类 side state 的恢复顺序

---

### 3. Scheduler 并发 contract 正在接口化

#34052 的 `SharedReadBoundary` 是一个明显信号。

此前很多“为什么这里要 event / wait / record_stream”的知识存在于实现细节中；现在正在变成 backend capability/declaration。

长期看，这会让新的 attention backend/spec backend 更容易安全接入 overlap scheduler，而不是复制一套 magic bool。

---

### 4. P/D 的 backend 正被重新定义为纯 data plane

RFC #33861 倾向于：

```text
Common protocol/control plane
         +
Thin transport backend
```

这与成熟分布式存储/网络系统非常相似：

- 上层维护 request/session/state machine
- transport 只完成 registration、peer setup、submit/poll

如果后续 RFC 落地，Mooncake/NIXL/MORI 的 feature parity 和 failure semantics 会更容易统一。

---

### 5. Spec verify backend 将越来越 workload-aware

#33650 已经证明 backend 选择取决于：

- q_len / draft block size
- context length
- TP / head layout
- KV dtype

因此未来一个合理方向不是“哪个 MLA backend 最快”，而是：

> **针对 capture graph 预先构建多个 backend/tactic，在运行时根据 batch/context bucket 选择。**

这与 GEMM autotune、CUDA Graph bucket、scheduler admission 的发展路径非常相似。

## 五、对 AI Infra 面试最有价值的知识点

### 1. DCP 为什么不能直接沿用 TP 的 GQA KV-head 切分？

推荐回答思路：

- TP 常按 head/channel 切。
- DCP 按 sequence/token 切。
- 同一个 DCP group 的各 rank 只是处理不同 token shard，应该使用相同的 K/V projection。
- 因此 Q 可以继续 shard，但 K/V 需要在 DCP group 内 replicate；否则 merge 后不是通信错误，而是数学语义错误。

对应 PR：#32858。

---

### 2. Prefix Cache hit 为什么会把 P/D Staging Buffer 搞错？

重点不是“cache hit 少算一些 token”，而是 transfer layout 从：

```text
uniform newly-computed chunks
```

变成：

```text
cached prefix + irregular new suffix
```

如果 chunk offset 仍由固定网格推导，就会写错 staging/ring/scatter 位置。

对应 PR：#30545。

---

### 3. `record_stream`、CUDA event/wait 和 Python 引用分别解决什么问题？

这是本周非常值得准备的并发题。

- Python reference：保证 object/tensor 不被析构。
- `record_stream`：告诉 caching allocator，该 tensor 的 storage 仍被另一个 stream 使用，不能过早复用。
- CUDA event / `wait_stream`：解决两个 stream 之间的执行顺序。
- 三者不能互相替代。

本周仍 open 的 #34076/#34077 正好各暴露了一类 silent corruption：生命周期过早结束，以及不同 stream 对同一 relay row 的 write-after-write race。

---

### 4. 为什么 HiCache 恢复 target KV 后，Spec acceptance 仍可能下降？

因为 speculative decoding 的可复用状态不只 target KV：

- draft KV
- DSA indexer
- SWA state

如果这些状态没有跟 target cache slot 一起恢复，模型可能仍然能生成正确结果，但 draft 的 proposal quality/状态连续性被破坏，acceptance 明显下降。

对应 PR：#30393。

---

### 5. Speculative Decoding 的性能模型不能只看 acceptance length

一个更完整的近似是：

```text
收益 ≈ 一次 verify 接受的 token 数
      / (draft cost + target verify cost + scheduler/metadata cost)
```

超长上下文下，`target verify cost` 本身可能受 KV 重读支配。#33650 在 acceptance 基本不变时，单纯把 verify MLA backend 换掉就让 decode 约 2x。

这是面试时很容易拉开深度差距的一点。

---

### 6. Scheduler 为什么会在 GPU 越来越快后成为瓶颈？

当低并发 kernel 已被 CUDA Graph、fusion、spec decode 压缩到很短后：

- 每 request allocator bookkeeping
- Python loop
- metadata recompute
- D2H/H2D
- event/fence

都可能暴露成 GPU bubble。

#33475 单纯批量 free 就让一个 scheduler hot function CPU 时间下降 61%，说明 scheduler optimization 不只是“选哪个 batch”。

## 六、适合做项目/源码阅读的切入点

如果希望把本周变化转化成可讲的项目经验，优先做下面三类实验：

### A. KV Cache correctness invariant

给 allocator/HiCache 增加 debug invariant：

```text
logical cached tokens
physical allocated slots
host sidecar state
spec draft state
```

在 eviction / rematch / L2 replay 后检查是否一致。

重点阅读：#34067、#30393。

### B. P/D + Prefix Cache transfer trace

构造：

```text
shared prefix 90%+
Prefill TP != Decode TP
RadixCache hit
Staging Buffer ON
```

打印每个 chunk 的：

- source logical range
- target staging slot
- scatter physical offset
- completion state

重点阅读：#30545、#33861。

### C. Spec verify roofline

固定 acceptance length，分别扫：

```text
context = 8K / 128K / 512K / 1M
q_len   = 1 / 2 / 4 / 8
KV dtype = bf16 / fp8
```

比较不同 MLA verify backend 的 memory traffic 和 step latency。

重点阅读：#33650、#33981。
