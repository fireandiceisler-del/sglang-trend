# SGLang 技术趋势周报 — 2026-W34

> 时间范围：2026-08-17 ～ 2026-08-23  
> 关注范围：KV Cache / Prefill-Decode Disaggregation / Scheduler / Speculative Decoding  
> 筛选原则：仅保留架构变化、重要性能优化、跨 Feature 组合能力、可靠性与 Roadmap；过滤普通模型适配、机械重构与低影响 Bugfix。

## 本周结论

本周最明显的变化不是某一个新 Feature，而是 **SGLang 正在把“异步推理系统的状态契约”做成一等公民**。

过去几周的主问题是 `DCP × PP × P/D × Spec × HiCache × Unified Memory` 能不能组合运行；本周进一步演进到：组合之后，**谁拥有状态、什么时候可以复用物理 slot、不同 rank 如何对状态达成一致、CUDA Graph replay 时 metadata 应该驻留在哪里、Router 与 Scheduler 谁负责最终 placement**。

可以把本周趋势概括为四句话：

1. **KV Cache 不再只是 K/V Tensor，而是一套多组件状态系统。** FULL、SWA、Mamba、DSA indexer、spec draft state 都需要明确的 logical index / physical slot / lifetime contract。
2. **P/D 的数据面和控制面正在分离。** 数据面越来越专注于 target KV / draft KV / state transfer；控制面开始强调 StateType、process generation、PP/CP consensus 与 failure lifecycle。
3. **Scheduler 的关键抽象正在从“等待整个 forward”转向“精确的 shared-read completion”。** CUDA Event、snapshot、WAR fence 逐渐取代粗粒度 stream sync。
4. **Speculative Decoding 的主要瓶颈已经不只是 acceptance rate。** 长上下文下，verify 的 KV traffic、GQA packing、split-KV occupancy、CUDA Graph metadata 和 workspace 生命周期都可以决定 Spec 是否真正快于 AR。

## 1. KV Cache：从“缓存 Tensor”走向“统一状态与容量管理”

### 1.1 Decode-side Radix Cache 开始覆盖 DeepSeek-V4 compressed KV

**PR [#35837](https://github.com/sgl-project/sglang/pull/35837) — Decode-side radix cache for DeepSeek-V4 / DSA compressed KV**

这是本周最值得关注的 KV Cache × P/D 交叉变化之一。此前 `--disaggregation-decode-enable-radix-cache` 对 DeepSeek-V4 compressed KV / SWA-compress 模型存在限制；该 PR 的核心判断是：这些 compressed state 实际仍然由 FULL allocator 的 page position 驱动，因此只要 page geometry 保持一致，Decode 侧 prefix reuse 可以与 compressed pool 保持 coherent，而不需要重新设计一套 tree。

跨节点 8P + 8D、TP8、NIXL、DeepSeek-V4-Flash 的 shared-prefix benchmark 中：

- median TTFT：**1919 ms → 1226 ms，-36%**
- mean TTFT：**-13%**
- P90 TTFT：**-9%**
- median E2E：**-8%**
- request throughput：**+3.3%**

这里很值得记住一个系统设计点：**Decode cache 的价值主要体现在减少 Prefill→Decode 的重复 prefix transfer，所以收益首先落在 TTFT，而不一定显著改变 decode-dominated throughput。**

### 1.2 Unified Memory eviction 开始按“共享容量是否真的不足”决策

**PR [#33091](https://github.com/sgl-project/sglang/pull/33091) — Stop eviction when shared allocation capacity is sufficient**

Unified Memory 下，一个逻辑 cache 的 eviction 可能影响共享 allocator 上的其他 cache component。该 PR 把显式 eviction 和 allocation-triggered eviction 分开，并在触发 eviction 前判断 **shared allocator 的真实可用容量是否已经足够**，避免为了满足局部 cache 的 free target 而过度驱逐共享前缀。

RTX 5090 / Qwen3.5 的测试中：

- retained prefixes：**10/28 → 19/28，+90%**
- prefix survival：**35.7% → 67.9%**
- cached tokens：**3840 → 7296，+90%**
- replay E2E：**4.105 s → 2.548 s，-37.9%**
- mean prefill latency：**-43.6%**

这说明 Unified Memory 下，LRU 本身并不足够；eviction policy 必须理解 **共享物理容量和 collateral eviction**。

### 1.3 HiCache + PP：cache event 本身也需要跨 Pipeline Rank 达成一致

**PR [#27010](https://github.com/sgl-project/sglang/pull/27010) — Fix PP inconsistency with HiCache L3**

这个方向把 HiCache consistency 问题从“缓存内容一致”推进到“异步完成事件数量也必须一致”。方案包含两层同步：

- Scheduler thread 之间通过 `pp_sync` 保证不同 PP rank 消费**完全相同数量**的 load/prefetch completion event；
- Prefetch thread 之间对 L3 可恢复长度做 `all_reduce(MIN)`，避免不同 PP stage 对某个 sequence 的可用前缀长度产生分歧。

Qwen3-32B、TP2/PP4、128 clients、10 rounds 的多轮测试很有代表性：只靠 L1 时 round 9 cache hit 已降到约 **3.5%**、平均 TTFT **8.92 s**；L2 为约 **37.9% / 1.86 s**；L3 仍保持约 **89.9% hit / 0.29 s TTFT**。

这类问题本质上和分布式存储很像：**不是“每个节点局部正确”就够，而是所有 stage 必须对同一个 logical progress 达成一致。**

### 1.4 Cache correctness 正在从“文本看起来正常”升级到 bit-exact oracle

**Roadmap [#34899](https://github.com/sgl-project/sglang/issues/34899) — Bit-exact correctness coverage for Unified Radix Cache**

本周值得持续关注的 testing 方向。Roadmap 的核心 contract 是：在 deterministic 且 prefill/decode 数学路径完全一致的模型上，先建立 `KL = 0` baseline，之后任何 cache restore 路径只要出现非零 KL，就应视为状态复用错误，而不是等待最终文本或 benchmark accuracy 明显下降。

目前 roadmap 已覆盖：

- Base cache path
- Mamba extra buffer / lazy extra buffer
- HiCache multi-turn
- MTP
- DSpark / DFlash

**Unified Memory 仍是未完成项。**

这是一个非常重要的工程趋势：缓存系统正在建立类似数据库 consistency test 的“精确 oracle”，而不是只靠 end-to-end 文本做模糊验证。

## 2. Prefill/Decode 分离：从 KV 搬运演进到“状态语义 + 控制面生命周期”

### 2.1 PP + P/D + DSpark 开始真正组合

**PR [#33863](https://github.com/sgl-project/sglang/pull/33863) — PP Support PD + DSpark**

这是本周 composability 最强的 PR 之一。

如果没有 PP，Prefill worker 可以拿到完整 target hidden states，生成 draft KV，再把 target KV + draft KV 传给 Decode。PP 后 target hidden states 分散在不同 stage，不能简单在每个 stage 独立生成 draft KV，因为 RMSNorm 必须作用在完整 context projection 上。

该方案保持 P/D 数据面不变：

```text
Prefill -> target KV + draft KV -> Decode
```

但在 PP 内部变为：

```text
ctx_i = h_i @ W_i.T
ctx_acc = recv_ctx_acc + ctx_i
最后一个 PP stage:
ctx_norm = RMSNorm(ctx_acc)
K,V = KVProj(ctx_norm)
```

每个 PP hop 只携带固定大小 `[num_tokens, hidden_size]` 的 context accumulator，而不是把全部 hidden states 穿过 P/D 边界。

更重要的是，该 PR 把 state component 匹配从**位置匹配**：

```text
prefill state[i] -> decode state[i]
```

改为按 **`(StateType, occurrence)`** 匹配。因为不同 PP rank 可能缺少可选的 `C128_STATE`，如果仍按数组下标匹配，draft SWA 甚至可能写入 target C128 state buffer。

这是本周非常典型的设计信号：**异步系统中的状态必须有 semantic identity，不能依赖容器中的偶然顺序。**

### 2.2 CP 场景开始区分“sharded KV”和“replicated state”

**PR [#36025](https://github.com/sgl-project/sglang/pull/36025) — MORI deduplicate CP-replicated state transfers**

Prefill CP8 / Decode TP8 下，KV page 本身按 CP rank 分片，但某些 state 是每个 CP rank 都复制一份的。此前 MORI 会让每个 rank 都发送完整 replicated state，导致相同 state 被重复发送 `cp_size` 次。

DeepSeek-V4-Pro、MI355X、16 × 65K prompt 测试：

- aggregate transfer：**2,470,901.8 → 371,486.9 MiB，-84.97%**
- TTFT p50：**+0.28%**
- TTFT p95：**+0.18%**
- input throughput：**-0.13%**

这个结果本身也很有价值：**流量减少 85% 并不意味着 latency 一定改善 85%。** 如果这部分流量已经被 overlap、不是 critical path，优化的价值更多是降低 fabric 压力、提升规模上限和避免未来 contention。

### 2.3 Cache-off Prefill 的最终 rank 选择开始回到 engine 内部 token telemetry

**PR [#35964](https://github.com/sgl-project/sglang/pull/35964) — Load-aware cache-off DP prefill routing**

设计变化很有意思：外部 Router 给出的 `routed_dp_rank` 在 cache-off P/D Prefill 模式下不再必须是最终决策，而可以作为 hint；SGLang 自己的 `total_tokens` scheduler 根据每个 worker 的真实 token load 做最终 placement。

Qwen3.5-397B-A17B NVFP4、DP/DEP4、AgentX 风格 workload：

- 外部 rank authoritative：各 rank prompt tokens = `[14.18M, 5.66M, 6.37M, 8.07M]`
- engine 内 load-aware：`[11.70M, 7.90M, 7.39M, 7.33M]`
- throughput：**13,301.16 → 15,128.90 tok/s/chip，+13.74%**

注意它只在 **RadixCache disabled** 时启用；cache-on 时仍由 cache affinity 决定。这个边界非常合理：

- 有 cache affinity：placement 是数据局部性问题；
- 无 cache affinity：placement 是负载均衡问题。

### 2.4 P/D 控制面开始显式处理 process generation

**PR [#36049](https://github.com/sgl-project/sglang/pull/36049) — Clean up stale staging watermark subscribers**  
**PR [#36029](https://github.com/sgl-project/sglang/pull/36029) — Refresh stale prefill bootstrap metadata**

两者反映的是同一个生产问题：**endpoint 不等于 process identity**。

Prefill 重启后可能继续使用相同 host/bootstrap endpoint，但 request-scoped receiver、ephemeral rank ports、watermark subscriber 已经属于新的 process generation。如果 Decode 只按 endpoint key 缓存状态，就可能继续向旧 receiver 发 WATERMARK，或者永久复用旧 bootstrap metadata。

#36049 引入 monotonic generation token，并在 failure cleanup 时只删除仍属于旧 generation 的 subscriber，避免 cleanup 与 restart re-register 发生 ABA race。生产 soak 中 3000 requests、约 10.3 次 20 GiB staging ring wrap 完成 3000/3000。

这和分布式存储中的 incarnation/epoch 概念完全一致：**同一个网络地址上的“新进程”必须被视为新的逻辑实体。**

## 3. Scheduler：从 coarse synchronization 走向精确 shared-read boundary

### 3.1 SharedReadBoundary 正逐渐成为 Overlap Scheduler 的核心并发 contract

**PR [#35947](https://github.com/sgl-project/sglang/pull/35947) — Publish DSV4 speculative prefill shared-read completion**  
**PR [#36054](https://github.com/sgl-project/sglang/pull/36054) — Enable overlap WAR barrier by default on ROCm**

Overlap Scheduler 的典型 hazard 是：下一批 Scheduler 操作想原地更新共享 metadata，但上一批 forward 还在另一个 stream / CUDA Graph 中读取它。

这里关键不是 tensor 是否“活着”，而是 **旧 consumer 的最后一次 read 到底什么时候完成**。`record_stream` 只能解决 allocator lifetime，不能阻止一个 persistent buffer 被下一次 forward 原地覆写。

因此最近的实现越来越倾向于：

1. metadata init 时创建本次 forward 的 snapshot；
2. backend 在真正完成共享状态读取后 publish CUDA Event / read-done boundary；
3. Scheduler 只等这个精确 boundary，而不是等待整个 forward stream。

#35947 把这个 contract 扩展到 DSV4 sparse prefill / spec draft-extend；#36054 则说明这个 WAR hazard 并不是 CUDA 特有，HIP/ROCm 同样需要同样的并发语义。

### 3.2 Mixed batch 不应该把 Prefill 和 Decode 强行走同一条 kernel path

**PR [#36065](https://github.com/sgl-project/sglang/pull/36065) — Split mixed GDN prefill and decode kernels**

此前 mixed chunk `[prefill | decode]` 会把整个 batch 都走 GDN extend path。问题是 decode token 的 Q 长度非常短，把它塞进 prefill kernel 会导致大量不必要工作。

Qwen3.8-27B、TP2、H20、64K Prefill 时，在 decode concurrency 953 下：

- TTFT 改善：**25.81%**
- mixed-window latency 改善：**26.04%**

代表性 kernel breakdown 中，旧 mixed path 的 causal-conv prefill 约 **4516.5 ms**，拆分后变为约 **47.9 ms prefill conv + 24.6 ms decode update + 403.0 ms recurrent decode**。

趋势非常清晰：**Continuous batching 的目标不是“尽量把所有 token 合成一个 kernel”，而是保留不同 phase 的最优执行语义，同时共享 Scheduler batch。**

### 3.3 Scheduler policy 开始显式接受 TTFT 与 ITL/throughput 的权衡

**PR [#35954](https://github.com/sgl-project/sglang/pull/35954) — DFlash/DSpark replacement prefill scheduling**

DSpark replacement prefill 的 delay 不再根据配置中的最大 request capacity，而根据实际 observed demand 决定，减少低负载下“一次只补一个 replacement prefill”的情况。

DSv4-Flash / DSpark / TP2 / concurrency 8：

- output throughput：**591.29 → 610.91 tok/s，+3.3%**
- ITL：**11.89 → 11.13 ms，-6.4%**
- requests per prefill pass：**+55.4%**
- 但 TTFT：**241.54 → 352.72 ms，+46.0%**

这是一个非常适合面试讨论的例子：**Scheduler 没有一个“全局最优”指标；不同 policy 本质是在 TTFT、ITL、throughput、fairness 之间做 Pareto trade-off。**

## 4. Speculative Decoding：瓶颈从 acceptance 转向 verify memory system

### 4.1 长上下文 NEXTN：acceptance 正常，也可能比 AR 更慢

**PR [#30105](https://github.com/sgl-project/sglang/pull/30105) — AITER GQA packing + split-KV routing for NEXTN**

这是本周最值得精读的 Spec 性能案例。

原问题很反直觉：随着 context 增长，Spec 在约 40K 后逐渐输给 non-spec，但 `accept_length` 仍然健康。Profiling 最终发现两个完全独立的问题：

- **Target verify 丢失 GQA amortization**：单 KV head 被 `.expand()` 成多个 Q head，kernel 误以为 `num_queries_per_kv = 1`，相当于把 GQA 退化成 MHA-style KV traffic。
- **Draft extend occupancy starvation**：短 Q 的 draft catch-up 落到没有 split-KV 的 prefill FMHA，只有极少 Q tile，HBM 利用率极低。

88K context 下：

- verify attention：**272 ms → 104 ms，2.6×**
- draft_extend attention：**~773 ms → ~5 ms**
- TPOT：**13.8 ms → 6.8 ms**
- Spec 相对 non-spec：从长 context 下反而变慢，变为 1.4K～88K 全区间 **1.35×～1.76× 加速**

最重要的结论：**Spec 性能 = 少做多少 target forward × 每次 verify/draft 的额外 memory/compute cost。Acceptance 只是其中一个变量。**

### 4.2 GQA-packed verify 本身仍有巨大收益空间

**PR [#35457](https://github.com/sgl-project/sglang/pull/35457) — Pack AITER target-verify GQA**

Kernel benchmark（batch 64，BF16）：

- 8K：**1.271 → 0.326 ms，3.90×**
- 32K：**5.555 → 1.246 ms，4.46×**

MI355X、TP2、Qwen3.5-397B MXFP4、EAGLE、C64 的 E2E benchmark：

- throughput/GPU：**+32.6%**
- median TTFT：**-13.9%**
- TPOT：**-24.9%**

这进一步说明 verify attention 已经是长上下文 speculative decoding 的一等性能对象，而不只是一个“正确性检查步骤”。

### 4.3 NVFP4 × Spec × CUDA Graph 正在收敛到“GPU-resident metadata/workspace”

**PR [#36038](https://github.com/sgl-project/sglang/pull/36038) — Native FP4 verify path with TRTLLM MHA**  
**PR [#36045](https://github.com/sgl-project/sglang/pull/36045) — Make FlashInfer NVFP4 speculative decoding graph-safe**

本周 NVFP4 Spec 暴露出的核心冲突是：Spec V2 希望 verify metadata 完全留在 GPU 并可进入 CUDA Graph replay，但传统 NVFP4 dequant workspace 仍依赖 CPU prefix metadata。

目前出现两条实现路线：

1. 直接走 TRTLLM MHA native FP4 decode/verify path，避免 CPU dequant workspace；
2. 保留 FlashInfer，但把 dequant workspace 与 prefix metadata 改为 GPU-resident，并把 workspace 纳入 token-pool memory accounting。

#36045 在 RTX PRO 5000 Blackwell / Qwen3.8-27B-NVFP4 上报告 32K/128K graph replay 均通过，acceptance 4.0；同时把 token pool 从错误的约 2.04M 调整为约 1.76M，显式预留 target / draft workspace。

这个方向说明 CUDA Graph compatibility 的本质不是“kernel 能不能 capture”，而是：**capture/replay 所有控制依赖是否都可以由 device-resident、地址稳定、容量可预估的状态表达。**

### 4.4 DFlash2：Spec 本身仍在继续做算法级演进

**PR [#35371](https://github.com/sgl-project/sglang/pull/35371) — DFlash2**

DFlash2 引入 block 内局部动态卷积和 candidate path selector，并把 selector 折叠进 draft CUDA Graph，使 proposal token 之间拥有更强的依赖建模，而不是单纯独立预测多个候选。

单 H200 / Qwen3.8-27B 的 GSM8K concurrency=1 benchmark 报告约 **236.1 tok/s，3.43× AR**。

本周 Spec 的两条路线其实是并行的：一条提升 draft algorithm 本身；另一条把 verify / KV / graph / scheduler 的系统成本压到足够低。生产性能最终取决于二者乘积。

## 5. 本周最重要的架构趋势

### 趋势 A：状态必须有 semantic identity，而不是 positional identity

PP + P/D + DSpark 用 `(StateType, occurrence)` 替代 `state[i]`；DCP/Unified Memory 也反复暴露 logical token、physical page row、local shard index 不能混用。

**经验：跨 rank / 跨 feature 传递的任何 state，都应该显式编码“它是什么”，而不仅仅是“它排第几个”。**

### 趋势 B：`record_stream`、生命周期和 happens-before 是三件不同的事

Tensor 仍然活着，不代表其内容不会被下一批原地修改。Overlap Scheduler 越来越依赖 immutable snapshot + CUDA Event + read-done boundary 来定义真正的 happens-before。

### 趋势 C：CUDA Graph 正把 host metadata 从 hot path 中赶出去

Spec V2、NVFP4 verify、DSV4 sparse metadata 都在向 GPU-resident metadata、静态 workspace、可预测 capacity 收敛。未来一个 backend 是否“graph-friendly”，很大程度上取决于它是否能摆脱 CPU prefix/state metadata。

### 趋势 D：Router 负责全局意图，Engine Scheduler 负责局部真实负载

[#25760](https://github.com/sgl-project/sglang/issues/25760) 的 SessionAware Router Roadmap 正在形成：bucket selection → sticky/cache-aware/load-based fallback；而 #35964 已经展示了 external rank hint + engine token-load refinement 的实际收益。

一个逐渐清晰的层次是：

```text
Router: session / bucket / cache locality / fleet-level policy
    ↓ hint + constraints
Engine Scheduler: real token load / KV pressure / local admission
    ↓
GPU execution
```

### 趋势 E：Speculative Decoding 越来越像 memory-system optimization

#30105 和 #35457 都说明：即使 acceptance 不变，只要 verify 破坏 GQA reuse、缺少 split-KV 或 workspace 引入 host sync，Spec 就可能失去全部优势。

因此以后看 Spec benchmark 不能只问：

```text
accept length 是多少？
```

还要问：

```text
verify 每 accepted token 搬了多少 KV？
是否保留 GQA sharing？
是否 split-KV？
metadata 是否 GPU resident？
CUDA Graph 中额外 launch / workspace 有多少？
```

### 趋势 F：Cache correctness 正在建立 exact oracle

Roadmap #34899 已经把 HiCache、MTP、DSpark/DFlash 纳入 exact-KL coverage。相比“最终回答是否正确”，这更接近数据库/存储系统里的 consistency invariant test。

| Spec startup | [#36050](https://github.com/sgl-project/sglang/pull/36050) | Qwen3.8-27B MTP, fresh Triton cache | 首批 C4 max TTFT **10.82→3.03 s (-72%)**，代价转移到 startup warmup |

一个值得单独记住的反例是 #36025：**优化 85% 网络流量却没有显著 latency 改善**。这正是性能分析中“总资源消耗”和“critical path”必须分开的经典案例。

## 7. 对 AI Infra 推理工程师面试的启发

本周内容非常适合转换成以下面试问题：

1. **为什么 `record_stream()` 不能解决所有 Overlap Scheduler 并发问题？**  
   它保证 allocator 不会过早复用 storage，但无法阻止下一批对 persistent buffer 的原地 mutation；需要 snapshot + CUDA Event / read-done boundary 建立 happens-before。

2. **为什么 DCP/P-D 里不能把所有“token index”当成同一种 index？**  
   logical token、DCP-sharded token、physical page row、compressed-state row 的映射不同；混用可能 silent corruption，而不是立即 crash。

3. **为什么 Spec acceptance length 很高，TPOT 仍可能比 AR 更差？**  
   Verify 可能破坏 GQA KV reuse、没有 split-KV、occupancy 过低，或者 metadata/workspace 引入 host sync。#30105 是很好的真实案例。

4. **P/D 为什么需要 process generation / epoch，而不能只识别 IP:port？**  
   进程重启可以复用相同 endpoint，但内部 rank ports、receiver、registered state 已经变化；没有 incarnation ID 会出现 ABA/stale-state 问题。

5. **为什么减少 85% transfer bytes 可能几乎不改善 TTFT？**  
   因为该传输可能已经异步 overlap，不在 critical path；优化仍然可以降低网络 contention、提高集群 scale ceiling。

6. **Scheduler 应该优化 TTFT 还是 ITL？**  
   没有单一答案。#35954 直接展示了 ITL/throughput 改善同时 TTFT 恶化的 Pareto trade-off。

7. **为什么 CUDA Graph compatible 不等于 kernel 可 capture？**  
   Graph replay 还要求 metadata device-resident、地址稳定、workspace 容量可提前计算，且不能在 replay 中依赖 CPU prefix metadata。

8. **Router 和 Engine Scheduler 的职责边界是什么？**  
   Router 更适合全局 session/cache/bucket/fleet policy；Engine 更掌握实时 token load、KV pressure 与 admission state。

## 8. 值得做成个人项目/面试 Demo 的方向

### Project A：KV allocator / eviction simulator

实现一个简化的 shared KV allocator，同时模拟：

- naive LRU
- component-local target eviction
- shared-capacity-aware eviction

复现“局部 cache 想腾空间，但共享 allocator 实际已经够用”时的过度 eviction，并统计 prefix survival / recompute tokens。

### Project B：长上下文 Spec attention microbenchmark

固定 acceptance，不改 draft model，只比较：

- GQA packed vs KV-head expanded
- split-KV vs no split-KV
- context 2K / 8K / 32K / 128K

测 kernel time、HBM bandwidth、TPOT，能够非常直观地解释 #30105。

### Project C：Overlap Scheduler metadata race demo

两个 CUDA stream：

- stream A 异步读取 shared metadata
- CPU/Scheduler 提前修改 buffer

分别展示：

- 只有 tensor lifetime protection
- immutable snapshot
- Event-based read-done fence

三种方案的差异。这是非常强的 CUDA + inference runtime 面试项目。

### Project D：P/D failure-generation fault injection

实现简化 Prefill/Decode control plane：

- Prefill 在相同 endpoint 重启
- ephemeral rank ports 改变
- Decode 保留旧 connection cache

比较 endpoint-only identity 和 `(endpoint, generation)` identity 下的恢复行为。

## 9. Roadmap：当前最值得持续观察的未完成组合

### Kimi K3 Roadmap [#32607](https://github.com/sgl-project/sglang/issues/32607)

目前值得注意的状态：

- Unified Memory × Speculative Decoding：**已标记完成**
- Unified Memory × P/D：**已标记完成**
- Unified Memory × HiCache：**仍未完成**
- `PP + Spec + PD Disagg`：**仍未完成**

这基本准确反映了下一阶段的难点：单个 feature 已经不是最大问题，**三到四个 feature 的组合状态空间才是。**

### Distributed KV Cache Roadmap [#21846](https://github.com/sgl-project/sglang/issues/21846)

Q3 目标继续明确指向：

- Agentic KV orchestration
- Direct L3 / globally shared cache
- Decode-side L2 RadixTree
- SWA / DSV4 / Mamba / DSpark 与 Decode Unified RadixTree 组合
- Prefill-as-a-Service PoC

### SessionAware Router Roadmap [#25760](https://github.com/sgl-project/sglang/issues/25760)

正在形成的 routing chain 是：

```text
bucket selection
  -> sticky
  -> cache-aware
  -> load-based
```

并计划结合 engine push-based load telemetry 与 Global KV Indexer。它和本周 #35964 的 engine-local load-aware placement 应该一起看。
