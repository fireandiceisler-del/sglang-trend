## 今日结论

今天的信息密度很高，最值得关注的不是某个单独 kernel，而是 **SGLang 开始系统性处理“异步并发后的状态一致性与 QoS”**：

1. **Scheduler：长 Prompt 不再天然独占 chunked prefill。** PR [#34623](https://github.com/sgl-project/sglang/pull/34623) 引入独立的 per-request long-prefill threshold，让一个调度轮次可以同时推进多个长请求，并允许排在长请求后面的短请求继续进入 Prefill。这是从“最大吞吐调度”向“混合流量 tail-latency/QoS 调度”迈出的重要一步。
2. **P/D + PP：bootstrap queue 被当成需要跨 stage 有序复制的状态。** Issue [#34572](https://github.com/sgl-project/sglang/issues/34572) 与 PR [#34568](https://github.com/sgl-project/sglang/pull/34568)、[#34569](https://github.com/sgl-project/sglang/pull/34569) 把 HiCache readiness、AbortReq、KV failure 等本地事件收敛进跨 PP stage 的 immutable ordered decision，避免各 stage 的队列历史分叉后进入不同 P2P round 并永久死锁。
3. **KV Cache / Unified Memory：virtual KV id → kernel id 的知识正在从 backend 中剥离。** PR [#34613](https://github.com/sgl-project/sglang/pull/34613) 把读路径映射集中到 `KVIndexSource`，目标是让 FA3/FA4/FlashInfer/TRTLLM-MHA/FlashMLA 等 backend 不再各自理解 Unified Memory 的地址空间。
4. **KV Prefill：大 KV pool 上的工作量必须与“本 batch 实际访问的数据”成比例，而不能与整个 pool 成比例。** WIP PR [#34638](https://github.com/sgl-project/sglang/pull/34638) 把 FP8 paged MLA prefill 的 whole-pool upcast 改为只 gather 当前 batch 的 KV rows；报告中的失败场景从单层 17.76 GiB 临时转换降到约 29 MB。
5. **Spec：CUDA Graph 的 key 不只是 token 数，还必须包含真实 request-slot geometry。** PR [#34636](https://github.com/sgl-project/sglang/pull/34636) 修正 DSpark compact ragged verify 的 capture geometry，说明 Spec + CUDA Graph 优化已经进入更细的“运行时 shape 必须严格落在 capture box 内”阶段。

整体趋势可以概括为：**SGLang 的优化重心正在从单路径更快，转向在 P/D、PP、DP、Spec、Unified Cache、Overlap Scheduler 同时开启时，仍然保证正确、有序、可组合，而且 tail latency 不失控。**

## 1. Scheduler：允许多个长请求并发 Chunked Prefill — #34623

**状态：Open；过去 24 小时新建。**  
PR：[Concurrent chunked prefill via --long-prefill-token-threshold](https://github.com/sgl-project/sglang/pull/34623)

### 解决的问题

当前 SGLang 的 `chunked_prefill_size` 同时承担了两个概念：

- 一轮调度允许的 Prefill token 总预算；
- 单个长请求一次最多推进多少 token。

结果是第一个 chunked request 会把共享的 `rem_chunk_tokens` 一次耗尽，**系统实际上最多只能有一个 request 处于 mid-prefill**。这会形成非常严重的 Head-of-Line Blocking。

PR 给出的生产数据很有代表性：

- Kimi-K3，642K～912K token 长 Prompt 在途时，**10.35% 请求 TTFT > 60 s**；相邻没有超长 Prompt 的时段只有 0.23%～0.56%。
- DeepSeek-V4-Flash，458K token Prompt、`chunked_prefill_size=4096` 时，需要约 **112 个连续 scheduler round** 才能完成，期间其他请求无法获得 prefill slot，TTFT p99 常态 12～14 s、峰值 27.7 s。

这说明 priority scheduling 本身解决不了问题：长请求已经进入 mid-prefill 后并不会被新的高优先级短请求抢占。

### 核心改动

新增：

```text
--long-prefill-token-threshold F
```

把两个维度拆开：

```text
batch token budget     = chunked_prefill_size
per-request quantum    = long_prefill_token_threshold
并发 mid-prefill 上限 ≈ chunked_prefill_size / F
```

同时做了几个很关键的配套设计：

- `chunked_req` → `chunked_reqs`，从单槽语义变成多请求集合。
- **Reserve-to-completion admission**：请求一旦成为不可抢占的 mid-prefill，就按“剩余 Prefill + clipped max_new_tokens”预留完成所需 KV 容量，而不是只按当前 chunk 扣预算，避免 N>1 后出现 KV overcommit deadlock。
- **Parking**：本轮 token budget 耗尽的 chunked request 保留 reservation，下一轮继续，而不是错误计入 inflight。
- `AddReqResult.SKIP` 不再终止 waiting queue 扫描：长请求 slot 满了以后，后面的短请求仍可以被调度。
- EAGLE 的 chunked-prefill tail token 处理改为 per-request，一次性对多个 mid-prefill row 做 pinned H2D + `index_copy_`。

### 当前结果

CPU 驱动真实 `PrefillAdder` 的 probe：

| 配置 | 本轮分配 | 同时 mid-prefill |
|---|---:|---:|
| stock | `[8192, 0, 0]` | 1 |
| `B=8192, F=2048` | `[2048, 2048, 2048]` | 3 |
| `B=8192, F=2000`，5 个长请求 | `[1984,1984,1984,1984,0]` | 4 |
| 1×500K + 3×2K，`F=2048` | `[2048,2000,2000,2000]` | 长请求与短请求同轮推进 |

GPU E2E benchmark 仍待补齐，因此目前应视为 **很有价值的 Scheduler 设计 PR，而不是已验证的 production default**。

- `python/sglang/srt/managers/scheduler_components/batch_result_processor.py`

### AI Infra 面试启发

这个 PR 非常适合回答：**“为什么 chunked prefill 仍可能导致 TTFT tail latency 爆炸？”**

核心不是“chunk size 太大”，而是要区分：

```text
全局 batch budget
        vs
单请求 service quantum
```

真正支持公平调度还必须解决：

```text
preemption / parking
KV capacity reservation
HOL blocking
completion guarantee
speculative state compatibility
```

这和 OS scheduler 的 time slice、网络 WFQ/DRR、存储 admission control 是同一类问题。

## 2. P/D + PP：把 Bootstrap Queue 变成有序一致状态 — #34572 / #34568 / #34569

**状态：Issue + Open PR series；过去 24 小时新建。**

- RCA：[Issue #34572](https://github.com/sgl-project/sglang/issues/34572)
- HiCache readiness consensus：[PR #34568](https://github.com/sgl-project/sglang/pull/34568)
- Ordered immutable decision：[PR #34569](https://github.com/sgl-project/sglang/pull/34569)

### 解决的问题

生产环境：

```text
PP=8 disaggregated prefill
TP=1
Mooncake KV transfer
HiCache L2-only
32K input，~90% shared prefix
高并发 cancellation
```

AbortReq / KV failure 爆发后，不同 PP stage 看到了不同的本地失败集合，于是：

```text
PP0-PP3 进入下一轮 microbatch
PP4-PP7 没进入
```

最终 8 个 scheduler 分别阻塞在 **不同的 PP P2P send/recv slot**。这不是“某个 NCCL collective 慢”，而是 stage 已经处在不同的逻辑 round；默认 watchdog 要到约 3600 s 后才暴露超时。

### 根因

旧协议允许本地事件直接改写某个 stage 的 queue history，例如：

- 本地 `KVPoll.Failed` 直接删 request；
- 第二轮 ring 传的是各 stage apply 后的局部结果，而不是 frozen decision；
- `AbortReq` 与 bootstrap decision 没有共同的全序；
- PP-wide good decision 后，某个 stage 的 metadata finalize 仍可能局部失败并 `continue`。

这实际上违反了一个分布式系统最基本的原则：

> **多个参与方依赖同一状态机继续执行时，不能允许本地事件绕过共识直接修改状态历史。**

### 核心改动

#34568 先把 HiCache storage prefetch readiness 纳入已有的两轮 PP bootstrap consensus：只有所有 stage 都 ready，请求才会 admission。

#34569 进一步引入：

```text
PPBootstrapDecision(sequence, good_rids, bad_rids)
```

语义类似一个轻量 ordered commit：

1. 第一轮收集各 stage 的 good intersection / bad union；
2. PP0 合并 pending abort / local failure；
3. 分配单调递增 sequence；
4. freeze immutable decision；
5. 第二轮每个 stage exactly-once apply，并原样转发同一 payload。

此外：

- Abort 被 fence 到 PP0 观察到的 decision sequence；
- 本地 KV failure 只能成为“下一轮 decision 的 proposal”，不能自行改 queue；
- metadata readiness 前置；
- sequence gap / payload violation / finalize violation 改成 fail-fast，而不是一小时后 watchdog 才报死锁。

### 验证

事件形状模拟 + abort storm：

- 80 个连续 decision，全部 8/8 stage 参与；
- same-sequence payload divergence：0；
- 38 个失败 RID 全部通过 ordered bad commit 清理；
- 各 stage local failure proposal 可以不同，但最终 committed set 一致；
- 约 7 小时 soak：`127569 launched / 127543 succeeded / 0 failed`，人工停止。

### 相关代码

#34569 的核心文件：

- `python/sglang/srt/disaggregation/prefill.py`
- `python/sglang/srt/managers/scheduler.py`
- `python/sglang/srt/managers/scheduler_pp_mixin.py`
- `python/sglang/srt/managers/io_struct.py`

### AI Infra 面试启发

这是一个非常好的“推理引擎为什么会遇到分布式一致性问题”的案例。

P/D + PP 并不是简单的：

```text
P 机器算完 KV -> 发给 D 机器
```

一旦加入 PP、cache readiness、abort、异步 transfer，真正需要一致的是：

```text
request lifecycle
admission decision
queue history
microbatch order
transfer state
```

你可以把 `PPBootstrapDecision(sequence, ...)` 类比成一个非常轻量的 **replicated state-machine log entry**：不是为了持久化，而是为了让所有 PP stage 对“下一步该处理谁”拥有同一个有序事实。

## 3. Scheduler + DP Attention：去掉 Symmetric-Memory Metadata 的阻塞式 GPU Rendezvous — #34625

**状态：Draft / stacked；最新实现 GPU 验证仍待完成。**  
PR：[Remove GPU rendezvous from symmetric DP metadata sync](https://github.com/sgl-project/sglang/pull/34625)

### 解决的问题

在 DP attention + overlap scheduler 中，metadata sync 的 GPU barrier 本身就是一次 rank rendezvous。

可能出现：

```text
Rank A: previous forward collective -> metadata barrier
Rank B: metadata barrier            -> previous forward collective
```

如果两个 collective 顺序反转，就形成经典的 distributed ordering deadlock。

粗暴方案是等待整个 forward stream，但这样会把本来可以 overlap 的 tail compute 全部串行化。

### 核心改动

新的方向是用 **generation marker + peer snapshot** 代替 blocking barrier：

- 每个 rank 把完整的 7-field metadata row 直接写入所有 peer 的 double-buffered symmetric region；
- 完整 row 可见后，再发布 system-scope generation marker；
- consumer acquire marker，snapshot 对应 peer row；
- generation 不匹配则 retry；
- slot 通过双缓冲轮换，不再引入额外 ACK rendezvous。

这本质上从：

```text
barrier synchronization
```

转向：

```text
publish -> versioned visibility -> acquire/snapshot
```

### 性能证据

注意：下面是 predecessor/frozen integration snapshot 的历史数据，**不是最新 marker-only head 的最终 benchmark**：

| Concurrency | Gloo TPOT | marker/ACK TPOT | 变化 |
|---:|---:|---:|---:|
| 3072 | 24.321 ms | 23.168 ms | -4.74% |
| 4096 | 27.657 ms | 26.069 ms | -5.74% |

同一批历史验证中，44×GB300 serving 运行完成数万请求且没有 hang；最新 head 仍需重新跑 multi-rank soak 和正式性能测试。

### 相关代码

- `python/sglang/srt/distributed/device_communicators/symm_mem_gather.py`
- `python/sglang/srt/distributed/device_communicators/symm_mem_marker.py`
- `python/sglang/srt/managers/scheduler_components/dp_attn.py`

### AI Infra 面试启发

需要区分两个概念：

```text
memory visibility
rank rendezvous
```

很多时候我们真正需要的是“某份数据写完整后其他 rank 能安全看见”，并不需要“所有 rank 在同一时刻到达 barrier”。

这也是 overlap system 的核心：**同步范围越大，正确性越容易，但 overlap 越少；高性能实现需要找到最小 correctness boundary。**

## 4. KV Cache / Unified Memory：统一 Virtual→Physical KV Index 边界 — #34613

**状态：Open；stacked on #34602。**  
PR：[one read-path id-space choke point](https://github.com/sgl-project/sglang/pull/34613)

### 解决的问题

`--enable-unified-memory` 下，`req_to_token` 保存的是 virtual KV slot id，而 attention kernel 需要 kernel-facing physical/dense id。

此前每个 attention backend 都必须自己知道：

```text
virtual id -> physical/dense id
```

因此 Unified Memory 实际上把 backend 锁死在少数实现上，抽象泄漏严重。

### 核心改动

引入集中式：

```text
KVIndexSource
    -> KVIndexBatchView
        -> attention backend
```

backend 不再自行 translate。

目标 backend compatibility：

| 模型 / KV layout | 之前 | 之后 |
|---|---|---|
| Unified MHA/SWA uniform-row | Triton | Triton + FA3 + FA4 + FlashInfer + TRTLLM-MHA |
| Unified MLA | 多 backend | 再增加 FlashMLA |
| asymmetric K/V / forced strided | Triton | 保持 Triton |

非 Unified Memory 情况则严格 passthrough，不额外做 tensor operation。

同时删除旧的 `unified_mem_hooks.py`，并增加 source-scan test，防止未来 attention backend 再偷偷引入 Unified translation。

### 性能影响

在 radix cache + overlap scheduler + CUDA Graph + page size 256 的 serving benchmark 中，各 backend 的 unified/non-unified 差异大多在约 ±1% 范围，说明抽象收敛没有引入明显 hot-path 成本。

### 相关代码

- `python/sglang/srt/mem_cache/kv_index_source.py`
- `python/sglang/kernels/ops/kvcache/kv_indices.py`
- `python/sglang/srt/layers/attention/flashinfer_backend.py`
- `python/sglang/srt/layers/attention/flashattention_backend.py`
- `python/sglang/srt/layers/attention/trtllm_mha_backend.py`
- `python/sglang/srt/layers/attention/flashmla_backend.py`
- `python/sglang/srt/model_executor/forward_batch_info.py`

### AI Infra 面试启发

这是典型的 **address-space abstraction** 问题。

类似 OS 中：

```text
virtual address -> physical address
```

推理引擎 Unified KV 也有：

```text
logical/virtual token slot -> physical KV storage row
```

一个好的架构应该让 kernel/backend 看到稳定的 canonical view，而不是让每个 backend 都理解 allocator 内部映射。

这能显著降低组合爆炸：

```text
N cache layout × M attention backend
```

不应该演化成 N×M 份定制 glue code。

## 5. KV Cache × Prefill：FP8 Paged MLA 从 O(pool) 改向 O(batch) — #34638

**状态：Draft / WIP；尚未完成 accuracy validation。**  
PR：[Gather only the batch's KV rows for fp8 paged prefill](https://github.com/sgl-project/sglang/pull/34638)

### 解决的问题

`FlashInferMLAAttnBackend.forward_extend` 的 paged 路径当前会：

```python
whole_kv_pool.to(q.dtype)
```

也就是说一次 Prefill 的临时转换成本与 **整个 KV pool 容量** 成正比，而不是与当前 batch 实际访问的 KV 数量成正比。

Kimi-Linear 8×B200 的失败场景：

- KV pool：约 16.5M tokens；
- 单层 BF16 临时 copy：**17.76 GiB**；
- 直接 OOM。

### 核心改动

计划让 paged wrapper 使用 compact index space，只 gather 当前 batch 所需 rows，并在 gather 时完成 dtype cast。

报告中的同一失败 batch：

```text
17.76 GiB / layer
        ->
~29 MB / layer
```

在原本能勉强运行的配置上，还可减少约 106 GiB / forward 的 conversion traffic。

DCP、Unified Pool、captured verify plan 因各自已有不同 index semantics，暂时保留原路径。

### 相关代码

该 PR 只改一个核心文件：

- `python/sglang/srt/layers/attention/flashinfer_mla_backend.py`

### AI Infra 面试启发

很典型的性能原则：

> **动态请求路径中的工作量应该跟 working set 成比例，而不是跟 provisioned capacity 成比例。**

KV cache 越做越大以后，任何 `O(pool_size)` 的临时 materialization 都会从“小浪费”变成 OOM 级别的设计问题。

当前 PR 仍是 WIP，应关注后续 P/D+DCP 的 correctness parity 和 benchmark。

## 6. Speculative Decoding：DSpark Ragged Verify CUDA Graph 必须按 Request Geometry Capture — #34636

**状态：Open；CPU regression 已通过，GPU E2E 待确认。**  
PR：[Key DSpark compact ragged CUDA graphs by request-slot geometry](https://github.com/sgl-project/sglang/pull/34636)

### 解决的问题

报告场景：

```text
graph sizes = [1, 32, 192]
verify width = 6
TP4 / 4×H20
```

192-token tier 实际语义是：

```text
32 requests × 6 verify tokens
```

但 capture 端把它重新解释成：

```text
192 request slots × 1 token
```

于是 runtime staging `[6] * 32` 到一个 capture geometry `[1] * 192` 的 graph，第一次 replay 就可能 illegal memory access。

### 核心改动

`_ragged_capture_slots` 从按 token 数估 slot：

```text
min(num_tokens, max_bs)
```

改成：

```text
num_tokens // captured_req_width
```

即 CUDA Graph key/capture box 显式尊重“request count × verify width”的真实几何。

### 相关代码

- `python/sglang/srt/model_executor/runner/decode_cuda_graph_runner.py`
- `test/registered/unit/model_executor/runner/test_decode_cuda_graph_runner.py`
- `test/registered/spec/dspark/test_ragged_verify.py`

### 工程影响

- 最大 tier 的 capacity-critical geometry 不变；
- 中间 tier 恢复正确 capture；
- 少数全 verify-len=1 且 request 数很多的 batch 会回退 eager，而不是错误 replay。

### AI Infra 面试启发

CUDA Graph 不是“batch size 对上就行”。对 ragged/spec decode 来说，真正的 graph contract 往往包括：

```text
request slots
per-request token width
total token tier
metadata layout
index-buffer shape
```

如果只用 `num_tokens` 作为 cache key，两个 token 总数相同但 geometry 不同的 batch，仍可能拥有完全不同的 memory access semantics。
