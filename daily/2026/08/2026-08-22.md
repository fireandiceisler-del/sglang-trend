## 今日结论

今天最清晰的主线不是某一个孤立 feature，而是 **SGLang 正继续把“异步状态”的 ownership / lifetime / synchronization contract 显式化**。

1. **KV Cache：HiCache 的核心难题已经从“能否异步搬 KV”转向“异步 DMA 尚未完成时，谁拥有 slot / node，以及什么时候允许重新分配”。** #35931 和 #35769 都在修同一类本质问题：逻辑 cache tree 已经变化，不代表物理 H2D/DMA 已结束；allocator、radix tree 与 transfer pipeline 必须共享明确的 ownership contract。
2. **P/D：从静态 P/D 拓扑向“Decode 侧缓存 + 运行时弹性角色”继续演进。** #35837 让 DeepSeek-V4 DSA compressed KV 进入 decode-side radix cache；#28403 则在推进不重载权重、不重建主 KV pool 的 Prefill ↔ Decode runtime role switch。
3. **Scheduler：Overlap Scheduler 的收益越来越依赖系统级去同步，而不只是 kernel 优化。** #34515 横跨 HiCache、稀疏 prefill、disagg transfer 和 speculative metadata，把多处 CPU/GPU 同步移出 critical path，在 AgentX GB300 长时间压测中总 token throughput/GPU 提升约 25%～30%。
4. **Speculative Decoding：分布式 adaptive spec 开始从“单 rank 本地策略”升级成“collective-safe 的全局决策”。** #35898 用已有 DP all-gather 达成 draft depth 共识；#35872 则说明即使只是 topk=1 的 token selection，删除一个无意义的 full-vocab softmax 也能让 ROCm draft CUDA Graph 缩短 8.7%。
5. **一个非常值得长期跟踪的新 RFC：Draft SWA 被重新定义为“已提交、可复用的 sidecar KV”与“仅当前 verify step 有效的 scratch”两类状态。** 这是 Spec × KV Cache × P/D × HiCache composability 的关键抽象升级。

## 1. KV Cache

### [NEW] #35931 — HiCache：拒绝复用仍被 in-flight load-back 占用的节点

PR: [#35931 — Reject load-back specs that claim nodes pinned by an in-flight load-back](https://github.com/sgl-project/sglang/pull/35931)

**解决的问题**

在 hierarchical cache + Unified Radix Tree 下，第一次 Host→Device load-back 尚未完成时，cache tree 的部分 Full device state 可能已经重新发布。此时第二个 load-back 可以从相同节点构造新的 SWA load spec，并试图接管仍由前一次 transfer 持有的 node，最终触发 foreign `load_back_pending_id` ownership 冲突，严重时直接让 scheduler 崩溃。

**核心改动**

- `build_load_back_spec` 在构造 transfer spec 时检查 `nodes_to_load`；只要节点仍被另一个 in-flight load-back pin 住，就拒绝本次 spec。
- 调用方不再冒险接管 slot，而是 back off / recompute。
- 对 load-back threshold 增加最小值保护，避免边界配置产生错误 skip 行为。

**工程影响**

这是典型的“**逻辑状态已经可见，但物理数据搬运尚未结束**”问题。修复选择 correctness-first：宁可暂时 recompute，也不能把仍在 DMA 使用中的 slot 交给第二个 owner。

**相关代码**

- `python/sglang/srt/mem_cache/unified_tree_core.py`
- `python/sglang/srt/mem_cache/unified_radix_cache.py`

**面试价值**

很适合回答：为什么异步 KV offload/load-back 不能只靠 radix tree 的 ref-count？因为至少还存在一层 **transfer ownership**；tree reference、allocator ownership、DMA lifetime 是三个不同概念。

### [UPDATED] #35769 — Buffer-mode HiCache：修 H2D use-after-free，并加入可选 anchor lock

PR: [#35769 — Fix buffer-mode HiCache load-back ownership races](https://github.com/sgl-project/sglang/pull/35769)

**解决的问题**

buffer-only host mode 中，storage prefetch 会先拿 device slots、排队 H2D，然后才由 radix insert 决定 canonical ownership。并发相同 prefix，或者 SWA tombstone 下仍存在 live Full-KV 时，insert 可能把“重复”的 slot 释放掉，但 H2D DMA 仍在写这些 slot，形成 queued **use-after-free / silent KV corruption**。

**核心改动**

- transfer 前先检查当前 live tree，要求 staged `matched_len` 与 unified tree 的 canonical hit 一致，否则放弃 staged result 并 recompute。
- insert 后再次 fail-stop 校验 canonical tree slice 是否与 incoming slots 一致。
- 可选 `SGLANG_ENABLE_HICACHE_BUFFER_ANCHOR_LOCK=1`：从 storage IO commit 到真正消费完成之间 pin 住 anchor；同时提供容量上限，避免锁把 device pool 吃满。

**工程影响**

这进一步确认 HiCache 的正确抽象不是“cache 命中了就搬回来”，而是：

`storage hit → reserve device ownership → async transfer → canonicalize tree ownership → publish reusable state`

每一步都有独立失败和竞争窗口。

**相关代码**

- `python/sglang/srt/mem_cache/buffer_mode/pipeline.py`
- `python/sglang/srt/mem_cache/unified_radix_cache.py`
- `python/sglang/srt/environ.py`

## 2. Prefill / Decode Disaggregation

### [NEW] #35837 — DeepSeek-V4 DSA compressed KV 支持 Decode-side Radix Cache

PR: [#35837 — Decode-side radix cache for DeepSeek-V4 (DSA compressed KV)](https://github.com/sgl-project/sglang/pull/35837)

**解决的问题**

P/D 场景下，Decode 侧已有 radix cache 能力，但 DeepSeek-V4 的 DSA compressed KV（C4/C128/indexer 等）具有派生式、位置相关的布局，不能直接套普通 MHA KV allocator 的假设。因此此前无法完整复用 Decode 侧 prefix state。

**核心改动**

- 把 DSV4 compressed pools 纳入现有 `[FULL, SWA]` unified-tree 生命周期，让压缩 KV 与 target prefix 一起维护一致性。
- 利用 `page_size=256` 与 compressed grouping 的对齐关系进行 decode-side cache reuse。
- 修复 cache-hit test kit 长期存在的一个隐藏问题：router `/server_info` 没有暴露真实 backend page size，导致 expected-cache 逻辑错误地按 `page_size=1` 计算。
- 当前仍明确拒绝不兼容的 HIP/NPU allocator/ring 组合，而不是 silent fallback。

**性能结果**

- 8×H20、4P+4D、NIXL：cache hit 可从 0 → 1024 → 2048 token；GSM8K 100 题准确率保持 0.96。
- 两节点 16×H20、8P+8D TP8 的 shared-prefix workload：
  - Median TTFT：**1919 ms → 1226 ms（-36%）**
  - Mean TTFT：约 **-13%**
  - P90 TTFT：约 **-9%**
  - Median E2E：约 **-8%**
  - request / output throughput：约 **+3.3%**
  - 256/256 请求成功，无 retraction。

**相关代码**

- `python/sglang/srt/mem_cache/kv_cache_builder.py`
- `python/sglang/test/kits/cache_hit_kit.py`
- `test/registered/disaggregation/test_disaggregation_decode_radix_cache_swa_dsv4.py`

**面试价值**

这里非常适合讨论：为什么 P/D 下 Decode 侧仍值得保留 prefix cache？因为 agentic / multi-turn workload 中，Decode 并不一定每次都只消费 Prefill 新传来的增量 KV；本地 L1/L2 命中可以直接减少跨 P/D transfer 与重新 materialize 的成本。

### [UPDATED] #28403 — P/D runtime role switching：运行时动态改变 P:D 比例

PR: [#28403 — Introduce runtime role switching between prefill and decode](https://github.com/sgl-project/sglang/pull/28403)

**核心设计**

这个 PR 的关键观察是：**token KV pool 本身并不天然属于 Prefill 或 Decode 角色**。真正角色相关的是 bootstrap queue、sender/receiver、poll thread、registration、metadata buffer 等 disaggregation control/data-path structures。

因此 role flip 可以设计成：

1. drain 当前 instance 到 idle；
2. 保留模型权重和主 KV pool；
3. teardown 当前 role-specific resources；
4. rebuild 新角色所需的 transfer/control structures；
5. 若切到 Decode，再按目标 batch size capture Decode CUDA Graph；
6. 重新 dispatch scheduler event loop。

提供 `/pd_role_switch` 控制接口，并通过 backend `supports_role_switch + teardown()` opt-in。

**验证**

- 25 个 round-trip cycle，共 **100 次 role switch**，报告无资源泄漏。
- Qwen3-32B、1P1D、Radix Cache ON 的代表性数据：
  - Output tok/s：2680 → 2655 → 2641（baseline / flip / flip-back）
  - Median TTFT：649 → 633 → 679 ms
  - Median TPOT：10.62 → 10.77 → 10.69 ms
- 说明 role switch 本身可做到接近 steady-state baseline。

**相关代码**

- `python/sglang/srt/disaggregation/role_switch.py`
- `disagg_service.py`
- `tokenizer_control_mixin.py`
- `model_runner_kv_cache_mixin.py`
- `invariant_checker.py`

**趋势判断**

P/D 正从“部署时固定资源配比”走向 **elastic serving**：未来 router 可以根据实时 prefill queue / decode pressure 动态重平衡 P:D ratio，而不用重新加载数百 GB 权重。

## 3. Scheduler

### [UPDATED] #34515 — 系统级移除 Scheduler 同步，强化 Overlap Scheduler

PR: [#34515 — Remove many scheduler synchronization to enable overlap scheduler on agent workload](https://github.com/sgl-project/sglang/pull/34515)

这是今天最值得精读的 Scheduler PR。

**解决的问题**

在 DSV4 / agentic / disaggregated sparse-prefill 场景，性能瓶颈已经不是单个 kernel，而是大量 scheduler-side CUDA sync 和 host stall：allocator cleanup、HiCache write/load-back、disagg transfer index preparation、speculative metadata、DP registration 等都会让 GPU 出现空洞。Blackwell MegaMoE 下，如果所有 SM 都被主 kernel 占满，side-stream/NCCL 甚至可能无法排空并出现 deadlock 风险。

**核心改动**

- HiCache：把 direct-IO readiness 等待放到 device-bound helper thread；批量化 unified write-back eviction；把 Full-KV load-back ownership 与辅助锁解耦。
- sparse prefill / allocator cleanup：避免数据相关的 `torch.unique` / scalar readback；预先构造 sparse prefill metadata。
- Overlap Scheduler：为 EAGLE / DFLASH / DSpark 发布更精确的 shared-read boundary，在 scheduler 重写 metadata 前确保旧 forward 已完成最后一次读取。
- Disaggregation：异步 staging transfer indices；减少 cached-prefix early-send 的阻塞；后台做 DP rank registration。
- Blackwell MegaMoE：默认预留少量 SM，使 communication / side-stream 能持续推进。

**性能结果**

AgentX、GB300、28 GPU（2×DEP8 Prefill + DEP12 Decode）、并发 1152、HiCache ratio 2.1 的长时间压测中，Total tokens/s/GPU 相对 baseline 大致：

- 10 min：**+30.2%**
- 15 min：**+29.6%**
- 20 min：**+29.0%**
- 25 min：**+27.0%**
- 30 min：**+29.9%**
- 35 min：**+25.5%**
- 40 min：**+27.2%**，而 baseline 在这一阶段崩溃。

DSpark GSM8K 1319 题保持约 0.966 accuracy，说明这些优化主要改变执行时序而非模型语义。

**相关代码**

该 PR 跨 40+ 文件，值得重点从以下目录看：

- `python/sglang/srt/managers/` — scheduler / metadata lifecycle
- `python/sglang/srt/mem_cache/` — HiCache / allocator
- `python/sglang/srt/disaggregation/` — transfer scheduling
- `python/sglang/srt/speculative/` — shared-read / WAR boundary

**面试价值**

可以用它回答一个很典型的问题：**“为什么 kernel 已经很快，GPU utilization 仍然低？”** 因为 host scheduler 的 `.item()`、allocation cleanup、metadata H2D、cross-stream fence、background IO completion 都可能把 GPU 主 stream 饿住。真正的 overlap optimization 往往需要改整个 runtime contract。

### [NEW] #35936 — Abort ownership 回归 Scheduler，避免 client disconnect 留下 zombie request

PR: [#35936 — Prevent zombie requests after client disconnect: always dispatch AbortReq](https://github.com/sgl-project/sglang/pull/35936)

这不是普通“HTTP 小修”，而是一个很清晰的 **request lifecycle ownership** 问题：streaming client disconnect 后，TokenizerManager 的本地 `rid_to_state` 可能已经被清掉；旧逻辑因此认为 request 不存在，不再向 Scheduler 发送 `AbortReq`，但 Scheduler 其实仍在 decode，直到 `max_tokens`。

修复后 `abort_request` 不再以 tokenizer 本地 bookkeeping 作为是否发送 abort 的依据——**Scheduler 才是请求是否仍存活的 source of truth**。重复/未知 abort 在 Scheduler 侧天然是安全 no-op。

相关代码：`python/sglang/srt/managers/tokenizer_manager.py`。

生产意义：一个被中断的长请求此前可以继续浪费数分钟 GPU，修复后 decode 很快停止。这类 bug 体现了多进程 serving 系统中“frontend state ≠ execution state”。

## 4. Speculative Decoding

### [NEW] #35898 — Adaptive Speculative Decoding 支持 DP Attention

PR: [#35898 — Enable adaptive speculative decoding under DP attention](https://github.com/sgl-project/sglang/pull/35898)

**问题本质**

Adaptive Spec 会按当前 batch 动态选择 `num_steps`。在 DP Attention 下，每个 rank 有自己的 local batch；若独立决策 draft depth，则 `num_draft_tokens` 不同，继而让 MLP-sync / verify collective 的 tensor shape 不一致，最终可能 NCCL hang。因此此前直接禁用了 adaptive + DP。

**核心改动**

不增加新 collective，而是把每个 rank 想要的 `num_steps` piggyback 到已有 MLP-sync `all_gather`：

- idle / 非 adaptive rank 投 `INT_MAX` sentinel；
- 所有 rank 对该列取 `min()`；
- `min` 既保证 collective shape lockstep，又不会迫使任何 rank 使用比自身容量判断更激进的 draft tier；
- rank-local EMA 继续学习，但真正 activation 由 consensus 决定。

**性能 / 正确性**

4×H200、TP4 / DP2 / EP4：

- concurrency=1：fixed accept_len 3.25 / adaptive 3.24，output 均 116 tok/s；
- concurrency=8：fixed 3.24 / adaptive 3.25，output 均 548 tok/s；
- 48 并发 shape-changing tier switch 也完成，无 deadlock。

也就是说：**当 policy 不降档时，跨 DP 共识几乎零额外开销。** 真正收益取决于低 acceptance、高负载场景。

**相关代码**

- `python/sglang/srt/managers/scheduler_components/dp_attn.py`
- `python/sglang/srt/managers/schedule_batch.py`
- `python/sglang/srt/speculative/adaptive_runtime_state.py`
- `python/sglang/srt/speculative/eagle_worker_v2.py`
- `python/sglang/srt/speculative/adaptive_spec_params.py`

**面试价值**

这是“本地最优策略为什么不能直接用于分布式系统”的标准案例：一个看似纯本地的 scheduler 决策，只要它决定了 collective tensor shape，就必须先形成全局共识。

### [NEW] #35872 — ROCm EAGLE topk=1 去掉无意义 full-vocab softmax

PR: [#35872 — Skip full-vocab softmax in EAGLE topk==1 draft on ROCm](https://github.com/sgl-project/sglang/pull/35872)

当 `topk=1` 时，EAGLE draft tree 实际退化成单链，后续只需要 argmax index，softmax probability 根本不会被消费。CUDA 早已有 fast path，但 ROCm 因历史 accuracy 回归一直保留 full-vocab softmax。

本 PR 在 ROCm + AITER 可用且 vocab 大于安全阈值时，用 `aiter.greedy_sample` 直接取 argmax，并且同时覆盖真正占时的 draft-decode loop 与 draft-extend site。

**Benchmark：Qwen3.5-397B-A17B-MXFP4，MI355X TP2**

- token selection：**149.1 µs → 18.0 µs，约 8.3×**
- draft CUDA Graph 总时间：**1.568 s → 1.433 s（-8.7%）**
- Median TPOT：concurrency 4～32 多数改善约 **1%～2%**，concurrency 64 约 0.5%
- 总吞吐变化较小且受 TTFT / scheduler jitter 影响，PR 没有把噪声包装成大幅收益。

同时发现 AITER `greedy_sample` 在 `vocab <= 16368` 时可能返回负的越界 index，因此新 fast path 明确加了 vocab guard，而不是无条件替换。

## 5. Roadmap / RFC

### [NEW RFC] #35789 — Draft SWA：Committed Sidecar KV vs Verify Scratch

RFC: [#35789 — Re-layer Draft SWA into Committed Sidecar KV and Verify Scratch](https://github.com/sgl-project/sglang/issues/35789)

这是今天最有架构含量的一条。

RFC 提议把 DSpark 等 speculative decoding 中的 draft SWA KV 拆成两类完全不同的状态：

```text
Draft SWA
├── committed sidecar KV   # content-scoped，可复用
└── verify temporary       # step-scoped，只是 scratch
```

**为什么重要**

当前 draft SWA pool 把“已接受 prefix 的 canonical draft KV”和“本次 verify 中可能被 reject 的临时 KV”混在同一生命周期里，带来三类问题：

1. rejected data 物理上残留后，很容易被误认为 committed cache artifact；
2. PD / HiCache 不知道哪些 draft state 可以安全传输、offload；
3. memory accounting 把 draft layer 当成 target average layer 计费，但 DSV4 DSpark draft layer 实际只有 SWA，没有 C4/C128/indexer/compression state，造成过度预留。

**新语义**

- committed sidecar：跟随 target prefix 生命周期，可 radix-visible、可 cache hit、可 P/D transfer、可 HiCache offload/load-back；
- verify scratch：只属于当前 speculative step，不进入 radix tree、不进入 HiCache、不跨 P/D 传输；
- 只有 accepted 且 canonical 的 draft KV 才能进入 sidecar；proposal scratch 不能因为物理内容“看起来像 KV”就直接 promote；
- `draft_swa_stage_count` 应从真实 capture/injection stages（如 `dspark_target_layer_ids`）推导，而不是只看逻辑 NextN layer 数。

**趋势判断**

这和近期 SGLang 大量 correctness PR 的方向高度一致：未来 cache/state 的核心抽象会更多基于 **semantic lifetime**，而不是“它恰好存在某个 tensor pool 里”。

## 8. 对 AI Infra 面试 / 项目实践的启发

### 8.1 异步 KV 系统里至少要区分三种 ownership

不要只回答“ref-count 防止被释放”。更完整的模型是：

- **cache/tree ownership**：这个 prefix/node 是否逻辑存在；
- **allocator ownership**：这些 physical slots 能否重新分配；
- **transfer ownership**：DMA / RDMA / async H2D 是否仍在访问这块内存。

#35931 / #35769 的错误都来自三者不同步。

### 8.2 P/D 分离不是“两个 server + 搬 KV”这么简单

真正成熟的 P/D 系统还要处理：

- Decode-side prefix reuse；
- local cache 与 incremental transfer 的组合；
- role-specific resource teardown/rebuild；
- draining 与 in-flight ownership；
- Decode CUDA Graph 重捕获；
- 动态 P:D ratio。

#35837 + #28403 可以作为一组理解。

### 8.3 Overlap Scheduler 的关键是 happens-before，而不是“多开一个 stream”

移除 `.item()` / synchronize 之后必须回答：scheduler 什么时候可以覆写 metadata？旧 forward 的最后读取点在哪里？异步 H2D 的 source tensor 谁 pin？NCCL side stream 是否有执行资源？

#34515 的价值就在于它把这些问题当作统一 runtime contract，而不是零散 micro-optimization。

### 8.4 分布式 adaptive policy 首先要保证 collective shape 一致

#35898 是很好的系统设计题：每个 DP rank 的本地最优 draft depth 可以不同，但 collective 需要一致 shape。最简单可靠的方案不是让每 rank 自己跑，而是先通过已有同步通道形成 conservative consensus。

### 8.5 “Committed state” 与 “temporary state” 应该从语义上分层

#35789 提出的 sidecar/scratch 划分值得迁移到更多状态系统：

- accepted/canonical → content-scoped，可复用/迁移；
- speculative/in-flight → step/request-scoped，不应进入长期 cache；
- 物理 buffer 是否还留着数据，不等于数据仍具备语义有效性。

这类语义分层往往比再加一个 bool flag 更能解决长期 composability 问题。
