# SGLang 每日技术动向 — 2026-08-26

> 观察窗口：过去约 24 小时。只保留 KV Cache、Prefill/Decode 分离、Scheduler、Speculative Decoding 四条主线；过滤纯模型适配、机械重构和无架构影响的小修复。

## 今日结论

今天最明显的趋势不是某个单 kernel 再快几个百分点，而是 **SGLang 正继续把异步推理里的“跨组件状态契约”显式化**：

1. **KV Cache × PP**：长期存在的 HiCache L3 + Pipeline Parallelism 状态分歧修复 #27010 正式合入，通过 scheduler 侧 completion-event 共识和后台 prefetch 的 `all_reduce(MIN)`，让多个 PP stage 对缓存进度达成一致。
2. **P/D × PP**：#36248 为 PP prefill 引入 Breakable CUDA Graph 的 proxy tensor 支持，2K 小 aggregate forward 的峰值吞吐从 34.9K 提升到 86.6K tok/s，说明小 chunk P/D prefill 的瓶颈很大一部分是 host launch/control bubble，而非 GPU compute。
3. **Scheduler**：#36310 尝试把单一 worst-case request limit 拆成 normal capacity 与 physical capacity，并只对“高 prefix hit + 小 uncached tail + 有界输出”请求开放额外 admission lane。代表 workload 请求吞吐提升 2.42×，但以减少 Full-KV pool 容量为代价。
4. **Spec × Overlap Scheduler**：#36324/#36335 把 EAGLE draft-extend CUDA Graph 的 backend capability 与 shared-state WAR 同步语义拆开。核心问题已经从“这个 backend 能不能 graph capture”升级为“graph replay 是否会重新读取 scheduler-owned shared state，以及 read-done event 应该在哪个 happens-before 边界发布”。

整体来看，SGLang 的优化重心越来越像一个高性能异步运行时：**capacity、ownership、shared-state read boundary、跨 stage 共识和控制面协议**正在成为一等抽象。

## 1. KV Cache：HiCache L3 × PP 一致性修复正式合入

### PR #27010 — Fix PP inconsistency with HiCache L3

- 状态：**Merged**（2026-08-25）
- PR：https://github.com/sgl-project/sglang/pull/27010
- Merge commit：`829138a31e4f464563defc35b10e3468542e9aa9`

### 解决的问题

HiCache 与 PP 组合时，不同 PP rank 的 scheduler / prefetch completion 状态可能逐渐分叉，最终导致各 stage 对同一请求的缓存可用长度理解不同，并引发 crash。

这不是普通的“cache miss 判断错误”，而是典型的 **分布式状态机一致性问题**：每个 PP stage 都有自己的异步队列、prefetch thread 和本地 L3 状态，但一次 pipeline forward 要求所有 stage 对请求是否 ready、已经 load/prefetch 多少 token 做一致决策。

### 核心改动

PR 引入两层同步：

- **scheduler thread 的 `pp_sync`**：PP0 先决定本轮应该消费多少 `ack_load_queue` / `ack_prefetch_queue` completion event，其他 PP stage 必须消费相同数量，避免 scheduler 状态机进度分叉。
- **prefetch thread 的 `all_reduce(MIN)`**：如果各 PP stage 在 L3 上实际可恢复的 prefix 长度不同，以所有 stage 的最小值作为本轮一致可用长度。
- 新增后台 `prefetch_sync_thread`，把跨 rank 的 collective 从 scheduler 主线程移走，避免直接阻塞 scheduling hot path。

### 性能 / 工程影响

SWE-bench Verified 的对照测试中，TP8 + L3 baseline 为 356/500，PP4×TP2 + L3 为 353/500；差异主要来自长时间运行时的容器退出，未观察到模型正确性系统性回归。

更重要的是多轮 HiCache 测试：L1/L2 容量不足后 cache hit rate 会明显下降，而 L3 能将后续 round 的 hit rate维持到接近 0.90，说明 PP 下 L3 一致性修复对长会话 / agentic workload 是实质能力补全。

- `python/sglang/srt/managers/scheduler.py`
- `python/sglang/srt/mem_cache/hicache_storage.py`
- `python/sglang/srt/mem_cache/hiradix_cache.py`

### AI Infra 面试启发

一个很好的面试问题是：**为什么 PP 下不能让每个 stage 独立判断“缓存是否 ready”？**

答案的关键不是“因为需要同步”，而是：pipeline batch 是一个跨 stage 的分布式事务；只要任意 stage 对 prefix 长度、completion event 数量或 request state 的理解不同，后续 collective / pipeline send-recv 就可能进入不同 control flow。因此需要把“本地异步缓存事件”提升成 **跨 stage consensus-like decision**，常见策略就是 sequence/round + MIN/AND 共识，而不是让每个 rank 自由推进。

## 2. KV Cache：HiSparse 开始补齐 PP 下的 layer-local index space

### PR #36331 — Fix layer indexing and enable prefetch under PP

- 状态：Open
- PR：https://github.com/sgl-project/sglang/pull/36331

### 解决的问题

`HiSparseCoordinator` 的 per-layer buffer 是按当前 PP rank 实际持有的 local layer slice 分配的，但 attention backend 传进来的却是 model-global `layer_id`。PP1 以后 global layer id 与 local array index 不再相同，因此同步 swap-in 本身就可能越界；旧逻辑只禁用了 shared-index prefetch，并没有真正解决 index-space mismatch。

### 核心改动

- 在 coordinator 公共入口统一做 `global_layer_id -> local_layer_id` 转换。
- 将 shared-index skip pattern 按当前 PP stage 的 `[start_layer, start_layer + layer_num)` 切片。
- 如果 stage 恰好从 skip layer 开始、无法携带上一 stage 的 device-side miss plan，则安全退回同步 swap-in。
- 在满足条件时重新允许 PP 下 shared-index prefetch。

### 性能 / 工程影响

GLM-5.2-NVFP4、8×RTX PRO 6000、P/D 场景中：

- TP8/PP1：`max_total_num_tokens = 238,720`，client goodput 约 180 tok/s；
- TP4/PP2：`max_total_num_tokens = 442,432`，约 **1.85× KV 容量**，client goodput约 **285 tok/s（1.58×）**。

PP2 的 decode 侧仍有约 46% KV pool 空余，说明此时瓶颈已经转移到 prefill，285 tok/s 还是一个下界。

### 相关代码位置

- `python/sglang/srt/managers/hisparse_coordinator.py`
- `python/sglang/srt/model_executor/model_runner.py`
- `python/sglang/srt/mem_cache/memory_pool.py`（local layer indexing convention）

### AI Infra 面试启发

这是非常典型的 **logical/global index 与 physical/local index 分离** 问题。DCP、PP、paged KV、SWA、HiSparse 都会制造新的 index space。做推理 runtime 时，最好在模块边界明确规定输入属于哪个 index space，并只在一个地方转换；如果把 global/local/page/token/slot index 混在热路径里，很多 bug 不会报错，而是变成 silent corruption 或只在特定 parallel topology 下出现。

## 3. P/D × PP：Prefill CUDA Graph 开始支持 PPProxyTensors

### PR #36248 — Support prefill CUDA graph proxy tensors

- 状态：Open，过去 24 小时持续更新
- PR：https://github.com/sgl-project/sglang/pull/36248

### 解决的问题

PP prefill 过去无法走 breakable prefill CUDA Graph：PP stage 需要交换 `PPProxyTensors`，且 attention layer 使用 global layer id，而 graph runner 假设普通非 PP layer list 和固定 tensor 输入输出。

因此当 P/D prefill 的 aggregate forward 很小时（例如固定 2K），GPU kernel 本身并不慢，真正的瓶颈是 Python/CPU launch、stage control 和 graph-less dispatch bubble。

### 核心改动

- 保留 global layer indexing，但只对当前 PP stage 的 local layer 判断 graph eligibility。
- 为 PP hidden state、residual、可选 top-k index 分配稳定的 CUDA Graph buffer。
- replay 前把 live `PPProxyTensors` 拷入稳定 buffer，capture/replay 后再把 padded 输出裁回真实 token 数。
- PP breakable prefill CUDA Graph 暂时显式 opt-in；默认只 capture 到 8K aggregate tokens，超过阈值自动回 eager。

### 性能 / 工程影响

Qwen3.5-397B-A17B NVFP4，GB300，TP1×PP4 Prefill + TP4 Decode，8K ISL / 1 OSL：

| Aggregate cap | Eager peak | Graph peak | 提升 |
|---|---:|---:|---:|
| 2K | 34,857 tok/s | 86,561 tok/s | **2.48× / +148.3%** |
| 4K | 66,194 | 127,942 | **1.93× / +93.3%** |
| 8K | 134,906 | 151,349 | **+12.2%** |
| 16K | 178,023 | 174,068 | -2.2% |
| 32K | 186,828 | 181,276 | -3.0% |

Profiler 中 PP 各 stage 的 `run_batch` wall time 下降约 **71–73%**，但 kernel busy time 基本不变（约 1.2% 内），非常直接地证明收益来自 host/control bubble 消除而不是模型计算变快。

- `python/sglang/srt/model_executor/runner/prefill_cuda_graph_runner.py`
- `python/sglang/srt/model_executor/cuda_graph_buffer_registry.py`
- `python/sglang/srt/model_executor/model_runner_components/cuda_graph_setup.py`
- `python/sglang/srt/model_executor/model_runner_components/layer_setup.py`
- `python/sglang/srt/model_executor/runner_utils/buffers.py`

### AI Infra 面试启发

这个 PR 很适合用来回答：**为什么 CUDA Graph 对小 batch / 小 prefill chunk 的收益反而更大？**

当 GPU compute 只有十几毫秒甚至更小，Python dispatch、kernel launch、stage bookkeeping 等固定开销占比迅速放大；CUDA Graph 把大量 host-driven launch 变成一次 replay，所以收益可以达到 2×。但 aggregate token 数变大后 compute 占主导，graph 还要承担 padding / capture-shape 限制，因此 16K/32K 甚至可能轻微回退——这也是为什么 runtime 应该做 size-aware graph/eager policy，而不是“全量 CUDA Graph”。

## 4. P/D：Mori 控制面继续向统一协议收敛

### PR #36160 — Align Mori prefill transfer control plane

- 状态：Open，过去 24 小时更新
- PR：https://github.com/sgl-project/sglang/pull/36160
- 关联方向：统一 P/D control plane（Mooncake / NIXL / Mori）

### 核心改动

- 把 Mori prefill transfer 的 control ownership 从 `Sender` 移到 `transfer_worker / Manager`。
- queued task 只按 room 标识，不再保存 Sender 对象引用。
- notify / failure 由 Manager 集中处理。
- Sender 退化成更简单的 `enqueue + poll` 角色。
- RDMA transport/data plane 本身不变。

### 工程意义

这是典型的 **control plane / data plane 解耦**。Mooncake、NIXL、Mori 的底层传输能力不同，但 request lifecycle、room、heartbeat、abort、terminal failure、completion notification 这些语义其实应该统一，否则每增加一种 transport backend 都会复制一套调度和错误恢复状态机。

### 相关代码位置

重点关注：

- `python/sglang/srt/disaggregation/` 下 Mori transfer worker / manager / sender 相关实现
- 与 Mooncake、NIXL 对应的 connection / transfer control path

### AI Infra 面试启发

可以类比存储系统：**transport backend 应该像 block device / RPC transport，只负责“怎么搬”；上层 manager 才负责“什么时候搬、失败怎么办、谁拥有 request state”。** 如果 Sender 同时持有传输、排队、重试、通知和 failure ownership，backend 数量增加后状态机很快不可组合。

## 5. Scheduler：从 worst-case 限流走向 cache-hit-aware over-admission

### PR #36310 — Add cache-hit-aware over-admission for bounded Mamba requests

- 状态：Open
- PR：https://github.com/sgl-project/sglang/pull/36310

### 解决的问题

Hybrid Mamba/GDN 模型的 `max_running_requests` 为了安全，通常按每个请求都可能增长到最大 context、都需要完整 Mamba/spec/scheduler/KV state 的 worst case 做限制。

但 agentic workload 很常见的一类请求是：长 prefix 已经在 device radix cache 中，真正需要 prefill 的 tail 很短，且 `max_new_tokens` 很小。这类请求的真实资源成本远低于 worst case，却仍会因为全局 request cap 排队。

### 核心设计

PR 把容量拆成：

- `normal_max_running_requests`：保持原有 worst-case 安全上限；
- `max_running_requests`：真正为 request-indexed pool、spec scratch、CUDA graph、额外 lane 预留的 physical capacity。

只有满足严格条件的请求才可进入 extra lane，例如：device-resident prefix hit、高 hit ratio、小 uncached prefill、有限 max-new-tokens、`ignore_eos=False`，并排除 session、host/storage cache、MM 等尚未验证的组合。

更重要的是，admission 不依赖可能在 overlap scheduler 下滞后的 aggregate metric，而复用真实资源 owner：`PrefillAdder`、request pool row、Mamba allocator 的 `schedulable_available_size()`。

此外还显式处理 overlap scheduler 的瞬时 Mamba slot 峰值：如果上一个 prefill result 仍可能 write back checkpoint，暂停 extra-lane admission；跨过 normal limit 的 batch 只复用 prefix，不把 request-specific suffix 再插入 radix tree。

### 性能 / 工程影响

RTX PRO 6000 Blackwell 96GB，Qwen3.6-35B-A3B-FP8，EAGLE + Mamba `extra_buffer_lazy`，代表 workload：4655 input / 4608 cached / 47 uncached / 64 max-new：

- request throughput：66.28 → **160.21 req/s，2.42×**；
- queue p50：1013.5 → **335.5 ms（-66.9%）**；
- TTFT p50：1184.7 → **548.0 ms（-53.7%）**；
- E2E p99：下降 **63.4%**；
- 256/256 请求完成，无 failure / retraction。

但不是免费午餐：physical request state 占用更多显存，Full-KV capacity 从 2,126,720 token 降到 1,447,616 token。因此目前保持 opt-in 是合理的。

- `python/sglang/srt/managers/scheduler_components/cache_hit_overadmission.py`
- `python/sglang/srt/mem_cache/allocator/mamba.py`
- `python/sglang/srt/mem_cache/kv_cache_configurator.py`
- `python/sglang/srt/model_executor/pool_configurator.py`

### AI Infra 面试启发

这类设计可以和数据库 admission control / storage QoS 类比：**安全上限不一定等于调度上限。** 更先进的 scheduler 可以根据请求的真实 resource envelope 做 bounded overcommit，但前提是资源边界必须可证明，而且不能依赖 stale metrics。面试时可以进一步讨论：如何防止短请求 lane 饿死普通请求？如何处理预测失误？为什么必须给 overcommit state 预留 physical pool，而不能只把 `max_running_requests` 数字调大？

## 6. Speculative Decoding × Scheduler：Draft-Extend CUDA Graph 的 capability / synchronization contract 被拆开

### PR #36324 — Enable draft-extend CUDA graph on FlashAttention (FA3)

- 状态：Open
- PR：https://github.com/sgl-project/sglang/pull/36324

过去 single-layer EAGLE + FA3 的 draft-extend 仍因为硬编码 backend allowlist 走 eager，即使 FA3 已具备可 capture 的 DRAFT_EXTEND_V2 machinery。

核心改动是新增 `AttentionBackend.supports_draft_extend_cuda_graph()`，用 backend capability 替代 `isinstance` allowlist。FA3/FA4 在非 SWA KV pool 下声明支持；SWA 暂时继续 eager。

H100 + Llama3.1-8B + EAGLE3 的 benchmark 中，吞吐提升只有约 0–1%，但这是预期的：这个 PR 的主要价值是消除 per-step host launch，并建立可扩展 capability contract；额外 startup cost约 +1.2s、graph memory +0.20GB。

### PR #36335 — TRTLLM-MHA draft-extend replay 与 `req_to_token` 写发生 WAR race

- 状态：Open
- PR：https://github.com/sgl-project/sglang/pull/36335

这个 PR 比性能更重要，因为它发现一个 **silent corruption**：

1. TRTLLM-MHA 的 captured draft-extend graph 在 replay 时会重新读取 device 上共享的 `req_to_token`；
2. runner 却可能在 replay launch **之前**发布 `shared_read_done_event`；
3. overlap scheduler 看到 event 后就允许下一 batch 改写 `req_to_token`；
4. 当前 graph replay 于是可能读到 torn / new batch page table，attention 输入错误但不会报错。

PR 没有粗暴地把 `draft_extend_metadata_captured_in_graph()` 改成 true，因为这个旧 capability 同时还意味着“可以跳过 eager metadata rebuild”等更强语义。它新增了独立能力：

`AttentionBackend.draft_extend_rereads_shared_state_in_graph()`

然后由 `EAGLEDraftExtendCudaGraphRunner` 决定 read-done event 应该在 replay 前还是 replay launch 后记录。TRTLLM-MHA 只声明“我会在 graph 内重新读取 shared state”，而不冒充“我的 metadata 完全由 graph 内 rebuild”。

### 相关代码位置

- `python/sglang/srt/layers/attention/base_attn_backend.py`
- `python/sglang/srt/layers/attention/trtllm_mha_backend.py`
- `python/sglang/srt/speculative/eagle_worker_v2.py`
- `python/sglang/srt/speculative/eagle_draft_extend_cuda_graph_runner.py`
- `python/sglang/srt/managers/scheduler.py`
- `python/sglang/srt/mem_cache/allocation.py`

### AI Infra 面试启发

这里最重要的知识点是：**“tensor 生命周期安全”与“shared buffer 不会被下一批改写”完全是两回事。**

`record_stream()` 能保证 allocator 不会过早复用 storage，但不能阻止另一个 producer 原地覆盖 persistent shared buffer；CUDA Event 也只有在记录位置正确时才形成正确 happens-before。一个成熟的异步 runtime 应该让 backend 显式声明：

- 哪些 state 是 scheduler-owned/shared；
- forward/graph replay 的最后一次读取在哪里；
- 哪个 event 表示真正的 read completion；
- 下一个 batch 从哪个 boundary 后才允许 overwrite。

这正是近期 SGLang `SharedReadEnds` / WAR fence 系列 PR 的共同方向。

## 7. 风险观察：Unified HiCache load-back 仍暴露异步 pin ownership invariant

### Issue #36377 — Crash in HiCache

- 状态：Open，新建于过去 24 小时
- Issue：https://github.com/sgl-project/sglang/issues/36377

Kimi-K3 + DCP8 + HiCache 的报告中，`UnifiedTreeCore.commit_load_back()` 触发：

```text
AssertionError: node 123645 pinned by load-back 124189, new anchor 123645
```

调用链经过：

- `schedule_policy.py -> PrefillAdder.add_one_req`
- `unified_radix_cache.py -> init_load_back / load_back / _load_back_transfers`
- `unified_cache/unified_tree_core.py -> commit_load_back`

这说明统一 radix tree 的 load-back state machine 仍存在值得跟踪的并发 ownership 边界：一个 node 已经被某个 pending load-back transaction pin 住时，另一次 load-back 又尝试用不一致的 pending id / anchor commit。

目前只有问题报告，还不能断言根因已经定位；但它和最近大量 HiCache async prefetch/load-back PR 指向同一类风险：**逻辑 tree state、physical slot ownership 和异步 IO transaction lifetime 必须属于同一个可验证状态机。**
