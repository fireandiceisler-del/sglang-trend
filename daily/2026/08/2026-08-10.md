## P0 — #34189：修复 Speculative Draft > 4 时的 Silent KV Corruption

- **方向**：KV Cache × Speculative Decoding
- **状态**：Merged
- **合入时间**：2026-08-10 06:54（Asia/Shanghai）
- **PR**：https://github.com/sgl-project/sglang/pull/34189

### 解决的问题

DeepSeek-V4 的 compressed-state ring 在 speculative verify 时，会先基于乐观的：

```text
seq_len = prefix_len + num_draft_tokens
```

制定写入计划，然后根据实际 `accept_len` 回滚到已提交长度。

旧实现把为了 speculative rollback 保留的尾部 padding 写死为 4：

```cpp
constexpr int32_t kMaxMTPDraftTokens = 4;
```

当：

```text
--speculative-num-draft-tokens > 4
```

时，planner 可能没有把所有未来 compression 仍需要的 committed tail 写进 ring。之后 compression 读到旧 slot，结果是 **没有越界、没有 NaN、没有 assertion，但 compressed KV/state 已经错了**。

这类问题尤其危险，因为它属于 silent correctness corruption。

### 核心改动

PR 不再把 padding 看作“当前 batch 的 speculative 参数”，而是把它定义为 **ring layout 本身的容量属性**：

```cpp
mtp_pad = ring_size > window_size
    ? ring_size - window_size + 2
    : 0;
```

同时：

- GPU planner 与 CPU host planner 共用同一语义；
- 修复此前 CPU/GPU planner write-set 不一致；
- `DSV4PoolConfigurator` 在启动阶段校验最大 speculative draft-token 数是否超出 ring capacity；
- 当前 ring 可支持：
  - c4：`num_draft_tokens <= 10`
  - c128：`num_draft_tokens <= 130`

### 为什么重要

这次修复把一个隐含假设：

```text
draft tokens <= 4
```

升级成了显式的 **memory-layout invariant**。

这是推理引擎里很典型的一类设计原则：

> speculative execution 使用的是 optimistic state，但 cache/allocator 最终必须以 committed state 为真值；任何 circular/ring buffer 都必须证明 rollback 后仍保留未来会被读取的数据。

### 验证与性能

新增 planner invariant 测试在旧实现上会出现 **19 个失败**；c4 的故障边界准确出现在 `D=5`，说明问题与硬编码 4 直接对应。

E2E 使用 DeepSeek-V4-Flash + DSPARK、TP4、block size 7（D=8）：

| 指标 | Before | After |
|---|---:|---:|
| GSM8K | 0.990 | 0.985 |
| GPQA mean | 0.7172 | 0.7374 |
| Throughput | 354.8 tok/s | 352.7 tok/s |

作者明确指出：这些 E2E 数字只能证明没有明显 regression，真正证明修复成立的是 planner/ring residency invariant。

### 相关代码位置

- DeepSeek-V4 compression planner：`c_plan.cuh`
- `plan_compress_prefill`
- `deepseek_v4_memory_pool.py`
- `get_compress_state_write_pad`
- `DSV4PoolConfigurator`

### AI Infra 面试启发

很适合被追问：

> speculative decoding 为什么不仅是“多算几个 token”，还会改变 KV Cache / recurrent-state 的内存正确性？

可以从三层回答：

```text
optimistic seq_len
    ↓
verify / rollback
    ↓
committed state
    ↓
ring slot residency / overwrite safety
```

重点是：**allocator 和 ring planner 不能只按 optimistic batch shape 推理，它们必须保证任意 accept length 下 committed tail 都不会提前被覆盖。**

## P0 — #34184：Prefill CUDA Graph 的 stale track row 会污染 Prefix Cache Checkpoint

- **方向**：KV Cache × Scheduler / CUDA Graph
- **状态**：Merged
- **合入时间**：2026-08-10 08:57（Asia/Shanghai）
- **PR**：https://github.com/sgl-project/sglang/pull/34184

### 解决的问题

在 hybrid-SWA / Mamba 类模型上，同时满足：

- Prefill CUDA Graph
- Chunked Prefill
- 并发请求
- Prefix Cache Hit

时，当前请求恢复 prefix 后，可能使用到 **另一个旧请求留下来的 conv state/checkpoint**。

原因是 CUDA Graph replay 会读取 captured slot 范围，而：

```text
mamba_track_mask
mamba_track_indices
```

在 live batch 之后的 tail row 没有被清零。

因此旧 row 仍然携带一个有效 destination slot，导致当前 replay 产生的 window/checkpoint 被 scatter 到旧请求的槽位中。之后那个旧请求如果再次命中 prefix，就会恢复错误状态，并在整个后续 generation 中持续错误。

### 核心改动

在 Prefill Graph 已经清理的 sentinel tail 基础上，把：

```text
mamba_track_mask
mamba_track_indices
```

也一起 zero-fill。

核心代码位于 prefill input/static buffer 管理路径，涉及：

- `PrefillInputBuffers.fill_from`
- buffer registry
- captured `req_slots`
- Mamba track scatter metadata

### 验证结果

32 个并发 prompt、prefill graph 开启、deterministic inference：

| Prefix Cache 场景 | Before 错误 logprob | After |
|---|---:|---:|
| 512-token hit | 1022 / 16384 | **0 / 16384** |
| 8-token hit | 16 / 256 | **0 / 256** |

这说明问题不是随机数值漂移，而是 static graph buffer 中的 stale ownership metadata 导致的确定性 state corruption。

### 工程意义

CUDA Graph 的“static”不只是要求地址稳定。

还要保证：

```text
captured buffer capacity
≠
live batch valid region
```

时，**所有 graph 会读到的 padding/tail metadata 都必须显式定义语义**。

对 prefix cache / recurrent state 更严格：token prefix 命中并不足以说明 cache state 可恢复，辅助状态（conv/Mamba/SWA state）必须与相同 request/version/slot 生命周期绑定。

### AI Infra 面试启发

这是非常好的 CUDA Graph correctness 题：

> 为什么 CUDA Graph replay 可能在没有任何非法访存的情况下产生错误结果？

答案可以强调：

- graph 固定的是执行结构和 buffer address；
- buffer 中上一轮 replay 留下的 **合法但过期 metadata** 仍可能被下一轮读取；
- 所以需要 padding policy、sentinel、generation/version 或明确的 tail clearing contract。

## P1 — #34191：P/D Prefill Server 跳过永远不会执行的 Spec Verify Scratch

- **方向**：P/D Disaggregation × Speculative Decoding × KV/State Memory
- **状态**：Open，CI 已开始运行
- **创建时间**：2026-08-10 04:27（Asia/Shanghai）
- **PR**：https://github.com/sgl-project/sglang/pull/34191

### 解决的问题

在 P/D disaggregation 中，**Prefill Server 不执行 TARGET_VERIFY**。

但当 hybrid linear-attention 模型开启 speculative decoding 时，prefill target worker 仍然会：

1. 分配 verify-only 的 per-draft-token Mamba state snapshot；
2. 分配 intermediate conv window cache；
3. 捕获永远不会 replay 的 target-verify CUDA Graph；
4. warmup 时执行 TARGET_VERIFY dummy forward。

也就是说，逻辑上已经做了角色拆分：

```text
Prefill server ≠ Decode server
```

但内存规划仍保留 aggregated engine 的 verify state。

### 核心改动

在：

```text
disaggregation_mode == "prefill"
```

且 worker 是 target worker 时：

- `kv_cache_configurator.py::_build_hybrid_req_pool`
  - `speculative_num_draft_tokens=None`
  - 不创建 verify-only `SpeculativeState`
- `cuda_graph_setup.py::capture_decode_graph`
  - 不捕获 TARGET_VERIFY graph
- `base_runner.py::_dummy_run`
  - warmup 使用普通 `DECODE`，不进入 TARGET_VERIFY

Draft worker、decode server 和非 P/D aggregated serving 不受影响。

### 内存收益

测试环境：

- Qwen3.5-397B-A17B-FP8
- 1P1D
- Prefill TP4 / Decode TP4
- Mooncake
- NEXTN speculative decoding
- `num_steps=3`
- `num_draft_tokens=4`

结果：

| 指标 | Patch | Baseline |
|---|---:|---:|
| GSM8K | 0.99 | 0.98 |
| MTP accept length | 3.474 | 3.481 |
| Prefill intermediate SSM cache | **不分配** | 4.31 GB/rank |

测试配置直接节省 **4.31 GB/rank**。

PR 给出的更深 PP / 256-slot 示例中，这部分 dead state 可达到约 **24 GB/rank**，足以让原本的 Prefill CUDA Graph capture 从 OOM 变为可行。

### 架构意义

这是一个很典型的 **role-specialized memory planning**：

```text
先根据执行角色做 reachable-state analysis
            ↓
只为实际可能执行的 phase 分配 runtime state
```

P/D 真正成熟后，不应该只是“把请求路由到两个进程”，而应该连：

- graph capture
- scratch space
- state pool
- warmup phase
- admission/capacity planning

都按 Prefill / Decode 的职责收缩。

## P1 — Issue #33356：DSpark CUDA Graph Capture 的 JIT / Completion Boundary 获得强定位

- **方向**：Speculative Decoding × Scheduler / CUDA Graph
- **状态**：Open，候选 root cause 已显著收敛
- **本窗口更新时间**：2026-08-09 11:41（Asia/Shanghai）
- **Issue**：https://github.com/sgl-project/sglang/issues/33356

### 问题背景

DSpark compact decode CUDA Graph 在较大 batch shape 上可能在 **server startup capture 阶段** 出现：

- CUDA illegal memory
- `CUDA_ERROR_ILLEGAL_ADDRESS`
- 甚至 host `SIGSEGV`

更麻烦的是，最先报错的 kernel 和 batch size 会漂移：Triton、TRT-LLM、DeepGEMM 都曾成为“表面故障点”。

### 最新进展

独立 H200 / TP4 复现中，通过：

```text
CUDA_LAUNCH_BLOCKING=1
```

故障稳定定位到：

```text
fused_norm_rope_v2.cuh:620
compressor norm + RoPE + store JIT kernel
```

当前最强 hypothesis 是：

```text
最后一次 eager warmup / first-use JIT
        ↓
没有最终 completion boundary
        ↓
torch.cuda.CUDAGraph() 开始 capture
        ↓
新的 non-uniform shape 触发的 JIT / driver work 跨入 capture
        ↓
CUDA context / capture corruption
```

候选修复是在最后一次 warmup 后、创建 CUDAGraph 前加入：

```python
device.synchronize()
tp_group.barrier()
```

H200 报告结果：

```text
Before: bs=60 失败 3/3
After : 报告的 35+35 shapes 全部 capture 成功，server ready
```

### 还不能下的结论

这还 **不是 production fix**：

- 原始 B300 / TP8 / v0.5.16 环境尚未完成候选 fix 验证；
- 不清楚只需要 device sync、只需要 TP barrier，还是两者都需要；
- 也可能通过提前 pre-JIT 所需 kernel 避免全局同步；
- 另一个已知的 c128 ragged planner race（#32467）可能与该路径叠加。

### AI Infra 面试启发

这说明 CUDA Graph capture 的正确性边界比“所有 tensor 地址固定”更宽：

```text
memory lifetime
+ stream ordering
+ distributed-rank ordering
+ first-use JIT/module loading
+ graph pool/workspace ownership
```

都属于 capture contract。

一个很好用的排障方法论是：

1. 用 `CUDA_LAUNCH_BLOCKING=1` 把异步错误尽可能前移；
2. 区分真正 faulting kernel 与“随后第一个检查到 CUDA error 的 kernel”；
3. 在 eager → graph capture 边界做最小同步消融实验；
4. 再判断应该用 barrier、event、pre-JIT，还是更细粒度的 stream dependency。

## 今天体现出的架构趋势

### 1. P/D 正从“计算角色拆分”升级到“完整 runtime 角色拆分”

今天 #34191 的价值不在三处 `if prefill`，而在于它明确了：

```text
Prefill / Decode 的职责不同
=> reachable execution phase 不同
=> state pool / graph / scratch / warmup 也应不同
```

未来 P/D 的优化空间会越来越多来自 **资源不对称化**，而不是只看 KV transfer bandwidth。

### 2. Speculative Decoding 正在把 KV Cache 变成一个事务式状态机

#34189 很像数据库里的：

```text
speculative state
commit / rollback
versioned residency
```

只不过对象变成 token、KV row、compressed state 和 ring slot。

接受长度是运行时动态值，所以内存管理必须对 **所有可能 accept length** 都保持不变量。

### 3. Hybrid Cache 的 correctness 不再只是“token → KV”

在 Mamba / SWA / DSV4 场景中，一条 request 的可恢复状态可能同时包含：

```text
Full KV
SWA KV
Mamba / Conv State
Compressed State
Indexer State
Draft State
```

Prefix Cache 命中只有在这些 side state 与 token prefix 属于同一生命周期时才真正正确。

### 4. CUDA Graph 正逐渐成为 Scheduler 的并发协议，而不仅是性能功能

#34184 与 #33356 分别暴露两类问题：

```text
A. graph replay 读取 stale static metadata
B. eager/JIT 工作尚未完成就进入 capture
```

本质都是缺少清晰的 happens-before / ownership contract。

## 对 AI Infra 面试 / 项目实践最值得掌握的 4 个问题

1. **P/D Prefill 为什么可以不分配 speculative verify state？**  
   从 execution reachability、role-specific memory planning 和 CUDA Graph phase specialization 回答。

2. **Speculative rollback 为什么可能破坏 KV ring？**  
   区分 optimistic `seq_len` 与 committed `accept_len`，说明 overwrite safety 必须对任意 accept length 成立。

3. **为什么 CUDA Graph 地址都没变，结果仍会错？**  
   stale metadata、padding/tail semantics、request-slot ownership 都可能合法访存但读取旧状态。

4. **为什么一个 kernel 报 illegal memory，不代表它就是 root cause？**  
   CUDA 默认异步执行；真正错误可能更早发生。用 `CUDA_LAUNCH_BLOCKING`、stream/event boundary、同步消融定位真实 fault point。
