# SGLang 每日动向 — 2026-08-08

> 检索窗口：2026-08-07 09:00 ～ 2026-08-08 09:00（Asia/Shanghai）  
> 仅关注：**KV Cache / P-D Disaggregation / Scheduler / Speculative Decoding**

## 今日结论

今天最值得关注的不是单一“大特性”，而是 SGLang 在把多个已经可用的优化组合成**可生产部署的推理系统**：

1. **KV Cache 从“能分层”进入“精确容量治理”阶段**：HiCache 开始分别处理 Full/SWA host pool 的容量比例和冗余副本回收；同时新的 KV sizing 修复开始考虑“模型权重在 engine 启动前已驻留 HBM”的场景。
2. **Speculative Decoding 的重点明显转向 composability**：DFlash 修复 overlap scheduler 下异步 state capture 丢失；DSpark 正在补 Prefill CP、DCP、P/D 等组合路径，而不是只优化单机 acceptance length。
3. **Scheduler 继续消除“全 batch 同步维护”**：SWA eviction 已正式改为按每个 KV handle 的累计 token 进度触发，避免大 batch 中所有请求在同一个 scheduler iteration 做 eviction。
4. **P/D 当前真正难点是组合可靠性**：DCP Roadmap 仍把 `DCP × DSpark × HiCache × PD Disagg` 的可组合性列为未完成项。对推理 Infra 来说，这比“某个 backend 能跑”更值得关注。

## 1. [Merged] Scheduler：SWA eviction 从全局节拍改成按请求累计进度触发

**PR:** [#33404 — Gate SWA eviction on accumulated tokens](https://github.com/sgl-project/sglang/pull/33404)  
**状态:** 已于 2026-08-08 合入

### 解决的问题

原先 SWA eviction 容易让大量 decode request 在相同 scheduler iteration 同时执行维护工作。batch 很大时，会形成周期性的 latency spike。

更早的 stagger 方案基于 `decode_batch_idx` 分相位，但 request retract 后重新进入 extend 时计数会重置，导致部分请求可能长期碰不到自己的 eviction phase。

### 核心改动

新的触发条件改成基于 KV handle 的**单调累计进度**：

```python
req.seqlen - 1 - sliding_window_size >= (
    req.kv.swa_evicted_seqlen + eviction_interval
)
```

也就是：只有当某个请求又累计产生了一个 eviction interval 的窗口外 token，才执行下一次 eviction。

### 工程影响

- 避免所有 request 在同一个全局 scheduler tick 做维护。
- retract / extend 后不会因为调度计数重置而 starvation。
- eviction overshoot 仍被 interval 限制。
- 没有改变模型计算，也没有改变 eviction 总频率，只改变**维护工作的时间分布**。

### 代码位置

- `python/sglang/srt/managers/schedule_batch.py`

### 面试启发

这是非常典型的高性能系统题：

> 周期性后台维护为什么会制造 tail latency？如何把“global phase”改成“per-object monotonic progress”？

可以类比 storage 中的 compaction / GC / cache eviction：**平均工作量不变，并不意味着延迟不变；工作是否被同步到同一时刻非常关键。**

## 2. [Merged] DFlash：修复 overlap scheduling 下 speculative state capture 丢失

**PR:** [#34026 — Propagate state capture outputs in DFlash](https://github.com/sgl-project/sglang/pull/34026)  
**状态:** 已于 2026-08-08 合入

### 解决的问题

DFlash target verify 在 overlap scheduling 下会产生延迟完成的 GPU→CPU state capture handle，例如 routed-expert / indexer state。

DFlash 自己重新构造 `GenerationBatchResult` 时没有把这些异步 handle 继续传给 scheduler，导致 scheduler 无法完成异步 copy 的 finalize。结果是：

- GPU 上计算出的 state 是正确的；
- host cache 却可能仍然是全 0 或旧数据。

非 overlap 模式没有问题，因为它走同步 copy。

### 核心改动

把两个 state-capture handle 沿现有 generation result 通路继续传给 scheduler，由统一 result processor 等待异步复制完成后 finalize host cache。

### 工程影响

这是一个很典型的 **async ownership / lifetime bug**：

```text
GPU forward
   ↓
async D2H handle
   ↓
GenerationBatchResult
   ↓
Scheduler finalize
   ↓
Host state cache
```

任何一层重建 result 时漏传 future/handle，都会出现“计算正确、缓存状态错误”的隐蔽问题。

### 代码位置

- `python/sglang/srt/speculative/dflash_worker_v2.py`

### 面试启发

可以重点理解：

- overlap scheduler 为什么会让同步代码中的简单 value 变成 future/handle；
- 异步 D2H 的 ownership 应该属于谁；
- 为什么 cache correctness 不只是 KV 本身，还包括 speculative routing/indexer 等 side state。

## 3. [Open] HiCache：SWA host pool 开始独立容量治理，并主动回收“host/device 共存”冗余副本

**PR:** [#34046 — Support SWA host cache sizing and coexistence reclaim](https://github.com/sgl-project/sglang/pull/34046)  
**状态:** Open，2026-08-08 新开

### 解决的问题

HiCache write-back 场景下，同一个 SWA component 可能已经重新驻留 device，但 host 上仍保留旧副本。压力大时，这种 host/device coexistence 会白白占满 SWA host pool。

同时 Full KV 与 SWA KV 每 token 字节数可能不同，简单按 token 数切 host pool，不能保证用户配置的容量比例真的成立。

### 核心改动

- Full / SWA component 在普通 eviction 前先回收自己已经冗余的 host value。
- 已经存在于 host 的 auxiliary value 不再重复 backup。
- 新增 `--hicache-swa-full-tokens-ratio`。
- Full/SWA host pool 改为按 **bytes per token** 做容量换算，而不是简单按 token 数平分。
- 设计覆盖 MHA、MLA、MTP draft pool。

### 工程影响

这代表 HiCache 的优化重点已经从“HBM → DRAM → Storage 能搬数据”转向：

```text
容量 accounting
+ 生命周期管理
+ 多 component 共存
+ mixed cache layout
```

这和真正的分层存储系统越来越相似。

### 代码位置

- `python/sglang/srt/mem_cache/hybrid_cache/hybrid_pool_assembler.py`
- `python/sglang/srt/mem_cache/pool_host/mha.py`
- `python/sglang/srt/mem_cache/pool_host/mla.py`
- `python/sglang/srt/mem_cache/unified_cache/components/{full,swa,mamba}_component.py`
- `python/sglang/srt/server_args.py`

### 面试启发

值得思考一个问题：

> 分层 KV Cache 的容量到底应该按 token、page 还是 byte 来定义？

对于 MHA / MLA / SWA / MTP，不同 component 每 token 的真实占用不同，最终资源治理必须落到 **byte budget + ownership**，不能只看逻辑 token 数。

## 4. [Draft] KV sizing：修复“权重已提前驻留 HBM”时 KV Cache 被高估

**PR:** [#34053 — Account resident weight memory in KV sizing](https://github.com/sgl-project/sglang/pull/34053)  
**状态:** Draft，2026-08-08 新开

### 解决的问题

IPC weight-cache daemon 可能在 engine 启动前就把模型权重放进 GPU。此时 ModelRunner 采样 `pre_model_load_memory` 时，权重已经占掉了一部分 HBM。

设：

- `P`：权重驻留前 free HBM
- `W`：提前驻留的 weight memory
- `f`：`mem_fraction_static`

旧公式相当于：

```text
f(P - W)
```

但与普通 disk-load 路径等价的正确预算应该是：

```text
fP - W
```

因此旧逻辑会多分配：

```text
W(1 - f)
```

### 核心改动

- loader 暴露 rank-local `preexisting_weight_memory_bytes`。
- target / draft / multi-runner / Frozen-KV MTP 的驻留权重统一纳入 accounting。
- 先在**每个 rank 本地**修正 free-memory baseline，再做 distributed MIN。
- post-capture KV resize 也使用修正后的基线。

### 工程影响

这里最重要的不是公式，而是：

> distributed memory sizing 的修正必须在 local baseline 上发生，再做全局 MIN；不能先 reduce 后再补一个全局 offset。

当不同 rank 的预驻留 footprint 不同，二者数学上不等价。

### 代码位置

- `python/sglang/srt/model_executor/model_runner.py`
- `python/sglang/srt/model_executor/model_runner_components/kv_pool_runtime.py`
- `python/sglang/srt/model_loader/loader.py`
- `python/sglang/srt/weight_cache/{daemon,ipc_loader}.py`
- `python/sglang/srt/speculative/base_spec_worker.py`

### 面试启发

这是非常适合系统面试展开的例子：

- HBM budget 如何计算；
- 为什么多 rank 要先 local accounting 再 reduce；
- 为什么 speculative draft model 的权重也会影响 target KV capacity；
- CUDA Graph capture 后为什么还可能需要重新 resize KV pool。

## 5. [Open] Spec：统一 DSV4 target-verify layout，顺带消除每 step 的 host list + H2D

**PR:** [#34047 — Derive dsv4 target-verify extend lengths from the layout](https://github.com/sgl-project/sglang/pull/34047)  
**状态:** Open，2026-08-08 新开

### 解决的问题

DSV4 target verify 同时维护 uniform / ragged 两套 extend-length 计算路径，增加了状态和逻辑分叉。

uniform path 还会每 step 在 host 构造 list，再 H2D 传给 GPU。

### 核心改动

- 删除 `compute_uniform_extend_lengths`。
- uniform target-verify 和 DSpark draft-block 也统一通过缓存的 `RaggedVerifyLayout`。
- 有真实 `extend_start_loc` 时直接走 `ExpandPrefillCausally` 的 vectorized device branch。
- 去掉 per-step host list build + H2D copy。

### 工程影响

这类优化非常符合 SGLang 最近的 Scheduler/Spec 演进：

> 不只是 kernel 更快，而是尽量把 metadata 的构造和传输也留在 GPU / graph-friendly 路径中。

### 代码位置

- `python/sglang/srt/layers/attention/deepseek_v4_backend.py`
- `python/sglang/srt/speculative/ragged_verify.py`

### 面试启发

在小 batch、decode/spec verify 场景里，几十微秒的 host metadata build 和 H2D copy 都可能成为 TPOT 的可见部分。分析推理引擎时不能只盯 GEMM/Attention kernel。

## 6. [Open] DSpark + Prefill CP：补齐 P/D co-located 部署中的组合兼容性

**PR:** [#33865 — Fix DSpark + DeepSeek V4 prefill CP compatibility](https://github.com/sgl-project/sglang/pull/33865)  
**状态:** Open，过去 24 小时持续更新

### 解决的问题

在 DeepSeek V4 的 P/D co-located 部署里，同时打开：

- DSpark speculative decoding
- Prefill Context Parallel
- `round-robin-split`

会遇到两个问题：

1. `markov_w2` 错用了 `attn_tp_group`；Prefill CP 下这个 group 可能退化为 world size 1，但 `lm_head` 仍按完整 TP shard。
2. DSpark aux hidden states 在 CP token layout 下没有恢复成全局 token 排布。

### 核心改动

- `markov_w2` 使用与 `lm_head` 一致的 shard group。
- 解除 DSpark + CP 的阻断，并对 auxiliary hidden states 做 all-gather + rerange。

### 工程影响

这项 PR 本身代码不大，但它代表当前 SGLang 的关键难点：

```text
Spec
 × Prefill CP
 × P/D
 × TP layout
```

每个特性单独工作，并不意味着它们组合后 tensor layout、group ownership、KV/state transfer 就仍然正确。

### 代码位置

- `python/sglang/srt/models/deepseek_v4.py`
- `python/sglang/srt/models/deepseek_v4_dspark.py`

### 面试启发

强烈建议掌握一个判断原则：

> 看到 collective bug，先问“这个 tensor 的逻辑 shard owner 是谁”，而不是先问“应该用 all-gather 还是 all-reduce”。

通信原语是结果，**layout / ownership 才是根因**。

## 7. [Open] DCP + Spec：draft worker 不应继承 target 的 attention-DCP layout

**PR:** [#33955 — Resolve attention-DCP per worker so drafts are not given the target's layout](https://github.com/sgl-project/sglang/pull/33955)  
**状态:** Open，过去 24 小时持续更新

### 解决的问题

Target 可以沿 token dimension 做 DCP，但 speculative draft worker 本质上仍是 TP-sharded，并不会按 target 的 DCP 方式切 token。

此前 DCP topology 是 process-global 的，draft worker 直接读取时会错误继承 target 的：

```text
attn_dcp_size / attn_dcp_rank
```

于是 draft attention 可能错误地再做 token sharding。

### 核心改动

- 增加 `draft_dcp_context()`：draft init / pool / attention backend / graph capture 范围内，将 attention-DCP 视为 `size=1, rank=0`。
- draft KV pool 的 page-size scaling 改为从实际 allocator 读取，而不是重新从全局 DCP 配置推导。
- 在 DCP8、token usage 0.97 的高占用场景验证无 server error。

### 工程影响

这是很重要的抽象方向：

> topology 不应该只是 process-global config，而应该是 **per worker / per tensor layout context**。

尤其 target、draft、prefill、decode 可能共享进程和 allocator，但拥有不同逻辑并行布局。

### 代码位置

涉及范围较广，核心包括：

- `python/sglang/srt/distributed/parallel_state_wrapper.py`
- `python/sglang/srt/layers/attention/triton_backend.py`
- `python/sglang/srt/model_executor/pool_configurator.py`
- `python/sglang/srt/speculative/{dflash,eagle,dspark,...}_worker_v2.py`

### 面试启发

可以把它类比成存储系统中的“physical resource shared, logical namespace isolated”：allocator 是共享物理资源，但 target/draft 的逻辑视图不能混用。

## 8. [Open] P/D Mooncake：避免 decode status receiver 被坏消息永久打死

**PR:** [#32909 — Keep decode status thread alive on bad messages](https://github.com/sgl-project/sglang/pull/32909)  
**状态:** Open，过去 24 小时更新

### 解决的问题

Mooncake decode KV manager 的 status thread 收到不符合 wire format 的消息时，异常会直接逃出线程：

```text
process 仍健康
/health 仍返回 200
但 decode control path 已死亡
```

之后 prefill status 无人消费，请求可能一直停在 `KVPoll.WaitingForInput`。

### 核心改动

对每条消息的解析/处理增加异常隔离，让单个 malformed message 不再终止整个 receiver thread。

### 工程影响

这是 P/D control-plane reliability 的典型问题：

> data plane 能跑、进程能活，并不等于 control plane 健康。

单纯 HTTP `/health` 很可能检测不到内部 receiver thread 已死亡。

### 面试启发

P/D 面试里可以进一步讨论：

- worker health 应该检测 process，还是检测关键 control loop 的 liveness？
- malformed control message 应该 fail-fast 还是 per-message isolation？
- 为什么分布式系统里“线程死、进程活”比直接 crash 更难排查？
