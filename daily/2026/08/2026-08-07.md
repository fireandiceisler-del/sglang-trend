## P0：过去 24 小时已合入的重要变化

### 1. HiCache：完整恢复 Speculative Decoding 的 draft-side cache

**PR**：[#30393 — Support packed and sidecar draft caches for MTP/EAGLE/DSpark](https://github.com/sgl-project/sglang/pull/30393)  
**状态**：✅ Merged（2026-08-06 14:31 CST）

#### 解决的问题

原来的 HiCache 主要围绕 target model KV 做 L2/L3 offload / reload，但 MTP、EAGLE、DSPARK 还可能维护独立的：

- draft KV
- DSA indexer cache
- draft SWA state

如果 target KV 命中而 draft state 没有同步恢复，会出现一个很隐蔽的问题：

> **Cache 系统认为 prefix hit，但 speculative decoder 实际拿到的是不完整状态。**

结果通常不是直接错误，而是 speculative acceptance rate 在 L2/L3 replay 后明显下降。

#### 核心改动

引入两种 draft cache 组织方式：

- **Packed**：适用于标准 NextN MTP/EAGLE、DeepSeek-V4 DSPARK 等，把 draft KV/indexer/SWA 作为 target host pool 的尾部 layer，一起搬运。
- **Sidecar**：适用于独立 EAGLE/EAGLE3、DFlash、部分 DSPARK，为 `DRAFT` / `DRAFT_INDEXER` / `DRAFT_SWA` 建独立 host pool，但复用 target KV/SWA 的 index space。

关键设计点是：**target 和 draft 的 host slot 必须一一对应**，HiCache 的一次 L2/L3 操作需要恢复完整推测执行状态，而不仅是一组 K/V tensor。

#### 性能 / 工程影响

DeepSeek-V4-Flash-0731 + DSPARK 的 L3 replay：

| 指标 | upstream/main | 本 PR |
|---|---:|---:|
| Cold accept length | 3.317 | 3.285 |
| Replay accept length | 2.660 | **3.323** |
| Replay accept rate | 33.57% | **46.86%** |

说明 replay 后 speculative efficiency 已基本恢复到 cold-run 水平。

重点看：

- `python/sglang/srt/mem_cache/hybrid_cache/hybrid_pool_assembler.py`

这是一个很好的“**缓存命中不等于执行状态命中**”案例。

### 2. P/D：Staging Buffer 正式支持 RadixCache 命中

**PR**：[#30545 — StagingBuffer Support radix cache](https://github.com/sgl-project/sglang/pull/30545)  
**状态**：✅ Merged（2026-08-06 23:59 CST）

#### 解决的问题

异构 TP 的 staging transfer 使用固定 grid 对传输 chunk 编号：

```text
chunk_idx = start_page / full_chunk_pages
```

但发生 RadixCache prefix hit 后，第一次发送的 cached prefix 可能跨越多个 grid slot，导致：

- ring allocation 越界
- decode prefix scatter offset 错位
- tail scatter 错误
- room 无法正确完成

本质问题是：**逻辑上的 cached prefix chunk 边界，与数据面的 staging allocation grid 不再一致。**

#### 核心改动

Prefill：

- 按 staging grid 拆分每次传输为多个 `TransferKVChunk`
- 恢复 cached-prefix early-send
- prefix snapshot 与 overlap scheduler 中正在增长的 `prefix_indices` 解耦

Decode：

- scatter 改为 arrival-driven
- 最后一个 chunk 也发送 `CHUNK_READY`
- room 完成必须等待：所有 rank Success + 所有 allocation 已 scatter + scatter event 完成
- decode-side cached prefix 被纳入 scatter offset 计算

#### 性能 / 工程影响

Qwen3.5-397B，128K shared prefix needle-in-haystack：

- Before：2 / 128
- After：**128 / 128**

8×GB300 AgentX 256K workload：

- TP4 → TP4：256.38 output tok/s/user
- DEP4 → TP4 + staging：**281.02 tok/s/user**
- interactivity **+9.61%**，总 TPS/GPU 基本持平（-0.16%）

- `python/sglang/srt/disaggregation/common/staging_buffer.py`
- `python/sglang/srt/disaggregation/common/staging_handler.py`
- `python/sglang/srt/disaggregation/mooncake/conn.py`
- `python/sglang/srt/disaggregation/nixl/conn.py`
- `python/sglang/srt/disaggregation/prefill.py`
- `python/sglang/srt/managers/schedule_batch.py`

#### AI Infra 面试启发

非常适合用来说明：

真正的生产 P/D 系统必须同时处理：prefix hit、异构 TP、chunked prefill、overlap scheduler、乱序到达、超时和失败清理。

### 3. Scheduler：SWA admission 修复，避免 retraction storm

**PR**：[#32700 — Restrict SWA chunk-cap escape hatch to true head-of-line livelock](https://github.com/sgl-project/sglang/pull/32700)  
**状态**：✅ Merged（2026-08-06 22:09 CST）

#### 解决的问题

此前 `_swa_chunk_cap` 只要发现 request 的 SWA budget 大于**当前剩余空间**就会缩小 chunk 并强行 admission。

设计初衷是解决一个永远不可能 fit 的大请求造成 head-of-line livelock；但在普通瞬时压力下，它也会触发：

```text
Prefill 持续吃 SWA headroom
        ↓
Decode 没有可释放缓冲区
        ↓
Decode allocation 失败
        ↓
大量 request retraction
        ↓
重新 prefill
        ↓
更多资源压力
```

形成自激式 retraction / re-prefill storm。

#### 核心改动

只有当：

```text
request SWA budget >= 整个 SWA pool
```

即 request **永远不可能完整 fit** 时才使用 escape hatch。

如果只是：

```text
current_remaining < request_budget < whole_pool
```

则 scheduler 等待正在 decode 的请求释放 window，而不是继续强行 admission。

#### 性能影响

TP4、8192 in / 1024 out、640 concurrency：

| 指标 | Before | After |
|---|---:|---:|
| Decode throughput | 3115 tok/s | **4226 tok/s (+36%)** |
| Extend GPU µs / prefill token | 85.7 | **56.2 (-34%)** |
| p50 latency | 168 s | **99 s (-41%)** |

#### 相关代码

- `python/sglang/srt/managers/schedule_policy.py`

#### AI Infra 面试启发

这是经典的资源调度题：

> admission policy 不能只看“当前 free resource”，还要区分 **temporary pressure** 和 **fundamentally unschedulable request**。

它和 OS 的内存压力控制、存储系统 backpressure、数据库 admission control 是同一种问题。

### 4. DSPARK：长上下文 verify 切到 fold_sq CuTe DSL MLA

**PR**：[#33650 — Allow DSPARK verify on cutedsl_mla](https://github.com/sgl-project/sglang/pull/33650)  
**状态**：✅ Merged（2026-08-07 04:54 CST）

#### 解决的问题

SGLang 之前认为 `cutedsl_mla` 只能支持 `q_len <= 4`，因此 Kimi-K3 DSPARK：


新版本 FlashInfer 的 monolithic MLA decode 已支持 `fold_sq`：把 verify 的多个 query token 折叠进 head / MMA tile，因此不再需要 q_len≤4 的限制。

| 每个 spec step | ~44 ms | **~22 ms** |
| Accept length | 4.34 | 4.26 |

即 **约 2× decode throughput**，accept length 基本不变。

更底层的 MLA kernel：

- TRTLLM：~1.263 ms
- CuTe DSL fold_sq：~320 µs

约 **3.9× kernel speedup**。

#### 相关代码

- `python/sglang/srt/arg_groups/overrides.py`

#### AI Infra 面试启发

### 5. PP + Mamba Cache：按 stage 真实 layer 计费

**PR**：[#33666 — Size the mamba pool per pipeline stage](https://github.com/sgl-project/sglang/pull/33666)  
**状态**：✅ Merged（2026-08-07 04:10 CST）

#### 解决的问题

PP 下每个 stage 只持有部分 Mamba layer，但旧代码计算每 request 的 Mamba state 成本时使用的是**整模型所有 Mamba layer**。

结果：每个 stage 都被按 whole-model cost 收费，容量被低估约 `pp_size` 倍。

Kimi-K3 PP8：

- 93 layers
- 69 linear-attention layers
- 实际每 stage 约 8～9 个 Mamba layer
- 旧算法却按 69 个 layer 计费

#### 核心改动

按 **最重 PP stage 的 Mamba layer 数量**计算 system-wide per-request state cost。

为什么不是每个 rank 各算各的？因为：

> `max_mamba_cache_size` / `max_running_requests` / `pp_max_micro_batch_size` 必须在所有 pipeline stage 上一致，否则不同 stage 会对同一个 batch 拆成不同 microbatch。

#### 容量变化

Kimi-K3 PP8：

| 指标 | Before | After |
|---|---:|---:|
| `max_mamba_cache_size` | 26 | **210** |
| `max_running_requests` | 6 | **52** |

并发上限提升约 **8.7×**，模型准确率维持同一水平。

#### 相关代码

- `python/sglang/srt/mem_cache/kv_cache_configurator.py`

#### AI Infra 面试启发

这是一个非常典型的“**逻辑模型容量 ≠ 每 rank 物理容量**”问题。

并行推理系统中的 memory accounting 必须基于：

- TP/PP/CP 实际 shard
- 最重 rank / stage
- 全局一致的 admission ceiling

否则会出现两类问题：容量严重浪费，或者不同 rank 对调度边界产生不同判断。

### 6. HiCache：把 host reload 从 indexed copy 推向 bulk copy / staging

**PR**：[#33891 — Coalesced HiCache reload fast path](https://github.com/sgl-project/sglang/pull/33891)  
**状态**：🟡 Open

#### 核心思路

当前 host KV allocator 容易产生离散 slot，reload 需要 per-token indexed copy，实测只有约 4～5 GB/s。

新方案：

1. Host allocator 优先分配连续 run；不足时再退化成最大连续区间。
2. Reload 根据布局走三种路径：
   - host 连续 + device 连续 → 单次 `copy_`
   - host 连续 + device 离散 → 先 bulk copy 到 device staging，再 `index_copy_`
   - 其它情况 → 旧 indexed fallback

#### 性能数据

GLM-5.2-FP8 TP8，128K evicted prefix：

- reload：1.036 s → **0.694 s（1.49×）**
- isolated per-layer H2D：约 4～5 GB/s → **~57 GB/s**

#### 代码位置

- `python/sglang/srt/mem_cache/memory_pool_host.py`
- `python/sglang/srt/mem_cache/pool_host/base.py`
- `python/sglang/srt/mem_cache/pool_host/coalesce_reload.py`
- `python/sglang/srt/mem_cache/pool_host/mla.py`

#### 值得关注的设计信号

HiCache 优化正在从“cache policy”逐渐进入：

> **allocator physical layout → transfer coalescing → staging → effective PCIe/NVLink bandwidth**

这与高性能存储系统里 extent allocation / scatter-gather / IO coalescing 是同一种优化思路。

### 8. PP + P/D + DSPARK：把 draft KV 构建扩展到 Pipeline Parallelism

**PR**：[#33863 — PP Support PD + DSpark](https://github.com/sgl-project/sglang/pull/33863)  
**状态**：🟡 Open

#### 为什么难

无 PP 时，prefill engine 可以直接拿完整 target hidden state 构建 draft KV。

PP 下 hidden feature 分散在不同 pipeline stage，而 draft KV 注入前需要对聚合结果做 RMSNorm：

```text
ctx_i = h_i @ W_i.T
ctx_acc = recv_ctx_acc + ctx_i
最后一个 PP stage:
    ctx_norm = RMSNorm(ctx_acc)
    K,V = KVProj(ctx_norm)
```

如果各 PP stage 独立 norm + inject，再相加，数学上并不等价。

#### 核心设计

- 每个 PP stage 只投影自己拥有的 target layer hidden state
- 用 `PPProxyTensors` 逐 stage 累加 `dspark_ctx_acc`
- 仅最后一个 prefill PP stage 做 RMSNorm + draft KV injection
- P/D 边界仍只传 **target KV + draft KV**，不把 hidden state 跨 P/D 发送
- 成功集合按 PP stage **intersection**，失败集合按 **union**
- 只有最后一个 PP stage 的 target + draft KV 都结束后才释放请求

#### 代码位置

- `python/sglang/srt/disaggregation/prefill.py`
- `python/sglang/srt/disaggregation/decode.py`
- `python/sglang/srt/managers/scheduler_pp_mixin.py`
- `python/sglang/srt/models/deepseek_v4_dspark.py`
- `python/sglang/srt/speculative/dspark_components/dspark_worker_v2.py`

#### 面试价值

这类问题非常像分布式事务 / barrier / pipeline protocol：

> 多 stage success 如何汇总、failure 如何传播、什么时候可以释放 buffer/request，以及“局部完成”与“全局完成”的区别。

## RFC / Roadmap

### 11. 新 RFC：P/D 控制协议统一，transport backend 只负责数据搬运

**Issue**：[#33861 — PD disaggregation: single protocol layer, per-backend transport](https://github.com/sgl-project/sglang/issues/33861)  
**状态**：🆕 Open RFC

目前 Mooncake / NIXL / MORI 各自实现了一套完整的：

- ZMQ bootstrap / socket loop
- message dispatch
- room / session lifecycle
- staging glue
- TP/DCP slice orchestration
- timeout / heartbeat
- failure propagation

结果已经出现行为漂移，例如：

- MORI decode manager 没有启动 heartbeat checker
- NIXL sender 没有统一 bootstrap timeout
- prefill-side transfer failure 的传播语义不一致
- transfer-info wire frame 在不同 backend 中位置不同
- staging / DCP relayout / session blacklist 在 backend 之间支持不对称

RFC 建议目标结构：

```text
Unified PD Protocol Layer
  ├── KVManager
  ├── KVSender
  ├── KVReceiver
  └── KVBootstrapServer
          │
          ▼
     BaseTransport
       ├── Mooncake
       ├── NIXL
       └── MORI
```

Protocol 决定：

> **哪些 bytes、什么时候、从哪里搬到哪里。**

Transport 只负责：

> `register_memory / open_peer / submit(src,dst,len) / poll`

这是今天最值得长期跟踪的架构信号之一。

**对分布式存储背景非常值得类比**：这相当于把 consensus/control protocol 与 RDMA/NVMe/network transport 解耦，避免每个 transport 重写状态机。

- Rust tree-core 仍在推进：[#28701](https://github.com/sgl-project/sglang/pull/28701)、[#29074](https://github.com/sgl-project/sglang/pull/29074)、[#32710](https://github.com/sgl-project/sglang/pull/32710)

趋势很明确：

```text
多份 Python Radix Tree 实现
        ↓
UnifiedRadixTree
        ↓
稳定 TreeCore Interface
        ↓
可替换的 Rust Tree Core
```

也就是说，KV Cache 的演进不仅是更多 caching policy，而是在逐步把 **tree state machine 从 Python Runtime 中抽离**。

## AI Infra 面试提炼

今天这些变化可以归纳成五个很值得面试表达的观点：

### 1. KV Cache 是“状态系统”，不是一个 tensor map

在 Spec + HiCache 下，需要管理：

```text
Target KV
Draft KV
DSA Indexer
SWA State
Mamba/SSM State
Slot Mapping
Eviction Lifecycle
```

只有这些状态在同一个语义边界内恢复，prefix cache hit 才真正有效。

### 2. P/D 的核心难题是协议，不是 RDMA 带宽

高性能传输库只解决：

```text
memory A → memory B
```

生产 P/D 还需要解决：

```text
什么时候分配？
chunk 怎么编号？
哪个 PP/TP rank 写？
什么时候算完成？
失败怎么传播？
缓存命中后 offset 如何变化？
请求什么时候可以释放？
```

### 3. Scheduler 是资源控制器

SWA admission 说明 scheduler 必须区分：

- 当前资源不足但未来可释放
- 永远不可能 fit
- 应等待
- 应拆 chunk
- 应 retract

这和数据库 admission control、storage backpressure、OS memory pressure 本质相通。

### 4. Speculative Decoding 的瓶颈会随 context length 迁移

短上下文可能 draft compute 占主导；长上下文下，verify 对 KV 的读取可能成为主瓶颈。

因此最佳策略不是固定一个 backend，而可能依赖：

```text
(TP, DCP, verify q_len, context length, KV dtype)
```

### 5. 并行系统的容量计算必须遵循“物理 shard + 全局一致性”

PP Mamba pool 的例子说明：

- 不能按整模型容量收费给每个 stage
- 又不能让每个 stage 得出不同的 microbatch ceiling
- 正确做法通常是根据真实 shard 计算，再以 bottleneck stage 建立 system-wide 一致上限
