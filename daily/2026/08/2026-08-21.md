> 统计窗口：约 2026-08-20 09:00 ～ 2026-08-21 09:00（Asia/Shanghai）  
> 关注范围：KV Cache、Prefill/Decode Disaggregation、Scheduler、Speculative Decoding。  
> 筛选原则：只保留架构、正确性、关键性能路径和 Roadmap/Release 信号；过滤纯模型适配、机械重构和无架构影响的小修复。

## 今日结论

今天最明显的趋势不是“又多了一个 kernel”，而是 **SGLang 正继续把异步 KV/state 的 ownership、传输 geometry、调度语义和 speculative critical path 显式化**。

1. **HiCache 的核心问题已经从“能不能异步搬 KV”进入“异步 H2D 到底归谁所有”。** PR [#35769](https://github.com/sgl-project/sglang/pull/35769) 修的是 buffer-mode load-back 与 Radix Tree canonical ownership 之间的竞态：如果 tree 在 H2D 完成前发生重叠发布，正在被 DMA 写入的 slot 可能被 dedup/free，最终形成 silent KV corruption。
2. **P/D transport 正从“传 KV tensor”演化为“传 typed state bundle”。** PR [#35718](https://github.com/sgl-project/sglang/pull/35718) 为 MXFP8 KV Cache 补齐 scale state 的传输，而且刻意不把 scale 塞进原有 `kv_data_ptrs`，而是走 multi-component state channel；这说明 KV 附属状态已经拥有独立的 layout/index semantics。
3. **P/D 的下一层瓶颈正在从 byte volume 转向 transaction geometry。** WIP PR [#35762](https://github.com/sgl-project/sglang/pull/35762) 尝试把 DCP1→DCP-N 的逐 token RDMA relayout 改成目标连续的大块传输，核心目标是减少 descriptor/transaction 数，而不是减少总字节数。
4. **CUDA Graph padding 不能只看 shape compatibility，还必须满足语义隔离。** PR [#35766](https://github.com/sgl-project/sglang/pull/35766) 发现 DP rank idle 时，为 Breakable Prefill CUDA Graph 构造的 dummy MAX_LEN token 会进入共享 MoE grouped GEMM，改变 expert M 维、tiling 和 reduction order，最终造成可观测的 logits/output 非确定性。
5. **Speculative Decoding 的优化重点继续从 acceptance rate 扩展到“只为真正消费者做计算”。** PR [#35546](https://github.com/sgl-project/sglang/pull/35546) 在 EAGLE draft-extend 中把 LM Head 投影提前裁剪到真正需要的 rows，draft-extend graph 时间下降 12.44%，固定 acceptance 条件下 output TPS/GPU 提升约 2.4%。
6. **KV Cache 甚至开始探索跨 scheduler/process 的全局资源化。** 新 RFC [#35648](https://github.com/sgl-project/sglang/issues/35648) 提议同一 GPU 上多个模型 replica 共用一个 controller-owned KV pool；真正困难的不是 CUDA IPC，而是 allocation、publication、refcount、eviction、generation 和 crash recovery。

## 1. KV Cache：HiCache buffer-mode 开始显式保护异步 load-back ownership

### PR #35769 — Fix buffer-mode HiCache load-back ownership races

- 状态：**Open**
- 链接：[#35769](https://github.com/sgl-project/sglang/pull/35769)

### 解决的问题

HiCache buffer-only host-memory 模式中，`init_load_back` 会先：

1. 为 storage prefetch 分配 GPU KV slots；
2. 发起按 layer gated 的 H2D；
3. 最后才把这些 slots 插入 Unified Radix Tree，由 tree 决定 canonical ownership。

问题在于，第 2 步和第 3 步之间存在一个真实的异步窗口。如果另一个请求在此期间发布了重叠 prefix，Radix Tree insert 可能认为当前 slots 是重复副本并释放它们；但 GPU DMA 仍然在往这些 slots 写数据。

这不是普通的 use-after-free：allocator 可能很快把同一 page 分给新请求，于是旧的 H2D 会直接污染新请求 KV，表现为 **silent corruption**，而不是稳定 crash。

SWA 场景更隐蔽：tree 的统一 match length 可能因为 SWA tombstone 看起来没有命中，但 Full-KV 实际已经有 canonical owner，因此必须同时检查 full-KV ownership。

### 核心改动

- 在 transfer 前重新 match live tree，只有当前 staged span 仍是 canonical candidate 才允许 H2D 继续。
- 同时要求 unified match 和 `full_kv_hit_length` 与 staged `matched_len` 一致，覆盖 Full/SWA ownership 分歧。
- insert 后再次校验 canonical tree slice；如果 tree 最终拥有的 physical slots 与 incoming slots 不一致，直接 fail-stop，而不是继续带着潜在 corruption 跑。
- 增加可选 `SGLANG_ENABLE_HICACHE_BUFFER_ANCHOR_LOCK=1`，在 prefetch 生命周期内给关键 tree path 加 anchor lock，减少 eviction/overlap 导致的无效预取。
- anchor lock 设置容量上限，避免为了保护 prefetch 反过来锁死过多 device KV。

### 性能 / 工程影响

这个 PR 的主要价值是 **正确性和故障隔离**，而不是宣称吞吐提升。它把“load-back 是一次 memcpy”重新定义成“load-back 是一个带 ownership reservation 的异步事务”。

对生产系统来说，这类修复尤其重要：同步版本往往不会出错，只有高并发 + prefix overlap + eviction + async H2D 的组合才会触发。

### AI Infra 面试启发

一个很好的面试问题是：**“异步 DMA 的 buffer 已经从逻辑数据结构中删除，为什么仍然不能 free？”**

答案不只是 `record_stream`。这里存在三层 ownership：

- allocator 是否认为 page free；
- radix tree 是否认为 page canonical；
- DMA/stream 是否仍在访问 page。

正确设计必须给三者建立 happens-before，而不是只维护 Python 对象生命周期。

## 2. P/D：MXFP8 KV Cache 开始把 scale 当作独立 state component 传输

### PR #35718 — Support MXFP8 KV cache in PD transfer

- 状态：**Open**
- 链接：[#35718](https://github.com/sgl-project/sglang/pull/35718)

### 解决的问题

MXFP8 KV Cache 之前在 P/D 路径上被直接拒绝，原因不是 K/V 本体不能搬，而是 **对应 scale buffers 没有暴露给 disaggregation transport**。

最容易想到的做法是把 scale buffers 直接 append 到 `kv_data_ptrs/kv_item_lens`，但这个 PR 明确没有这样做。原因很关键：多个 P/D call site 会根据这个 list 的长度推导 layer 数和 transport geometry，粗暴 append 会让协议两端对“一个 layer 有多少 buffer”的理解发生偏移。

### 核心改动

- scale 不进入原来的 KV pointer list，而是走已有的 **multi-component state channel**。
- 该 channel 已经承载 `SWA_RING`、`C128_STATE`、`MINIMAX_INDEX_K` 等 KV-adjacent state。
- Full attention scale 与 SWA scale 分成两个 component：
  - Full scale 跟随完整 sequence index；
  - SWA scale 必须通过 `translate_loc_from_full_to_swa` 映射到 ring/local index。
- `item_lens` 根据具体内存布局计算，区分 page-leading interleaved layout 与 flat per-slot layout。
- 修复相关 KV pool 的 `_kv_buffer_descs` 构建，使 transport 能正确描述这些 buffer。

### 性能 / 工程影响

没有宣称新的 transport speedup，但给出了端到端正确性验证：单机 1 Prefill + 1 Decode、TP2、Mooncake over IB、Prefill 开 HiCache、`--kv-cache-dtype mxfp8`，AIME26 score 0.9333、error rate 0%。

真正重要的架构信号是：**P/D 协议中的“KV state”已经不是单一 K/V tensor。** Scale、SWA ring、linear-attention state、indexer state 都可能有不同的物理 layout 和 index-space。

## 3. P/D × DCP：开始把逐 token RDMA 重排成目标连续的大块传输

### PR #35762 — Pack DCP1→DCP-N PD KV transfers into dest-contiguous RDMA blocks

- 状态：**Draft / WIP**
- 链接：[#35762](https://github.com/sgl-project/sglang/pull/35762)

### 解决的问题

DCP 的 token ownership 是 cyclic / strided 的。DCP1 Prefill 向 DCP-N Decode 传 KV 时，如果按照逻辑 token 一个个 relayout，就可能产生 **一个 token 对应一个 RDMA transaction/descriptor**。

这类瓶颈有一个常见误区：总传输字节数没变，所以看起来“带宽应该差不多”。实际上对 RDMA/NIXL/Mooncake，transaction 数、descriptor 数、registration/layout 处理开销都可能让有效带宽大幅下降。

### 核心改动方向

- 在 Prefill 侧先 gather 当前 destination rank 拥有的 MLA rows；
- 按 destination-contiguous layout 打包；
- Mooncake/NIXL 发送 page-sized 或更大的连续 block，而不是 per-token tiny transfer；
- 引入 `common/dcp_pack.py` 作为独立 packing 层。

DSPARK 当前明确留给 follow-up，因此这还不是完整的 `DCP × Spec × P/D` 组合解。

### 性能 / 工程影响

目前仍是 WIP，**没有正式 benchmark，不能把它当成已验证性能提升**。但它非常值得跟踪，因为它延续了最近一周 SGLang P/D 的一个明确方向：

> 传输优化不只看 byte size，也必须看 scatter/gather geometry 和 transaction granularity。

- `python/sglang/srt/disaggregation/base/conn.py`
- `python/sglang/srt/disaggregation/mooncake/conn.py`

### AI Infra 面试启发

RDMA 性能题可以从三个量来拆：

- bytes transferred；
- number of transactions / WRs / descriptors；
- memory locality / destination contiguity。

很多“理论带宽很高但实测只有几十 MB/s”的根因，恰恰是第二项而不是第一项。

## 4. Scheduler：Breakable Prefill CUDA Graph 的 dummy padding 会改变 MoE 数值路径

### PR #35766 — Avoid MAX_LEN padding for prefill BCG when a DP rank is idle

- 状态：**Open**
- 链接：[#35766](https://github.com/sgl-project/sglang/pull/35766)

### 解决的问题

Breakable Prefill CUDA Graph（BCG）在 DP attention 下需要各 rank 进入兼容的 graph shape。当某个 DP rank 本轮没有真实 token 时，MAX_LEN padding 会制造 dummy EXTEND request。

普通 padding 的直觉是：“反正会被 mask 掉，不影响结果。”但这里 dummy token 为避免 MoE all-to-all starvation，会被当成真实 row 进入共享 expert grouped GEMM。

结果是：

- per-expert M 维变化；
- kernel tiling / reduction order 变化；
- BF16/FP8 产生微小数值漂移；
- MoE top-k routing 在边界处可能翻转；
- 多层累积后变成实际 logits/output 非确定性。

### 核心改动

当任一 DP rank idle 时，不再启用 MAX_LEN BCG 路径，回退到 SUM_LEN/eager prefill；只有所有 rank 都有真实 token 时继续享受 BCG。

### 性能 / 工程影响

PR 给出的复现实验非常有价值：

- clean main：8 次运行出现 2 种输出，首个 divergence token=45，最大 logprob delta 0.206 nats；
- 加 gate 后：8/8 bit-identical，delta=0；
- DSv4-Pro TP8/DP2：原始配置出现 4/8 输出分歧，首个 divergence token=5，最大 delta 0.459。

代价只发生在 idle-rank / 低负载 prefill step；高负载、所有 DP rank 都有真实工作时仍保留 graph 路径。

### 相关代码位置

- `python/sglang/srt/model_executor/forward_batch_info.py`
- `test/registered/models_e2e/test_deepseek_v4_flash_fp4_b200.py`

### AI Infra 面试启发

这是一个很典型的 CUDA Graph 面试题：**“padding 为什么可能改变模型输出？”**

关键不是 padding tensor 本身，而是 padding row 有没有真正被所有下游算子 mask 掉。只要它进入 grouped GEMM、collective、expert routing 或动态 kernel selection，它就可能改变其他真实请求的执行 geometry，进而改变浮点 reduction order。

所以 CUDA Graph 的 shape padding 需要证明的是 **semantic isolation**，不只是 shape validity。

## 5. Speculative Decoding：EAGLE 在 LM Head 之前裁掉无用 draft rows

### PR #35546 — Prune draft-extend logits to selected rows

- 状态：**Open，过去 24 小时继续更新**
- 链接：[#35546](https://github.com/sgl-project/sglang/pull/35546)

### 解决的问题

EAGLE draft extension 在 CUDA Graph 中会为每个 draft row 计算完整 vocab logits，但后续 speculative worker 实际只消费每个 request 的 selected rows。

这意味着大量 LM Head GEMM 和 output copy 最终不会被使用。

### 核心改动

- draft hidden/spec-state 的完整 evolution 保持不变；
- 只在进入 LM Head 之前选择真正会被消费的 rows；
- eager path 保持原行为；
- CUDA Graph buffer registry 和 draft-extend runner 补齐对应 row-selection metadata。

这比“算完 logits 再 slice”更重要，因为真正省掉的是 **最昂贵的 vocab projection 本身**。

### Benchmark

Qwen3.5-397B-A17B-NVFP4、4×GB300、TP4/DP4/EP4、FP8 KV、NEXTN 5 steps / 6 draft tokens：

- acceptance：3.684 → 3.653，基本同一水平；
- target-step host time：29.689 → 28.997 ms，**-2.33%**；
- fixed-acceptance output TPS/GPU：4526.98 → 4635.01，**+2.39%**；
- exact-context matched pair：约 **+2.45%**；
- draft-extend CUDA Graph：1.113 → 0.975 ms，**-12.44%**；
- selected-row LM projection：0.372 → 0.297 ms；
- large output copy：0.098 → 0.018 ms；
- graph capture memory：0.15 → 0.07 GB，约 **-53%**。

## 6. RFC：Same-GPU 多 replica 共享全局 KV Pool

### Issue #35648 — Same-GPU model replicas with managed CUDA MPS and a shared KV pool

- 状态：**Open RFC**
- 链接：[#35648](https://github.com/sgl-project/sglang/issues/35648)

### 提案核心

面向小/中模型，在一张 NVIDIA GPU 上运行多个 homogeneous scheduler replica，并组合：

- native DP request routing；
- 可选 CUDA MPS；
- daemon-owned shared weight allocation；
- **一个由所有 colocated scheduler 共用的 global HBM KV pool**。

RFC 设想由 `DataParallelController` 成为 shared KV metadata authority，单独 CUDA helper process 持有物理 KV slab 并导出 CUDA IPC handle，各 scheduler 只能写自己 lease 的 pages。

### 为什么值得关注

它指出了一个非常准确的系统问题：**CUDA IPC 只解决“大家能看到同一块显存”，没有解决“谁可以写、谁可以 free、谁持有 reference、crash 后怎么回收”。**

如果每个 replica 独立 KV pool：

- 相同 prefix 被重复存储；
- 一个 rank OOM/retract 时，另一个 rank 的空闲 page 无法借用；
- cache locality 依赖 sticky routing；
- HBM 容量被静态切片。

共享 pool 的潜在收益包括更高 prefix reuse、更少 stranded capacity、更低 retraction，但代价是 controller RPC、metadata contention、跨进程同步和恢复复杂度。

### 当前边界

RFC 明确把 speculative decoding、SWA、Mamba、HiCache、P/D disaggregation 等复杂组合排除在第一版之外，因此 **这是架构探索，不是已完成能力**。

### AI Infra 面试启发

如果面试官问“怎么跨进程共享 KV Cache”，一个成熟答案应该把问题拆成：

1. physical memory sharing；
2. page allocator ownership；
3. prefix directory / radix metadata；
4. refcount / pin / eviction；
5. generation tag 防 ABA/stale read；
6. writer publication protocol；
7. scheduler crash / controller crash recovery。

真正难的是后六项。

## 今日技术趋势归纳

### KV Cache：从“缓存 tensor”转向“管理异步状态 ownership”

今天 #35769 和 #35648 看似一个是 bugfix、一个是 RFC，本质上都指向同一件事：KV Cache 的复杂度已经不在 K/V 数组本身，而在 **ownership、publication、lifetime、eviction 和 recovery**。

### P/D：从“传数据”转向“传 typed state + 优化 transfer geometry”

#35718 解决的是 state schema；#35762 解决的是 physical transaction geometry。两者叠加后，P/D backend 的职责越来越像一个通用 distributed state-transfer runtime，而不只是 KV memcpy。

### Scheduler：Graph optimization 必须建立 semantic contract

#35766 说明一个 optimization 是否安全，不能只验证 graph 能 capture/replay，还要验证 dummy rows、metadata padding、collective participation 对真实请求没有语义影响。

### Spec：acceptance 之外，critical-path work reduction 越来越重要

#35546 是很典型的“先找 consumer，再做 expensive projection”。当 draft/verify 已经高度工程化后，Spec 的优化会越来越像 compiler/runtime optimization：减少 materialization、减少 vocab projection、减少 copy、减少 metadata synchronization。
