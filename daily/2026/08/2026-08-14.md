## 1. KV Cache

### 1.1 [#34653] Unified Cache 默认提前释放 window 外 SWA slot — **已合入**

PR: https://github.com/sgl-project/sglang/pull/34653  
状态：Merged，2026-08-13 14:31（北京时间）

#### 解决的问题

Unified Radix Cache 在 chunked prefill 时，以前会把已经滑出 Sliding Window 的 SWA slot 一直保留到请求结束。这样做语义简单，但会白占 SWA pool 容量。

该 PR 将 `SGLANG_OPT_UNIFIED_CACHE_FREE_OUT_OF_WINDOW_SLOTS` 从 opt-in 改成默认开启：**当 token 已经不可能再参与当前 SWA window 时，允许在请求结束前释放对应 slot。**

#### 核心改动

行为变化集中在 Unified Radix Tree 的 chunked-prefill caching path：

```text
old:
chunked prefill -> window 外 SWA slot 仍保留 -> request finish 再释放

new:
chunked prefill -> window 外 SWA slot 可提前释放 -> 更早回收 SWA capacity
```

可以显式设置该优化为 `False` 恢复旧行为。

#### 性能 / 工程影响

这是一个 **default behavior flip**，影响所有启用了 Unified Radix Cache 且含 SWA component 的 server。PR 的 bit-exact 测试覆盖 hybrid SWA + Mamba：prefill/decode 多种 cache-hit 场景的 KL divergence 均为 0，并且 multi-turn `cached_tokens` 没有缩短。

更重要的是，它直接引出了下面的 #34565：**更激进的内存回收会改变未来分支请求还能复用多深的 prefix。** 这就是缓存容量与复用率之间的真实工程 trade-off。

#### 相关代码位置

- `python/sglang/srt/mem_cache/unified_radix_cache.py`

#### 面试启发

面试里如果被问“Sliding Window KV 为什么还要放进 Radix Cache”，不要只回答“为了 prefix cache”。更好的回答是：

> Full-attention KV 和 SWA state 的生命周期不同。SWA 只需要保留最近一个 window，但 prefix reuse 的边界又依赖 SWA state 是否仍存在，因此 eviction policy 必须同时考虑 **当前请求计算所需容量** 与 **未来共享前缀的可复用深度**。

### 1.2 [#34565] 在 SWA 分支点保留可复用状态 — **Open**

PR: https://github.com/sgl-project/sglang/pull/34565

#### 解决的问题

#34653 提前释放 window 外 SWA slot 后，一个新的 agent/subagent 请求如果从更早的共享 prefix 分叉，可能出现：

```text
Full KV: 仍然存在
SWA state: 已被释放
=> Full KV 看似可命中，但无法直接恢复完整 hybrid state
=> 被迫重算 prefix
```

#34565 的目标是复用 Mamba branching 的思路，在 **branching point** 保存必要 SWA state，让 fork 出来的新请求仍可从那个边界恢复。

#### 性能影响

内部 shared-prefix 模拟：

| 指标 | Before | After |
|---|---:|---:|
| Token hit rate | 43.81% | **60.75%** |
| Cached tokens | 939,264 | **1,302,528** |
| Mean TTFT | 1,569.93 ms | **1,069.58 ms** |
| P95 TTFT | 3,427.47 ms | **2,372.52 ms** |
| Input throughput | 66,310 tok/s | **70,510 tok/s** |

AgentX 整体 workload 因多数请求是已有会话 continuation，整体收益较小；但新 fork 的 subagent 首请求，token hit rate 从 **50.26% → 54.13%**。

这是典型的 **agentic workload 改变 cache policy**：传统 LRU 只看“最近访问”，但 agent tree 里“未来可能从哪个 prefix fork”是上层已知信息。缓存设计正在从 request-local recency 走向 workflow-aware retention。

### 1.3 [#34780] DCP 下强制 Mamba checkpoint depth invariant — **Open**

PR: https://github.com/sgl-project/sglang/pull/34780

#### 解决的问题

Mamba checkpoint `H(S)` 是一个严格的 **point state**：它只表示处理完 token `[0, S)` 后的 recurrent state，因此它只能挂在 cumulative depth 恰好为 `S` 的 radix node 上。

DCP 会把有效 cache page size 放大为：

```text
allocator_page_size * dcp_size
```

但 Mamba tracker 可能仍在更细的边界上产生 checkpoint。旧逻辑会把 radix key 向下 page-align，却仍把更深位置的 `H(S)` 挂到这个更浅的 node 上。之后 warm cache hit 恢复该 state 时，就会从错误的 token depth 继续计算，形成 silent correctness error。

#### 核心改动

- 在 clone / quantize / donate Mamba state 之前验证 checkpoint depth 是否与 effective page size 对齐。
- Finished request：如果 Mamba checkpoint 不合法，只缓存 Full KV，不挂 Mamba state。
- Unfinished request：如果 checkpoint 不合法，跳过整个 radix handoff，避免 request 与 tree 同时认为自己拥有同一批 KV slot。
- `no_buffer` 的状态按 `H(kv_committed_len)` 解释。
- 自动 Mamba strategy 变成 DCP-aware，并拒绝显式 `no_buffer + DCP` 的不安全组合。

#### 性能 / 工程影响

没有 hot-path kernel 变化，仅增加常数级 cache admission 检查。核心价值是 **将“page alignment”从 allocator implementation detail 提升为 state semantic invariant**。

#### 相关代码位置

- `python/sglang/srt/mem_cache/unified_cache/components/mamba_component.py`
- `python/sglang/srt/arg_groups/overrides.py`
- `python/sglang/srt/server_args.py`

#### 面试启发

非常适合回答“为什么分布式 cache bug 很容易 silent corruption”：

> 物理地址/页号一致，不代表状态语义一致。对于 recurrent state、compressed state、speculative state，必须额外维护 **state corresponds to which logical token prefix** 的不变量。DCP 改变 page granularity 后，如果只做物理对齐而不检查 semantic depth，就会把合法内存映射成错误模型状态。

### 1.4 [RFC #27574] Programmatic KV Cache for Agentic Workloads — **窗口内更新**

Issue: https://github.com/sgl-project/sglang/issues/27574

这份 RFC 正在把 agentic cache 管理上升到 Router / Orchestrator 层。核心思想不是让外部直接控制 cache internals，而是提供 provider-neutral hint：

- `Share`：跨 worker / shared tier 复用已有 prefix
- `Prefetch`：请求到来前主动升温
- `Demote`：长 tool gap 时把 KV 下沉到 colder tier
- `Pin`：在有限 TTL 内保护高价值 prefix
- `Retain`：给 eviction priority 提供软偏置

当前 POC 已覆盖把 bounded Pin 映射成 Mooncake L3 TTL lease。RFC 给出的 H100 实验中，压力下淘汰 24.18 GB / 95,232 keys 后：未 retain 的 cold worker 需要重算 10,032 tokens，而一小时 retain 的路径从 L3 恢复 10,016 tokens，只计算 16 tokens。

**趋势判断：** SGLang 的 KV Cache 正从“engine 内部的替换算法”演进为“router 知道 workflow，engine 保留资源所有权，二者通过 hint 协同”的两层控制体系。

## 2. Prefill / Decode Disaggregation

### 2.1 [#34773] Decode Worker 支持 per-request Conditional Aggregation — **Draft**

PR: https://github.com/sgl-project/sglang/pull/34773

这是今天最有架构含量的 P/D 变化。

#### 解决的问题

传统 P/D 是静态角色：Prefill worker 算 prompt，Decode worker 等 KV transfer。对于短 prompt、低负载或网络/Prefill 排队较重的请求，这种固定分工未必最优。

#34773 引入 `do_local_prefill`，允许 Router **逐请求**决定：

```text
request A -> Prefill worker -> KV transfer -> Decode worker
request B -> Decode worker 本地做 prefill -> 直接 decode
```

同一个 Decode pool 可以同时服务两条路径。

#### 核心改动

- 新增 `--disaggregation-decode-enable-conditional-agg`。
- Local-prefill request 留在普通 `waiting_queue`。
- 远端已传 KV 的 request 放入独立 `disagg_decode_prebuilt_queue`。
- Scheduler 需要同时协调：local chunked prefill、remote preallocation、KV transfer、capacity recovery、retraction、abort、idle detection。
- 当 local prefill chunk 因 KV capacity 无法继续时，可先运行已经 ready 的 transferred decode 请求，等页释放后再重试 local admission。

#### Benchmark

1P + 1D、4×B200、每侧 TP2/EP2、AgentX trace、concurrency=28：

| 指标 | Control | Conditional | 变化 |
|---|---:|---:|---:|
| Request throughput | 0.1651 req/s | 0.1747 | **+5.8%** |
| Output throughput | 44.41 tok/s | 48.67 | **+9.6%** |
| Total token throughput | 3,392.52 tok/s | 3,591.50 | **+5.9%** |
| Avg TTFT | 20,945.69 ms | 19,122.37 | **-8.7%** |
| P50 TTFT | 609.50 ms | 533.11 | **-12.5%** |
| Avg ITL | 13.49 ms | 20.19 | **+49.6%（变差）** |

22 个真正走 conditional path 的请求，paired comparison 显示 Avg TTFT 下降 **36.2%**，但 Avg ITL 恶化 **62.5%**。

#### 这组数据怎么理解

Local prefill 把 P/D 之间的“网络与排队开销”换成了 Decode GPU 上的 prefill compute：

```text
TTFT 更好
  ↑
避免远端排队 / transfer

但 decode GPU 被 prefill 占用
  ↓
ITL / TPOT 可能更差
```

所以 conditional aggregation 不是简单的性能开关，而是一个 **multi-objective routing problem**。真正 production-ready 的下一步应该是 Router 根据 prompt length、Prefill queue、Decode load、KV locality、TTFT/ITL SLO 做 policy。

- `python/sglang/srt/managers/schedule_batch.py`
- `python/sglang/srt/managers/scheduler_pp_mixin.py`

#### 面试启发

如果面试官问“P/D 一定比 unified serving 快吗”，这个 PR 就是非常好的反例：

> P/D 的收益依赖 prompt/decode 比例、网络、队列和 GPU 利用率。短 prompt 或 Prefill 排队严重时，把少量 prefill 放回 Decode GPU 可能显著降低 TTFT；但它会争抢 decode compute，因此 TPOT/ITL 可能恶化。最优方案是动态 routing，而不是固定 P/D topology。

## 3. Scheduler

### 3.1 [#34608] 将真实 Scheduler Load 发布给 Router — **Open**

PR: https://github.com/sgl-project/sglang/pull/34608

#### 解决的问题

Cache-aware router 过去常用 router-side inflight counter 估算 worker load，但这个数字存在两个结构性误差：

1. 它只知道“这个 Router 自己发出去的请求”，看不到其他 Router 或 direct client 流量。
2. streaming request 会一直占着 inflight counter，但它在 Scheduler 中真正占用的 request/KV 资源并不等价于连接持续时间。

#### 核心改动

新增 per-scheduler ZMQ PUB socket，发布紧凑的 `LoadStat`：

```text
num_running_reqs
num_waiting_reqs
num_tokens
max_total_num_tokens
```

- 新 flag：`--load-publish-endpoint`，默认关闭。
- 复用 Scheduler 已有 `LoadSnapshot`，避免重复扫 queue。
- load 发生变化立即发布；无变化时约 1 秒 heartbeat。
- 即使 Scheduler 因 KV pressure / disagg transfer 暂时没有 batch，也会从 idle path 继续发布负载。
- publish failure 是 best-effort，不让观测链路拖垮主循环。

#### 相关代码位置

- `python/sglang/srt/managers/scheduler.py`
- `python/sglang/srt/managers/scheduler_components/load_publisher.py`
- `python/sglang/srt/managers/scheduler_components/kv_events_publisher.py`
- `python/sglang/srt/disaggregation/kv_events.py`
- `python/sglang/srt/server_args.py`

#### 面试启发

这是一个很典型的 distributed serving control-plane 设计：

> Router 做全局决策，但只有 Scheduler 知道真实 GPU/KV 状态。正确做法不是让 Router 猜，而是把 Scheduler 的“局部真相”以低开销 telemetry 发布出去，再由 Router 汇总成全局 routing policy。

可以顺势讨论 stale telemetry、heartbeat、backpressure、best-effort observability、load metric 应该选 request count 还是 KV occupancy。

## 4. Speculative Decoding

### 4.1 [#34775] 将 DSA Cache Relocation 从逐层 234 次操作压到 2 次 launch — **Draft**

PR: https://github.com/sgl-project/sglang/pull/34775

#### 解决的问题

DSA speculative cache relocation 目前每层都需要：

```text
1 × latent-KV assignment
1 × index-key gather
1 × index-key scatter
```

GLM-5.2 有 78 层，因此一次 relocation 产生：

```text
78 * 3 = 234 GPU operations
```

这属于典型的 **kernel-launch / per-layer orchestration overhead**。

#### 核心改动

- 多层 latent KV + paged index K/scale 使用 overlap-safe Triton gather/scatter。
- 缓存对齐后的 buffer pointer table。
- scatter 前先 stage 所有 source，确保 chain/cycle/duplicate assignment 语义正确。
- 生产路径从逐层 loop 改成 **exactly two full-cache launches**。

#### Microbenchmark（MI355X，78 层）

| Decode batch | Moved slots | Old p50 | Batched p50 | Speedup |
|---:|---:|---:|---:|---:|
| 1 | 6 | 2.662 ms | 0.035 ms | **75.67×** |
| 8 | 48 | 2.773 | 0.038 | **73.76×** |
| 32 | 192 | 2.862 | 0.044 | **64.56×** |
| 128 | 768 | 2.916 | 0.112 | **26.04×** |
| 256 | 1,536 | 2.901 | 0.239 | **12.16×** |

当前 matched serving-level throughput 还在等待 prerequisite #34140 合入后补测，因此这些数字应视为 **relocation microbenchmark**，不能直接等价为 E2E 加速。

- `python/sglang/srt/mem_cache/dsa_cache_layer_split.py`
- `python/sglang/srt/mem_cache/memory_pool.py`

- `python/sglang/srt/speculative/eagle_utils.py`

#### 面试启发

Speculative decoding 的常见面试答案只盯：

```text
speedup ≈ acceptance length / verify cost
```

但 production engine 还要考虑 **draft/target state commit、KV relocation、index cache movement、graph replay 和 host launch 数**。当模型层数很深时，“每层一个小操作”会成为非常可观的固定成本。

### 4.2 [#34517] GQA Target Verify 跨 Query Head 复用 KV tile — **Open**

PR: https://github.com/sgl-project/sglang/pull/34517

#### 解决的问题

GQA 中多个 Q head 共享同一 KV head。EAGLE target verification 的 split-KV 路径如果按 Q head 独立扫描 prefix KV，就会反复从 HBM 读取同一段 KV，尤其在高并发下变成 memory-bandwidth bottleneck。

新 grouped-head verify kernel 的思路是：

```text
旧：Q0 扫 KV，Q1 再扫同一 KV，Q2 再扫...
新：一次加载 KV tile，在一个 program 中给一组 Q head 复用
```

#### Kernel benchmark（MI355X）

相对 split-KV，prefix 1K～16K 的加速约 **1.18×～1.50×**。

早期 serving A/B 在 concurrency 4～128 上曾看到 **+2.21%～+10.97%** throughput，acceptance length 保持约 3.36～3.42；不过 PR scope cleanup 后的 same-GPU paired comparison 在 C4 为 -0.87%、C64 为 +0.13%，都落在 run-to-run noise 内。

因此目前最稳妥的结论是：**kernel-level KV bandwidth reduction 已经成立，但最终 E2E 收益尚未被干净地证明。**

#### 相关代码位置

- `python/sglang/kernels/ops/attention/verify_mla.py`
- `python/sglang/srt/layers/attention/triton_backend.py`
- `python/sglang/srt/configs/model_config.py`
- `test/registered/attention/test_verify_shared_kv.py`

#### 面试启发

这可以和 MQA/GQA 的基本原理串起来：既然多个 Q head 本来就共享 K/V projection，那么 verify kernel 也应该尽可能 **在片上复用同一个 KV tile**，而不是只在模型数学层面共享 KV、在 kernel 层又重复搬运。

## 7. 今天最值得形成的 AI Infra 面试知识点

### A. P/D 不是固定拓扑，而是一个动态资源分配问题

可以把 #34773 抽象成：

```text
选择 remote prefill:
  + Decode GPU 不被 prompt compute 打断
  - 多一次排队 + KV transfer

选择 local prefill:
  + 减 TTFT / 避免 transfer
  - 抢占 decode GPU，ITL 可能恶化
```

因此 Router policy 最终需要同时观察 prompt length、P/D queue depth、KV locality、network transfer cost、TTFT SLO 和 TPOT/ITL SLO。

### B. Cache correctness 不只是“key 是否匹配”

#34780 的关键点是：

```text
radix node depth == recurrent checkpoint semantic depth
```

这类 invariant 同样适用于 compressed KV、Mamba state、DSA index state、speculative draft state。任何跨 page size、DCP、PP、offload tier 的转换都应该问一句：**这个 state 到底代表计算到第几个 token？**

### C. Speculative Decoding 不能只优化 acceptance rate

#34775 / #34517 分别说明两类典型瓶颈：

- state relocation 的 per-layer launch overhead；
- verify 阶段对共享 KV 的重复 HBM traffic。

真正的 decode speedup 是：

```text
acceptance benefit
- draft cost
- verify compute/memory cost
- state commit/relocation cost
- scheduler/graph/launch overhead
```

### D. Router 与 Scheduler 应形成反馈闭环

#34608 说明一个通用架构原则：**全局控制面不要靠本地推测状态做 routing。** Scheduler 发布局部真实负载，Router 做跨 worker 决策，是更稳健的设计。

### E. Agentic Serving 正在改变 KV policy

#34565 + #27574 都在说明：multi-turn / subagent / tool-call workload 下，未来复用概率不是纯随机的。上层 workflow 已经知道哪些 prefix 会 fork、暂停、恢复，因此未来 KV cache 竞争点会从传统 LRU 继续向 **branch-aware / TTL / priority / prefetch / demote** 演进。
