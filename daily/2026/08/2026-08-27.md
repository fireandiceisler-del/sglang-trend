## 今日结论

过去 24 小时最明显的趋势不是“又多支持了一个 backend”，而是 SGLang 继续在三个系统瓶颈上向下挖：**P/D 把优化重点从传输字节数推进到 RDMA transaction / descriptor 数量；Scheduler 开始删除在特定拓扑下逻辑上多余的 collective；Speculative Decoding 则首次把经典逐 token rejection verification 替换为更高接受率、仍保持 target distribution 的 block verification。**

KV Cache 侧也延续了最近几周的主线：HiCache 已经不再只是 KV tensor 的分层缓存，而是在为 FULL / SWA / Mamba 等异构状态建立显式的恢复、预算和异步生命周期契约。同时，SWA eviction/free 热路径正在主动消除 `torch.unique` 一类会触发 host/device 同步的数据依赖操作。

今天优先级最高的 3 个 PR：**#35762（DCP P/D KV packing） > #36568（DP1 scheduler metadata no-gather） > #36516（Block Verification）**。

## 1. P/D：DCP1 → DCP-N 的 KV transfer 从“每 token 一次 RDMA”改为目标连续块传输

**PR:** [#35762 — Pack DCP1→DCP-N PD KV transfers into dest-contiguous RDMA blocks](https://github.com/sgl-project/sglang/pull/35762)  
**状态:** Draft / Open；过去 24 小时持续更新，最新更新时间约 2026-08-27 08:52（UTC+8）。

### 解决的问题

DCP 的 token ownership 是 cyclic 的。Prefill 端 DCP1、Decode 端 DCP-N 时，如果直接按最终 owner 做 relayout，原路径会把逻辑连续的一段 KV 拆成大量离散 token，最终形成**每 token / 每 layer 一个 RDMA descriptor**。

关键点是：**总传输字节数并没有变，但 transaction 数量暴涨。** 对 NIXL/Mooncake 这种 RDMA transport 来说，descriptor 构造、提交、doorbell、completion 等固定成本会压过真正的数据搬运。

### 核心改动

Prefill 侧先按照 Decode DCP rank 的 ownership gather MLA KV rows，放入预注册的 staging/pack buffer，再让 Mooncake/NIXL 发送 page-sized 或更大的连续块。

新路径保留 fallback：pack buffer 不够时退回原来的 per-token RDMA，不牺牲正确性。

### 性能 / 工程影响

8×B300、Kimi-Linear、Prefill TP4/DCP1 → Decode TP4/DCP4、NIXL：

| ISL / concurrency | TTFT p50 | Output throughput |
|---|---:|---:|
| 32K / 1 | 518.2 → 311.7 ms（**-39.9%**） | 52.9 → 79.5 tok/s（**+50.5%**） |
| 32K / 8 | 3759.9 → 2298.4 ms（**-38.9%**） | 64.4 → 102.6 tok/s（**+59.4%**） |
| 131K / 1 | 2203.3 → 1426.3 ms（**-35.3%**） | 14.0 → 21.0 tok/s（**+50.5%**） |
| 131K / 8 | 16400.7 → 10280.2 ms（**-37.3%**） | 15.3 → 24.2 tok/s（**+58.0%**） |

传输 MB 数在 A/B 中保持一致，因此收益主要来自**更少的 RDMA transaction，而不是少传了数据**。代价是每个 Prefill TP rank 约 `4 × 31.5 MB` pack buffer。

正确性侧，8×B300 注册测试 6/6 通过，GSM8K 0.91，并覆盖 chunk / virtual-page 边界以及 32K needle-in-a-haystack。

### 相关代码位置

- `python/sglang/kernels/ops/kvcache/pd_dcp_gather.py`
  - `copy_mla_rows_into_pack`
- `python/sglang/srt/disaggregation/common/dcp_pack.py`
  - pack buffer sizing / staging / DCP ownership relayout
- Mooncake / NIXL 的 P/D manager 中新增 staging memory registration 和 packed transfer 接入

### AI Infra 面试启发

这是一个非常典型的“**带宽没变，性能却能提升 50%**”的问题。面试时可以从以下角度回答：网络性能不仅由 bytes 决定，还由 message size、descriptor 数、doorbell、PCIe/NIC submission、completion polling 和 CPU control-plane overhead 决定。小包过多时，系统是 transaction-bound，而不是 bandwidth-bound。

## 2. Scheduler：DP=1 时跳过冗余 metadata all-gather，Decode TPS +11.45%

**PR:** [#36568 — skip redundant scheduler metadata gather for DP1](https://github.com/sgl-project/sglang/pull/36568)  
**状态:** Draft / Open；2026-08-27 凌晨新建并持续更新。

### 解决的问题

在 attention DP size = 1 时，Scheduler 的 batch mode、token count、CUDA Graph eligibility、TBO metadata 等状态已经是本地唯一值，而且 TP schedulers 消费同一份请求流。

原实现仍然执行 scheduler metadata all-gather，等价于为了确认“大家都知道的同一个值”而额外付出：

- 一次 device collective；
- 一次 host synchronization；
- decode 每 step 的固定控制面延迟。

这种固定成本在 batch=1、长 decode、低延迟场景尤其显著。

### 核心改动

- `dp_size == 1` 时默认不做 metadata all-gather；
- 本地 `finalize_local()` 直接填充 `global_num_tokens`、TBO split、forward mode、graph eligibility 等后续消费者需要的信息；
- 多 DP 仍保持原同步路径；已有环境变量 override 继续保留。

### 性能 / 工程影响

2 nodes × 4 GB300，TP8/DP1，ISL=89,472、OSL=1,024，batch=1：

| 指标 | Main | PR | 变化 |
|---|---:|---:|---:|
| Pure decode TPS/user | 351.46 | 391.70 | **+11.45%** |
| Mean decode step latency | 14.336 ms | 12.852 ms | **-10.35%** |
| Full-request TPS | 168.87 | 178.37 | **+5.63%** |
| Mean request latency | 6.064 s | 5.741 s | **-5.33%** |
| Mean TTFT | 3.148 s | 3.128 s | -0.64% |

TTFT 基本不变、decode step 显著下降，和“优化的是每-step scheduler control-plane”这一机制吻合。

### 相关代码位置

- `python/sglang/srt/managers/scheduler_components/dp_attn.py`
  - `MLPSyncBatchInfo.finalize_local`
  - `should_skip_scheduler_all_gather`
  - `prepare_mlp_sync_batch_raw`

### AI Infra 面试启发

这类优化的核心不是“少一个 all-gather”，而是**什么时候可以证明一个 collective 是语义冗余的**。需要说明 rank invariance 的来源，以及为什么 DP1 可以本地 finalize，但 DP>1 默认不能照搬。生产系统里，删除同步之前必须先证明 metadata 的 ownership 和一致性边界。

## 3. Speculative Decoding：引入 lossless Block Verification，接受长度和吞吐同时提高

**PR:** [#36516 — Support block verification for rejection sampling](https://github.com/sgl-project/sglang/pull/36516)  
**状态:** Open；2026-08-26 22:41（UTC+8）新建。

### 解决的问题

经典 speculative rejection sampling 对 draft token 按顺序逐 token 验证，遇到第一个 rejection 就停止。这是 lossless 的，但并不是给定 draft/target distribution 下的最优 block acceptance 策略。

Block Verification 把整个 draft block 联合考虑，在保持最终输出**严格服从 target model sampling distribution**的前提下，提高期望接受 token 数。

### 核心改动

新增 Triton `speculative_sampling_block_kernel`，实现 block-level acceptance 与 residual correction sampling，并通过新参数：

```bash
--speculative-use-block-verification
```

接入：

- EAGLE / EAGLE3 / NEXTN linear-chain rejection sampling；
- DSPARK 的 sampling accept path；
- topk=1 chain drafting。

Tree drafting、DFLASH 等不同 verify family 暂不支持；greedy decoding 下则退化为经典规则，因此没有额外收益也不会改变结果。

### 性能 / 工程影响

RTX PRO 6000 Blackwell，ShareGPT，concurrency=8：

| γ | temp | Accept length | Output throughput |
|---|---:|---:|---:|
| 4 | 1.0 | 2.61 → 2.69 | 759.3 → 785.9 tok/s（**+3.5%**） |
| 8 | 1.0 | 3.10 → 3.24 | 639.7 → 664.3 tok/s（**+3.8%**） |
| 8 | 0.6 | 3.52 → 3.61 | 724.6 → 735.6 tok/s（**+1.5%**） |

收益随 draft block 变长、sampling temperature 提高而增大，符合算法预期。

当前需要继续观察的是 TP>1 / DSPARK multi-GPU E2E validation；PR 自身也明确把这部分列为待补验证项。

- `python/sglang/kernels/ops/speculative/reject_sampling.py`
  - `speculative_sampling_block_kernel`
  - `chain_block_speculative_sampling_triton`
- `python/sglang/srt/speculative/eagle_utils.py`
  - `eagle_sample`
- `python/sglang/kernels/ops/speculative/dspark/dspark_accept.py`
- `python/sglang/srt/arg_groups/speculative_hook.py`

### AI Infra 面试启发

Speculative Decoding 的性能不只是“drafter 越准越好”。接受算法本身也决定有效 accept length。好的回答应该区分：

1. draft quality；
2. target verify cost；
3. acceptance rule；
4. correction sampling 的 lossless 条件。

Block Verification 是一个很好的例子：**不改 draft model、不改 target model，仅改变 verifier 的统计决策，就可以提高吞吐。**

## 4. KV Cache / HiCache：buffer-only host mode 开始恢复 Mamba recurrent state

**PR:** [#36345 — Support Mamba in buffer-only host memory mode](https://github.com/sgl-project/sglang/pull/36345)  
**状态:** Open；过去 24 小时内继续更新。

### 解决的问题

`--hicache-host-memory-mode buffer_only` 原先只允许 FULL / FULL+SWA。对 Mamba/GDN hybrid model 来说，仅恢复 prefix KV 不够：radix node 对应的 recurrent state 也是 prefix correctness 的组成部分。

如果只把 KV page 从 L3 拉回而不恢复结束该 prefix 的 Mamba state，cache hit 在逻辑上就是假的。

### 核心改动

一次 staged Mamba state 需要完成两份 device handoff：

- 写入 tree node 的 Mamba slot，形成可发布的缓存节点；
- 写入当前 consuming request 自己的 slot，供马上执行的 extend forward 使用。

这里刻意没有复用 deferred D2D：request 获取独立 H2D，因为 deferred D2D 可能在 node H2D 尚未完成时读取该 slot，形成 read-before-write hazard。

同时 Scheduler admission 通过 `mamba_host_hit_length` 把这部分 staged state 占用纳入预算，避免“缓存恢复正确了，但 admission 没收费”导致池容量被过度承诺。

### 正确性结果

H200、Inkling：512-token prefix 从 L3 buffer-only path 恢复后，8/8 均命中 512 tokens，`avg_kl_div = 0.0`，即与重新计算 prefix bit-exact 对齐。

### 相关代码位置

- HiCache buffer-only read / load-back controller：`_prepare_mamba_handoff`
- Scheduler：`python/sglang/srt/managers/scheduler.py` 中 staged Mamba admission accounting
- Model runner：`python/sglang/srt/model_executor/model_runner.py` 中 deferred Mamba COW/clear 与 forward read ordering

### AI Infra 面试启发

对于 hybrid model，所谓“KV Cache”实际已经是一个 **state closure**：只有恢复所有影响未来 token 的状态，prefix reuse 才是正确的。KV、SWA window、Mamba recurrent state、DSA indexer、spec draft state 都可能属于 closure 的一部分。

## 5. KV Cache × Scheduler：SWA eviction free 去掉隐式 stream sync，RL workload +5%

**PR:** [#36372 — sync-free in-place out-of-window SWA frees](https://github.com/sgl-project/sglang/pull/36372)  
**状态:** Open；过去 24 小时内持续更新。

### 解决的问题

`free_swa_out_of_window_slots` 原本使用 `torch.unique` / boolean mask 去找要释放的 page。由于输出 shape 数据依赖，PyTorch 需要知道 GPU 计算结果大小，会把本应与 forward overlap 的 scheduler 热路径强制同步。

也就是说，看起来只是“做一次 free”，实际上可能让整个 scheduler pass 等 GPU。

### 核心改动

利用 SWA eviction range 的强 invariant：这是 page-aligned、首次释放、位于 eviction frontier 之前的连续 segment，因此无需动态 `unique` / `nonzero`。

改为固定 shape：

- page representatives：`free_index[::page_size]`；
- paged allocator：`free_page_ids`；
- multi-ended allocator：`free_v_pages_lazy`；
- 不满足 invariant 时退回 legacy `free_swa`。

### 性能影响

内部 RL rolling workload 中，旧路径累计约 139 秒 scheduler stall / 1200 秒运行时间；仅此修复使 E2E output throughput：

**11,411 → 12,013 tok/s，约 +5%。**

### AI Infra 面试启发

GPU serving 的 CPU/Scheduler 优化里一个常见陷阱是：**Python 代码没有显式 `torch.cuda.synchronize()`，并不代表没有同步。** 数据依赖 shape 的 `unique/nonzero/item/tolist`、CPU readback 等都可能形成隐式 barrier。

## P/D 控制面继续收敛：Mori Sender 进一步降级为 enqueue + poll

**PR:** [#36160 — Align Mori prefill transfer control plane for unified control plane](https://github.com/sgl-project/sglang/pull/36160)

这个 PR 没有新的 benchmark，因此不列入前三，但架构方向值得继续跟踪：Mori 正把 Prefill transfer 的状态机从 Sender 移到 transfer worker / Manager，queued work 只携带 room，不再持有 Sender reference；成功通知、失败收敛和 timeout 都由 Manager 集中处理，而 Sender 只负责 enqueue + poll，RDMA data plane 本身不变。

这延续了此前统一 Mooncake / NIXL / Mori 控制协议的方向：**transport backend 应主要负责 data movement，而 request lifecycle / terminal state / failure semantics 应归公共 control plane。**

相关改动集中在 Mori KV Manager / transfer worker，以及公共 `TransferKVChunk`。

## 今日架构趋势

### 1. P/D：瓶颈从 bandwidth 转向 transaction granularity

过去容易用“KV 有多少 GB、网络多少 GB/s”估算传输成本，但 #35762 清楚说明，**相同 bytes 下，descriptor topology 就能带来 1.5×+ 的系统吞吐差异**。后续 P/D 优化会越来越关注 packing、registration、staging、batching 和 completion pipeline。

### 2. Scheduler：性能优化正在变成“证明哪些同步不必要”

#36568 删除 DP1 collective、#36372 删除 data-dependent free 同步，本质都是同一件事：通过更强的 invariant，把运行时动态协调替换为本地固定 shape / 固定语义操作。

### 3. Spec：从 drafter / kernel 优化进入 verifier algorithm 优化

#36516 的价值在于，Spec 的优化空间不只在 draft model 或 target attention kernel。**acceptance algorithm 本身也是一等性能组件。**

### 4. KV Cache：从 tensor cache 走向 heterogeneous state cache

Mamba buffer-only 的加入再次证明：对 hybrid / spec 系统，缓存正确性不能只定义为“KV bytes 一样”，而要定义为恢复后的整个 future-execution state 与 recompute 等价。
