## P0：本日最重要变化

### 1. Overlap Scheduler 用“窄 CUDA Event”约束跨 Rank Collective 顺序 — PR #34449

- PR：[Fix GPU DP metadata rank ordering under overlap](https://github.com/sgl-project/sglang/pull/34449)
- 状态：**Draft / Open**，2026-08-11 20:43 UTC 创建
- 方向：**Scheduler × Speculative Decoding × DP Attention**

**解决的问题**

Qwen3.5 MTP + DP Attention + overlap scheduling 下，step N 的 draft-extend 仍可能在 forward stream 上执行 MoE/DeepEP 或 output collective，而 step N+1 已经在 schedule stream 上启动 DP metadata all-gather。

如果不同 rank 进入这两个 rank-coupled collective 的顺序不同，就可能形成：

```text
rank A: previous forward collective -> next metadata collective
rank B: next metadata collective     -> previous forward collective
```

最终互相等待，表现为 serving hang。

**核心改动**

不是让 schedule stream 等完整 forward stream，而是：

1. 在“上一轮最后一个跨 rank communication”之后记录一个 external CUDA event；
2. CUDA Graph replay 与 eager draft-extend 都发布这个 event；
3. 下一轮 DP metadata all-gather 只等待该 event；
4. event 之后的 norm / LM-head tail compute 仍可继续与 scheduler metadata 同时执行。

这实际上是在运行时中显式编码一条最小的 happens-before：

```text
rank-coupled forward communication
             ↓ event
next DP metadata all-gather
```

而不是：

```text
whole forward complete
             ↓
next DP metadata all-gather
```

**性能 / 工程影响**

44×GB300、7P+1D、decode DP/TP/EP16、MTP3 的压力测试：

- concurrency 3072：30,720 / 30,720 请求完成，0 error；
- concurrency 4096：40,960 / 40,960 请求完成，0 error；
- GSM8K 200/200 完成，score 0.935。

窄 event 与“等待整个 forward stream”的性能基本在 run-to-run noise 内：

| Concurrency | whole-forward TPOT | narrow-event TPOT | whole-forward TPS | narrow-event TPS |
|---:|---:|---:|---:|---:|
| 3072 | 30.743 ms | 30.643 ms | 82,243.8 | 82,476.9 |
| 4096 | 37.675 ms | 37.573 ms | 87,041.1 | 87,409.4 |

重点不是得到显著加速，而是 **恢复正确性时没有把 overlap 整体打掉**。

**AI Infra 面试启发**

这是非常典型的 CUDA + 分布式通信组合题：**两个 CUDA stream 各自有序，不代表多个 rank 对 collective 的全局进入顺序一致。** `wait_stream()` 是正确但过度同步的办法；更好的设计是找出最后一个真正需要全局有序的操作，并建立精确 event dependency。

### 2. GDN MTP：从“缓存所有 Draft State”转向“最终 State 重算 + Side Stream Overlap” — PR #30967

- PR：[Add MTP cache mode for final-state recompute, with FlashInfer kernel integration and overlapped CUDA-graph state recovery](https://github.com/sgl-project/sglang/pull/30967)
- 状态：**Open**；本窗口更新于 2026-08-11 23:58 UTC
- 方向：**Speculative Decoding × KV/SSM State Management**

**解决的问题**

Gated DeltaNet 的 MTP target-verify 需要推进 recurrent state。传统 `full` 模式为每个 draft position 保存完整 `[V, K]` intermediate recurrent state，verify 结束后直接取 accepted position。

`none` 模式不保存这些中间 state，显著减少 speculative state 占用，但必须从 committed `h0` 重放 accepted prefix 来恢复 `hK`；如果这个 replay 直接放在 decode critical path，就会把节省显存换成额外延迟。

**核心改动**

PR 把重算拆成一套可 overlap 的异步恢复路径：

- verify 只保存 post-conv `k/v` 与 α/β gate 等 recurrence inputs；
- SM100+ 使用 FlashInfer output-only WY verify kernel，不写每个 draft 的完整 state；
- verify 后只恢复 **最终 accepted state**；
- recovery 直接读取持久 token-major buffer 的 strided view，减少额外 copy；
- recovery 放到独立 CUDA side stream，与下一轮 draft compute overlap；
- 按 batch bucket 捕获 recovery CUDA Graph；
- 非 FlashInfer / 非 Blackwell 路径保留 Triton fallback。

这个设计的本质是：

```text
更多显存：cache S1, S2, S3, ... -> 低重算
```

转成：

```text
更少显存：cache recurrence inputs -> 只重算 accepted SK
                               ↘ 与 next draft overlap
```

**性能 / 工程影响**

Qwen3.5-397B-A17B-NVFP4、TP4：

| Batch size | full baseline | none + FlashInfer | 提升 |
|---:|---:|---:|---:|
| 64 | 7,312.98 tok/s | 7,953.32 tok/s | ~8.8% |
| 128 | 11,626.15 | 12,834.41 | ~10.4% |
| 256 | 16,385.06 | 18,526.52 | ~13.1% |
| 512 | 19,879.96 | 23,407.08 | ~17.7% |

GSM8K accuracy：`none + FlashInfer = 0.977`，`full baseline = 0.975`，没有看到明显正确性回退。

**AI Infra 面试启发**

这是经典的 **memory vs recomputation** trade-off，但关键不是简单“少缓存、多计算”。真正让方案成立的是：重算是否可以 **异步化、图捕获、与下一步并行**。如果能把 recompute 从 critical path 隐藏掉，重新计算反而可能同时降低显存并提高吞吐。

### 3. PP + P/D + DSpark：不传 Hidden State，按 PP Stage 累积 Context Projection — PR #33863

- PR：[PP Support PD + DSpark](https://github.com/sgl-project/sglang/pull/33863)
- 状态：**Open**；本窗口更新于 2026-08-11 22:10 UTC
- 方向：**Prefill/Decode Disaggregation × Speculative Decoding × Pipeline Parallelism**

**解决的问题**

无 PP 时，Prefill worker 可以拿到完整 target hidden states，本地构造 DSpark draft KV，再把 target KV + draft KV 传给 Decode。

PP 后，DSpark 所需的 target hidden features 分散在不同 PP stage；如果各 stage 独立做 KV projection，数学上并不等价，因为 RMSNorm 必须作用在完整 context projection 累积结果之后。

**核心设计**

P/D data plane 仍保持：

```text
Prefill -> target KV + draft KV -> Decode
```

**不跨 P/D 边界传 hidden states。** 每个 PP stage 只计算自己的局部 projection contribution：

```text
ctx_i = h_i @ W_i.T
ctx_acc = recv_ctx_acc + ctx_i
```

最后一个 PP stage 再：

```text
ctx_norm = RMSNorm(ctx_acc)
K, V = KVProj(ctx_norm)
```

因为：

```text
concat(h1, ..., hk) @ W_fc.T
= sum_i(h_i @ W_i.T)
```

所以可以把跨 PP payload 固定在 `[num_tokens, hidden_size]`，而不是把所有原始 hidden states 拼接搬运。

同时，Scheduler / transfer control plane 也做了关键收敛：

- successful bootstrap / transfer 使用 **有序交集**；
- failure 使用 **有序并集**，任一 PP rank 失败升级为全局失败；
- KV 只有在本地 transfer 到 terminal state 后才释放；
- state component 不再按 list position 对齐，而按 `(StateType, occurrence)` 匹配；
- 避免某些 PP rank 缺少可选 `C128_STATE` 时，把 draft SWA 错写到 target state。

**性能 / 工程影响**

当前 PR 给了 H20 accuracy validation（MMLU 0.878、GSM8K 0.945、GPQA 0.961），但还没有完整 serving speed benchmark，因此当前更应把它看成 **组合能力 / correctness 架构 PR**。

### 4. Unified Radix Cache 引入 Agentic-Aware T-LRU — PR #34012

- PR：[Add Agentic-Aware Tail-Optimized LRU eviction to the unified radix cache](https://github.com/sgl-project/sglang/pull/34012)
- 状态：**Open**；本窗口更新于 2026-08-12 00:17 UTC
- 方向：**KV Cache**

传统 LRU 只根据 recency 决定淘汰；T-LRU 开始把 **下一轮 prompt 预估 + TTFT SLO** 纳入 cache eviction。

核心思想：一段 conversation 长度为 `L`，若下一轮预计增加 `Q_hat` token，系统允许最多 `xi` token 的 recompute，那么只有：

```text
max(L + Q_hat - xi, 0)
```

之前的历史必须继续驻留；剩余 tail 即便提前淘汰，下次 recompute 仍在 TTFT budget 内，因此可优先释放。

新增：

```text
--radix-eviction-policy tlru
--tlru-threshold N
--tlru-next-prompt-estimate M
```

C=32 的 agentic trace 上，T-LRU 相比 LRU：

- TTFT p95：**-6.9%**
- TTFT p99：**-8.6%**
- ITL p95：**-17.2%**
- ITL p99：**-43.9%**
- aggregate throughput / GPU prefix hit 基本不变

代价是 eviction/write-back 更积极，但该实验里平均 HBM↔DRAM 流量仍只有十几 MB/s 量级。

- `python/sglang/srt/mem_cache/evict_policy.py`
- `python/sglang/srt/mem_cache/cache_init_params.py`
- `python/sglang/srt/mem_cache/kv_cache_builder.py`
- `python/sglang/srt/mem_cache/unified_cache/unified_tree_core.py`
- `python/sglang/srt/server_args.py`

**面试启发**：KV Cache policy 正在从“通用 cache 算法”转成 **serving objective-aware resource management**。Agentic workload 下，cache hit rate 本身不是最终目标，TTFT tail / ITL tail / admission 才是。

### 5. P/D 大规模拓扑触发 ZMQ Context Socket 上限，修复已合入 — PR #34450

- PR：[Raise PD zmq per-context socket cap via SGLANG_DISAGGREGATION_ZMQ_MAX_SOCKETS](https://github.com/sgl-project/sglang/pull/34450)
- 状态：**Merged**，2026-08-11 22:27 UTC
- 方向：**Prefill/Decode Disaggregation / Production Scaling**

Prefill KV manager 会为每个 Decode endpoint 缓存 PUSH socket 和 PAIR monitor socket。到 `16 decode replicas × 32 DP ranks` 时，同一 libzmq context 需要约 1025 sockets，超过默认 `ZMQ_MAX_SOCKETS=1023`；此时即使 Linux `ulimit -n` 足够，P/D transfer worker 仍会在 connect 阶段失败。

修复新增：

```text
SGLANG_DISAGGREGATION_ZMQ_MAX_SOCKETS
```

默认设为 16384，并在 KV manager context / `CommonKVReceiver` context 建 socket 前配置。

**相关代码**

- `python/sglang/srt/disaggregation/common/conn.py`
- `python/sglang/srt/environ.py`

**面试启发**：大规模 P/D 部署的瓶颈不只 RDMA/NVLink。**控制面连接数、socket/context cap、FD、monitor channel、endpoint cache** 都可能先于数据面带宽成为扩展上限。

### 6. Wide-EP P/D + DP Attention + MTP 出现“non-idle but empty rank” — PR #34474

- PR：[Guard attn layers against empty DP-attention batch](https://github.com/sgl-project/sglang/pull/34474)
- 状态：**Open**，本窗口新建
- 方向：**Scheduler × P/D × Speculative Decoding**

在 wide expert-parallel disaggregated decode 中，一个 DP rank 某轮可能 **0 requests**，但它仍处于 `target_verify`，因此从协议角度并非 idle。旧代码只检查 `not is_idle()`，于是空 rank 仍进入 attention，并在 `reshape(0, -1)` 一类路径崩溃。

修复让空 rank 跳过 attention compute，但仍参加外围 collective。

这个 PR 改动很小，但概念很重要：

```text
idle rank != empty local batch
```

分布式推理中，一个 rank 即使本地没有 token，也可能必须进入 collective 来保持全局协议推进。

4×MI355X、wide-EP16 2P1D + MTP 的验证中，旧版本 warmup 崩溃；补丁后 GSM8K 0.973，非 MTP baseline 0.975。

## Issue：KV Allocator 的 OOM Check 晚于 GPU Kernel Launch — #34399

- Issue：[Paged KV allocator launches allocation kernels before checking OOM](https://github.com/sgl-project/sglang/issues/34399)
- 状态：**Open**，2026-08-11 新建
- 方向：**KV Cache / Allocator Correctness**

`PagedTokenToKVPoolAllocator.alloc_extend()` / `alloc_decode()` 当前会先 launch Triton allocation kernel，再判断 `free_pages` 是否足够。

当实际需要 3 pages 但逻辑 free list 只有 1～2 pages 时，kernel 已经可能读取 free-list 逻辑边界以外的位置，随后 CPU 才返回预期的 OOM。

Issue 给出的 deterministic backing-storage 示例中：

```text
logical_free_pages = [7]
page_ids_used      = [7, 99, 101]
```

说明虽然最终接口可能表现为“受控 OOM”，GPU 侧实际上已经发生了不合法的逻辑读取。

建议修复非常直接：**capacity precondition 必须在 output allocation / Triton launch 前完成**。

**相关代码**

- `python/sglang/srt/mem_cache/allocator/paged.py`

**AI Infra 面试启发**：资源分配器的 OOM path 也必须是 first-class correctness path。检查“是否有资源”不能放在有副作用的设备 kernel 之后；否则错误处理虽然表面返回成功，CUDA worker 状态可能已被污染。

## 今日架构趋势归纳

### 1. Scheduler 的同步粒度正在从“stream”缩到“真实数据/collective 边界”

#34449 的价值不只是修 hang，而是把同步语义从：

```text
previous forward done
```

细化成：

```text
previous rank-coupled operation done
```

这类精确 dependency 是把 overlap scheduler 做到 production 的必经阶段。

### 2. Speculative state 管理从“空间换时间”转向“异步重算”

#30967 说明在 CUDA Graph + 多 stream 环境里，recompute 不一定意味着慢。只要 recovery 能提前准备输入、固定 shape、独立 stream 执行并被下一轮 draft 隐藏，**recompute 可以成为省显存又增吞吐的设计**。

### 3. P/D 的复杂度正在从 Data Plane 转向 State Schema + Control Plane

#33863 仍坚持只传 target KV + draft KV，避免把 hidden state 变成新的 P/D data plane；但为此必须解决 PP stage 间 context accumulation、transfer completion consensus、optional state component 对齐。

这说明 P/D 真正成熟之后，核心问题往往不是“怎么 copy KV”，而是 **如何定义可演进、可组合、可恢复的 state protocol**。

### 4. KV Cache 策略开始直接优化用户 SLO

T-LRU 不再追求单一 cache hit，而是根据预计下一轮 prompt 和 TTFT recompute budget 判断哪些 tail 可以安全释放。对于 agentic workload，这比纯 LRU 更接近 serving 的真实目标函数。

## 对 AI Infra 面试 / 项目实践的启发

1. **CUDA stream ordering 与 distributed collective ordering 是两层问题。** 同一个 rank 内 stream 有序，不自动给你跨 rank 全局一致顺序。
2. **不要把 recompute 等价成性能退化。** 要问能否 side-stream overlap、CUDA Graph capture、预分配和 zero-copy。
3. **分布式状态要有类型，而不是依赖数组位置。** `(StateType, occurrence)` 比 `state[i] -> state[i]` 更能承受 PP/Spec 可选组件。
4. **Allocator 的失败路径也要无副作用。** OOM check、credit check、admission check 都应该在设备操作前建立明确 invariant。
5. **Cache policy 的 KPI 应该是服务 SLO，而不只是 hit rate。** 对 agentic workload，tail latency 和可 admission 的活跃会话数量往往更重要。
6. **规模化 P/D 要算控制面资源。** endpoint 数量乘以 DP/replica 后，ZMQ socket、FD、monitor channel、connection cache 都要进入 capacity planning。
