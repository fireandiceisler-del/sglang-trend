## 今日结论

今天最明显的主线不是新增一个孤立的“更快 kernel”，而是 SGLang 在继续把 **异步推理系统中的隐式状态，改成可验证的显式 contract**：

1. **KV Cache allocator 正继续把 source of truth 从 GPU 搬回 host。** 新 PR #35592 直接去掉 SWA free path 上会触发 device sync 的 `> 0` liveness mask；配套 Tracking #35223 已把目标明确成“host 规划 whole-page allocation，GPU 表只做 write-only execution projection”。
2. **P/D decode 的 retraction 开始从“必须预留 1:1 host pool”转成“按实际 burst 容量规划 + request-scoped failure”。** #35543 将 backup-only host pool 默认比例从 device pool 的 1.0 降到 0.2；备份放不下时只 abort 对应 request，而不是让 scheduler 因 host pool exhaustion 崩掉。
3. **Scheduler 里“派生状态不能长期粘住”再次成为 correctness/liveness 主题。** 新 Issue #35537 证明 `batch_is_full` 作为 per-pass admission hint 被保存在长生命周期 `ScheduleBatch` 上后，会让 waiting queue 在资源充足时仍饥饿数分钟。
4. **Spec × CUDA Graph × P/D × PP 的组合边界正在补齐。** #35588 修 Full Prefill CUDA Graph 的 live-token boundary 和 EAGLE hidden-state capture；#33863 则持续推进 `PP + P/D + DSpark`，把 PP 内部 context accumulation、draft KV owner、跨 stage transfer consensus 与 state-component matching 都显式化。
5. **Hybrid Mamba/Radix 的 index-space invariant 仍是高风险区。** #35412 修复 DCP 下 decode checkpoint depth 不落在 RadixTree page grid 上时会产生的 silent wrong-state reuse；这是典型的“数值没 crash，但缓存语义已经错了”。

## 1. KV Cache：SWA slot liveness 从 device readback 移到 host bookkeeping — PR #35592

**状态：Open；2026-08-20 08:04（北京时间）创建，仍在活跃更新。**  
PR: https://github.com/sgl-project/sglang/pull/35592  
Tracking: https://github.com/sgl-project/sglang/issues/35223

### 解决的问题

`SWATokenToKVPoolAllocator.free_swa()` 过去会：

```text
full slot ids
  -> gather full_to_swa_index_mapping
  -> swa_indices[swa_indices > 0]
  -> free SWA slots
```

关键问题在 `swa_indices > 0`：它产生 data-dependent 结果，scheduler 为了知道真正要 free 的元素集合，需要等待 device 结果。对 Overlap Scheduler 来说，这会把 CPU free path 排到正在飞行的 forward / WAR fence 后面，破坏原本希望的 CPU/GPU overlap。

### 核心改动

PR 把“这个 range 的 SWA peer 是否还活着”的判断交给调用方，因为调用方本来就在 host 侧掌握：

- `node.swa_tombstone`
- `req.kv.swa_evicted_seqlen`
- Unified Tree component 是否已被释放

并把 allocator API 拆出清晰语义：

```text
free(x) == free_full(x) + free_swa(x)
```

也就是说，不再让 allocator 到 GPU mapping 里“反查”生命周期，而是让 owner 明确告诉 allocator：这一段该释放 full、SWA，还是两者。

### 性能 / 工程影响

- `page_size == 1` 时，逐 decode step 的 `free_swa_out_of_window_slots` 可以直接做到 **sync-free**。
- paged 配置还没有完全结束：`_expand_to_full_pages()` 仍有 `torch.unique`，所以整个 host-allocator roadmap 尚未完成。
- 这比“减少一个 kernel”更重要：它是在把 **scheduler control plane 的真值从 device state 解耦出来**。

### 相关代码位置

- `python/sglang/srt/mem_cache/allocator/swa.py`
- `python/sglang/srt/mem_cache/common.py`
- `python/sglang/srt/mem_cache/unified_radix_cache.py`
- `python/sglang/srt/mem_cache/unified_cache/components/{full_component,swa_component}.py`
- `python/sglang/srt/disaggregation/decode_kvcache_offload_manager.py`
- `python/sglang/srt/managers/scheduler_pp_mixin.py`

### AI Infra 面试启发

一个很好的面试题是：

> 为什么“GPU 上已经有完整 allocator metadata”仍不意味着 scheduler 应该读取它来做 free decision？

核心答案：**execution-plane state 和 control-plane source of truth 不应该混为一体。** GPU readback 会引入 stream synchronization、data-dependent shape、WAR dependency；如果 allocation/free 的事实本来由 host 决定，GPU 表更适合只是 kernel 消费的 projection。

## 2. KV Cache / P-D：Decode retraction host pool 不再要求 1:1 镜像 — PR #35543

**状态：Open；2026-08-20 00:16 创建，08:16 后仍有更新。**  
PR: https://github.com/sgl-project/sglang/pull/35543

### 解决的问题

P/D decode 发生 retraction 时，为了之后可以 resume，请求的 KV 可以先从 device 备份到 host pool。旧设计默认要求 backup-only host pool 至少和 device pool 一样大，本质上是为了“任何 retraction 都必须能完整备份”而提前保留 1:1 DRAM。

这在大 HBM 机器上非常昂贵，而且真实 retraction burst 往往只覆盖 device token 的一小部分。

### 核心改动

- backup-only `host_pool` 的默认 `hicache_ratio` 从 **1.0 → 0.2**。
- `retraction_backup()` 从“分配失败直接抛 RuntimeError”改成返回 `None/False`。
- 如果 host backup 放不下，而 device KV 已经释放：
  - 只把该 request 标记为 `FINISH_ABORT`；
  - 不把它放回 resumable retracted queue；
  - scheduler 继续服务其他请求。
- 如果用户真正启用了共享 HiCache，则仍沿用正常 HiCache pool sizing，而不是强制使用 0.2 backup-only 配置。

### 性能 / 工程影响

这不是吞吐 benchmark，而是 **capacity planning 与 failure domain** 的变化：

- 默认 backup-only host slot 预算从 device pool 的 100% 降到 20%。
- 代价是极端 retraction burst 可能让单个请求失败。
- 收益是用 request-scoped failure 换取更低 DRAM 预留，并避免 host backup exhaustion 升级成 scheduler/process 级故障。

这是一种很典型的生产系统取舍：**不为最坏情况无限 over-provision，而是定义可控的降级语义。**

### 相关代码位置

- `python/sglang/srt/managers/schedule_batch.py`
- `python/sglang/srt/mem_cache/common.py`
- `python/sglang/srt/mem_cache/kv_cache_builder.py`
- `python/sglang/srt/mem_cache/unified_radix_cache.py`
- `python/sglang/srt/server_args.py`

### AI Infra 面试启发

可以把它类比为数据库/存储系统的 admission + spill：

> 资源备份池是否必须覆盖全量 working set？如果不能覆盖，失败应该落在哪个 fault domain？

优秀答案不是“永远分配更多内存”，而是明确：**capacity model、overflow policy、请求可恢复性、资源释放顺序，以及失败是否影响其他 tenant/request。**

## 3. Scheduler：`batch_is_full` sticky state 造成 waiting queue starvation — Issue #35537

**状态：Open Issue；2026-08-19 22:46（北京时间）新建。**  
Issue: https://github.com/sgl-project/sglang/issues/35537

### 解决的问题

在 `max_running_requests=4 + chunked prefill` 的复现中，4 个冷请求只跑 3 个，第 4 个一直在 waiting queue；此时：

- KV pool 使用率 ≤ 4%；
- Mamba state pool 只用了 16/24 slot；
- 不是实际资源不足。

生产化复现里 queued request 最长等了约 **4.5 分钟**，直到一个正在 decode 的请求完全结束才被重新 admission。

### 根因

`running_batch.batch_is_full` 本来更像是 **当前 scheduler pass 的派生 admission hint**，但它保存在长生命周期的 `ScheduleBatch` 中：

1. 最后一次 chunked-prefill continuation 占据最后一个 allocatable slot；
2. 当前 pass 把 `batch_is_full=True`；
3. 进入 steady-state decode 后，没有事件重新计算该 flag；
4. 后续 `_get_new_batch_prefill_raw()` 每轮都在入口 early-return；
5. waiting queue 被饿死，直到 running batch 缩小触发 rebuild/reset。

### Proposed fix 与验证

Issue 作者提出每轮进入 `_get_new_batch_prefill_raw()` 时重新计算/清掉这个 per-pass hint，再由本轮真实 resource gates 重新决定 fullness。

同一复现中：

- 修复前：3 running + 1 waiting；
- 修复后：4 个都立即 admission；
- 4 个请求均在 **8.3–9.2s** 完成；
- decode 阶段 queue event 为 0。

这还不是已合入 PR，因此当前应视为 **高价值 scheduler liveness diagnosis**，不是已发布修复。

### 相关代码位置

- `python/sglang/srt/managers/scheduler.py`
- `Scheduler._get_new_batch_prefill_raw()`
- `ScheduleBatch.batch_is_full`
- `PrefillAdder` 的 allocatable-request / token budget gates

### AI Infra 面试启发

这里非常适合考 scheduler 状态机：

> 哪些字段是 persistent state，哪些只是 derived/cache state？derived state 如果跨 epoch/pass 保存，需要什么 invalidation contract？

这和数据库缓存失效、分布式 lease、CPU scheduler runqueue flag 本质类似：**缓存一个判断本身没有错，错的是没有定义它何时失效。**

## 4. Spec × Prefill CUDA Graph：修 FullCG padding boundary 与 EAGLE hidden capture — PR #35588

**状态：Open；2026-08-20 07:13（北京时间）创建。**  
PR: https://github.com/sgl-project/sglang/pull/35588

### 解决的问题

Full Prefill CUDA Graph 采用固定 token bucket，capture bucket 可能大于实时 batch token 数。

两个组合问题：

1. 某些模型会依赖 `num_token_non_padded` mask 掉 bucket 尾部；即使 attention tensor 没有走 gathered buffer，也必须知道真实 live-token boundary。旧 FullCG 路径可能缺失/复用 stale boundary，padding row 会继续传播。
2. EAGLE target prefill 需要 **完整 target hidden-state sequence**。FullCG 如果按普通 `LAST` hidden mode capture，就无法满足 target prefill，最终被迫 fallback eager。

### 核心改动

- FullCG 无论是否 gathered，都注册并填充 live `num_token_non_padded`。
- EAGLE target prefill 在 FullCG 下 capture `FULL` hidden states。
- breakable draft worker 仍保留 `LAST`，避免无必要扩大 capture payload。
- eager fallback 收窄到 `tc_piecewise`，不再把已经能满足 FULL 的 FullCG/Breakable 路径一起禁掉。

### 性能 / 工程影响

作者没有给新的速度 benchmark；42 个 focused tests 通过。

价值主要是：**把 Full Prefill CUDA Graph 从“单独能跑”推进到和 EAGLE / padding semantics 可组合。** 对大规模 serving 来说，CUDA Graph compatibility matrix 本身就是 runtime 能否稳定使用优化路径的一部分。

### 相关代码位置

- `python/sglang/srt/model_executor/cuda_graph_buffer_registry.py`
- `python/sglang/srt/model_executor/model_runner_components/cuda_graph_setup.py`
- `python/sglang/srt/model_executor/runner/prefill_cuda_graph_runner.py`

### AI Infra 面试启发

CUDA Graph 的核心坑之一是：**shape 被固定不等于语义也被固定。**

即便物理 tensor bucket 固定为 N，运行时仍需要单独传递：

- live token count；
- valid row mask/boundary；
- hidden-state capture mode；
- request-specific metadata。

否则 padded rows 是“合法内存”但“非法语义”，错误不会以 OOB 的形式暴露，而会成为 silent data corruption。

## 5. P/D × PP × Spec：PP + P/D + DSpark 继续收敛 control/data plane — PR #33863

**状态：Open；本窗口内继续更新（2026-08-20 07:14 北京时间仍有更新）。**  
PR: https://github.com/sgl-project/sglang/pull/33863

### 解决的问题

无 PP 时，P/D + DSpark 的 Prefill worker 可以直接拿到完整 target hidden states，生成 draft KV，然后把：

```text
Target KV + Draft KV
```

传给 Decode。

PP 后 hidden feature 被拆到不同 pipeline stage。如果每个 stage 独立对自己的 hidden 做 RMSNorm + KV projection，数学上不等价于完整 target projection。

### 核心设计

每个 PP stage 先算自己的线性贡献：

```text
ctx_i = h_i @ W_i.T
```

PP 内累积：

```text
ctx_acc = recv_ctx_acc + ctx_i
```

只有最后一个 PP stage 执行：

```text
RMSNorm(ctx_acc) -> KVProj -> Draft KV
```

因此：

- **hidden states 不跨 P/D boundary**；
- P/D data plane 仍保持 `target KV + draft KV`；
- 最后 PP stage 是 draft KV owner；
- 各 PP stage 只负责自己的 target KV。

更重要的是，PR 同时补了 control plane：

- bootstrap / transfer 成功取 **ordered intersection**；
- failure 取 **ordered union**；
- 任一 PP stage 失败都变成全局失败；
- local transfer 未 terminal 前禁止提前 release KV；
- P/D state component 从“按 list index 对齐”升级为按 **`(StateType, occurrence)`** 匹配，避免可选 C128/SWA state 在不同 PP rank layout 下错写目标 buffer；Mooncake 与 NIXL 都适用。

### 性能 / 准确性

当前 PR 没有给出吞吐 benchmark。H20 上给出的功能准确性验证：

- MMLU: 0.878
- GSM8K: 0.945
- GPQA: 0.961
- AIME25 ×16: 98.33% ± 2.11%

- `python/sglang/srt/disaggregation/{prefill,decode,utils}.py`
- `python/sglang/srt/disaggregation/mooncake/conn.py`
- `python/sglang/srt/disaggregation/nixl/conn.py`
- `python/sglang/srt/managers/scheduler_pp_mixin.py`
- `python/sglang/srt/speculative/dspark_components/{dspark_worker_v2,dspark_kv_inject,dspark_config}.py`

### AI Infra 面试启发

这条 PR 非常值得用来回答：

> “为什么支持 PP、支持 P/D、支持 Spec 三件事都完成后，PP × P/D × Spec 仍然不是自动成立的？”

因为 composability 不只是数据格式兼容，还包括：

- **谁拥有 state**；
- **谁是最后写者**；
- **什么时候可以 release**；
- **跨 stage 成功/失败如何达成一致**；
- **optional state layout 如何做语义匹配而非位置匹配**。

这已经非常接近一个分布式存储/事务协议问题，而不是单纯的推理 kernel 问题。

## 6. Hybrid KV / Spec：DCP 下 Mamba checkpoint depth 必须落在 RadixTree page grid — PR #35412

**状态：Open；本窗口内持续 review/更新。**  
PR: https://github.com/sgl-project/sglang/pull/35412

### 解决的问题

Mamba state checkpoint 只有在 RadixTree 能表示的逻辑 depth 上才可安全复用。

旧 decode tracking 只要求：

```text
mamba_track_interval % configured_page_size == 0
```

但 DCP 下 tree 的实际 page 是：

```text
page_size * dcp_size
```

因此真正的 break condition 是：

```text
mamba_track_interval % (page_size * dcp_size) != 0
```

例如：

```text
page_size=64, dcp=8
configured track interval=256
tree page=512
```

checkpoint 可以在 depth=256 生成，但 RadixTree 只能把它挂到前一个 512-grid node。之后 cache hit 会恢复一个“已经消费过更多 token”的 recurrent state，再把那些 token 重新消费一遍 —— **不会 OOB、不会 assert，直接 silent wrong output。**

### 核心改动

新增：

```text
mamba_track_grid(tree_page)
  = lcm(mamba_checkpoint_grid(tree_page), mamba_track_interval)
```

并统一用于：

- normal decode checkpoint boundary；
- batch-result processor；
- Spec verify/prepare；
- DSpark worker；
- DFlash worker。

作者指出，在受影响配置上 snapshot write 频率会下降（例如 256 → 512 grid），但 cache node depth 本身不变；改变的是挂到 node 上的 state 是否真的对应该 node 的 token depth。

### 验证状态

目前没有 live accuracy benchmark；PR 明确计划补 8×B300 cold-vs-warm teacher-forced/logprob 级验证。因此这条应该视作 **高风险 correctness fix，仍需运行时证据闭环**。

### 相关代码位置

- `python/sglang/srt/runtime_context.py`
- `python/sglang/srt/managers/schedule_batch.py`
- `python/sglang/srt/managers/scheduler_components/batch_result_processor.py`
- `python/sglang/srt/speculative/spec_utils.py`
- `python/sglang/srt/speculative/dspark_components/dspark_worker_v2.py`
- `python/sglang/srt/speculative/dflash_worker_v2.py`

### AI Infra 面试启发

这类问题的关键概念是 **index space / granularity contract**。

同一个“token position”在系统里可能同时受：

- allocator page size；
- DCP logical page；
- Mamba chunk；
- checkpoint interval；
- RadixTree node depth

约束。只验证任意两个局部条件都可能不够；最终必须证明 **可缓存 state 的 logical depth 属于所有相关 grid 的交集**，因此 `LCM` 是非常自然的工程表达。

## Roadmap / Tracking 更新

### Host-side whole-page allocator — Tracking #35223

https://github.com/sgl-project/sglang/issues/35223

该 Tracking Issue 在本窗口内更新，并把 #35592 纳入 in-flight 工作。目标已经相当明确：

```text
Host:
  whole-page allocation/free source of truth
  req.kv.kv_allocated_len single writer

GPU:
  req_to_token
  full_to_swa_index_mapping
  free_pages
  => write-only projections for kernels
```

这说明最近几天看到的一系列 page alignment、deferred free、SWA liveness PR 不是零散修 bug，而是在为同一件事收口：**让 overlap scheduler 的资源回收不再依赖 GPU readback。**

剩余明显缺口是 paged SWA `_expand_to_full_pages()` 里的 `torch.unique` / page representative readback。
