## 今日结论

今天最强的信号不是某一个独立优化，而是 **DCP、HiCache、P/D 和 Speculative Decoding 继续向可组合架构收敛**。

1. **DCP × HiCache × DSpark 开始真正打通。** 新 PR #35221 不只是去掉兼容性 guard，而是修正了 draft HiCache sidecar 的容量语义：DCP 下必须按 target cache 的 **logical index space** 而不是单 rank 的 physical rows 来规划 host pool。
2. **P/D 的数据搬运正在从“能传”转向“批量、连续、少描述符”。** #35186 针对 Prefill DCP1 → Decode DCP8 的 MLA KV relayout，用 GPU staging 把 strided KV 行聚合成连续 RDMA block；基线 56K token 场景约 168K descriptors/rank，目标降到约 2.6K/rank。
3. **P/D 热路径里仍有很可观的 host/device 冗余。** 已合入 #35070 删除 Decode PREBUILT 阶段完全不会参与 forward 的 prompt → CUDA `input_ids` 搬运，生产 AgentX A/B 中 output TPS/user +17.98%，strict decode TPS/GPU +12.74%。
4. **Scheduler 的 KV 生命周期语义正在显式化。** #35204 明确区分 cache-owned 和 request-owned KV，不再用“已接受 token 数”间接推导应释放的 KV 范围；这是 overlap scheduling 下避免隐性 KV leak 的关键 contract。
5. **Overlap Scheduler × EAGLE v2 继续把 WAR fence 推到真正的最后读取边界。** #34890 的最新版本把 staged draft-extend 的 shared-read-done 放到 verify，报告 TP4 / concurrency 128 下 decode throughput +36%，forward occupancy 65% → 94%。

## 1. KV Cache / HiCache

### [#35221 — HiCache: Support DCP with DSpark](https://github.com/sgl-project/sglang/pull/35221) — Open

**为什么重要**

过去 `DCP + HiCache + DSpark` 会在 ServerArgs 阶段直接被拒绝。去掉 guard 后暴露出更本质的问题：

- target KV cache 的索引是 DCP-wide logical space；
- draft host pool 却按单 rank physical rows 估算；
- 当 L1 eviction 进入没有 host backing 的 logical range 时，draft KV transfer 会报 `CUDA error: invalid argument`。

**核心改动**

- 允许 `--dcp-size > 1` 时使用 `DSPARK + HiCache`，其他 speculative algorithm 仍保持 guard；
- full draft HiCache sidecar 从 `host_pool.size` 改为按 `host_pool.logical_size` 规划；
- legacy draft HiCache 路径同步使用 logical capacity；
- 增加 DCP-expanded draft sidecar sizing regression test。

**验证 / 工程影响**

8×B300、TP8/DCP8、Kimi-K3 target + DSpark draft、HiCache L2、正常 CUDA Graph 路径下：

- 64 requests × 16,384 input tokens；
- concurrency = 48；
- 64/64 成功；
- 1,048,576 input tokens 在 52.00 s 内完成，约 20,164 input tok/s；
- 修复后未出现 scheduler exception / CUDA error。

这更像一个 **composability milestone**，而不是单点 bugfix：DCP 把“物理容量”和“逻辑索引空间”分离后，任何 sidecar / offload / draft state 都必须明确自己依赖的是哪一种容量。

**相关代码**

- `python/sglang/srt/mem_cache/hybrid_cache/hybrid_pool_assembler.py`
- `python/sglang/srt/mem_cache/kv_cache_builder.py`
- `python/sglang/srt/server_args.py`
- `test/registered/unit/mem_cache/test_hybrid_pool_assembler.py`

**面试启发**

一个很好的 AI Infra 面试题是：**为什么 DCP 下 `physical pool size` 和 `logical token capacity` 不再等价？如果 draft cache / HiCache 仍按 physical size 分配会发生什么？**

### [#35204 — Scheduler: Release all request-owned KV on no-insert cleanup](https://github.com/sgl-project/sglang/pull/35204) — Open

**问题**

`RadixCache.cache_finished_req(..., is_insert=False)` 过去根据 committed token IDs 推导释放范围。但 overlap scheduling 下存在这样的合法时序：

```text
forward 已经 commit 一个 KV slot
        ↓
sampled output token 还没有被 accept / commit
        ↓
异常 / transfer failure 触发 no-insert cleanup
```

此时 token list 比真实 committed KV 少一个元素，最后一个 request-owned KV slot 会泄漏。

**新的 ownership contract**

```text
[0, cache_protected_len)              -> cache-owned，必须保留
[cache_protected_len, kv_len_to_handle) -> request-owned committed KV，必须释放
[kv_len_to_handle, allocated_end)     -> over-allocation，由 release_kv_cache 处理
```

修复后直接从 `req_to_token` mapping 取 KV indices，再调用 allocator `free_segment`，不再依赖 output token 数量间接判断 KV 生命周期。

**相关代码**

- `python/sglang/srt/mem_cache/radix_cache.py`
- `test/registered/unit/mem_cache/test_decode_radix_lock_ref.py`

**面试启发**

这是典型的“**业务状态 ≠ 资源 ownership 状态**”问题。Spec decoding、异步 sampling、P/D failure path 越复杂，越不能用 token list、HTTP response 状态等上层状态推导底层 KV ownership。

### [Issue #35129 — 长 Agent Session 在 DSPARK + HiCache 下稳定出现 0 prefix hit](https://github.com/sgl-project/sglang/issues/35129) — Open / Production Risk

这是今天最值得继续观察的 KV Cache issue。

报告环境是 DeepSeek-V4-Flash-0731、8×H20、TP8、DSV4、DSPARK、HiCache `write_through_selective`。生产流量里：

- 6～13 万 token 的长多轮 Agent session，每轮都出现 `#cached-token: 0`；
- 同一时间的短请求 prefix hit 可到约 98%；
- 抓包确认相邻 turn 有 70%～75% byte-level common prefix；去掉移动的 `cache_control` 后，至少 53% body 是 byte-identical stable prefix；
- 5 小时内 eviction token 数约为 uncached input 的 **14×**，但 peak full-token usage 只有 **0.08**；
- HiCache load-back 几乎没有发生。

Reporter 进一步给出源码级假设：SWA tombstone match validation、full→SWA mapping 在 chunk front 被清零、以及 device-only SWA/HiCache 语义之间可能形成链式 veto，最终把长前缀 match 截断到 0。**这一因果链目前仍是 reporter analysis，并非 maintainer 已确认结论。**

这个 issue 很重要，因为它说明 cache correctness 不只表现为“错误输出”或 OOM，也可能表现成 **silent cache effectiveness collapse**：模型完全正确，但 TTFT、GPU 算力和 cache churn 全部恶化。

## 2. Prefill / Decode Disaggregation

### [#35070 — PD: Avoid unused PREBUILT prompt tensor transfer](https://github.com/sgl-project/sglang/pull/35070) — **Merged**

这是过去 24 小时里最明确的已合入 P/D 性能收益。

**问题**

Decode 侧 `PREBUILT` batch 本身不会进入 model forward，但 `prepare_for_prebuilt` 仍然会：

1. 读取所有 transferred prompt；
2. flatten；
3. 构造 CUDA `input_ids`；
4. 随后在 first decode step 又从 relay metadata 重建真正输入。

也就是说，长上下文 P/D 请求每个 PREBUILT step 都在做一次完全无用的 prompt H2D/构造。

**核心改动**

- `extend_num_tokens` 直接从已有 `extend_range` 计算；
- PREBUILT 阶段令 `input_ids = None`；
- cache locations、seq lens、req-pool indices、sampling metadata、relay semantics 不变。

**性能**

AgentX 393-trace，Qwen3.5-397B-A17B NVFP4，24×GB300，4P+1D，concurrency 896：

| Metric | Baseline | PR | Change |
|---|---:|---:|---:|
| Exact-shape output TPS/User | 71.755 | 84.654 | **+17.98%** |
| Strict decode TPS/GPU | 3890.433 | 4385.898 | **+12.74%** |

44 个真实 PREBUILT prompt shape replay 中，无用 transfer 从 **1.690525 ms → 0.001745 ms / target-step**，GPU-visible timeline 节省约 1.689 ms。

**相关代码**

- `python/sglang/srt/disaggregation/decode_schedule_batch_mixin.py`
- `test/registered/unit/disaggregation/test_disaggregation_wire.py`

**面试启发**

P/D 性能分析不能只盯 RDMA 带宽。一个非常常见的瓶颈是 **控制面/中间态为了“方便”复制了最终不会参与 forward 的大 tensor**。先画清数据生命周期，再决定哪些 tensor 真正需要 materialize。

### [#35186 — PD: Stage MLA DCP relayout before Mooncake RDMA](https://github.com/sgl-project/sglang/pull/35186) — Open

**问题**

Prefill DCP=1、Decode DCP>1 时，每个 Decode rank 只拥有 Prefill KV token 的一个 strided subset。Mooncake legacy relayout 要求 source/destination 都连续才能合并 transfer，因此 source stride 会退化成：

```text
1 token × 1 layer = 1 RDMA descriptor
```

以 Kimi K3 MLA FP8 为例，每 token/layer 约 576 B。56K-token、DCP8、24 MLA layers 时，每个 Decode rank 约产生 **168K 个小 descriptor**，8 张 RDMA device 聚合带宽只有约 **1.23 GB/s**。

**方案**

Prefill 侧增加 opt-in GPU staging：

```text
strided source KV
   ↓ Triton byte-preserving gather
contiguous layer-major staging buffer
   ↓
page/layer granularity Mooncake RDMA
```

- 用 `uint8` gather 保证 FP8 KV byte-exact；
- 目标 full-page block 约 64 × 576 B = 36 KiB；
- 预计 descriptor/rank 从约 **168K → 2.6K**，约 64× 减少；
- staging 超过 buffer 时按 page boundary 分批；
- Triton gather 失败会熔断并回退 legacy path，RDMA transfer 错误不会被吞掉。

**注意：这里的 168K → 2.6K 是设计预期，不是已经完成的端到端 benchmark。** PR 当前仍明确标注 post-change bandwidth / TTFT 待目标 RDMA 环境验证。

**相关代码**

- `python/sglang/srt/disaggregation/common/staging_buffer.py`
- `python/sglang/srt/disaggregation/common/staging_handler.py`
- `python/sglang/srt/disaggregation/mooncake/conn.py`
- `python/sglang/srt/disaggregation/prefill.py`
- `test/registered/unit/disaggregation/test_dcp_staging_gather.py`
- `test/registered/disaggregation/test_kimi_linear_pd_dcp4.py`

**面试启发**

这是一个标准的 RDMA 性能题：**总字节数没变，为什么带宽能差几十倍？** 答案往往不是 link bandwidth，而是 descriptor 数、message size、doorbell/queue 开销、PCIe/NIC transaction 粒度以及 CPU control-plane cost。

## 3. Scheduler

### [#35084 — DCP: Drop prefill index-selection syncs by taking each rank's rows by stride](https://github.com/sgl-project/sglang/pull/35084) — Open

**问题**

DCP prefill metadata 原来用 CUDA boolean mask 选择本 rank 的 prefix KV rows：

```python
indices[indices % dcp_size == dcp_rank]
```

mask 输出长度依赖数据，会落到 `nonzero()`，从而把 surviving count 读回 host。结果是在 **每个 prefill forward 的 scheduler thread 上产生一次 device sync**。

**关键观察**

DCP allocator page 已经扩大为 `page_size * dcp_size`，Radix Tree 也按同样粒度分页，因此 prefix length 天然按 `dcp_size` 对齐。本 rank 行可以直接用 stride 得到：

```python
indices[dcp_rank::dcp_size] // dcp_size
```

这既消掉 `nonzero()` host sync，又把 gather 变成 strided view。

**验证**

DCP8 + TP8 DeepSeek-V3.1、16K input、chunked prefill、90% cache-hit workload 中，每 rank 每次比较 1,843 个真实 prefix rows，8 次调用 **0 mismatch**；profile 中对应 `aten::nonzero` 从 1 次降到 0。

**相关代码**

- `python/sglang/srt/layers/dcp/layout.py`
- `python/sglang/srt/layers/dcp/planner.py`
- `python/sglang/srt/model_executor/forward_batch_deepseek_mha_mixin.py`
- `python/sglang/srt/models/deepseek_common/attention_forward_methods/forward_mha.py`

**面试启发**

GPU tensor API 看起来只是一个 mask，但 data-dependent shape 很容易偷偷引入 host sync。优化时要问：**输出 shape 能否由系统 invariant 提前推导？** 如果可以，就有机会把动态选择变成静态 stride / view。

### [#35191 — Scheduler: Cap prefill-delayer queue target by admission capacity](https://github.com/sgl-project/sglang/pull/35191) — Open

Prefill Delayer 原来用 observed `max_prefill_bs` 限制 queue accumulation target。低 QPS / trickle arrival 时，observed high-watermark 可能长期只有 1，于是每来一个请求就立刻满足 trigger，prefill 永远被打散成 tiny batch。

新逻辑优先使用配置的 `prefill_max_requests` 作为 admission capacity，只有未配置时才退回 observed `max_prefill_bs`。

这属于小改动但有明确调度含义：**batching target 应该受可用 admission capacity 约束，而不是被历史观测值自我锁死。** PR 未给出端到端 benchmark，因此目前只应视为调度策略修正，不应推断具体吞吐收益。

## 4. Speculative Decoding

### [#34890 — Spec: Publish EAGLE v2 shared-read-done at verify with staged draft-extend](https://github.com/sgl-project/sglang/pull/34890) — Open / 本窗口继续更新

这条 PR 不是今天新建，但过去 24 小时继续更新，且性能结果很有价值。

**核心问题**

Spec V2 + Overlap Scheduler 中，scheduler 需要知道什么时候可以安全重写 shared request / attention metadata。原来的 WAR fence 放在 draft-extend step tail，粒度太粗；如果 draft-extend metadata 可以在 verify 前 staging，那么实际最后读取 shared state 的 phase 已经变成 target verify。

**改动**

- backend 显式声明 `supports_draft_extend_metadata_staging`；
- staged path 下，EAGLE v2 的 `last_shared_read_runner` 指向 target runner；
- shared-read-done 在 verify-time publication；
- DSV4 draft-extend 的 SWA write-location translate 移出 captured graph；
- 不能 staging 的 backend 仍在 step tail 重新 publish fence，保持旧语义。

**性能**

EAGLE、TP4、concurrency 128：

- decode throughput：**+36%**；
- forward occupancy：**65% → 94%**。

**相关代码**

- `python/sglang/srt/layers/attention/base_attn_backend.py`
- `python/sglang/srt/layers/attention/deepseek_v4_backend.py`
- `python/sglang/srt/layers/attention/flashinfer_backend.py`
- `python/sglang/srt/speculative/eagle_worker_common.py`
- `python/sglang/srt/speculative/eagle_worker_v2.py`

**面试启发**

`record_stream`、tensor lifetime 和 WAR fence 是三件不同的事。这里真正要保证的是：**scheduler 的下一次 write 必须 happens-after 当前 forward 对 shared metadata 的最后一次 read**。最优 fence 应该贴近“语义上的最后 reader”，而不是贴在整个 phase / graph 的末尾。

## 今天最值得记住的 5 个架构点

1. **DCP 带来 logical address space，任何 KV sidecar/offload pool 都不能默认 physical rows == logical capacity。**
2. **P/D 的性能瓶颈不仅是 RDMA bandwidth，还包括 descriptor 粒度、数据连续性和无用 tensor materialization。**
3. **KV ownership 应由资源生命周期直接定义，而不是从 output token 等上层状态反推。**
4. **GPU hot path 中 data-dependent shape 往往意味着隐藏的 host synchronization。**
5. **Overlap Scheduler 的 fence 应贴着真实 shared-state 最后 reader，而不是笼统贴在 CUDA Graph / phase 末尾。**
