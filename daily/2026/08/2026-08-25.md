## 1. [Merged] #32162 — HiSparse multi-step speculative swap kernel

PR: https://github.com/sgl-project/sglang/pull/32162  
状态：**2026-08-25 08:29 CST 合入**

### 解决的问题

原有 HiSparse swap 路径按 speculative step 串行处理。以四步 MTP 为例，需要重复执行四轮：

```text
cache lookup -> swap -> cache-state update
```

更麻烦的是，不同 speculative step 可能访问相同 top-k item，但旧路径无法跨 step 去重 host miss，因此会重复搬运相同数据。

### 核心改动

新的实现把 `[batch, steps, top_k]` 看成一个整体 working set，拆成两个 kernel：

- **Gather kernel**：flatten 全部 speculative step，统一查询 extra page / hot cache，跨 step deduplicate host miss，每个 unique miss 只拷贝一次到 scratch device slot。
- **Commit kernel**：按 request 更新 CLOCK cache、scratch/hot slot、token→slot hash table，并处理 overflow。

这两个 kernel 之间需要 grid-wide completion，因此在支持的 Hopper GPU 上使用 Programmatic Dependent Launch。

一个值得注意的语义设计是：**当前 attention call 的 resolved device location 保证精确；只有当 unique working set 超过 hot-cache capacity 时，对“下一次调用的 cache admission”允许近似。** 也就是说，近似策略不能污染当前请求 correctness。

### 性能结果

H20，CUDA Graph，4 speculative steps，top-k=2048，4096-entry hot cache，576-byte MLA cache item，约 782 unique misses/request：

| 指标 | 原路径 | Multi-step | 改善 |
|---|---:|---:|---:|
| Batch-64 latency | 794.42 µs | 411.85 µs | **-48.2%** |

- `python/sglang/kernels/jit/csrc/kvcacheio/hisparse_spec.cuh`
- `python/sglang/kernels/jit/csrc/kvcacheio/hisparse.cuh`

### 对 AI Infra 面试的启发

这是一个很典型的 **“把 speculative dimension 暴露给 cache subsystem”** 的优化。可以深入讨论：为什么逐 step 调用看起来模块化，却会丢掉跨 step deduplication 与 batch-level locality；以及为什么 cache policy 可以近似，但当前调用的数据定位不能近似。

## 2. [New] #36232 — Refactor HiCache host pool management

PR: https://github.com/sgl-project/sglang/pull/36232  
状态：Open；2026-08-25 07:00 CST 新建，今天持续更新

### 解决的问题

HiCache 的 host memory 已经同时承担至少三类职责：

1. L3 storage ↔ L1 GPU 的 staging；
2. L2 cache retention；
3. 多种模型状态的 backup / restore。

旧接口仍把它抽象成“一块 physical KV pool”，因此每增加一种 state 都会出现 controller 特判。Draft KV 就是最明显的例子：有独立 registration、allocation、storage I/O、transfer 和 cleanup 分支。

### 核心改动

PR 把原来混在一起的概念拆成三层：

| 层次 | 责任 |
|---|---|
| Physical host pool | buffer、layout、free list、pool-specific allocation |
| `PoolEntry` | 一个逻辑 pool 的 host/device pool、layer mapping、allocation/eviction callback、index ownership、packed draft view |
| `HostPoolGroup` | 跨 pool 的 allocation、free、transfer resolution/release、capacity 与 lifecycle 协调 |

关键设计包括：

- 设一个 **anchor entry**（通常是 KV），提供兼容属性和默认 allocation target；
- SWA、Mamba 等作为独立 `PoolEntry`；
- `indices_from_pool` 表示 derived sidecar 复用另一个 pool 的 index ownership；
- `resolve_host_transfers()` 可以对多个未分配 pool **原子分配**，任何一个失败则 rollback 前面已经成功的 allocation；
- Draft KV 不再使用 `has_draft / mem_pool_host_draft / has_mtp_draft` 等 controller 特判；
- packed MTP draft state 可以直接挂在已有 entry 的 storage 上，而不是强制拥有独立 host allocation。

该 PR 只面向 `UnifiedRadixCache`，legacy HiRadixCache 明确不进入这套新接口。

### 工程影响

这是管理层重构，没有给 performance benchmark，但代码量 **净减少 152 行**（352 additions / 504 deletions），更重要的是它在清理 state-specific control flow。

它为后续这些组合打基础：

```text
FULL KV
SWA KV
Mamba recurrent state
Spec draft KV
L3 storage sidecar
retraction backup
```

不再要求每种 state 单独修改 cache controller。

## 3. [Active] #33091 — Shared-capacity-aware eviction for Unified Memory

PR: https://github.com/sgl-project/sglang/pull/33091  
状态：Open；今天继续更新

### 解决的问题

UnifiedRadixCache 的 FULL / SWA / Mamba component 共享 physical memory。旧的 allocation-driven eviction 使用 component-local shortfall：

```text
“FULL 还差 N 个 token” -> 继续 evict FULL prefix
```

但某次 eviction 可能顺带触发 peer state compaction，已经释放了足够共享容量。旧逻辑仍会按原始 shortfall 继续删除可复用 prefix，造成 over-eviction。

### 核心改动

把两类语义拆开：

- `evict()`：保留显式“按组件数量完成淘汰”的语义；
- `evict_for_alloc()`：面向 allocation，只要 shared allocator 已经足够满足 pending allocation 就提前停止。

并把 KV、Mamba、P/D Decode、HiCache load-back、streaming session 等 allocation-driven 路径切到新接口。

### 性能 / Cache retention

RTX 5090，Qwen3.5，受控 cache pressure：

| 指标 | Baseline | PR | 改善 |
|---|---:|---:|---:|
| Prefix retained | 10 / 28 | 19 / 28 | **+90%** |
| Cache survival | 35.7% | 67.9% | **+32.2 pp** |
| Reused cached tokens | 3,840 | 7,296 | **+90%** |

Qwen3.5-4B 六次重复：

- 28 个 replay 总 E2E：`4.105s -> 2.548s`（**-37.9%**）
- mean replay prefill：`105.65ms -> 59.54ms`（**-43.6%**）

30-request shared-prefix fan-out，concurrency=6：

- prefix hit：`24/30 -> 30/30`
- p95 E2E：`1.445s -> 1.208s`（**-16.4%**）
- mean prefill：`167.3ms -> 101.6ms`（**-39.3%**）
- p95 prefill：`516.4ms -> 251.6ms`（**-51.3%**）

## 4. [Active] #33863 — PP support for P/D + DSpark

PR: https://github.com/sgl-project/sglang/pull/33863  
状态：Open；今天继续更新

### 解决的问题

没有 Pipeline Parallelism 时，P/D + DSpark 可以在 Prefill 侧捕获 target hidden state、生成 draft KV，再把 `target KV + draft KV` 发送给 Decode。

但 PP 下 target hidden states 分散在不同 stage。每个 stage 独立做 DSpark context projection 并不等价，因为 **RMSNorm 必须在完整 context projection 累加之后执行**。

### 核心设计

这个 PR 非常值得关注的一点是：**它没有扩大 P/D 边界的数据面。**

P/D 仍然保持：

```text
Prefill -> target KV + draft KV -> Decode
```

不传 hidden states。

每个 PP stage 先计算自己的局部贡献：

```text
ctx_i = h_i @ W_i.T
ctx_acc = recv_ctx_acc + ctx_i
```

最后一个 PP stage 再做：

```text
RMSNorm(ctx_acc)
-> KV projection
-> write draft KV
```

因此额外 PP payload 始终是 `[num_tokens, hidden_size]`，而不是把所有 layer hidden states 沿 P/D 边界搬过去。

### 今天值得注意的 correctness contract

PP stage 可能暴露不同 state component layout。例如 final PP rank 可能有：

```text
target SWA, draft SWA
```

Decode rank 可能是：

```text
target SWA, target C128_STATE, draft SWA
```

如果按 list index 匹配：

```text
source state[i] -> dest state[i]
```

就会把 draft SWA 错写进 target C128 state。

新的方案改为按：

```text
(StateType, occurrence)
```

匹配 Mooncake / NIXL state component，并为 mixed-version peer 保留 positional fallback。

此外，PP control plane 采用：

- 成功：ordered intersection；
- 失败：ordered union；
- 任一 stage failure -> global failure；
- local transfer 到 terminal state 前不释放 KV。

### Accuracy

H20 验证结果：

- MMLU：0.878
- GSM8K：0.945
- GPQA：0.961
- AIME25：98.33% ± 2.11%

当前 scope：支持 `PP + DSPARK + PD prefill`；尚不支持 PP + DSPARK Decode / unified serving / context parallelism。

### 相关代码

- `python/sglang/srt/speculative/dspark_components/dspark_worker_v2.py`
- `python/sglang/srt/speculative/dspark_components/dspark_kv_inject.py`
- `python/sglang/srt/models/deepseek_v4_dspark.py`
- `python/sglang/srt/disaggregation/prefill.py`
- `python/sglang/srt/disaggregation/utils.py`

这个 PR 可以提炼出两个高价值问题：

1. **什么时候应该跨 P/D 传中间 activation，什么时候应该在 Prefill 内部先完成分布式 reduction？**
2. **分布式 state descriptor 为什么必须带类型身份，而不能依赖各 rank 恰好拥有相同 list layout？**

## 5. [New Issue] #36140 — DFLASH 尚不支持 P/D Disaggregation

Issue: https://github.com/sgl-project/sglang/issues/36140  
状态：Open；2026-08-24 12:36 CST 创建

### 现象

DFLASH 在 Decode 侧开启 P/D 时，第一层问题是：

```text
batch.spec_info is None
```

因为 `build_disagg_draft_input()` 目前支持 EAGLE / DSPARK，却没有 DFLASH wiring。

但更重要的是：即使本地补上 `spec_info`，真实请求仍然会 hang，最后 watchdog 自杀退出。

### 真正的架构问题

DFLASH 的 draft 依赖 Prefill 阶段捕获的 **per-layer target aux hidden states**，这些 hidden states 用来向 draft layer KV cache 注入状态。

当前 P/D：

- 会传 target KV；
- 不会传 DFLASH draft-side injected KV；
- 现有 `hidden_states_tensor` 只覆盖 EAGLE 风格的 final hidden state，不包含 DFLASH 的 multi-layer aux hidden。

因此 DFLASH 的 first-step draft 并不是：

```text
target KV + bonus token -> draft state
```

的闭包。

### 工程含义

后续需要在三种方向里明确选择：

1. P/D 传 multi-layer aux hidden；
2. Prefill 直接构建并传 injected draft KV；
3. 在支持完整协议前明确拒绝 `DFLASH + P/D`，而不是 crash/hang。

### 对 AI Infra 面试的启发

判断一个 speculative algorithm 是否能与 P/D 组合，不能只问“KV transfer backend 支不支持”。更核心的问题是：

> **Decode 侧恢复 draft execution 所需的 state closure 是什么？这些状态能否由 target KV + token metadata 重建？**

EAGLE、DSPARK、DFLASH 的答案并不相同。

## 6. [Active] #35300 — Target-only mixed chunked prefill for DSpark

PR: https://github.com/sgl-project/sglang/pull/35300  
状态：Open；今天继续更新

### 解决的问题

此前 DSpark 会强制关闭 mixed chunked prefill。结果是长 Prompt 在连续 Prefill chunk 执行期间，正在 streaming 的 decode request 可能完全不前进，导致 ITL max / P90 出现尖峰。

### 核心改动

这个 PR 没有尝试在 MIXED batch 里执行完整 DSpark draft/verify，而采用一个更保守的最小服务量：

```text
Prefill request: normal extend
Running DSpark request: advance exactly 1 target-only token
Next decode batch: resume normal speculative verify
```

Overlap Scheduler 下还需要：

- 从 `FutureMap` resolve authoritative sequence length；
- 把 mixed token 放到 reserved verify window 的第一个 KV slot；
- 先 snapshot committed prefix length，再把 forward-facing seq_len +1；
- 对跳过常规 seq-len D2H 的 attention backend，只在真正构造 mixed batch 时 materialize 很小的 CPU mirror；
- target-only token 需要单独 settle 到 `kv_committed_len`。

### 性能 / QoS

测试 workload：512 prompts，随机 ISL≈32768、OSL=512、concurrency=16。PR 给出的 profiling 显示 **maximum ITL 显著下降**。作者没有提供可引用的文本数值，因此这里不做数字外推。

### 相关代码

从 diff 看，改动集中在：

- DSpark server args/config handling
- `ScheduleBatch` mixed preparation
- scheduler batch-result processing
- prefill stats / overlap sequence-length relay

### 对 AI Infra 面试的启发

这是 Scheduler QoS 的经典问题：吞吐最优并不等于 tail latency 最优。一个长 Prefill job 如果能无限占据 GPU，decode streaming 的 ITL 会很差。这里的“每个 mixed batch 至少推进 1 个 target token”可以理解为 **minimum service quantum**。

## 7. [Active] #35670 — DSpark compact verify graph + folded verify epilogue on Ascend NPU

PR: https://github.com/sgl-project/sglang/pull/35670  
状态：Open；今天继续更新

### 解决的问题

Ascend DSV4 的 DSpark 路径仍有两类额外开销：

1. SPS 已经为每个 request 选了更短 verify length，但 target model 仍按统一最大 window 做 verify；
2. accept/finalize 以及部分 hidden/KV commit 仍留在 graph 外的 host path。

### 核心改动

- 根据 per-request verify length 构造 compact/ragged verify window；
- target-verify CUDA Graph/NPU Graph 按 compact token tier 选择 replay graph；
- 固定 graph-owned buffer，但 replay 前刷新 seq_len、page table、compressor location/state、sparse index 等 live metadata；
- 增加 NPU-local bucketed layout cache；
- 把 greedy accept/finalize 与可安全执行的 hidden/KV commit 折叠进 verify graph；
- grammar、sampling、logits adjustment 等非 graph-safe 情况继续走 eager fallback。

### Accuracy / Performance

- GPQA-Diamond：**0.91**
- 暂无独立 speed number。

预期收益来自两部分：**少 verify 不必要的 token + 少 host/kernel launch boundary**。

### 对 AI Infra 面试的启发

CUDA/NPU Graph 优化的下一阶段不是“把 forward 放进 graph”这么简单，而是：

> **哪些 scheduler/spec state transition 可以安全地折叠进 graph，同时保留动态 logical layout？**

固定物理 buffer 与动态 ragged request layout 可以共存，但 metadata ownership 必须非常清楚。

## 8. [New RFC] #36224 — First-Class, Versioned KV Hint Envelope

RFC: https://github.com/sgl-project/sglang/issues/36224  
状态：Open；2026-08-25 06:17 CST 创建

### 为什么重要

Agentic workload 的 orchestrator/router 往往知道 engine 本身不知道的信息：session 生命周期、trajectory 分支、哪些上下文之后大概率不会再使用、哪些 prefix 值得提前恢复。

过去可以靠 ad-hoc request field 把这些 hint 塞进 SGLang，但这不是稳定 API。

### 提议的接口

RFC 定义版本化 `KvHints` envelope：

```json
{
  "protocol_version": "0.1",
  "message_id": "...",
  "actions": [
    {
      "action_id": "...",
      "action_type": "kv.demote",
      "action_version": "1.0",
      "payload": {}
    }
  ]
}
```

关键语义：

- envelope version 与 action version 独立演进；
- `action_id` 作为幂等键；
- hint 是 request metadata，不是 sampling parameter；
- malformed / unsupported envelope 在 ingress 拒绝；
- 某个 action unsupported 不影响同 envelope 里的其他 action；
- handler 必须 bounded + fail-open：hint 失败只能退回正常 cache lookup/recompute，不能影响 generation correctness。

首批计划动作：

- `kv.deref@1.0`：完成 session 后释放本地 reusable KV；
- `kv.demote@1.0`：把 eligible snapshot 发布到 storage，再让本地 leaf 可回收；
- `kv.prefetch@1.0`：即使低于常规 threshold，也请求正常 HiCache restoration。

传播链计划是：

```text
HTTP / native gRPC
-> GenerateReqInput
-> tokenizer / IPC request struct
-> scheduler Req
-> KvHintManager
-> radix cache / HiCache / storage backend
```

### 对 AI Infra 面试的启发

这是非常好的“Router 与 Engine 的职责边界”题：

- Router 可以提供 **intent**；
- SGLang 仍拥有 scheduling / allocation / eviction / transfer / failure handling；
- 协议需要 versioning、idempotency、capability discovery、telemetry 与 fail-open semantics。

它避免了两种极端：Router 完全看不到 cache；或者 Router 直接远程操纵 allocator 内部结构。

## 对 AI Infra 面试 / 项目实践的启发

今天最适合拿来准备的几个问题：

1. **多种逻辑 cache/state 共享 host memory 时，allocator 的 API 应该按“pool”还是按“request transaction”设计？如何保证部分 allocation 失败后的 rollback？**
2. **为什么 shared-memory allocator 的 eviction 停止条件不能只看某一个 component 的 token deficit？**
3. **如何判断一种 speculative decoding 算法是否天然兼容 P/D？需要传哪些状态才能在 Decode 侧闭包重建？**
4. **PP 各 stage state layout 不同，为什么 `(StateType, occurrence)` 比位置索引更可靠？更进一步，descriptor 应不应该版本化？**
5. **长 Prefill 与 streaming Decode 冲突时，如何同时优化 throughput 和 tail ITL？minimum service quantum、priority、preemption 各有什么代价？**
6. **Agentic Router 应该能控制 KV 到什么程度？如何设计 hint API，既利用全局信息，又不破坏 Engine 的 correctness ownership？**

一个很适合自己动手做的小项目是：实现一个 toy multi-pool cache simulator，支持 FULL/SWA/sidecar 三种 state，比较：

```text
component-local eviction
vs
shared-capacity-aware eviction
```

再加入 atomic multi-pool allocation + rollback。这个项目很容易在面试中展示你对 KV Cache 的理解已经超出“PagedAttention 的 block table”。
