## 1. KV Cache：deferred free 的 tensor aliasing 修复已合入

**PR:** [#34067 — Fix batched KV free aliasing](https://github.com/sgl-project/sglang/pull/34067)  
**状态:** ✅ Merged  
**合入时间:** 2026-08-08 18:34（Asia/Shanghai）

### 解决的问题

批量 free 为了减少 allocator 操作，会先把待释放 index 放进 `free_group`，之后再统一执行。但原实现直接保存了 tensor view；这个 view 可能指向 `req_to_token` 的某一行。

问题在于 `RadixCache.cache_unfinished_req()` 会在 prefix rematch 时覆盖这行数据：

```text
old request KV indices
        │
        └── view ──> deferred free queue
                         │
Radix rematch 覆盖原 row  │
                         ▼
                 free_group_end()
                 释放“新值”而非旧 KV
```

于是会出现非常危险的不一致：

```text
RadixCache: 认为 token 已经 eviction
Allocator: 对应 SWA / page slot 实际仍占用
```

最终表现可能是 **cache 明明还有很多可 eviction 容量，但新请求分配失败**。

### 核心改动

把 ownership 规则下沉到 allocator 边界：只要进入 deferred free queue，就立即 snapshot/clone 输入。

覆盖：

- token allocator
- paged allocator
- SWA allocator
- NPU allocator
- HiSparse allocator
- unified allocator

同时恢复 `RadixCache.cache_unfinished_req()` 直接传原始 `kv_indices` view，因为 allocator 现在自己负责取得所有权。

### 验证

Unified-cache alias reproducer：

```text
逻辑 SWA evicted / 物理 SWA freed
修复前：20 / 5
修复后：20 / 20
```

### 相关代码

重点看：

- `python/sglang/srt/mem_cache/allocator/*`
- allocator 的 `free_group` / `free_group_end`
- `RadixCache.cache_unfinished_req`

### AI Infra 面试启发

这是很典型的系统题：**延迟执行的操作不能借用一个未来可能被修改的 view。**

可以类比：

- io_uring 提交后的 buffer lifetime
- async RDMA send buffer ownership
- deferred reclamation / epoch GC
- GPU stream 上异步 kernel 的 tensor lifetime

面试里如果问“为什么逻辑 cache size 和实际可分配 KV slot 可能不一致”，这个 PR 是非常好的真实案例。

## 2. KV Cache / Unified Memory：淘汰压缩路径去掉逐项 GPU→CPU 同步

**PR:** [#34066 — batch lazy-compaction mapping lookup](https://github.com/sgl-project/sglang/pull/34066)  
**状态:** 🟡 Open

### 解决的问题

Unified Memory lazy compaction 在搬迁 survivor 时，对每个物理 slot 都做：

```python
physical_to_virtual[src].item()
```

`.item()` 会触发 GPU→CPU 同步。压力大、需要大量 compaction 时，这变成严重的 CPU/GPU synchronization hotspot。

### 核心改动

把逐项 lookup 改成：

- 一次 indexed tensor gather 获取整个 move batch 的 virtual IDs
- invalid mapping assertion 从“每 row 一次”降为“每 batch 一次”

### 性能影响

Eviction-heavy benchmark 中，Unified Memory 吞吐提升：

| 模型 | 压力配置下提升 |
|---|---:|
| Qwen3.5-0.8B | +91.6% / +128.2% |
| Qwen3.5-4B | +36.3% / +37.8% |
| Qwen3.5-9B | +20.4% / +23.6% |

Profiler 中：

```text
aten::item in _flush: 32,646 -> 18   (-99.9%)
_flush CPU time:      1060.4ms -> 68.0ms (-93.6%)
```

### 相关代码

重点看 `MultiEndedAlloc._flush` 以及：

- physical ↔ virtual mapping
- lazy compaction
- survivor relocation

测试入口：

- `test/registered/unit/mem_cache/test_multi_ended_allocator.py`

### AI Infra 面试启发

**GPU kernel 快不代表系统快。** 一个藏在 allocator slow path 里的 `.item()`，在 eviction-heavy workload 下可以把整个 cache 管理路径串行化。

看到 Python/CUDA 混合代码时，应特别敏感于：

```text
.item()
.cpu()
synchronize()
隐式 D2H scalar read
```

## 3. Scheduler：限制连续 Prefill，避免 Decode 饥饿

**PR:** [#34058 — bound consecutive prefills to protect decode](https://github.com/sgl-project/sglang/pull/34058)  
**状态:** 🟡 Open

### 解决的问题

当前 `Scheduler.get_next_batch_to_run()` 的基本策略是：只要有 eligible prefill，就优先运行 prefill。

持续 prompt-heavy / chunked-prefill 流量下，新 prefill 每轮都存在，running decode 可能长期拿不到 GPU。

生产问题 #32549 报告：

> 250+ active streams 下，大约 **24 秒才获得一次 decode batch**。

而且 DSPARK / EAGLE 都能复现。

这会同时恶化：

- TTFT：prefill 已完成也要等第一次 decode 才能吐首 token
- ITL / TPOT：已有 stream 长时间拿不到下一 decode step
- request residence time
- 活跃请求数，进一步形成拥塞正反馈

### 核心改动

新增 opt-in 参数：

```text
--max-consecutive-prefill-batches N
```

行为：

```text
N = 0：保持现在 prefill-first 行为
N > 0：连续 N 个 prefill 后，若 decode runnable，则保留一次 decode turn
无 decode 可跑：继续 prefill，不人为 idle GPU
一次 decode 完成：prefill counter 清零
```

它没有强制 mixed prefill+decode，因此仍兼容当前 EAGLE / DSPARK 的调度模型。

### 相关代码

- 新 `ConsecutivePrefillLimiter`
- `Scheduler.get_next_batch_to_run()`
- `ServerArgs.max_consecutive_prefill_batches`

### 工程影响

这是从“strict priority”向“bounded fairness”的小步演进。默认关闭，因此不会直接改变现有部署，但提供了明确的：

```text
Prefill throughput  <---- trade-off ----> Decode TTFT / ITL fairness
```

控制旋钮。

### AI Infra 面试启发

调度器不能只谈 GPU utilization / throughput。

可以从这个 PR 引出三个经典问题：

1. strict priority 为什么会 starvation？
2. 为什么降低 chunk size 不能从根本上解决 starvation？
3. bounded fairness、WFQ/token budget、deadline scheduling 各有什么取舍？

## 4. P/D + Scheduler + Spec：两类跨 CUDA stream 的 silent corruption

这两条 PR 很值得一起读，因为本质都是 **异步所有权/顺序错误，而不是数值算法错误**。

### 4.1 PR #34076：forward stream 还在读，tensor 已被 scheduler 释放/复用

**PR:** [#34076 — Pin overlap batch tensors freed while forward-stream kernels still read them](https://github.com/sgl-project/sglang/pull/34076)  
**状态:** 🟡 Open

发现两处 use-after-free seam：

#### Seam A：Spec-V2 mid-forward rebind

`_forward_isolation` 在 forward 前 snapshot `ScheduleBatch`，结束时恢复；但 Spec-V2 会在 forward 中把 `input_ids` / `out_cache_loc` 等字段 rebind 到新 tensor。

恢复旧 snapshot 时，新 tensor 的最后一个 Python ref 被丢掉，但 forward stream 上已 enqueue 的 kernel 可能仍在读取。

#### Seam B：`mix_running_indices`

Schedule stream 已经认为索引 tensor 生命周期结束并释放，而 forward stream 的 gather 尚未执行；caching allocator 可以把同一 block 分给下一次 allocation。

于是 kernel 读到的是**合法地址上的新内容**，不会 crash，只会产生错误 token。

### 修复

- `_forward_isolation` restore 前，把 post-forward 当前 attr 再 pin 进已有的 2-iteration lifetime ring
- 对 `mix_running_indices` 调用 `record_stream()`，让 allocator 知道 forward stream 尚未使用完

这是 CUDA/PyTorch 异步内存生命周期的标准正确姿势。

### 4.2 PR #34077：旧请求的 relay tail write 覆盖新请求 staging

**PR:** [#34077 — Fence relay staging writes behind the in-flight forward's tail relay writes](https://github.com/sgl-project/sglang/pull/34077)  
**状态:** 🟡 Open

### 解决的问题

同一个 `req_pool` row 可能先属于旧 request，随后被 scheduler 释放并马上分给新 request。

但此时存在两个 stream：

```text
forward stream: 旧 request 的 tail publish/stash 尚未执行完
schedule stream: 新 request 已开始 bootstrap staging
```

如果顺序变成：

```text
new staging write
old tail write   <- 后到，覆盖新 request
```

新请求第一次 resolve 会读到旧 owner 的：

- bonus token
- top-k
- seq_len

仍然是“值都合法，但语义属于另一个请求”的 silent corruption。

### 受影响路径

- P/D decode bootstrap（non-spec）
- EAGLE P/D speculative bootstrap
- HiSparse staging → decode rebuild

### 核心改动

`FutureMap` 增加 staging fence：

```text
H2D payload materialize
       ↓
schedule_stream.wait_stream(forward_stream)
       ↓
publish / stash
```

注意 fence 特意放在 H2D **之后**，避免把 pageable H2D 也阻塞在等待 forward 的路径上。

### 验证

测试可稳定重现：

```text
期望新请求: (bonus, seq_len) = (222, 9)
无 fence:    读到旧请求         = (111, 40)
```

修复后 10/10 测试通过；steady-state decode 不增加额外 fence，因此设计目标是不影响 TPOT。

### 相关代码

- `python/sglang/srt/managers/overlap_utils.py`
- `python/sglang/srt/managers/scheduler.py`
- `python/sglang/srt/disaggregation/decode_schedule_batch_mixin.py`
- `python/sglang/srt/speculative/eagle_disaggregation.py`

### AI Infra 面试启发

这是非常好的“GPU 版并发 bug”案例：

> **CPU 控制流里的对象生命周期结束，不代表 GPU stream 上的消费者已经结束。**

需要区分：

- ownership：谁拥有 buffer？
- lifetime：什么时候才能 reuse？
- ordering：两个 stream 谁先写？
- visibility：event/fence 保证了什么？

`record_stream` 解决 lifetime，`wait_stream/event` 解决 ordering；二者不是一回事。

## 5. Scheduler：复用 Mamba batched boundary mask，继续压低 host overhead

**PR:** [#33477 — Reuse batched Mamba boundary mask](https://github.com/sgl-project/sglang/pull/33477)  
**状态:** 🟡 Open，本窗口内有实质更新（overlap correctness fix）

### 解决的问题

`ScheduleBatch.prepare_for_decode()` 已经批量算过 Mamba track-boundary mask，但 result processing 又逐 request 重算一次边界并调用 prefix-cache bookkeeping。

在约 1,000 running requests 的 profile 里，这个纯 host work 已经可见。

### 核心改动

- 保存当前 boundary mask 的 host copy
- overlap 下额外保存 one-step-lookahead mask
- snapshot 每个 request 的 decode batch counter
- result processing 根据 overlap 实际推进 0/1 batch 选择正确 mask
- 用 `kv_committed_len` 作为 authoritative committed boundary

这一版特别处理了旧优化 #31369 曾因 overlap / cache-hit 语义错误被 revert 的问题。

### 性能数据

约 1,000 running requests：

```text
_mamba_check_track_boundary: 10,174 calls / 18.20 ms -> 0
_mamba_prefix_cache_update:  10,174 calls / 31.47 ms -> 22~34 calls / 0.07~0.09 ms
process_batch_result_decode: 27.11 ms -> 24.19 ms (-10.8%)
```

BS=1024、3000 decode steps 的 method-level benchmark：

```text
1.8672 ms/step -> 1.5155~1.5260 ms/step
约 -18.3% ~ -18.8%
约省 0.35 ms / decode step host time
```

### AI Infra 面试启发

低延迟 decode 下，CPU scheduler 的 0.3ms 不是“小数点误差”。当 GPU 单步只有几毫秒甚至更低时，host bookkeeping 很容易成为 bubble。

## 6. Speculative Decoding：Paged DSA index cache 在 tree decoding 下的地址语义修复

**PR:** [#34140 — Preserve paged DSA index cache during tree decoding](https://github.com/sgl-project/sglang/pull/34140)  
**状态:** 🟡 Open  
**创建:** 2026-08-09 08:52（Asia/Shanghai）

### 解决的问题

DSA speculative decoding 在：

```text
speculative_eagle_topk > 1
page_size = 64
```

时，需要复制 tree branch 的 partial-prefix page。

`IndexKeyCache.move()` 接收的是 **physical token-slot ID**，但真正的 index cache 存储布局是 page-major：

```text
[num_pages, page_size * payload]
```

旧实现却直接把 token slot 当 page row：

```python
index_k[tgt_loc] = index_k[src_loc]
```

这是地址语义错误，不只是 off-by-one。

MI355X 上约 27K aggregate sequence tokens 后出现 HSA hardware exception；CUDA 的 page-64 layout 也具有相同潜在问题。

### 核心改动

新增 `MoveKAndS`：

```text
physical token slot
      ↓
(page, offset)
      ↓
copy 128-byte FP8 index key + 4-byte FP32 scale
```

并且：

- ROCm 保留 AITer 16×16 preshuffled K layout
- CUDA 保留 row-major layout
- 先 gather 到 scratch，再 scatter，保证 source/destination overlap 时仍是 assignment semantics

### 相关代码

- `python/sglang/kernels/ops/attention/dsa/index_buf_accessor.py`
- `python/sglang/srt/mem_cache/index_key_cache.py`
- `python/sglang/srt/mem_cache/dsa_cache_layer_split.py`
- `test/registered/kernels/ops/attention/test_dsa_index_cache_move.py`

### 验证

- MI355X：4/4 paged move cases pass
- GB300：4/4 pass
- GB300 EAGLE top-k 2 workload：357,376 completion tokens，0 server exception
- ROCm combined stack：317,649 completion tokens，0 server exception

### AI Infra 面试启发

Paged KV/index cache 最容易出现的错误之一，就是把：

```text
logical token index
physical token slot
page id
page offset
```

混成同一种 ID。面试解释 PagedAttention / KV allocator 时，最好主动强调这几个 namespace 的映射关系。

## 7. DSpark：shared-expert 加载回归导致 acceptance rate 与吞吐暴跌

**PR:** [#34139 — DeepSeek V4 DSpark shared-expert loading performance regression](https://github.com/sgl-project/sglang/pull/34139)  
**状态:** 🟡 Open  
**创建:** 2026-08-09 08:28（Asia/Shanghai）

### 解决的问题

在 #33889 把 shared-expert fusion 改成 model-local 后，DSpark draft model 可以构造 fused shared-expert slot；但它的 checkpoint loader 实际只支持单独的 `shared_experts.*` 权重。

```text
Draft acceptance: 39.69% -> 13.59%
Accepted tokens / verify: 2.984 -> 1.680
```

### 核心改动

对 `DeepseekV4ForCausalLMDSpark` 明确禁用 unsupported shared-expert fusion，并增加 target/draft construction isolation regression test。

### 性能影响

2× RTX PRO 6000 Blackwell Max-Q，TP2，DSpark block size 5：

| 并发 | 修复前 | 修复后 | 提升 |
|---:|---:|---:|---:|
| 1 | 104.7 tok/s | 200.1 tok/s | +91.1% |
| 2 | 164.1 | 299.1 | +82.3% |
| 4 | 244.7 | 432.2 | +76.6% |
| 8 | 344.1 | 593.7 | +72.5% |
| 16 | 535.7 | 909.9 | +69.9% |
| 32 | 777.1 | 1318.4 | +69.7% |

### AI Infra 面试启发


## 8. 风险追踪：DSpark corruption 在 B300 + 官方 v0.5.17 上得到高概率复现

**Issue:** [#33800 — DSpark output corruption](https://github.com/sgl-project/sglang/issues/33800)  
**状态:** 🔴 Open / Production correctness risk

### 本窗口的新信息

此前 SM120 上报告的是某些 draft depth 下低概率 silent corruption。过去 24 小时新增的 B300（sm_103a）复现更严重，并且确认存在于 **官方 v0.5.17 tag**：

| 构建 / block size | corruption |
|---|---:|
| main，native block=5 | 50.5% / 39.0%（两个 cold boot） |
| main，block=4 | 4.5% |
| main，block=3 | 0% / 0.17%（各 600 次） |
| main，无 speculation | 0% |
| v0.5.17，native block=5 | **49.0%** |
| v0.5.17，block=3 | 0%（600 次） |

这次 reproducer 非常简单：固定 291-token prompt，concurrency 12，要求逐字 echo 8 个 opaque identifier；无需长时间 agent workload，几秒内即可触发。

### 当前判断要谨慎

SM120 的一条已确认 root cause 是 non-TileLang mHC combine fallback 把大临时 tensor 分配进 NCCL symmetric memory pool，可能与 in-flight collective buffer 发生冲突；相关最小修复见 [#34021](https://github.com/sgl-project/sglang/pull/34021)，#29927 的 kernel rewrite 也能规避这一分配模式。

但最新 B300 证据说明：**不能简单假设当前 stable release 的 DSpark correctness 已经覆盖所有硬件 / topology / allocator shape。** 在 #33800 完全收敛前，生产部署仍应保留 A/B correctness 与 acceptance-length 监控。

### AI Infra 面试启发

这是一个特别值得记住的例子：

> speculative decoding 理论上 distribution-preserving，但实现中的 cache/state/collective corruption 可以让错误结果仍以正常 HTTP 200、正常 finish_reason 返回。

所以生产 correctness 不能只靠 crash/error rate，需要：

- spec-on vs spec-off deterministic A/B
- acceptance length 异常监控
- state/KV invariant
- 长上下文/不同 batch shape 的 stress test

## 今日可复述的系统设计观点

- **Deferred operation 必须明确 ownership。** 保存 view 不等于保存值；异步 free/send/copy 都要考虑 source 是否会被改写。
- **GPU 异步系统里 lifetime 和 ordering 是两个不同问题。** `record_stream` 防止 allocator 提前复用；event/wait/fence 解决跨 stream 先后关系。
- **Cache 的逻辑 accounting 必须和物理 allocator 保持一致。** 否则 eviction 指标再漂亮也可能真实 OOM/分配失败。
- **Prefill-first 是 throughput policy，不是公平 policy。** 持续到达下它可以让 decode 无限饿死，需要显式 bounded fairness 或更完整的 token/deadline scheduler。
- **Speculative decoding 的核心指标不只是 draft latency，而是 acceptance × verify × state correctness 的系统乘积。** acceptance 下跌和 silent state corruption 都会把理论 speedup 直接吃掉。
