## 今日结论

今天的主线可以概括成一句话：**SGLang 正把“缓存容量、调度决策和 speculative state”从静态配置，逐步变成由真实运行时状态驱动的系统。**

1. **KV Cache：allocator/bookkeeping 正继续从 eager device operation 转向 lazy / capacity-aware 策略。** Mamba slot free-list 不再每次释放都重建大 tensor；Unified Memory 则开始区分“显式 eviction”和“为了满足 allocation 的 eviction”，避免 peer component 已释放容量后仍继续误删可复用 prefix。
2. **HiCache：PP 下的难点已经明确是跨 stage 的控制面共识。** #27010 继续推进 PP scheduler queue event 数量同步，以及 L3 prefetch 长度的 `all_reduce(MIN)`，本质上是在保证不同 PP rank 看到同一个 cache state machine。
3. **P/D：调度正在从“外部 router 决定一切”转向“cache affinity 与 rank-local token load 分层决策”。** #35964 在 cache-off prefill 场景让 `routed_dp_rank` 退化成 hint，再由 SGLang 的 `total_tokens` scheduler 选择真实执行 rank，实测 new-prefill throughput/chip 提升 13.74%。
4. **Scheduler：DFlash/DSpark 的 replacement prefill 开始基于真实 observed demand 而不是配置容量做 batching。** #35954 明确展示了 throughput / ITL 与 TTFT 的权衡：批量替换能提升吞吐，但会主动牺牲一部分首 token 延迟。
5. **Speculative Decoding：今天最重要的变化是 #30105 正式合入。** AITER/NEXTN 在长上下文下的性能退化并不是 acceptance 下降，而是 verify 的 GQA KV traffic 放大 + draft_extend 的 split-KV occupancy starvation；修复后 88K context 的 TPOT 从 13.8 ms 降到 6.8 ms，Spec 相比非 Spec 在 1.4K～88K 区间重新保持 1.35×～1.76× 优势。
6. **另一个值得警惕的边界是 quantized KV × Spec × CUDA Graph。** 新 Issue #36010 暴露 NVFP4 KV 的 dequant workspace 依赖 host-side prefix metadata，而 Spec verify 正刻意走 GPU-only metadata 路径；这是一个不能靠“补一个 D2H”完整解决的架构冲突。

## 1. KV Cache

### [NEW] #35971 — Mamba device free-list 改为 deferred release

PR: [#35971 — perf(mamba): defer device free-list merging until allocation needs released slots](https://github.com/sgl-project/sglang/pull/35971)

**解决的问题**

`MambaSlotAllocator.free()` 过去每释放一次 slot 都会：

```python
self.free_slots = torch.cat((self.free_slots, free_index))
```

这意味着一次很小的 request release，成本却与当前整个 free-list 大小相关：`O(F + K)`。在 request turnover 较高时，这个大 tensor 重建会直接进入 scheduler bookkeeping 热路径。

**核心改动**

- `free()` 只把释放的 chunk 记录到 `release_slots`，并更新计数，热路径降为近似 `O(1)`。
- allocation 时优先使用现有 `free_slots`；只有不足时才统一 merge pending release chunks。
- 单个 pending chunk 可直接复用，多个 chunk 才一次性合并。
- 对 Mamba ping-pong mapping 先 snapshot 再释放，避免原 buffer 被清理/复用后 deferred release 读到错误 slot。
- invariant checker 开始把 pending release 算入 leak diagnosis。

**性能影响**

代表性 allocator microbenchmark：

| 场景 | Before | After | Speedup |
|---|---:|---:|---:|
| CPU pool=65,536, batch=1 | 35.33 µs | 8.98 µs | 3.93× |
| CUDA pool=65,536, batch=1 | 18.43 µs | 8.19 µs | 2.25× |

CUDA sweep 整体约 **1.79×～2.25×**；最大 CPU pool 场景最高约 **5.05×**。

**相关代码**

- `python/sglang/srt/mem_cache/allocator/mamba.py`
- `python/sglang/srt/mem_cache/memory_pool.py`
- `python/sglang/srt/managers/scheduler_components/batch_result_processor.py`
- `python/sglang/srt/managers/scheduler_components/invariant_checker.py`

**AI Infra 面试启发**

这是典型的 allocator hot-path 优化：**free 不一定要立即整理物理结构，只要 capacity accounting 是正确的，就可以把昂贵 compaction/merge 延迟到真正需要容量时。** 这和存储系统里的 delayed coalescing、LSM compaction、deferred reclamation 是同一类思想。

### [UPDATED] #33091 — Unified Memory eviction 改为 shared-capacity-aware

PR: [#33091 — Stop eviction when shared allocation capacity is sufficient](https://github.com/sgl-project/sglang/pull/33091)

**解决的问题**

Unified Radix Cache 的 FULL / SWA / Mamba component 共享物理 memory pool。旧 allocation-driven eviction 按“某个 component 自己缺多少”持续驱逐，但 eviction 一个 FULL leaf 可能顺带释放 Mamba state，并通过 compaction 让整个 shared allocator 已经足够完成本次 allocation。

如果仍按 component-local shortfall 继续删，就会 **过度 eviction 可复用 prefix**。

**核心改动**

- 保留显式 `evict()` 的原有语义。
- 新增 `evict_for_alloc()`：目标不是“删够 N 个 component item”，而是“shared allocator 已足够满足 pending allocation 就停止”。
- UnifiedRadixCache 针对 FULL / SWA / Mamba 分别检查实际 schedulable capacity。
- allocation-driven KV、Mamba、disaggregated decode、HiCache load-back、streaming session 等路径统一改走该入口。

**性能影响**

cache pressure benchmark 中：

- retained prefixes：**10/28 → 19/28（+90%）**
- cached tokens reused：**3,840 → 7,296（+90%）**
- Qwen3.5-4B replay E2E：**4.105 s → 2.548 s（-37.9%）**
- mean replay prefill latency：**105.65 ms → 59.54 ms（-43.6%）**
- concurrent shared-prefix p95 prefill latency：约 **-51.3%**

**相关代码**

- `python/sglang/srt/mem_cache/base_prefix_cache.py`
- `python/sglang/srt/mem_cache/unified_radix_cache.py`
- `python/sglang/srt/mem_cache/unified_cache/components/mamba_component.py`
- `python/sglang/srt/disaggregation/decode.py`

**趋势判断**

Unified Memory 正从“多个 cache component 共用一块显存”进一步变成真正的 **cross-component allocator**：eviction policy 不能再只看逻辑 cache tree，而必须看共享物理 allocator 的实时可分配容量。

### [UPDATED] #27010 — HiCache × Pipeline Parallelism：建立跨 stage cache-state 共识

PR: [#27010 — Fix PP inconsistency with HiCache L3](https://github.com/sgl-project/sglang/pull/27010)

**解决的问题**

HiCache + PP 下，各 PP rank 本地的 load/prefetch completion queue 和 L3 可用长度可能不同。如果每个 scheduler 独立消费本地事件，就可能让不同 stage 对同一 request 的 cache 状态产生分歧，最终 PP pipeline 失步甚至 crash。

**核心改动**

- 新增 scheduler 间的 `pp_sync`：PP0 决定本轮要消费多少个 `ack_load_queue` / `ack_prefetch_queue` 等 completion event，其他 PP stage 必须消费完全相同数量。
- prefetch thread 对各 stage 的 L3 prefix length 做 `all_reduce(MIN)`，只承诺所有 stage 都确实拥有的共同长度。
- 把 prefetch 长度同步移到新的 background `prefetch_sync_thread`，避免 scheduler 主线程直接执行不适合 PP 控制面的 collective。

**工程验证**

SWE-bench Verified：TP8 baseline 356/500，PP4×TP2 + L3 为 353/500；351 case 两边共同成功。多轮缓存 benchmark 到第 9 轮时：

- L1：hit rate 0.035，TTFT 8.92 s
- L2：hit rate 0.379，TTFT 1.86 s
- L3：hit rate **0.899，TTFT 0.29 s**

**相关代码**

- `python/sglang/srt/managers/cache_controller.py`
- `python/sglang/srt/managers/scheduler.py`
- `python/sglang/srt/mem_cache/hicache_storage.py`
- `python/sglang/srt/mem_cache/hiradix_cache.py`
- `python/sglang/srt/mem_cache/unified_radix_cache.py`

**AI Infra 面试启发**

PP 中的 cache hit 不是一个 rank-local 事实。只要一次 request 需要所有 stage 协同执行，**可复用 prefix 的长度也必须是一个 distributed consensus value**；最安全的语义通常是所有 stage 的 intersection / minimum，而不是最快 stage 的本地结果。

## 2. Prefill / Decode Disaggregation

### [NEW · DRAFT] #35964 — Cache-off P/D Prefill 增加 token-load-aware DP routing

PR: [#35964 — Add load-aware cache-off DP prefill routing](https://github.com/sgl-project/sglang/pull/35964)

**解决的问题**

外部 DP-aware router 可以携带 `routed_dp_rank`，过去这个 rank 在 `DataParallelController` 中是 authoritative 的。但在 **RadixCache 已关闭** 的 P/D Prefill 场景，没有 prefix affinity 需要保持，此时按 request 数平均并不等于按 token 工作量平均。

实际 workload 中曾出现：

```text
DP0=14.18M, DP1=5.66M, DP2=6.37M, DP3=8.07M prompt tokens
```

最重 rank 是最轻 rank 的约 2.5 倍；DP attention + EP MoE 下，这会转化成其他 rank 的全局等待。

**核心改动**

新增 `--enable-dp-prefill-load-aware-routing`，仅允许：

- DP attention
- `disaggregation-mode=prefill`
- DP size > 1
- RadixCache disabled
- `load-balance-method=total_tokens`

在此模式中：

- 外部 `routed_dp_rank` 只作为 hint；
- SGLang 根据 worker token-load snapshot + `DPBudget` 做真实 placement；
- 实际执行 Prefill 的 rank 会注册给 Decode bootstrap，因此后续 KV transfer 仍能找到正确发送方；
- cache-on 场景明确拒绝该模式，避免破坏 prefix/session affinity。

**性能影响**

Qwen3.5-397B-A17B NVFP4、DEP4 Prefill、AgentX mixed-length workload：

| Placement | New-prefill tok/s/chip | Per-rank prompt tokens |
|---|---:|---|
| 外部 rank authoritative | 13,301.16 | [14.18M, 5.66M, 6.37M, 8.07M] |
| SGL token-load placement | **15,128.90** | [11.70M, 7.90M, 7.39M, 7.33M] |

吞吐提升 **13.74%（1.137×）**，384/384 请求完成，无 cancellation/overflow。

> 注：PR 作者明确把它定位为 paired diagnostic，而非 leaderboard 结果，因为测试时长未达到 dashboard 的完整 performance gate。

**相关代码**

- `python/sglang/srt/managers/data_parallel_controller.py`
- `python/sglang/srt/server_args.py`

**AI Infra 面试启发**

一个很重要的调度原则：**cache affinity 与 compute/load balancing 是两个目标。** 有 cache 时，路由需要优先保留数据局部性；没有 cache affinity 时，再让 rank-local scheduler 依据 token work 做二级负载均衡，通常比外部 router 只看 request count 更合理。

### [UPDATED] #33863 — PP + P/D + DSpark 继续收敛到“固定数据面 + 分布式控制面共识”

PR: [#33863 — PP Support PD + DSpark](https://github.com/sgl-project/sglang/pull/33863)

这个 PR 在窗口尾部继续活跃，是当前最值得跟踪的 composability 工作之一。

**核心设计**

P/D 边界保持不变：

```text
Prefill -> target KV + draft KV -> Decode
```

不跨 P/D 传 hidden state。PP 各 stage 只计算本地 context projection：

```text
ctx_i = h_i @ W_i.T
ctx_acc = recv_ctx_acc + ctx_i
```

最终 PP stage 再统一执行 RMSNorm + KV projection 并生成 draft KV。这利用了：

```text
concat(h1, ..., hk) @ W.T == sum_i(h_i @ W_i.T)
```

从而避免在 PP stage 之间传递不断增长的 raw hidden-state payload。

**更关键的控制面变化**

- transfer success：各 PP stage 做 ordered intersection；
- failure：做 ordered union，任一 stage 失败即全局失败；
- KV 直到本地 transfer 到 terminal state 才允许 release；
- state component 不再按 list index 对齐，而按 `(StateType, occurrence)` 匹配，避免某些 PP stage 缺少 `C128_STATE` 时把 draft SWA 错写进 target state buffer；Mooncake / NIXL 都覆盖该语义。

**当前 scope**

- 支持：`PP + DSPARK + PD prefill`
- 暂不支持：`PP + DSPARK decode`
- 暂不支持：`PP + DSPARK unified serving`
- 暂不支持：`DSPARK + context parallelism`

**相关代码**

- `python/sglang/srt/managers/scheduler_pp_mixin.py`
- `python/sglang/srt/disaggregation/prefill.py`
- `python/sglang/srt/disaggregation/utils.py`
- `python/sglang/srt/speculative/dspark_components/dspark_worker_v2.py`
- `python/sglang/srt/speculative/dspark_components/dspark_kv_inject.py`
- `python/sglang/srt/models/deepseek_v4_dspark.py`

**趋势判断**

P/D + PP + Spec 的真正难点已经明显从“数据怎么传”转向 **不同并行维度如何对 request admission / transfer completion / state layout 达成同一个决策**。

## 3. Scheduler

### [NEW] #35954 — DFlash/DSpark replacement prefill batching 改为 observed-demand-driven

PR: [#35954 — Prevent one-at-a-time DFlash/DSpark replacement prefills below the request limit](https://github.com/sgl-project/sglang/pull/35954)

**解决的问题**

旧逻辑用 `--max-running-requests` 推导 replacement batching threshold，却拿这个 threshold 去和“全部可分配 request-pool slot”比较。

当真实 workload concurrency 低于配置上限时，**从未使用的空闲 slot** 会立刻满足阈值，于是 replacement request 被一个一个 admit，每次都可能单独跑一次 draft prefill，失去 batching 收益。

**核心改动**

- per-rank 维护由真实 admission / active request 建立的 observed request target。
- 自动 batching 在 observed target < 8 时关闭；达到规模后等待 2～4 个 free slot 再批量补位。
- workload 扩张时立即 admission；真实 contraction 后再降低 target。
- incomplete refill 有 scheduler-pass 上限，避免为凑 batch 无限等待。
- prefill-only batch 和 priority preemption 不走这套等待。

**性能与权衡**

DeepSeek-V4-Flash DSpark TP2、concurrency=8：

| 模式 | Output tok/s | Mean ITL | Mean TTFT | Req / prefill pass |
|---|---:|---:|---:|---:|
| 不等待 | 591.29 | 11.89 ms | 241.54 ms | 1.326 |
| 自动 replacement batching | **610.91** | **11.13 ms** | 352.72 ms | **2.060** |

即：

- output throughput **+3.3%**
- ITL **-6.4%**
- 每次 prefill admission 数 **+55.4%**
- 但 TTFT **+46.0%**

**相关代码**

- `python/sglang/srt/managers/min_free_slots_delayer.py`
- `python/sglang/srt/managers/scheduler.py`
- `python/sglang/srt/server_args.py`

**AI Infra 面试启发**

这是很好的 latency-throughput tradeoff 案例：continuous batching 并不是“batch 越大越好”。Scheduler 需要区分 **steady-state decode efficiency** 和 **new request TTFT**，并根据真实 demand 而不是配置上限决定是否值得等待凑批。

### [MERGED] #30105 — AMD AITER NEXTN：修复长上下文 verify GQA traffic 与 draft_extend occupancy

PR: [#30105 — Fix AITER GQA packing + split-KV routing in NEXTN spec attention](https://github.com/sgl-project/sglang/pull/30105)

**状态：已于本窗口内合入。**

这是今天最重要的已合入性能变化。

**解决的问题**

ROCm/gfx950 + AITER + NEXTN 的 GQA MoE 模型在 context 超过约 40K 后，Spec 反而比普通 autoregressive decode 慢；但 `accept_length` 仍保持约 2.4～3.4，GPU 也有 95%～99% busy。

说明问题不在 draft quality，而在 attention kernel 路径：

1. `target_verify` 把单个 local KV head 用 `.expand()` 扩成多个 Q head，导致 `num_queries_per_kv=1`，GQA 共享 KV 的收益被破坏，接近 MHA 式重复扫 KV，约放大 7× KV traffic。
2. `draft_extend` 落到不支持 split-KV 的 prefill FMHA；此时 Q 很短而 K 很长，只有极少 Q tile，HBM 利用率约 0.2%，严重 occupancy starvation。

**核心改动**

- verify：直接传真实单 KV head，让 `unified_attention` 正确恢复 GQA group packing。
- draft_extend_v2：同样切到 `unified_attention`，同时获得 GQA packing + split-KV；用 2D block table 和 `kv_indptr` 构造实际 K length。
- 新增 `SGLANG_AITER_UNIFIED_DRAFT_EXTEND` 独立开关，便于单独回退/bisect。

**性能影响**

2×MI350X、Qwen3.5-397B-A17B MoE：

| Metric | Before | After |
|---|---:|---:|
| verify attention @88K | 272 ms | **104 ms** |
| draft_extend attention @88K | ~773 ms | **~5 ms** |
| TPOT @88K | 13.8 ms | **6.8 ms** |
| Spec vs non-Spec | >40K 后变慢 | **1.4K～88K 全程快 1.35×～1.76×** |

中等 batch（conc 4～16）下，MXFP4 / FP8 两类权重都保持约 **1.34×～1.58×** per-token speedup。

**正确性**

- old/new draft_extend logit diff：`0.000e+00`
- GSM8K 512 题：accuracy 0.971，invalid 0
- heterogeneous 2K～61K context、concurrency=8 stress：无 crash/NaN/truncation，accept length 2.73

### [NEW] #35996 — MTP draft dedup 提前到 KV pool sizing 之前，回收约 38% KV capacity

PR: [#35996 — Fix MTP draft embed/lm_head dedup running after KV pool sizing](https://github.com/sgl-project/sglang/pull/35996)

**解决的问题**

NEXTN/MTP draft 起初拥有自己的 `embed_tokens` / `lm_head`，后续会与 target 共享并释放重复权重。但旧初始化顺序是：

1. 先根据当前 free memory 给主 KV pool 定容量；
2. 后面才 dedup draft embed/lm_head 并 `empty_cache()`。

因此虽然最终释放了约 2.5 GB VRAM，KV pool sizing 已经结束，这部分显存整个进程都无法转化成 KV capacity。

**核心改动**

把 `init_token_map()` / `init_lm_head()` 提前到 `EagleWorkerV2.__init__` 末尾，确保在 target memory pool sizing 之前先完成共享与释放。

**性能 / 容量影响**

RTX 4090D 48 GB、Qwen3.5-27B FP8 + NEXTN：

```text
max_total_num_tokens: ~273K–286K -> 397K
```

约增加 **111K token / ~38% KV capacity**。

**相关代码**

- `python/sglang/srt/speculative/eagle_worker_v2.py`

**面试价值**

初始化顺序本身就是 memory allocator policy。**任何会释放大块 persistent memory 的 dedup / weight sharing，都应该发生在 KV capacity sizing 之前**；否则“显存最终空出来了”并不等于 allocator 会重新规划它。

### [NEW ISSUE] #36010 — NVFP4 KV × Spec：GPU-only metadata 与 host-side dequant workspace 冲突

Issue: [#36010 — NVFP4 KV cache + speculative decoding: extend_prefix_lens_cpu is None](https://github.com/sgl-project/sglang/issues/36010)

**现象**

`--kv-cache-dtype nvfp4` 与 NEXTN/MTP 组合时，target verify 会在 FlashInfer dequant workspace 路径崩溃：

```text
TypeError: 'NoneType' object is not subscriptable
```

- CUDA Graph 开启：server 在 graph capture 阶段就失败。
- CUDA Graph 关闭：server 可以启动，但第一个请求的 runtime target-verify 仍失败。

**根因**

Spec verify 为了避免每步 D2H，同步构造的是 GPU-only `ForwardBatch`，故意不填：

- `extend_prefix_lens_cpu`
- `extend_seq_lens_cpu`

但 NVFP4 FlashInfer dequant workspace 又要求 host-side prefix lengths 来决定哪些 KV page 需要 dequantize。

也就是说，两条各自合理的优化假设发生了冲突：

```text
Spec: verify metadata 应留在 GPU，避免每步 D2H
NVFP4 dequant workspace: page selection 需要 CPU prefix metadata
```

**为什么不能简单修**

Graph-off 可以临时补 CPU mirror，但每个 verify step 会多一次 batch-sized D2H sync；Graph-on 更麻烦，因为 capture 内不能根据 runtime host value 决定 page selection，否则 replay 会使用错误页面。

更合理的方向可能是：

- 把 workspace page planning 移到 graph 外的 metadata/plan phase；或
- 使用 fused NVFP4 extend kernel，彻底删除 host-side page-selection dependency。

**相关代码位置**

- `python/sglang/srt/layers/attention/flashinfer_backend.py`
- `python/sglang/srt/mem_cache/memory_pool.py`
- `ForwardBatch.init_new` 的 CPU/GPU-only metadata 分支

**AI Infra 面试启发**

CUDA Graph 的难点并不只是“算子能不能 capture”，而是 **captured region 的所有控制决策是否只依赖 replay-safe device state**。一旦 hot path 依赖 CPU-side dynamic metadata，就必须重构 planning boundary，而不是简单包一层 graph。

---

### 其他值得跟踪：#35985 — FA3 Spec 在 context wall 附近的 page-table headroom

PR: [#35985 — Fix FA3 page_table OOB near context wall under speculative decoding](https://github.com/sgl-project/sglang/pull/35985)

FA3 CUDA Graph 的 page table 过去只按 `context_len` 分配，但 speculative `draft_extend / target_verify` 实际会发布：

```text
cache_seqlens = seq_len + speculative_num_draft_tokens
```

因此普通 decode 尚未越界时，Spec 可能已让 block table 访问超过静态容量并触发 CUDA illegal memory access。修复方式是把 graph-side `max_context_len / max_num_pages` 显式增加 draft-token headroom。

这再次说明：**Speculative Decoding 改变的不只是一次 forward 生成多少 token，也会改变 page-table、req-to-token 和 CUDA Graph static buffer 的容量上界。**

## 6. 今天最值得记住的 AI Infra 面试 / 项目实践结论

1. **Free path 不一定要立即 compact。** 只要 accounting 正确，deferred reclamation 可以显著减少 scheduler 热路径上的大 tensor copy。
2. **共享 allocator 下 eviction 必须面向“可分配容量”，而不是单个 cache component 的逻辑数量。** 否则 collateral release 已足够时仍会过度驱逐 prefix。
3. **P/D 的路由决策应分层：有 cache 时优先 locality；无 cache 时优先真实 token work。** request count 往往不是好的 compute-load proxy。
4. **PP + Cache / P-D + Spec 的核心是 distributed state-machine consensus。** 成功取 intersection，失败做 union，release 必须等所有相关 stage 达到 terminal state。
5. **Spec acceptance 高不代表性能一定好。** verify 的 GQA packing、KV memory traffic、split-KV、occupancy 和 draft catch-up 都可能成为真正瓶颈。
6. **显存 sizing 是初始化协议的一部分。** weight sharing / dedup 必须在 KV pool capacity planning 前完成，否则释放出来的显存可能永远不会被 KV allocator 利用。
7. **CUDA Graph 逼迫 runtime 明确 planning boundary。** 如果 captured forward 依赖 CPU-only 动态 metadata，最终通常需要把决策上移到 graph 外，而不是继续加同步补丁。
