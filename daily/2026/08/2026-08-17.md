## 1. P/D：Abort 中的 KV page 不能在 transfer 完成前复用

### PR #35049 — Deferred decode-side KV release for aborts mid-transfer

- 状态：**Draft / Open**
- 链接：https://github.com/sgl-project/sglang/pull/35049
- 创建：2026-08-17 02:07（北京时间）

### 解决的问题

当前 P/D 中，如果 Decode 侧请求因为 timeout、long-ITL 或 `/abort_request` 被取消，而 Prefill → Decode 的 KV transfer 仍在进行：

1. Decode 立即释放该请求的 KV pages 和 request-pool slot；
2. allocator 很快把这些页分配给新请求；
3. 旧请求尚未结束的 Prefill transfer 随后继续写这些物理页；
4. 新请求获得了被旧请求污染的 KV，**不会抛异常，只会 silent corruption**。

这也是为什么 decode 侧不能简单采用更激进的 LIFO/O(1) free-slot reuse：复用越快，race window 越危险。

### 核心改动

PR 引入一个默认关闭的 deferred-release 路径：

- Prefill 侧先将 transfer room 标记为 `Failed`，阻止继续 enqueue 新 chunk；
- 真正拥有该 room 的 transfer worker 在当前 in-flight write drain 后发送 `ABORT_ACK`；
- Decode 侧 abort 后不立即 free，而是把 request 放入 held list；
- 每个 scheduler step 早期执行 `resolve_deferred_releases()`；
- 只有收到所有被通知 Prefill ranks 的 ACK 后，才释放 KV pages / request slot；
- 若某 rank 已死亡或 ACK 丢失，则以约 30 秒 timeout 作为最终 backstop。

配置：

- `SGLANG_DISAGGREGATION_DEFERRED_DECODE_KV_RELEASE`
- `SGLANG_DISAGGREGATION_DEFERRED_DECODE_KV_RELEASE_TIMEOUT`

### 相关代码

- `python/sglang/srt/disaggregation/mooncake/conn.py`
- `python/sglang/srt/disaggregation/common/conn.py`
- `python/sglang/srt/disaggregation/decode.py`
- `python/sglang/srt/managers/scheduler.py`
- `python/sglang/srt/managers/scheduler_pp_mixin.py`
- `test/registered/unit/disaggregation/test_deferred_decode_kv_release.py`

### 工程影响

当前仍是 Draft，作者明确说明尚缺真实 P/D cluster 的 integration validation，因此**不能视为生产修复已完成**。但它揭示的 invariant 非常重要：

> `free(KV page)` 必须 happens-after 所有可能写该 page 的远端 transfer 完成。

### AI Infra 面试启发

这是非常好的“分布式存储背景 → AI Infra”面试题：**GPU KV allocator 本质上也在管理可复用存储块，一旦远端 DMA/RDMA 生命周期跨越本地对象生命周期，就需要 lease / ACK / epoch / fence 一类机制。** `record_stream` 或 Python 引用计数都解决不了跨机器写入者的问题。

## 2. P/D：KV cache 碎片化使 4.8 GB/s 降到 15.5 MB/s

### PR #35036 — Route equal-TP fragmented KV transfer through staging

- 状态：**Open**
- 链接：https://github.com/sgl-project/sglang/pull/35036

### 解决的问题

在 equal-TP 的 MHA/GQA P/D 部署中，Decode 侧经过 Radix Cache reuse 和 allocator pressure 后，目标 KV pages 可能高度不连续。

直接路径会把每个 `(fragment group × layer)` 变成独立 transfer entry。作者给出的 engine-level 数据非常夸张：

| Transfer entries | 带宽 |
|---:|---:|
| 1 | 4792 MB/s |
| 4096 | 15.5 MB/s |

这说明瓶颈不是网络 payload，而是**每个 transaction 的固定 D2H / transfer setup cost**。

### 核心改动

当检测到碎片 group 足够多时：

```text
fragmented device KV
      ↓ local gather
contiguous staging buffer
      ↓ one bulk RDMA
remote staging buffer
      ↓ scatter
fragmented decode KV pages
```

即用额外一次本地 gather/scatter，换掉数千次远端小 transfer。

相关开关：

- `SGLANG_DISAGG_STAGING_BUFFER`
- `SGLANG_DISAGG_STAGING_MIN_GROUPS`，默认 8
- `SGLANG_DISAGG_STAGING_ALWAYS`

### 性能

200 个并发 long shared-prefix requests：

| 指标 | Before | Staging | 变化 |
|---|---:|---:|---:|
| Request throughput | 1.41 req/s | 1.76 req/s | **+25%** |
| TPOT | 23.03 ms | 13.80 ms | **-40%** |
| Staging transfer | — | 90/90 成功 | 0 failures |

健康的非碎片路径约 1.47 → 1.49 req/s，基本无回退。

- `python/sglang/srt/disaggregation/mooncake/conn.py`
- `python/sglang/srt/disaggregation/decode.py`
- `python/sglang/srt/disaggregation/common/staging_buffer.py`
- `python/sglang/srt/disaggregation/common/staging_handler.py`
- `python/sglang/srt/disaggregation/common/utils.py`
- `python/sglang/srt/disaggregation/utils.py`
- `python/sglang/srt/environ.py`

### AI Infra 面试启发

这和存储系统里的 scatter-gather I/O、small I/O amplification 完全同构：

> **不要只看总 bytes，要同时看 I/O/transfer transaction 数量。**

当固定启动成本很高时，`copy + coalesce + bulk transfer + scatter` 反而比 zero-copy 小包直传快很多。

## 3. Scheduler × Spec：shared-buffer read ownership 正在变成正式 contract

### PR #35057 — Multi-layer EAGLE last shared-read owner 修正

- 状态：**已合入**，2026-08-17 06:28（北京时间）
- 链接：https://github.com/sgl-project/sglang/pull/35057

Multi-layer EAGLE 的一步是：

```text
draft organize → target verify → draft extend
```

最后读取 shared buffer 的其实是 **draft runner**，但之前从基类继承后指向 target runner。

当前由于该路径仍退化到 coarse WAR fence，作者说明这次修复暂时没有性能行为变化；但它先把 ownership contract 修对，避免后续 fine-grained fence 基于错误 owner 发布 read-done event。

- `last_shared_read_runner`
- backend 的 `shared_read_ends`

成为唯一事实来源。

NGRAM 因此可以从 whole-forward coarse fence 切换到更精确的 read-done event。

### 相关代码

#35059：

- `python/sglang/srt/model_executor/runner/decode_cuda_graph_runner.py`
- `python/sglang/srt/speculative/spec_info.py`
- `python/sglang/srt/speculative/spec_registry.py`

### 架构意义

Overlap Scheduler 的优化越来越不像“多开一个 stream”，而是在定义一个真正的并发协议：

```text
Scheduler writes shared metadata
        ↓
GPU forward reads metadata
        ↓ precise read-done event
Scheduler may mutate/reuse metadata
```

如果这个边界不由真正的 reader/backend 自己声明，中央 scheduler 很难覆盖 EAGLE、DSPARK、NGRAM、hybrid backend、wrapper backend 等组合。

### AI Infra 面试启发

可把它类比为 lock-free / RCU 系统中的 ownership contract：**调用层不应该猜资源最后在哪里被消费，真正的 owner 应声明 release point。**

## 4. Adaptive Spec：启动参数不能再作为运行时真相

### PR #35024 — Size speculative buffers from runtime bags

- 状态：**Open**
- 链接：https://github.com/sgl-project/sglang/pull/35024

### 解决的问题

Adaptive speculative decoding 可以通过 `get_context().override` 在运行时切换 step configuration，但 `ServerArgs` 仍停留在进程启动时的值。

因此此前多个路径会出现“算法已经变了，但容量规划还认为自己在旧配置”的问题，包括：

- DSA seed predicates。

### 核心改动

统一改为读取当前 runtime spec bag，把动态 spec state 当成 source of truth，而不是继续读取静态 `ServerArgs`。

## 5. KV Cache × EAGLE：SWA eviction frontier 的 key-space 语义修复已合入

### PR #34870 — Fix SWA eviction frontier for bigram keys

- 状态：**已合入**，2026-08-16 11:52（北京时间）
- 链接：https://github.com/sgl-project/sglang/pull/34870

### 问题本质

Unified Cache 在 EAGLE 下使用 bigram key。bigram key 的 entry 数量比它覆盖的 token 数少 1，因此直接拿 token-space 的 `effective_cache_len` 去计算 SWA eviction frontier，会产生 off-by-one/page-boundary 语义错误。

一个具体例子：

- `sliding_window_size=127`
- `page_size=64`
- `seq_len=1024`

此前：

| Key | Insert boundary | Eviction frontier | Live SWA tail |
|---|---:|---:|---:|
| Raw | 1024 | 896 | 128，正确 |
| Bigram | 960 | 896 | **64，不足** |

SWA tail 太短后，后续 match 失败，`cache_protected_len` 不前进，下一次 insert 会把 tree 已经拥有的 KV 当成重复块再次 free，最终出现 pool-accounting / memory-leak crash。

### 修复

先构建真正的 `RadixKey`，然后用 **key length** 而不是 token count 计算 `free_out_of_window_slots`。

修复后该案例 frontier 从 896 调整到 832，保留完整 128-token live tail。

### 验证

8×H200、gpt-oss-120b、EAGLE3：修复后无 leak；相关 Unified Radix Cache / SWA tests 合计 **1048 passed**。

### 相关代码

- `python/sglang/srt/mem_cache/unified_radix_cache.py`
- `test/registered/unit/mem_cache/test_unified_radix_cache_unittest.py`

### AI Infra 面试启发

这类 bug 的关键不是“减 1”，而是 **不同模块是否在同一个 index space 里讲话**：token index、RadixKey index、page boundary、spec tree node index 都可能不相同。AI Infra 里大量 silent correctness bug 都来自跨组件 index-space 语义混用。

## 7. Roadmap #34899：缓存正确性的判据从 accuracy 升级为 “Any nonzero KL is a bug”

- 状态：Open，过去 24 小时有更新
- 链接：https://github.com/sgl-project/sglang/issues/34899

核心思路：最终文本或 GSM8K accuracy 并不能证明 KV/state restore 正确。错误 cache block 仍可能生成流畅文本，甚至 KL 漂移很小。

Roadmap 希望在满足 deterministic + batch-invariant 前提的模型/执行路径上建立更强 contract：

> 同一 token 的 prefill 与 decode 若数学路径一致，则 logprob 应完全一致；**任何非零 KL 都视为 cache/state reuse bug。**

当前进度：

- [x] Base cache path
- [x] Mamba `extra_buffer`
- [x] Mamba `extra_buffer_lazy`
- [x] HiCache multi-turn
- [ ] Speculative Decoding
  - [ ] MTP
  - [ ] DSpark / DFlash
- [ ] Unified Memory

### 架构意义

这代表 SGLang 正把缓存正确性从“集成测试看结果像不像”变成真正的 **state restoration invariant**。随着 KV Cache 不再只是 K/V，而是同时包含 SWA、Mamba recurrent state、DSA index、spec draft state，这类 oracle 会越来越重要。

## 8. Spec target verify：去掉 QKV materialization，整体吞吐 +3.48%

### PR #33778 — Avoid materializing GDN QKV tensors during target verification

- 状态：Open；过去 24 小时更新了 profiling / benchmark 结果
- 链接：https://github.com/sgl-project/sglang/pull/33778

### 核心思路

`causal_conv1d_update` 本来已经产生 packed QKV。此前 GDN speculative target verify 又运行一次 `fused_qkv_split_gdn_prefill_kernel`，复制成三个 contiguous Q/K/V tensors。

Triton target verify 本身支持显式 stride，因此 ReplaySSM / Triton 路径可以直接使用 `torch.split` / view，不做实际 materialization；确实要求 contiguous 的 FlashInfer、CuTeDSL、Prefill 等路径保持原行为。

| QKV split GPU time | 56.946 µs | 0 | **-56.946 µs** |
| CUDA Graph kernels | 452 | 428 | **-24** |
| Graph span | 8132.684 µs | 8040.898 µs | **-1.129%** |

三组交替 GSM8K benchmark 聚合：

- output throughput：6377.324 → 6599.263 tok/s，**+3.48%**
- latency：5.373 → 5.227 s，**-2.72%**
- engine TPOT：9.776 → 9.563 ms，**-2.18%**

## 9. HiCache：L2 transfer 层的职责边界已经开始收敛

- 状态：**已合入**，2026-08-16 15:33（北京时间）

## 10. HiCache 架构观察：L2 正从 cache tier 变成 transit buffer

### PR #34798 — Buffer-only mode for HiCache host memory layer

- 状态：Open / Preview
- 链接：https://github.com/sgl-project/sglang/pull/34798

过去 24 小时该 PR 继续更新。其设计方向很值得跟：在 host memory 较小的机器上，不再强求 L2 host tier 自己维护完整 tree/cache semantics，而是把 L2 当 **I/O buffer**：

- L2 主要负责隐藏 L3 ↔ GPU 的 I/O latency；
- 更大的 L3 承担真正容量层与 hit-rate 来源；
- 避免小 L2 在压力下频繁 tree eviction / metadata churn。

目前设计文档和 benchmark 仍待补充，因此这里只作为架构信号，不当成已验证结论。

### PR #26691 — MLA Host KV 跨 TP rank 去重

- 状态：Open，过去 24 小时更新
- 链接：https://github.com/sgl-project/sglang/pull/26691

MLA 下 TP ranks 持有相同 KV。该 PR 让：

- 只有 rank 0 保存真实 host KV；
- 其他 rank 只维护 allocator bookkeeping；
- load 时 rank 0 H2D，再经独立 NCCL group broadcast 给其他 ranks。

理论 host KV memory 节省比例为：

```text
(tp_size - 1) / tp_size
```

但当前还缺 TP>1 多 GPU benchmark，而且 DSA/spec draft pool 不在支持范围，暂不视作成熟能力。

## 对 AI Infra 面试与项目实践最有价值的 6 个问题

1. **为什么一个 request 被 abort 后，KV page 不能立即 free？**  
   因为逻辑 request lifetime 结束，不代表异步 RDMA/DMA write lifetime 已结束。复用前必须建立 transfer completion 的 happens-before。

2. **为什么多一次 gather/scatter 反而能让 KV transfer 快几十到几百倍？**  
   因为小 transaction 的固定成本主导，性能模型必须同时考虑 bytes 与 operation count。

3. **Overlap Scheduler 为什么需要 backend 声明 shared-read end？**  
   scheduler 无法可靠推断 wrapper/spec algorithm 内部最后读取共享 metadata 的位置；错误 fence 会产生 WAR race 或失去 overlap。

4. **Adaptive speculative decoding 为什么会影响 KV allocator 和 CUDA Graph？**  
   draft steps/tree width 改变后，每请求 reserve、graph shape、verify input、P/D state count 都随之改变；静态启动参数会变成 stale config。

5. **为什么最终 accuracy 正常不能证明 KV cache 正确？**  
   cache/state corruption 可以只造成微小 logit drift，甚至文本完全一样。bit-exact/zero-KL 可以提供更强的 restoration oracle。

6. **为什么 stride-aware kernel 是推理优化的重要能力？**  
   很多时间浪费在“为了满足 kernel API 而 materialize contiguous tensor”，而不是数学计算本身。能直接消费 view/stride 可以减少 kernel launch、显存流量和 graph span。
