## 今日结论

今天最清晰的架构主线不是某个单点 kernel，而是 **Unified Memory 正从 allocator 内部实现，升级为贯穿 Scheduler、P/D transport 和 host offload 的系统级契约**。

新出现的一组连续 PR **#36729 → #36730 → #36731** 分别补齐了三个层次：

1. Scheduler 不再把 FULL KV 和 SWA KV 当成两个静态容量池，而是按**共享 byte budget**做联合 admission / reclaim；
2. P/D 不再直接把 Unified Memory 暴露的 virtual token id 当成可传输地址，而是显式建立 **virtual id → physical page envelope** 的转换与 transfer lifetime；
3. Decode retraction / offload 的 host pool 也改成与 device 相同的共享 byte-arena 语义，避免 host 侧重新退化成两个互不借用容量的固定池。

这组变化说明 SGLang 的 KV 管理正在进一步明确一个重要原则：**逻辑 token identity、物理 page ownership、可用容量和异步 transfer lifetime 是四个不同的概念，不能再由同一个“token 数”近似表达。**

另一条明显主线是异步执行的正确性边界继续收紧。HiCache #36738 要求 H2D load-back 在 transfer stream 上显式等待旧 forward 的最后写入；Multi-layer EAGLE #36752 则反过来把 scheduler 所需的“最后读取完成”精确发布到 final draft graph，而不是退回等待整个 forward stream。两者放在一起看，本质都是在建立更准确的 **happens-before contract**。

Speculative Decoding 侧还有一个很典型的 CUDA Graph contract 修复：#36749 暴露出 **request batch size != verify output row count**。Spec verify 的 logits 是 token-row 粒度，`bs=3, draft_tokens=4` 实际可以产生 12 行 logits；如果 CUDA Graph buffer 仍按 3 行分配，不只是性能退化，而会直接导致越界和 device-side assert。

## 1. KV Cache

### 1.1 PR #36729 — Unified Hybrid-SWA 改为共享 byte budget

**状态：Open；2026-08-28 04:54（北京时间）创建。**  
PR: https://github.com/sgl-project/sglang/pull/36729

#### 解决的问题

Unified full-attention pool 和 sliding-window pool 实际共用同一个 byte arena，但旧的 admission/capacity 逻辑仍分别按 FULL token capacity 和 SWA token capacity 判断。

这会出现一种典型的“物理内存够、逻辑容量检查却拒绝”的情况：

- FULL 一侧暂时空闲很多；
- SWA 一侧需要更多空间；
- 两者实际上可以在共享 arena 中借用 byte；
- 但静态 per-pool gate 会提前拒绝请求。

同时，metrics 如果继续报告固定 token capacity，也无法反映当前 shared arena 下某一侧真正还能兑现多少容量。

#### 核心改动

- 用显式 **shared byte budget** 初始化 unified hybrid-SWA pool；
- Scheduler admission、decode preallocation、retraction resume 都改为 FULL/SWA **joint reservation**；
- reclaim 可以从另一侧的 evictable bytes 中回收空间；
- `full_available_size()` / `swa_available_size()` 一类容量指标开始表达当前状态下的 **realizable capacity**，而不是静态上限。

#### 相关代码位置

重点建议看：

- `python/sglang/srt/managers/schedule_policy.py`
- `python/sglang/srt/managers/scheduler.py`
- `python/sglang/srt/disaggregation/decode.py`
- `python/sglang/srt/mem_cache/multi_ended_allocator.py`
- `python/sglang/srt/mem_cache/unified_memory_pool.py`
- `python/sglang/srt/model_executor/pool_configurator.py`

#### 性能 / 工程影响

PR 没有给 E2E benchmark，因为没有修改 kernel；价值主要在**提高可用容量并避免错误拒绝**。

更重要的是，Scheduler 的 admission model 开始从：

```text
FULL token count <= FULL capacity
SWA token count  <= SWA capacity
```

变为更接近：

```text
bytes(FULL reservation) + bytes(SWA reservation)
    <= shared physical budget + reclaimable bytes
```

这对 hybrid attention / agentic long-context workload 很重要，因为不同阶段 FULL 与 SWA 的压力并不固定。

#### AI Infra 面试启发

一个很值得准备的问题：

> 两类 KV cache 共享一块显存时，为什么不能分别维护两个 token capacity？

核心回答应包括：不同 KV component 的 **bytes/token 不一定相同**，且共享 arena 允许动态借用；所以 admission 应基于共同物理资源的 byte accounting，而不是两个静态逻辑 token 上限。

### 1.2 PR #36738 — HiCache load-back 显式等待旧 forward 写完

**状态：Open；2026-08-28 06:17（北京时间）创建。**  
PR: https://github.com/sgl-project/sglang/pull/36738

#### 解决的问题

Overlap Scheduler 可能在上一轮 forward 仍异步写 KV page 时，就逻辑上释放 finished/retracted request 的 page，并把 page 重新分给别的请求。

如果新的 consumer 仍在 compute stream 上执行，CUDA stream 顺序通常会自然保证旧写入先完成；但 HiCache load-back 的 H2D copy 在**独立 transfer stream** 上进行，不继承 compute stream 的顺序。

于是可能出现：

```text
old forward:       write page X  ------------------>
Scheduler:         free X -> reuse X
HiCache H2D:                restore prefix to X ---->
old forward:                         late write X
```

最终恢复好的 prefix 被旧 forward 的晚到写入覆盖，形成 timing-dependent silent corruption。

#### 核心改动

- `HiCacheController` 增加 `load_fence_stream`；
- `start_loading()` 在提交 H2D copies 前，让 `host_to_device_stream` wait `forward_stream`；
- Scheduler 在启用 hierarchical cache 时，把 ModelRunner 的 `forward_stream` 绑定给 cache controller。

#### 相关代码位置

- `python/sglang/srt/managers/cache_controller.py`
- `python/sglang/srt/managers/scheduler.py`

#### 性能 / 工程影响

额外代价是 **每次 load-back submission 一个 `wait_stream`**，不是每个 page/copy 一个 wait。PR 没有给 E2E benchmark。

工程意义远大于这点同步开销：它把“page 已经从 allocator 角度可复用”和“旧 GPU producer 已经真正停止访问 page”明确区分开。

#### AI Infra 面试启发

这里非常适合用来区分三个概念：

- allocator lifetime；
- CUDA stream execution lifetime；
- logical cache ownership。

`free()` 完成，只表示 allocator 允许复用，并不代表别的 CUDA stream 已经停止访问这块物理地址。

## 2. Prefill / Decode Disaggregation

### 2.1 PR #36730 — Unified Memory P/D 使用 page-envelope + physical index contract

**状态：Open；2026-08-28 04:54（北京时间）创建。**  
PR: https://github.com/sgl-project/sglang/pull/36730

#### 解决的问题

Unified Memory 对上层暴露的是 **virtual token IDs**，而 NIXL / Mooncake / Mori 一类 P/D transport 最终操作的是具体物理 buffer。

如果直接把 virtual id 当成 transport index，compaction 或 FULL/SWA 物理布局差异会让远端拿到错误位置。

Speculative Decoding 又让问题进一步复杂：target KV 与 draft KV 可能共享逻辑 token identity，但二者的物理 layout 并不一定一致，因此不能再默认“target index vector == draft index vector”。

#### 核心改动

- Unified MHA/SWA pool 显式提供 **contiguous page envelopes**；
- 在真正发起 P/D transfer 前，把 virtual token IDs 翻译成 physical page indices；
- transfer in-flight 时禁止 compaction 改变它所引用的物理页；
- `BaseKVManager` 增加可选的 separate draft KV indices 接口；
- 保留 decode retraction 的 CPU-copy fallback；
- 不支持的组合在 startup 阶段 fail fast。

#### 相关代码位置

重点看：

- `python/sglang/srt/disaggregation/base/conn.py`
- `python/sglang/srt/disaggregation/decode.py`
- `python/sglang/srt/disaggregation/prefill.py`
- `python/sglang/srt/mem_cache/unified_memory_pool.py`
- `python/sglang/srt/mem_cache/multi_ended_allocator.py`

#### 性能 / 工程影响

当前没有 transfer benchmark。

但这是一个很关键的架构边界：**transport layer 应消费稳定的 physical transfer descriptor，而不是理解 allocator 的 virtual address space。**

这样未来 allocator 做 compaction、FULL/SWA 动态布局甚至进一步 page migration 时，P/D backend 不需要复制 allocator 语义。

#### AI Infra 面试启发

可以类比虚拟内存：

> 为什么 RDMA / GPU DMA 不能直接拿一个“逻辑 token id”去传？

因为 token id 是逻辑身份，不保证对应稳定的物理地址；数据传输需要在某个明确的 lifetime 内绑定到物理 page，并保证这段时间映射不发生变化。

### 2.2 PR #36731 — Decode host offload 也采用共享 page-envelope arena

**状态：Open；2026-08-28 04:55（北京时间）创建。**  
PR: https://github.com/sgl-project/sglang/pull/36731

#### 解决的问题

#36729 让 device FULL/SWA 使用 shared byte budget，#36730 又把 P/D transport 改为 physical page-envelope；如果 Decode retraction/offload 的 host pool 仍然分别固定分配 FULL host pool 和 SWA host pool，就会重新引入同样的容量割裂。

例如 device 侧允许 FULL/SWA 动态借 byte，但 host 侧某一池已经满了，就可能出现“device 能退、host 不能接”的不一致。

#### 核心改动

- 新增基于单个 shared byte arena 的 page-envelope host pool；
- FULL/SWA host extents 原子 reservation；
- 两侧可以联合 reclaim evictable bytes；
- retraction / decode offload 前做 virtual→physical page translation；
- D2H transfer in-flight 期间阻止 compaction。

#### 相关代码位置

- `python/sglang/srt/disaggregation/decode_kvcache_offload_manager.py`
- `python/sglang/srt/mem_cache/pool_host/unified.py`
- `python/sglang/srt/mem_cache/pool_host/base.py`
- `python/sglang/srt/mem_cache/hybrid_cache/hybrid_pool_assembler.py`
- `python/sglang/srt/mem_cache/unified_memory_pool.py`
- `python/sglang/srt/disaggregation/decode.py`

#### 性能 / 工程影响

暂无 host-transfer benchmark。工程价值是把 device allocator、P/D wire contract 和 host backing store 的资源模型统一起来。

从系统设计角度，这一组三个 PR 可以概括成：

```text
Scheduler resource model
        ↓
virtual cache identity
        ↓ translate + pin lifetime
physical page envelope
        ↓
P/D transport / D2H offload
        ↓
shared host byte arena
```

## 3. Scheduler

### 3.1 PR #36752 — Multi-layer EAGLE 发布 final shared-read event

**状态：Open；2026-08-28 07:59（北京时间）创建。**  
PR: https://github.com/sgl-project/sglang/pull/36752

#### 解决的问题

Overlap Scheduler 希望尽早准备/写下一批 shared metadata，但必须先知道上一轮 forward 的**最后一个 reader**何时完成。

Multi-layer EAGLE 之前没有发布 final draft graph 的 shared-read completion event，因此 scheduler 只能 fallback 到更粗的 forward-stream fence。

粗 fence 虽然安全，但会把其实已经可以 overlap 的 CPU/Scheduler 工作继续串行化。

#### 核心改动

- 在最后一个 draft step 后发布 `shared_read_done_event`；
- per-step replay 与 single-graph replay 都覆盖；
- final draft runner 成为 Scheduler 的 shared-read event owner。

#### 相关代码位置

- `python/sglang/srt/speculative/multi_layer_eagle_draft_extend_cuda_graph_runner.py`
- `python/sglang/srt/speculative/multi_layer_eagle_worker_v2.py`

#### 性能 / 工程影响

暂无 E2E benchmark，但其优化目标很明确：把

```text
wait whole forward stream
```

收紧为：

```text
wait exact last shared-metadata read event
```

这与最近 SGLang 一系列 WAR fence / SharedReadEnds 改造是一致方向：Scheduler 要最大化 overlap，就需要 backend 明确声明**真正的最后读取边界**。

#### AI Infra 面试启发

很适合回答：

> 为什么 CUDA Event 往往比 `stream.synchronize()` 更适合推理引擎？

因为推理引擎通常只需要等待某个特定 dependency，而不是等待 stream 上所有之后无关的工作。精确 event 可以保留更多并行度。

## 4. Speculative Decoding

### 4.1 PR #36749 — Breakable CUDA Graph 的 buffer size 从 request rows 修正为 token rows

**状态：Open；2026-08-28 07:40（北京时间）创建。**  
PR: https://github.com/sgl-project/sglang/pull/36749

#### 解决的问题

Breakable CUDA Graph 的 `_output_rows()` 原来隐含假设：body 输出的 leading dimension 不会大于 capture batch size。

但 Speculative Target Verify 的 row unit 是 **draft tokens**，不是 requests。

实际案例：

```text
ShapeKey(size=3)
num_draft_tokens=4
next_token_logits.shape = (12, vocab)
```

旧实现只分配 / 暴露 3 行：

- verify 只能看到实际 logits 的 1/4；
- `accept_index` 可能直接访问 tensor 边界之外；
- 最终表现为 device-side assert，线上看起来甚至可能只是“hang”；
- 同时 `LogitsProcessorOutput` 本身也不被 BCG output helper 支持，因此 Spec Decode 经常只能退回 eager。

#### 核心改动

- `LogitsProcessorOutput` 的 `_output_rows()` 返回真实 token row 数；
- capture buffer 使用 `max(capture_size, actual_output_rows)`；
- `_alloc_full_buffer()` / `_slice_output()` / `_copy_output_to_buffer()` 支持 `LogitsProcessorOutput`；
- 对未显式支持的 populated field fail loudly，防止未来静默丢 logprob / diffusion 等字段。

#### 相关代码位置

- `python/sglang/srt/model_executor/runner_backend/breakable_cuda_graph_backend.py`
- `test/registered/unit/model_executor/runner_backend/test_breakable_cuda_graph_backend_lpo.py`

#### 正确性 / 性能结果

新增 9 个 CPU regression case；把实现恢复到修复前时为 **6 failed / 3 passed**，修复后 **9 passed**。

作者还在 Decode CUDA Graph + NEXTN 的组合分支上跑过 HumanEval+、GSM8K、needle retrieval 和长 agent tool-call sanity，但该分支叠加了另外两个 patch，所以这些结果只能证明组合路径可运行，不能作为本 PR 单独的性能或 accuracy A/B。

正式 decode A/B benchmark 仍 pending。

#### AI Infra 面试启发

这里一个非常重要的抽象问题是：

> CUDA Graph 的 shape key 应该描述“请求数”，还是描述“执行 tensor 的真实几何”？

答案通常不是二选一。不同 forward mode 的 leading dimension 语义不同：decode 常是 request rows，spec verify 可能是 request × draft token rows，MoE 又可能是 routed token rows。Graph/buffer abstraction 必须明确 **row unit**，否则 shape cache 很容易产生 silent contract mismatch。

## 5. Roadmap / RFC

### RFC #36522 — KV Cache Compression API 在窗口内继续更新

Issue: https://github.com/sgl-project/sglang/issues/36522  
状态：Open；本窗口内于 2026-08-27 13:41（北京时间）更新。

这个 RFC 尝试把 KV compression 正式接到 HiCache 的 **L1↔L2 / L2↔L3** 边界，而不是让某个 codec 直接侵入 Scheduler 或 Radix Tree。

当前设计中比较值得关注的点：

- codec 作为 `HostKVCache` 的可插拔实现；
- target (`lm`) 与 speculative `draft` pool 可以独立配置 codec；
- 支持 MHA / MLA / Mamba / DSA 等不同 cache kind；
- 对需要 RoPE undo/redo 的 codec，要求 cache operation 携带 position metadata；
- 对跨 layer compression，引入 streaming multi-layer load contract；
- lazy compression 需要明确 CPU/CUDA worker、staging buffer 和 priority；
- GPU decompression 必须遵守现有 load stream / event ordering；
- variable-size compressed blob 最终还需要独立的 allocator、fragmentation 和 compaction contract。

### 为什么值得跟

这说明 HiCache 的抽象正在从：

```text
HostKVCache = 一块 host tensor
```

向：

```text
HostKVCache = storage format + async codec + metadata + lifetime contract
```

演进。

尤其值得注意，RFC 还明确区分 target/draft role。这与今天 #36730 的 separate draft physical indices 方向高度一致：**Speculative state 不应再被默认视为 target KV 的简单附属品。**

## 8. 对 AI Infra 面试最有价值的 6 个问题

1. **一个 KV page 被 allocator free 之后，为什么仍然可能不能立即被另一个 CUDA stream 安全覆盖？**
2. **Unified FULL/SWA 共用显存时，为什么 admission 应按 byte budget，而不是分别按 token capacity？**
3. **P/D 为什么需要 virtual token ID → physical page descriptor 的显式转换？compaction 如何影响这个 contract？**
4. **为什么 target KV 与 speculative draft KV 可以共享逻辑 token identity，却不能保证共享同一组 transport indices？**
5. **Overlap Scheduler 中，等待 whole forward stream 与等待 exact last-reader CUDA Event 的吞吐差别来自哪里？**
6. **Spec verify 中为什么 `batch_size=32` 不一定意味着 graph output buffer 的 leading dimension 也是 32？**

如果把今天的内容真正吃透，核心不是记 PR，而是掌握一个越来越反复出现的推理引擎设计原则：

> **把 logical identity、resource capacity、physical ownership、async lifetime 和 execution geometry 分开建模。**

这也是最近 SGLang 在 KV Cache、P/D、Scheduler 和 Speculative Decoding 四条线逐渐汇合的地方。
