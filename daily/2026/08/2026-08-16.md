# SGLang 每日技术简报 — 2026-08-16

> 检索窗口：2026-08-15 09:00 ～ 2026-08-16 09:00（Asia/Shanghai）  
> 只关注：KV Cache、Prefill/Decode Disaggregation、Scheduler、Speculative Decoding。  
> 筛选原则：优先架构变化、组合正确性、性能数据和生产级风险；过滤纯模型适配、机械重构和无架构影响的小修复。

## 今日结论

过去 24 小时的主线非常清晰：**SGLang 正继续把优化重心从单点 kernel/feature 推向“跨阶段流水化 + 异步状态生命周期 + feature composability correctness”**。

最值得精读的变化有四个：

1. **P/D 开始做 layer-wise KV transfer**：Prefill 不再等整次 forward 完成后一次性传 KV，而是按 layer group 边算边传，直接把 KV transfer 从 TTFT 串行尾部搬进 prefill compute 的重叠窗口。
2. **Scheduler 的 read-done fence contract 继续显式化**：wrapper attention backend 必须声明真正 child backend 的最后读边界，避免 Scheduler 在 CUDA Graph 仍读取共享 metadata 时提前覆盖。
3. **Speculative decode 与 SWA cache 的生命周期开始补齐**：DFLASH/DSPARK 之前绕过了普通 decode 的 SWA eviction bookkeeping，导致 sliding-window KV 失去“滑动”语义；修复后长 decode 的 TPOT/ITL 明显下降。
4. **DSPARK 出现新的 silent correctness 风险**：多位置 verify 在异构并发 batch 下可产生看起来合理、但字符错误的 identifier；这比 crash 更危险，因为服务返回 200 且无异常。

从架构演进看，本日最重要的信号不是某一个 PR，而是：**KV、P/D、Scheduler、Spec 已经不能分别验证，必须围绕“状态在哪、谁拥有、何时可覆盖、如何证明恢复等价”建立统一 correctness contract。**

## 1. P/D：Layer-wise KV Transfer，把 KV 传输流水化进 Prefill

### PR #34905 — `feat: add layer-wise KV transfer for PD disaggregation`

- 状态：Open
- 链接：https://github.com/sgl-project/sglang/pull/34905

### 解决的问题

传统 P/D 路径大致是：

```text
Prefill 全部计算完成
        ↓
KV / state 整体传输
        ↓
Decode 开始
```

KV transfer 暴露在 TTFT critical path 上。#34905 改成按 layer group 执行：

```text
Layer group 0 compute ──→ transfer group 0 KV
Layer group 1 compute ──→ transfer group 1 KV
Layer group 2 compute ──→ transfer group 2 KV
                         ...
```

即 **compute / communication pipeline**。

### 核心改动

- KV manager：支持 per-layer subset KV/state transfer、request-scoped pipeline context、ready CUDA event、分组 byte accounting。
- Memory pool：为 MHA/MLA、DSA、SWA、Mamba、DeepSeek-V4 stateful pool 建立 `layer_id -> buffer handles`。
- ModelRunner：增加 split-prefill init / layer-group execution / finalize，跨 group 保存 hidden states、residual 和模型状态。
- Scheduler：新增 `LayerPipelinedKVTransferAdapter`，负责 compatibility planning、layer-group 大小、sender orchestration、final metadata 和 fallback。
- Spec：EAGLE 与 DSPARK worker 也透传 split-prefill 生命周期。
- 当前 transfer backend 仅支持 **Mooncake**。

### 性能影响

Qwen3.5-35B-A3B-FP8，4×RTX 5090：

- TTFT：**下降 15.9%～35.3%**
- Prefill throughput：**提升 0.26%～8.18%**

DeepSeek-V4-Flash，8×H100：

- 中高并发 8K prompt：TTFT **下降 4.4%～16.9%**
- Prefill throughput：**提升 2.3%～2.7%**
- 60K prompt 或高 cache-hit 时收益明显缩小，因为 prefill compute 变短/排队占主导，KV transfer 更容易重新暴露到 critical path。

这是一个非常典型的结论：**overlap 优化的收益取决于可被隐藏的 compute window，而不是 transfer 本身快了多少。**

### 面试启发

如果面试官问“P/D 分离后 TTFT 还能怎么优化”，一个高质量回答应从：

> **整块 KV transfer → layer-wise pipeline → CUDA event 建 dependency → compute/comm overlap → cache-hit/queueing 改变 overlap window**

展开，而不是只回答“换 RDMA / 提高带宽”。

## 2. Scheduler：Shared Read Ends 必须由真正读取 metadata 的 child backend 决定

### PR #34982 — `[Fix] Delegate shared-read-ends declarations in wrapper attention backends`

- 状态：Open
- 链接：https://github.com/sgl-project/sglang/pull/34982

### 解决的问题

Overlap Scheduler 会在 GPU forward 尚未完全结束时准备下一 batch，因此共享 request / attention metadata 的覆盖必须满足：

```text
previous forward 最后一次 read
        happens-before
scheduler 下一次 write
```

问题是 wrapper backend 以前可能直接继承默认声明，而真正执行读的是 child backend。

具体案例：

```text
TboAttnBackend
   └── DeepseekV4AttnBackend
```

child 在 non-DSPARK target verify 中声明需要读到 `POST_REPLAY`，wrapper 却报告 `IN_REPLAY`，于是 Scheduler 可能**提前释放 WAR fence**，在 child 仍跨 graph segment 读取 metadata 时开始写下一批数据。

### 核心改动

把概念显式命名为 `SharedReadEnds`：

- `PRE_REPLAY`
- `IN_REPLAY`
- `POST_REPLAY`
- `UNKNOWN`

并要求 wrapper 聚合/委托 child 的真实声明：

- `HybridAttnBackend`
- `TboAttnBackend`
- `HybridLinearAttnBackend`
- `MiniMaxHybridAttnBackend`

多个 child 时使用“**最晚结束的 read**”作为 fence release point。

### 工程影响

这是 correctness 优先于 overlap 激进程度的典型设计：

> fence 过晚 → 少一点 overlap；  
> fence 过早 → silent race / metadata corruption。

随着 backend wrapper、TBO、Spec、breakable CUDA Graph 越来越多，靠“默认某个时刻安全”不可维护，必须让 backend 显式声明生命周期 contract。

### 相关代码

- `python/sglang/srt/layers/attention/base_attn_backend.py`
- `python/sglang/srt/layers/attention/tbo_backend.py`
- `python/sglang/srt/layers/attention/hybrid_attn_backend.py`
- `python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py`
- `python/sglang/srt/model_executor/runner/decode_cuda_graph_runner.py`
- `python/sglang/srt/model_executor/runner_utils/shared_read_event.py`

### 面试启发

这里很适合回答“Overlap Scheduler 为什么难”：真正难点不是把 CPU 调度和 GPU execution 并行，而是建立 **buffer ownership / read boundary / write-after-read fence / CUDA stream ordering** 的完整 happens-before 关系。

## 3. KV Cache × Spec：DFLASH/DSPARK 补齐 SWA eviction bookkeeping

### PR #34924 — `[Spec] Fix SWA eviction bookkeeping for DFLASH-family decode`

- 状态：Open
- 链接：https://github.com/sgl-project/sglang/pull/34924

### 解决的问题

DFLASH family（包括 DSPARK）通过 `DFlashDraftInputV2.prepare_for_decode()` 预留 target KV，但没有执行普通 decode 路径的：

- `batch.maybe_evict_swa()`
- `req.decode_batch_idx` 推进

结果是 hybrid-SWA 模型虽然配置了很小 sliding window，**SWA token 却跟 full KV 一起线性增长**，最终触发 KV cache retraction / OOM。

### 核心改动

在 reserve 新 target KV 之前：

1. 调用 `batch.maybe_evict_swa()`；
2. 每个 active request 每次 decode iteration 推进 `decode_batch_idx`。

只改一个核心文件：

- `python/sglang/srt/speculative/dflash_info_v2.py`

### 性能结果

H100×4，DeepSeek-V4-Flash，32 requests，1K input / 32K output：

| 指标 | Before | After |
|---|---:|---:|
| KV pool full / retraction | repeatedly | none |
| Duration | 468.00 s | 369.78 s |
| Output throughput | 2240.55 tok/s | 2835.66 tok/s |
| Mean TPOT | 8.01 ms | 4.42 ms |
| Mean ITL | 8.06 ms | 4.45 ms |
| Max ITL | 129233 ms | 6762 ms |
| Accept length | 5.22 | 5.25 |

值得注意的是 accept length 基本没变化，因此收益不是“draft 更准”，而是 **cache 生命周期恢复正确后避免了 allocator/retraction 的系统性抖动**。

### 面试启发

Speculative decoding 不只会改变计算图，还会改变“一次 decode step 消费/产生多少 token”。因此任何基于 token clock 的机制——SWA eviction、KV allocation、cache metrics、admission control——都必须重新审计。

## 4. KV Cache：Unified Cache 的 load-back pin 从单 owner 变成并发 owner 集合

### PR #34975 — `fix(unified-cache): allow multiple concurrent load-back pins per node`

- 状态：Open
- 链接：https://github.com/sgl-project/sglang/pull/34975

### 解决的问题

HiCache + Unified Cache 在小显存、频繁 device eviction ↔ host load-back 的场景下，一个 radix node 可以同时被两个合法 load-back 读取：

- 一个 descendant load-back 的 Full-KV chain 覆盖该 ancestor；
- 另一个 request 又以该 ancestor 为 anchor，恢复独立 eviction 的 Mamba state。

原实现只有：

```python
load_back_pending_id: Optional[int]
```

无法表示多个并发 reader，于是出现 assertion。

### 核心改动

改成：

```python
load_back_pending_ids: set[int]
```

- commit 时加入 anchor id；
- ack 时移除自己的 id；
- **只有最后一个 pin drain 后**，host duplicate 才允许进入 reclaim 路径；
- tree split 时复制 pin set。

### 工程影响

这本质上不是“把字段改成 set”，而是在修正 cache node 的并发所有权模型：

> host KV/state 被多个 DMA reader 同时引用时，reclaim 条件必须是 reference set 清空，而不是单一 transaction 完成。

RTX 5090 + HiCache ratio 12 的 production-trace replay 中，修复后可连续跑 400 span，不再触发原 assertion。

### 相关代码

- `python/sglang/srt/mem_cache/unified_cache/unified_tree_core.py`
- `test/registered/unit/mem_cache/test_unified_loadback_multipin.py`

### 面试启发

这是把分布式存储里的 **pin / refcount / deferred reclaim / ABA-style lifecycle** 直接映射到 GPU/Host KV cache 的好例子。KV Cache 不只是“大块显存管理”，已经越来越像一个异步多层存储系统。

## 5. Spec Correctness：DSPARK multi-position verify 出现 silent identifier corruption

### Issue #34959 — `DSPARK silently corrupts identifiers on DeepSeek-V4-Flash`

- 状态：Open
- 链接：https://github.com/sgl-project/sglang/issues/34959

这是今天风险等级最高的观察项之一。

### 现象

在异构并发 batching 下，DSPARK 会把 prompt 中要求原样复现的 identifier 悄悄改成相似字符串，例如：

```text
kimi-k3   → kimi-kw
nova-x7   → nova-7
apollo-n9 → apollo-n11
```

更危险的是：

- temperature=0 也复现；
- response 正常返回，无 error/warning；
- speculative decoding 关闭后为 0 corruption；
- `block_size=1` 后也为 0 corruption；
- verify window 越宽，错误率总体越高。

报告数据：

| DSPARK block size | Temp 0 | Temp 1 |
|---:|---:|---:|
| 6 | 1.03% | 0.82% |
| 5 | 0.32% | 0.77% |
| 1 | 0% | 0% |
| Spec off | 0% | 0% |

### 为什么重要

现有 greedy accept 逻辑理论上只会提交：

1. 与 target prediction 相同的 draft token；或
2. target 的 bonus token。

所以如果最终 emitted token 错了，嫌疑更集中在 **target verify forward / token alignment**，而非简单“draft 质量差”。当前重点怀疑：

- multi-position target verify 的 causal mask；
- position ID；
- draft KV placement；
- request-to-token mapping；
- CUDA Graph replay metadata；
- batch slot reuse / stale metadata。

### 面试启发

这能回答一个非常好的问题：

> “为什么 speculative decoding 理论上 lossless，工程上仍可能 silent corruption？”

因为“算法上的 accept rule lossless”只成立于 **target verify logits 与 request/position/KV mapping 都正确** 的前提。系统层 metadata race 或 index-space bug 可以破坏这个前提。

## 6. Roadmap：Unified Radix Cache 开始推动 bit-exact correctness oracle

### Issue #34899 — `Bit-exact correctness coverage for Unified Radix Cache`

- 状态：Open / Roadmap
- 链接：https://github.com/sgl-project/sglang/issues/34899

当前方向是：对于能够做到 deterministic 且 prefill/decode 数学路径一致的模型，使用同一 token 的 logprob 建立 **exact-zero KL** correctness gate：

> 如果重算与 cache restore 真正等价，那么任意非零 KL 都应被视为 KV/state reuse bug，而不是等到偏差超过经验阈值才报警。

当前 roadmap：

- [x] Base cache path
- [x] Mamba `extra_buffer`
- [x] HiCache multi-turn
- [ ] Mamba `extra_buffer_lazy`
- [ ] MTP
- [ ] DSPARK / DFLASH
- [ ] Unified Memory

与之直接相关的 **PR #34939** 在本窗口新增 DSPARK `return_logprob` 支持，把 DFLASH/DSPARK 的 chain verify logprob 统一到 `compute_spec_v2_chain_logprobs`，为后续 exact-KL 覆盖补基础能力：

https://github.com/sgl-project/sglang/pull/34939

### 面试启发

生产级 cache correctness 不能只靠 GSM8K / output text。更强的测试分层应包括：

```text
bit-exact / KL oracle
    > deterministic replay
    > state save/load equivalence
    > workload accuracy benchmark
```

前者更接近“系统 invariant 测试”，而不是“模型效果测试”。

## 7. 组合风险观察：DSPARK × EPLB 在 draft CUDA Graph capture 崩溃

### Issue #34974

链接：https://github.com/sgl-project/sglang/issues/34974

DeepSeek-V4-Flash 上开启 `--enable-eplb` + DSPARK 时，draft-model CUDA Graph capture 会进入 expert-distribution recorder；由于 draft MoE 路径缺少正确的 current-layer context，`layer_idx=None`，最终在 `scatter_add_` 发生维度错误并导致所有 TP rank 启动失败。
