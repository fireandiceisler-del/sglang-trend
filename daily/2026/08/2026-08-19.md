## 一、Speculative Decoding

### 1. [#35371] DFlash2：local convolution + candidate selector — **已合入**

**解决的问题**

传统 block speculative proposal 的各 slot 独立性较强。DFlash2 增加两类 checkpoint 驱动的能力：一是 block 内 grouped dynamic depthwise convolution，让后面的 proposal position 能直接看到本 block 前面的 proposal；二是 candidate selector，不再对每个 slot 独立 argmax，而是从 target head top-K 候选中结合相邻 transition score 选择整条路径。

**核心改动**

- block 内动态 depthwise convolution；
- top-K candidate + adjacent transition scoring；
- greedy 使用 best path，sampling 使用 inverse-CDF walk，并把真实 proposal distribution `q` 交给 lossless verify；
- selector decode 被折叠进 draft CUDA Graph，一个 Triton program 处理一个 request 的路径 walk。

**性能影响**

作者公布的单 H200、Qwen3.8-27B、block size 8 数据中：

- GSM8K acceptance length：MTP `5.02`，DSpark `4.36`，DFlash2 `5.46`；
- GSM8K concurrency=1：autoregressive `68.9 tok/s`，DFlash2 `236.1 tok/s`，即 **3.43×**；
- concurrency=8：DFlash2 `1328.7 tok/s`，约 **2.84×** autoregressive；
- concurrency=32：DFlash2 `1922.5 tok/s`，约 **1.45×** autoregressive；
- 新 convolution + selector 的额外 step cost 约 **1.5%–2.7%**。

这些数字是该 PR 给定 checkpoint / workload 的结果，不应直接外推到其他模型。

**相关代码**

- `python/sglang/kernels/ops/speculative/dflash.py`
- `python/sglang/srt/models/dflash.py`
- `python/sglang/srt/speculative/dflash_worker_v2.py`
- `python/sglang/srt/speculative/dflash_utils.py`

**面试启发**

Speculative Decoding 的核心并不只是“draft model 更小”。真正的优化目标是：在增加极少 proposal cost 的情况下提高 `E[accepted tokens / verify step]`。因此一个很好的面试追问是：**为什么 acceptance length 提升 20% 不一定带来 20% throughput 提升？** 因为 draft/selector 成本、target verify 成本、batch size 和 memory traffic 都会改变收益兑现比例。

### 2. [#35413] DSpark：从 CUDA Graph capture 自动推导 verify-budget cost table — **Open**

**解决的问题**

在 compact ragged verify 下，如果没有外部 SPS table，planner 的 cost table 缺少真实硬件成本，目标函数容易退化成“verify 全部 candidate”，因此所谓 compact scheduling 实际无法根据成本做 trimming。

**核心改动**

新增 opt-in `SGLANG_DSPARK_ENABLE_CAPTURE_DERIVED_SPS=1`：启动阶段复用已经 capture 的 verify-tier / draft-batch CUDA Graph，测出当前 **模型 × GPU × TP topology** 的实际 cost curve，再安装到已有 `SpsAdditiveCostTable`。用户显式提供的 SPS table 仍具有更高优先级，功能默认关闭。

**性能影响**

PR 给出的 H200 compact-ragged 数据：

- Qwen3-14B：cc48 `+14.4%`，cc64 `+24.1%`；
- Qwen3-8B：约 `+8.3% / +5.6%`，短测 cc128 趋势约 `+22.9%`；
- Qwen3-4B：cc128 趋势约 `+11.8%`；
- **DeepSeek-V4-Flash TP4 反而回退约 `-6.3% / -8.0%`**；
- 低并发 cc1–16 基本在 ±1.8% 内，accept length 基本不变；
- 启动 calibration 额外约 2.4s（Qwen3-4B）到 9.0s（DSV4）。

这组正负结果本身很重要：**自适应 cost model 也必须被模型/拓扑级 benchmark 验证，不能因为“自动 profile”就默认更优。**

- `python/sglang/srt/speculative/dspark_components/dspark_sps.py`
- `python/sglang/srt/speculative/dspark_components/dspark_worker_v2.py`
- `python/sglang/srt/model_executor/runner/decode_cuda_graph_runner.py`

**面试启发**

这是一个非常典型的 online/offline cost-model 设计题：什么时候应该静态表，什么时候应该启动时 profile，什么时候应该运行时在线学习？还要考虑 calibration 时间、测量噪声、CUDA Graph shape coverage 和 workload shift。

## 二、KV Cache / DCP / Hybrid State

### 3. [#35298] DCP 对外宣告 logical KV-event block size — **Open**

**解决的问题**

DCP 下存在两种 page 粒度：

```text
physical page = page_size
logical page  = page_size * dcp_size
```

allocator / radix tree / KV event 实际按 logical page 工作，但 `/server_info` 的 KV-event descriptor 却宣告 physical page。KV-aware Router 按文档用错误 block size hash prompt 后，就会出现非常危险的现象：**KV store/event 都正常，本地 metrics 也正常，但 Router lookup 永远 miss，命中率稳定为 0。**

**核心改动**

- 增加 `ServerArgs.kv_event_block_size = page_size * dcp_size`；
- KV-event descriptor 对外宣告该 logical width；
- publisher 数量仍按 DP 语义，不因为 DCP 扩大。

**验证**

4×H200、TP4/DCP4、`page_size=64` 的测试中，修复前 descriptor 报 64，而 wire event 实际 block size=256；修复后两者统一为 256，KV-aware Router 命中恢复到该 256-token logical page 下的理论上限。

**相关代码**

- `python/sglang/srt/server_args.py`
- 语义来源：`mem_cache/kv_cache_configurator.py`、`mem_cache/kv_cache_builder.py`

**面试启发**

这是一个很好的“分布式缓存为什么会 silent miss”问题：**Producer/Consumer 不仅要共享 hash 算法，还必须共享 block granularity、index space 和 shard semantics。** 只要逻辑页与物理页定义不一致，系统不会 crash，却可能让整个缓存层失效。

### 4. [#35412] DCP 下 Mamba decode checkpoint 必须落在 tree-page grid — **Draft / 尚未完成 CI**

**解决的问题**

radix tree 只能给某些 token depth 命名。decode path 当前按 `mamba_track_interval` 产生 recurrent-state checkpoint，但 DCP 后 tree page 为 `page_size * dcp_size`。当：

```text
mamba_track_interval % (page_size * dcp_size) != 0
```

checkpoint state 可能覆盖到更深 token，却被挂到前一个 radix node；后续请求从该 node 恢复 state 后再次消费已经包含进 state 的 token，从而形成 silent correctness bug。

PR 点名的现实组合是 Kimi-K3 TP8/DCP8 + HiCache：物理 page=64、tree page=512、默认 track interval=256，因此落在 break condition。

**核心改动**

引入：

```text
mamba_track_grid(tree_page)
  = lcm(mamba_checkpoint_grid(tree_page), mamba_track_interval)
```

并把 normal decode、DFlash、DSpark、spec verify/prepare 的 checkpoint depth 全部约束到同一 grid。Kimi-K3 DCP8 对应 checkpoint grid 从 256 调整为 512。

**相关代码**

- `python/sglang/srt/managers/schedule_batch.py`
- `python/sglang/srt/managers/scheduler_components/batch_result_processor.py`
- `python/sglang/srt/speculative/dflash_worker_v2.py`
- `python/sglang/srt/speculative/dspark_components/dspark_worker_v2.py`
- `python/sglang/srt/speculative/spec_utils.py`

**注意**：截至本简报窗口结束，该 PR 仍是 Draft，作者明确注明尚未跑完测试，因此应视为高价值 correctness 信号，而不是已确认修复。

**面试启发**

对于 hybrid attention，缓存的不再只是 token→KV，而是 token depth→recurrent state。面试中可以把它抽象成：**checkpoint 的语义版本/逻辑时间必须和索引结构可表达的边界一致。** 这和数据库 WAL LSN、snapshot boundary 的思想其实很接近。

### 5. [Tracking #35223] KV allocator 转向 host-side page bookkeeping — **新 Tracking Issue**

这是今天最值得跟踪的 KV/Scheduler 架构方向之一。当前 allocator 的 source of truth 仍部分放在 GPU：free page 时需要 `torch.unique(...)`、SWA mapping gather 和 liveness filter，这些 data-dependent device→host 读取会强制 stream synchronization；Overlap Scheduler 下，它们会排在 WAR barrier 后面，CPU 因此等待上一轮 forward 排空。

目标设计是：

- host 端以 whole page 规划 allocation；
- 每个 request 维护 page-ceiled `req.kv.kv_allocated_len`，且只有一个 writer；
- `free()` 按整页直接释放，不再在正常路径做 GPU dedup/liveness readback；
- `req_to_token` / `full_to_swa_index_mapping` / `free_pages` 逐步退化为 **GPU kernel 的 write-only projection**，scheduler 不再读取它们作为控制面 source of truth。

Tracking issue 已把 #35265、#35286、#35382 列为 landed，并继续跟踪 #35396、#35401。

**面试启发**

这是 CPU/GPU 异步 runtime 里非常典型的优化：**控制面的 authoritative metadata 尽量留在 CPU；GPU metadata 应被视为执行面的 projection，而不是需要频繁 readback 的真值。** 否则一个看起来很小的 `.item()` / `unique()` 就可能摧毁 overlap。

## 三、Prefill / Decode Disaggregation

### 6. [#35281] Mooncake / NIXL / Mori defensive protocol 行为开始统一 — **Open，RFC #33861 Step 1**

这个 PR 是 [RFC #33861](https://github.com/sgl-project/sglang/issues/33861) 与实施计划 #34510 的继续推进。它还没有抽出最终 Common protocol/Transport，但先把三个 backend 的 control-plane 行为拉齐。

**核心改动**

- Mori Decode 接入现有 heartbeat checker，Prefill 能识别 Common `ABORT`；
- NIXL / Mori worker 在 room teardown 后丢弃 stale queued work，避免读取已经删除的 transfer metadata；
- Mooncake / NIXL 对 malformed control frame 做“单消息隔离”，坏消息不再杀死长期 control thread；
- Mori speculative MHA descriptor 按 Common planner 的 `[K_main..., V_main..., draft_K..., draft_V...]` 语义选择，修正 draft region / V offset、same-PP offset 与 hybrid MLA slicing；
- Mooncake 在启动 receive thread 前先初始化 session failure state，消除 init race。

**相关代码**

- `python/sglang/srt/disaggregation/mooncake/conn.py`
- `python/sglang/srt/disaggregation/nixl/conn.py`
- `python/sglang/srt/disaggregation/mori/conn.py`

**工程影响**

这批修改本身没有 benchmark，但价值在生产可靠性：P/D 后端逐步从“每个 transport 自己实现一套半独立 state machine”向 **统一 protocol semantics + backend-specific transport** 收敛。后续真正值得看的是 room tombstone、idempotent teardown、terminal-state、ACK/cancel/quiescence 是否被抽到 Common 层。

**面试启发**

可以把 P/D transfer backend 看成分布式存储里的多种 replication transport：数据面可以不同，但 failure detector、request identity、abort、terminal state、重试与资源释放语义不能各写一套，否则组合规模一大就会出现幽灵 room / stale work / double terminalization。

### 7. [#35364] P/D Decode retraction backend 增加 host-memory capacity fallback — **Open**

**解决的问题**

此前 `host_pool` retraction backend 基本按“功能是否支持”选择，却没有在选择时验证 host RAM 能否 1:1 mirror device KV pool。GB300 这类 HBM 总量已经可以接近甚至超过主机内存容量：PR 给出的 4×GB300 示例里，约 1110 GiB HBM 对 955 GiB Grace LPDDR5X，hybrid-SWA TP4 的 host mirror 需要约 1059.8 GB，而可用 host memory 约 854 GB，默认推导出的 backend 因此必然启动失败。

**核心改动**

- 自动推导 `host_pool` 时先做容量估计；放不下则退化为 `cpu_tensor` 并 warning；
- 用户显式指定 `host_pool` 仍然 hard fail；
- 用 world CPU group 做 rank 一致性 MIN agreement，避免不同 rank 得出不同 backend；
- 修正 PP/DP local scheduler count；
- 把 MTP/EAGLE draft pools 纳入估算；
- 兼容不同 KV-size accessor shape。

**相关代码**

- `python/sglang/srt/mem_cache/kv_cache_builder.py`
- `test/registered/unit/mem_cache/test_decode_retraction_capacity.py`

**工程影响**

steady-state decode 路径不变，收益主要是把“默认配置必崩”变成资源感知 fallback。这个方向比单独修一次 OOM 更重要：**runtime backend selection 应同时看 capability 与 capacity。**

## 四、Scheduler

### 8. [#35017] DP-attention 下 Prefill 后插入可配置 Decode interval — **Open，过去 24h 有更新**

**解决的问题**

DP attention 中每个 rank 可以本地调度 attention，但所有 rank 仍共同参与 MoE collective。若某个 rank 持续有 chunked-prefill continuation，它可能一直赢得 prefill-first 决策，让其他 rank 的 decode 请求长期得不到机会，形成跨 rank 的 decode starvation。

**核心改动**

新增 `--prefill-decode-interval N`（默认 0，不改变现有行为）：发生 EXTEND 后，在后续 N 个 scheduler round 暂缓新 prefill，让 running batch 获得 decode 时间。DP-attention 下不使用纯本地信号，而复用已经全局同步的 `is_extend_in_batch` 来保证所有 rank 对 interval 的理解一致。

**验证数据**

8×B200、DeepSeek-V4-Pro FP4、TP8/DP8/EP8、DP-attention、MTP3、interval=16 的 3600s AgentX prototype：

- concurrency=56：`30.755 tok/s/user`，`23,559 tok/s/GPU`，cache hit `95.945%`；
- concurrency=84：`23.242 tok/s/user`，`26,110 tok/s/GPU`，cache hit `94.703%`；
- cc84 共完成 7,096 个 profiled requests，0 request errors。

PR 没有给出严格 A/B baseline，因此这里不把上述数字表述为“提升百分比”；它们主要证明该 fairness mechanism 在长时 AgentX workload 下可稳定运行。

**相关代码**

- `python/sglang/srt/managers/scheduler.py`
- `python/sglang/srt/server_args.py`

**面试启发**

“Prefill-first 一定能降低 TTFT”是错误的泛化。DP/EP 组合下，一个 rank 的局部最优调度会通过 collective 把其他 rank 一起拖住。这里本质是 **distributed scheduling fairness**：局部 queue policy 必须考虑跨 rank synchronization domain。

## Roadmap / 架构趋势

今天可以看出四个越来越明显的演进方向：

1. **Spec Scheduler → profile-guided。** 固定 verify budget 正被模型/硬件/TP 相关的成本模型替代，但 DSV4 的负收益说明它必须保留 fallback 与 per-model gating。
2. **KV Cache → logical-state protocol。** DCP logical page、Mamba checkpoint grid、Router hash block size 都在说明：KV correctness 的关键已经不是“有没有 cache”，而是参与者是否共享同一个 logical index space。
3. **P/D → common control protocol。** Mooncake/NIXL/Mori 的 heartbeat、ABORT、stale-work、descriptor planning 正在逐步对齐，最终目标是 protocol 与 transport 解耦。
4. **Scheduler → host-authoritative bookkeeping + distributed fairness。** 一边减少 GPU metadata readback，一边让 DP ranks 对 phase/fairness 决策达成一致，都是在减少异步系统里的隐式同步与局部决策漂移。

## AI Infra 面试速记

- **Spec 的目标函数**：不是最大 acceptance，而是最小单位 accepted token 的总成本；必须同时考虑 draft、verify、memory traffic 和 batch scaling。
- **DCP KV contract**：physical page ≠ logical page；Router / event publisher / radix tree 必须在同一个 hash/block/index-space 语义上。
- **Hybrid state cache**：Mamba/SSM state 是带逻辑时间的 checkpoint，checkpoint depth 必须落在 radix tree 可表达的边界。
- **P/D backend selection**：capability check 不够，还要做 capacity check，并保证所有 rank 对 fallback 决策一致。
- **Overlap scheduler**：避免 GPU→CPU data-dependent readback；控制面 authoritative bookkeeping 尽量留在 host。
- **DP scheduling**：局部 prefill-first 可能通过 collective 造成全局 decode starvation，调度策略需要跨 rank 一致的 fairness signal。
