## 今日结论

今天最值得关注的变化不是新增一个孤立 feature，而是 SGLang 继续把 **异步推理的状态边界做显式化**：

1. **Spec × KV Cache × CUDA Graph**：NVFP4 speculative decoding 开始彻底去除对 CPU prefix metadata 的依赖，让 target verify / draft extend 的 metadata 与 workspace 都能留在 GPU；与此同时，新 Native MTP 原型明确规定 **draft KV 与 target KV 必须隔离**。
2. **KV Cache 热路径开始按“实际引用工作集”而不是“池总容量”付费**：FA3 MLA 从每层、每步 dequantize 整个 FP8 KV pool，转向只 materialize page table 真正引用的页。
3. **P/D 正在补齐分布式系统式的控制面 contract**：NIXL transfer failure 需要显式推送给 Decode，而不能只依赖 300s timeout；CP 下 replicated state 也开始避免每个 rank 重复发送。
4. **Scheduler 保持 zero-overhead baseline 的思路更明确**：只有 DSpark 才需要的 request-generation bookkeeping，不应让所有 serving mode 共同承担；同时 `generation` 本身就是典型的 slot-reuse / ABA 防护。

如果只精读三条，建议按：**#36045 → #36087 → #36108/#36033**。

## 1. [Spec × KV Cache] #36045 — 让 FlashInfer NVFP4 speculative decoding 真正 CUDA-Graph-safe

PR: https://github.com/sgl-project/sglang/pull/36045  
状态：Open；创建于 2026-08-23 14:59（北京时间）

### 解决的问题

NVFP4 KV cache 下，FlashInfer 旧的 dequant workspace 依赖 **CPU-side prefix metadata**。但 speculative decoding 的 target verify / draft extend metadata 可能只存在 GPU 上，因此会出现两类问题：

- target verify / `DRAFT_EXTEND_V2` 无法构造正确 workspace；
- 更危险的是复用旧 prefill workspace metadata，产生 stale state。

这和 CUDA Graph 的核心约束冲突：**capture/replay 阶段不能临时回 CPU 查询动态 prefix 信息，也不能在 graph 中做动态分配。**

### 核心改动

- 增加 fixed-grid Triton kernel，把 NVFP4 cached prefix 直接按 physical KV slot 解量化到 FP8 workspace。
- target verify 与 `DRAFT_EXTEND_V2` 的 request index、seq len、mapping、write location 保持 device-resident。
- 保留 graph padding 的 slot 0 隔离语义，不在 CUDA Graph 内分配。
- draft worker 的独立 FP4 dequant workspace 被纳入 token-pool memory budget，避免“启动看起来能分配，实际 draft workspace 把显存吃穿”。

### 性能 / 工程影响

SM120、Qwen3.8-27B-NVFP4：

| Cached prefix | Target verify / layer | Draft extend / layer | Effective BW |
|---:|---:|---:|---:|
| 32K | 0.229 ms | 0.228 ms | ~448 GB/s |
| 128K | 1.021 ms | 1.021 ms | ~401 GB/s |

对 16 个 full-attention target layer + 1 个 MTP draft layer，作者估算 dequant 成本约：

- 32K：**3.89 ms / speculative cycle**
- 128K：**17.35 ms / speculative cycle**

另一个很重要的工程结果：在 `mem_fraction_static=0.93` 下，token pool 从错误的 **2,035,968** slots 修正为 **1,760,832** slots，说明辅助 workspace 必须进入统一显存预算。

- `python/sglang/kernels/ops/quantization/nvfp4_kv_cache.py`
- `python/sglang/srt/layers/attention/flashinfer_backend.py`
- `python/sglang/srt/layers/quantization/fp4_kv_cache_quant_method.py`
- `python/sglang/srt/mem_cache/memory_pool.py`
- `python/sglang/srt/model_executor/pool_configurator.py`

### AI Infra 面试启发

这是一个很好的问题：**“为什么 CUDA Graph-safe 不只是 kernel 可 capture？”**

答题重点应包含：动态 metadata 的 host dependency、workspace 地址稳定性、graph replay 的 allocation-free 要求、padding slot 隔离、以及辅助 workspace 必须参与 capacity planning。

## 2. [KV Cache] #36087 — FA3 MLA 只 dequantize 真正被引用的 FP8 KV pages

PR: https://github.com/sgl-project/sglang/pull/36087  
状态：Open；创建于 2026-08-23 21:17（北京时间）

### 解决的问题

FA3 absorbed-MLA 旧路径每层每次 forward 都执行近似：

```python
kv_cache = key_buffer.to(q.dtype)
```

这意味着即使 page table 只引用 KV pool 的 1%，也会把**整个 pool**从 FP8 materialize 成 BF16/FP16。

DeepSeek-R1、131,072 pages 的例子中，每层会把 72 MiB FP8 转成 144 MiB BF16，并在 61 层重复执行。

### 核心改动

- Triton kernel 只转换 page table 引用的 MLA KV rows。
- 使用 persistent dense shadow，仍保留原 physical page ID，因此 FA3 不需要额外 compact/remap metadata。
- 所有 MLA layer 共用一个 shadow workspace。
- 用 epoch tensor 去重多个请求共享的 page，避免每个 forward 清空 workspace。
- persistent tensor 设计使其兼容 CUDA Graph replay。

### 性能 / 工程影响

SM90 microbenchmark：

| 路径 | 引用 pages | 每层时间 |
|---|---:|---:|
| 整池 `to(bfloat16)` | 131,073 | 0.221 ms |
| selective eager | 1,440 | 0.024 ms |
| selective CUDA Graph | 1,440 | **0.006 ms** |
| selective CUDA Graph | 16,384 | 0.021 ms |
| selective CUDA Graph | 65,536 | 0.097 ms |

在约 1,440 live rows 的场景，61 层 conversion component 估算从 **13.48 ms → 0.37 ms**。

代价是每 rank 固定约 **144 MiB BF16 shadow + 0.5 MiB epoch state**。

注意：当前优化路径明确排除了 speculative / cascade / SWA / CP / DCP / draft 等组合，说明后续重点仍是 composability。

### 相关代码

- `python/sglang/kernels/ops/kvcache/mla_buffer.py`
- `python/sglang/srt/layers/attention/flashattention_backend.py`

### AI Infra 面试启发

这是典型的 **capacity vs working set** 优化：

> KV pool 很大，不代表每一步都应该对整个 capacity 做 O(N) 工作；热路径应尽量只与当前 live / referenced working set 成正比。

还能继续追问 persistent shadow 为什么比每步 compact buffer 更适合 CUDA Graph，以及 epoch-based dedup 如何避免 memset/clear 成本。

## 3. [Speculative Decoding] #36112 — Native MTP：把 draft block 放回 target model，但 KV 生命周期仍必须隔离

PR: https://github.com/sgl-project/sglang/pull/36112  
状态：Open；创建于 2026-08-24 06:05（北京时间）

### 解决的问题

这是一个早期原型：Qwen3-Next 的 MTP block 不再作为独立 draft model 走一套完整 loading path，而是直接嵌入 target model，并复用现有 EAGLE v2 orchestration。

目标是减少：

- 单独 draft model 初始化 / loading 路径；
- target 与 draft 两套模型生命周期带来的调试复杂度。

### 核心改动

- 新增 `--enable-native-mtp`。
- target model 内初始化 embedded `mtp` block，并在 target checkpoint loading 时加载 MTP weights。
- speculative orchestration 复用 EAGLE v2，只替换 draft runner 构造。
- **draft KV 仍与 target KV 完全分离**，避免 draft forward 覆盖 target cache state。
- MVP 阶段 draft CUDA Graph 暂时关闭，先走 eager draft execution。

### 性能 / 工程影响

目前尚无 accuracy / benchmark，因此它应被视为**架构方向信号，而不是可用性能结论**。

真正值得关注的是 owner boundary：**weight/model ownership 可以合并，KV/state ownership 不一定能合并。** Speculative draft 的状态是可丢弃/可验证的，而 target committed KV 是正确性基线，二者生命周期不同。

### 相关代码

- `python/sglang/srt/models/qwen3_next.py`
- `python/sglang/srt/speculative/eagle_worker_v2.py`
- `python/sglang/srt/speculative/native_mtp_worker.py`
- `python/sglang/srt/speculative/spec_info.py`
- `python/sglang/srt/server_args.py`

### AI Infra 面试启发

面试可用问题：**“为什么把 MTP block 嵌进 target model 后，不能顺便共用 target KV cache？”**

核心答案：draft token 尚未 commit，verify 可能 reject；共享同一 committed KV namespace 会让 speculative side effect 污染 target correctness state。

## 4. [Scheduler × DSpark] #36093 — 只有需要 generation 的 feature 才承担 generation bookkeeping

PR: https://github.com/sgl-project/sglang/pull/36093  
状态：Open；创建于 2026-08-23 22:41（北京时间）

### 解决的问题

DSpark 的 delayed confidence relay 可能晚到；request-pool slot 又会被新请求复用。因此 SGLang 用 `req_generation` 区分：

```text
slot = 17, generation = 41   # old request
slot = 17, generation = 42   # new request
```

否则旧请求的异步结果可能被错误写给新请求——本质上是一个 **ABA / slot reuse** 问题。

问题在于旧实现对所有请求都更新 generation，即使非 DSpark serving 根本不用它，而且 batched admission 还是每个请求做一次 CPU Torch scalar op。

### 核心改动

- `ReqToTokenPool` / `DecodeReqToTokenPool` 的 generation tracking 改为 opt-in。
- 只有 speculative algorithm = DSpark 时由 `ModelRunner` 开启。
- 单请求 DSpark 保留 scalar update；batch admission 改为一次 vectorized indexed update。
- regular 与 disaggregated Decode request pool 共用实现。

### 性能 / 工程影响

Request-pool `alloc()` microbenchmark：

| Batch | Baseline | 非 DSpark 新路径 | DSpark 新路径 |
|---:|---:|---:|---:|
| 1 | 9.652 us | **1.225 us** | 10.256 us |
| 64 | 496.762 us | **12.307 us** | 50.736 us |
| 1024 | 8,024.461 us | **201.693 us** | 507.782 us |

非 DSpark 大 batch admission 约 **40×** 改善。E2E 因模型计算占主导，仅看到约 0.6%～2.0% 的小幅收益。

### 相关代码

- `python/sglang/srt/mem_cache/memory_pool.py`
- `python/sglang/srt/model_executor/model_runner.py`
- `python/sglang/srt/disaggregation/decode.py`

### AI Infra 面试启发

两个非常好的讨论点：

1. **generation counter 为什么能解决 slot reuse 的异步结果错配？**——它把物理 slot identity 扩展为 `(slot, generation)` 逻辑 identity。
2. **zero-overhead scheduler 怎么设计？**——feature-specific metadata 应 feature-gated，而不是所有请求共同承担。

## 5. [P/D] #36025 — Prefill CP 下去掉重复发送的 replicated state，状态流量 -84.97%

PR: https://github.com/sgl-project/sglang/pull/36025  
状态：Open；创建于 2026-08-23 11:16（北京时间）

### 解决的问题

当 Prefill 使用 CP，且所有 CP ranks 都参与 P→D transfer 时：

- KV page 是按 CP rank 分片的；
- 但 `state_indices` 是 replicated 的。

旧 MORI 路径让每个 CP rank 都发送同一份完整 replicated state，因此 state traffic 被放大约 `cp_size` 倍。

### 核心改动

- 把“CP replicated state 只需要一个 rank 发送”的 policy 下沉到 `CommonKVManager`。
- MORI 中只有 Prefill CP rank 0 enqueue state；非零 CP rank 只传自己的 KV shard。
- cache layer-split 是例外：每个 rank 仍必须发送自己真正拥有的 state layers。

### 性能 / 工程影响

MI355X、DeepSeek-V4-Pro、Prefill CP8 / Decode TP8、16 × 65,536-token prompts：

- aggregate `kv_transfer_total_mb`：**2,470,901.8 → 371,486.9 MiB（-84.97%）**
- TTFT p50：6557.8 → 6575.9 ms（+0.28%，基本无变化）
- TTFT p95：9353.7 → 9370.7 ms（+0.18%）
- input throughput：-0.13%

这是一个很有价值的反例：**网络字节减少 85% 并不保证 TTFT 立刻下降。** 如果关键路径瓶颈不在这部分 state traffic，收益首先体现为网络容量、扩展性和与其他流量的 contention margin，而不是单请求 latency。

### 相关代码

- `python/sglang/srt/disaggregation/common/conn.py`
- `python/sglang/srt/disaggregation/mooncake/conn.py`
- `python/sglang/srt/disaggregation/mori/conn.py`

### AI Infra 面试启发

面试中遇到“P/D + CP 如何传 KV/state”，要先区分数据的 distribution semantics：

- **sharded data**：每个 rank 都有独有部分，必须分别传；
- **replicated state**：只需要一个 rank 传；
- **layer-split state**：看似 state，但 ownership 又是分片的。

不能仅凭 tensor 名称决定 transfer policy。

## 6. [P/D Reliability] #36108 / Issue #36033 — NIXL transfer failure 从 300s timeout 变成显式终止信号

PR: https://github.com/sgl-project/sglang/pull/36108  
Issue: https://github.com/sgl-project/sglang/issues/36033  
状态：PR Draft；创建于 2026-08-24 03:58（北京时间）

### 解决的问题

Mooncake / MORI 在 Prefill KV transfer 失败时会向 Decode 推送 terminal failure；NIXL 旧实现只记录 Prefill 本地失败。

结果是 Decode 并不知道远端已经失败，只能等：

```text
SGLANG_DISAGGREGATION_WAITING_TIMEOUT = 300s
```

这不是普通 timeout 参数问题，而是**分布式控制面缺失 terminal state propagation**。

### 核心改动

- Prefill transfer worker 失败时向所有唯一 Decode endpoint 发送 `NIXL_TRANSFER_FAILURE`。
- 在发布本地 Failed 之前先 snapshot endpoint，避免 cleanup 把通知目标 race 掉。
- Decode 默认启动 control listener，收到 failure 后立即把 room 置为 terminal。
- malformed / late notification 被忽略，防止已清理 room 被重新污染。
- 若通知失败，仍保留原 waiting timeout 作为 fallback。

### 性能 / 工程影响

没有吞吐收益目标；价值是把 failure detection 从“最多约 300 秒等待”改为主动通知。

Loopback TCP/ZMQ fault injection（500 samples）：

- median：**0.0911 ms**
- P95：0.1129 ms
- P99：0.1234 ms

### 相关代码

- `python/sglang/srt/disaggregation/nixl/conn.py`
- `test/registered/unit/disaggregation/test_nixl_backend_basic.py`

### AI Infra 面试启发

这是典型的 **data plane / control plane 分离**问题：

> RDMA/NIXL 的数据传输失败，并不会自动让远端应用层状态机知道“这个 request 已经终止”。

生产级 P/D 协议必须定义：success、failure、abort、late message、peer restart、timeout、idempotency 等控制语义，而不仅仅是“KV 能搬过去”。

## 今日架构趋势

把今天几条变化连起来看，SGLang 的演进有三个明显方向：

### 1. GPU-resident control metadata 正在成为 CUDA Graph + Spec 的硬约束

NVFP4 Spec 的问题说明：只要一个 attention / cache path 仍要求 CPU prefix metadata，就很容易和 speculative graph replay 冲突。未来 backend interface 很可能需要更清楚地区分：

- host planning metadata；
- graph-stable device metadata；
- persistent workspace；
- per-step scratch。

### 2. KV / state 的优化单位从“整个池”变成“真正 live 的 working set”

#36087 是非常典型的方向：pool capacity 可以很大，但 decode step 只应该为 referenced pages 付费。这和之前 Unified Memory、SWA、HiCache 的很多优化是同一个思想：**把 O(capacity) 热路径逐渐消掉。**

### 3. P/D 已经越来越像一个完整分布式存储/传输系统

今天同时出现：

- CP replicated state 去重；
- backend failure terminal notification；
- endpoint snapshot / cleanup race；
- timeout fallback。

这说明 P/D 的难点已经不只是 RDMA bandwidth，而是 **ownership、failure semantics、state machine 和拓扑相关的数据分布语义**。

## 面试速记

今天建议真正记住下面 6 句话：

1. **CUDA Graph-safe = 地址稳定 + allocation-free + metadata 不依赖运行时 host round-trip。**
2. **Spec draft KV 与 target committed KV 的生命周期不同，不能因为 model ownership 合并就直接共用 cache state。**
3. **KV 热路径应按 referenced/live working set 付费，而不是按 pool capacity 做 O(N) materialization。**
4. **异步 request-pool slot 复用需要 generation/version，避免 delayed result 命中新请求——本质是 ABA。**
5. **P/D + CP 中要先判断 state 是 sharded、replicated 还是 layer-owned，再决定谁发送。**
6. **分布式 KV data plane 之外必须有 terminal failure/abort/control plane；300s timeout 不能替代失败传播协议。**
