## 1. Kimi-K3 DCP Decode 打通 Mooncake L3

**PR：[#33767](https://github.com/sgl-project/sglang/pull/33767)**  
**状态：Open，2026-08-06 新开**

### 要解决的问题

此前 Kimi-K3 在 DCP 模式下只能完成 GPU L1 与 Host L2 之间的缓存移动，不能可靠写入 Mooncake L3。主要障碍包括：

- DCP 的每个 Rank 持有不同 token shard，不能继续使用普通 TP 下的 Rank-0 replicated layout。
- Prefill 可能使用 DCP1，而 Decode 使用 DCP8；两端若直接按本地布局生成 key 和 object，无法跨请求复用。
- Kimi-K3 不只有 MLA KV，还包含 Mamba/KDA recurrent state。
- KDA 每 64 token 产生状态，但完整 DCP8 checkpoint 边界是 512 token，状态和 KV 页面容易对应错位。
- DSPARK Decode 同时注册 target KV 与 draft KV，而 Prefill 只提供 target metadata，首个真实 P→D 请求会因为 metadata 不一致失败。

### 核心改动

- Decode 继续使用 `ChunkCache`，通过专用 offload manager 把完整页面写入 Mooncake，而不是给 Decode 强行加入 RadixCache。
- 为 Mooncake 定义与本地 DCP 拓扑无关的 canonical layout：
  - `canonical_dcp_size = 8`
  - `canonical_page_size = 64`
- DCP1 写入时把连续页面 scatter 成 8 个 canonical shard；DCP8 每个 Rank 只读写自身 shard。
- MLA KV 与 Mamba/KDA sidecar 使用同一 token hash chain 和 checkpoint 边界。
- 只在完整 512-token checkpoint 处发布 KDA 状态，尾部不完整区间下次恢复后重算。
- target KV layer ID 与 draft KV layer ID 使用独立命名空间，避免 DSPARK 注册冲突。

### 工程影响

这是一个典型的“**持久化格式必须独立于运行时并行布局**”设计。它使下面的链路成为可能：

```text
DCP1 Prefill
   │
   │ P→D 实时传输
   ▼
DCP8 Decode ── MLA KV + KDA State ──> Mooncake Canonical L3
   ▲                                      │
   └──────── 下一轮 Prefill 恢复 ──────────┘
```

PR 给出的验证中，520 / 1030 / 1671 token 输入在 warm cache 和清空 L1/L2 后的 L3 恢复分别命中 512 / 1024 / 1536 token，并验证了 DSPARK 请求、历史状态恢复与 sidecar 生命周期。

### 关键代码位置

- `python/sglang/srt/disaggregation/decode_kvcache_offload_manager.py`
- `python/sglang/srt/managers/cache_controller.py`
- `python/sglang/srt/mem_cache/pool_host/mla.py`
- `python/sglang/srt/mem_cache/storage/mooncake_store/mooncake_store.py`
- `python/sglang/srt/disaggregation/{prefill,decode,utils}.py`
- `python/sglang/srt/server_args.py`

面试官可能继续追问：

## 2. Unified Mamba Radix Handoff 的瞬时容量被纳入 Admission

**PR：[#33773](https://github.com/sgl-project/sglang/pull/33773)**  
**状态：Open，2026-08-06 新开**

### 要解决的问题

混合 Mamba 模型在 unified memory 压力较大时可能触发：

```text
AssertionError: Can not alloc mamba cache
```

问题不在长期平均容量，而在 **radix-cache handoff 的瞬时峰值**：缓存一个未完成请求时，需要先分配新的 Mamba slot，再把当前 tracking state 捐赠给 radix tree。旧 admission 只计算稳定态占用，没有预留这段短暂的“双份状态”空间。

此外，分配失败后的回收逻辑只尝试驱逐 Mamba cache，即使 Full KV cache 也占用了同一 unified byte pool。

### 核心改动

- Admission 按请求实际需要的 Mamba slot 数计算预算。
- 为正在运行和新接纳请求预留 radix handoff 峰值。
- 回收顺序改为：
  1. 先驱逐可回收的 Mamba 状态；
  2. 不足部分再驱逐 Full KV，释放共享容量。
- 增加分配诊断和 CPU regression tests。

### 工程影响

该改动不增加 GPU 同步，只增加常数级 Host accounting。新回归用例在主分支上 5 个失败，在该 PR 上全部通过；相关测试共 30 个通过。

这个 PR 的价值在于说明：

> **Admission control 必须按操作峰值而不是最终稳定态计算资源。**

这与存储系统中的 copy-on-write、日志切换、checkpoint publish 和 compaction headroom 是同一类问题。

### 关键代码位置

- `python/sglang/srt/managers/schedule_policy.py`
- `python/sglang/srt/mem_cache/allocation.py`
- `python/sglang/srt/mem_cache/memory_pool.py`
- `python/sglang/srt/mem_cache/unified_cache/components/mamba_component.py`

## 3. Scheduler WAR Fence 与 CUDA Graph 元数据读取边界对齐

**PR：[#33587](https://github.com/sgl-project/sglang/pull/33587)**  
**状态：Merged，2026-08-05 20:52 UTC 合入**

### 要解决的问题

Overlap Scheduler 会在 GPU 执行上一批 forward 时，让 CPU 准备下一批请求。但下一批准备过程会改写共享 request / attention metadata，因此必须等上一批完成最后一次读取后才能写入。

旧设计存在两个问题：

- Decode 只能在整个 CUDA Graph replay 前后发布 fence，无法表达 graph 内部“元数据已经读完”的精确边界。
- Prefill 使用整个 forward 级别的粗粒度 barrier，导致本可并行的 CPU 调度工作被推迟。

TRTLLM MHA 的 SWA cache write 还可能在 fence 提前解除后重新读取 live `full_to_swa` mapping。

### 核心改动

- Decode：将多数 `read_done` fence 推迟到 CUDA Graph metadata 初始化完成后解除。
- Spec Decode / Target Verify：允许具体 speculative backend 声明是否支持更早解除 fence。
- Prefill：通过 `SGLANG_ENABLE_PREFILL_WAR_READ_DONE=1`，在 metadata 初始化结束后解除 fence。
- TRTLLM MHA：在 metadata preparation 阶段 snapshot SWA write location，后续各层使用 snapshot，不再读取可被 Scheduler 改写的 live mapping。

### 性能与工程影响

PR 的 Nsight 时间线显示：

- 长 Prefill 中，Scheduler 操作可以与 forward kernel 基本完全重叠。
- 短 Prefill 中，Scheduler 能在 kernel launch 完成后更早启动。
- 多轮请求场景中，forward occupancy 和 TTFT 均得到改善。

该改动同时覆盖 Decode、Prefill 和 Target Verify，是今天唯一已经合入的核心 Scheduler 变化。

### 关键代码位置

- `python/sglang/srt/model_executor/runner/decode_cuda_graph_runner.py`
- `python/sglang/srt/model_executor/runner/prefill_cuda_graph_runner.py`
- `python/sglang/srt/model_executor/runner_utils/war_event.py`
- `python/sglang/srt/layers/attention/trtllm_mha_backend.py`
- `python/sglang/srt/speculative/spec_registry.py`

### 面试启发

这是经典的跨 CPU/GPU 流水线依赖问题：

- RAW：GPU 必须看到 Scheduler 写好的 metadata。
- WAR：Scheduler 重写 metadata 前，必须确保 GPU 已完成最后一次读。
- Snapshot：把后续 kernel 会读取的数据固化，缩短共享状态的生命周期。

关键不是“加 barrier”，而是把 barrier 放在 **最晚保证正确、又最早允许并行** 的位置。

## 4. DSPARK 多 TP Rank 状态分歧修复继续推进

**PR：[#33614](https://github.com/sgl-project/sglang/pull/33614)**  
**状态：Open，过去 24 小时继续更新**

### 要解决的问题

当 `TP > 1` 时，DSPARK 在各 Rank 上独立产生多个会改变后续状态的决策：

- Markov draft chain 每一步 proposal token；
- Target Verify 的 `correct_len`、`bonus`、`cap_trim_lens`；
- Prefill 的 `next_token_ids`。

SGLang 为减少通信默认不强制同步采样结果。一旦任意 Rank 的 token 或 accept length 不同，sequence length 和 KV state 会逐步漂移，最终在后续 collective 中死锁。

### 核心改动

新增 `DsparkTpSync`：

- 每个 Markov step 都广播 Rank 0 proposal，不能只在整个 draft block 结束后同步。
- Verify finalize 和 KV commit 前广播 accept-related decisions。
- Prefill 进入 draft path 前广播 `next_token_ids`。
- CUDA Graph 内使用已有 TP PyNCCL communicator；DP Attention 下使用 `attn_tp_group`。

代价是每个 Decode step 增加约 `gamma + 3` 次 `[batch_size]` 小张量广播。

### 验证结果

- GSM8K 200 题准确率：`0.965`，invalid 为 `0`。
- 注入 Rank-local accept divergence 后：旧实现死锁，新实现由 Rank 0 广播覆盖差异并正常启动。
- 42 个连续请求，每个生成 512 token，合计 21,504 token，全部返回 HTTP 200。
- 温度为 1 的测试中平均 accept length 为 `2.86`（block size 4）。

### 关键代码位置

- `python/sglang/srt/speculative/dspark_components/dspark_tp.py`
- `dspark_draft.py`
- `dspark_draft_sampler.py`
- `dspark_verify.py`
- `dspark_worker_v2.py`

### 面试启发

仅同步 RNG seed 并不能保证状态机一致：各 Rank 可能消耗不同数量的随机数，也可能因浮点误差、mask 或 batch shape 走不同路径。真正需要同步的是 **会进入持久状态的语义决策**。

## 5. Unified Memory 与 P/D Disaggregation 的传输边界逐渐清晰

**PR：[#33362](https://github.com/sgl-project/sglang/pull/33362)**  
**状态：Open，过去 24 小时更新**

### 要解决的问题

Unified KV/Mamba pool 在上层使用 virtual ID，底层数据采用 page-major envelope layout，并可能在 compaction 时搬动物理页面；而 Mooncake RDMA 直接按：

```text
pointer + physical_index × item_length
```

访问原始字节。如果传输期间页面被 compact，远端读到的位置就会失效。

### 核心改动

- KV 与 Mamba 状态按完整 page envelope 注册和传输，而不是逐 layer 注册。
- 在 Prefill send 和 Decode preallocation handoff 处把 virtual ID 翻译成 physical page ID。
- PD + Unified Memory 强制使用 lazy compaction。
- 引入 `disagg_move_gate`：存在 in-flight transfer 时禁止物理页面搬迁。
- Decode request pool 增加预分配行，保持 request-row invariant。
- Mooncake 对同一 raw allocation 的重复 region registration 做去重。

### 验证结果

Kimi-Linear-48B、Prefill TP2 + Decode TP2、Mooncake RDMA 测试中：

- PD Unified GSM8K 400 题准确率 `0.910`；
- 非 P/D Unified baseline 为 `0.900`；
- Static Pool 为 `0.915`；
- 19K prompt、3 个 Prefill chunk 的检索测试能够正确使用首块传输的 KV；
- 既有 disaggregation unit tests 共 92 个通过。

### 面试启发

这与存储中的 DMA pinning、zero-copy buffer lifetime 和 compaction epoch 非常相似：

> 传输协议不仅需要“地址”，还需要保证从注册、提交到 completion 的整个期间，地址对应的数据不会被移动或复用。

## 新问题与风险观察

### 1. Mamba Host Cache 已备份，但节点被直接从 Radix Tree 删除

**Issue：[#33713](https://github.com/sgl-project/sglang/issues/33713)**

Unified cache 在设备层驱逐 hybrid-KDA/Mamba node 时，只检查 Full KV component 的 `host_value`，忽略 Mamba component 已经存在的 Host copy，导致整个 node 被 prune，而不是降级为 Host-resident leaf。

结果是下一次相同 prefix：

- Radix Tree 找不到节点；
- 不会发起 H→D load back；
- 即使 L2 实际已有数据，也表现为完整 cache miss。

重点代码：

- `python/sglang/srt/mem_cache/unified_cache/unified_tree_core.py`
- `python/sglang/srt/mem_cache/unified_cache/components/mamba_component.py`

### 2. Cold Long Prompt 因 Chunked Prefill 永久错过 Write-through

**Issue：[#33714](https://github.com/sgl-project/sglang/issues/33714)**

当首次请求的 extend length 超过 `chunked_prefill_size` 时，请求被永久标记为 chunked，Unified HiCache 的 write-through eligibility 直接返回 false。即使 Prefill 最终完成，也不会触发 `BACKUP_HOST` 或 `BACKUP_STORAGE`。

观测结果：

- Cold 4,100-token prompt：成功写 L3；
- Cold 8,200-token prompt：零 storage write；
- 第二次请求因大部分 prefix 已命中、extend 变短，才开始写入 L3。

推荐方向是 **backup-on-finalize**：Prefill 分块不应等价于整个请求永远不能持久化。

重点代码：

- `python/sglang/srt/mem_cache/unified_cache/unified_tree_core.py`
- `python/sglang/srt/managers/schedule_policy.py`
- `python/sglang/srt/mem_cache/hi_mamba_radix_cache.py`

## 对 AI Infra 面试的提炼

今天的变化可以整理成五个高价值问题：

1. **为什么 P/D 传输必须区分 virtual page ID 与 physical page ID？**  
   上层稳定索引用于管理和引用，DMA/RDMA 需要当前物理地址；compaction 会让两者映射变化。

2. **为什么跨 DCP 拓扑的 L3 缓存需要 canonical layout？**  
   持久化对象必须由逻辑 token 范围定义，而不是由当前节点的本地并行切分定义。

3. **为什么 Admission 需要计算瞬时峰值？**  
   Radix handoff、COW、checkpoint publish 都可能在旧资源释放前先分配新资源。

4. **Overlap Scheduler 的 WAR fence 应放在哪里？**  
   放在 GPU 对共享 metadata 的最后一次读取之后，而不是整个 forward 结束之后；必要时通过 snapshot 缩短读取生命周期。

5. **为什么 Speculative Decoding 多 Rank 不能只同步随机种子？**  
   要同步的是 proposal、accept length 和 KV commit 等会改变状态机的语义结果。
