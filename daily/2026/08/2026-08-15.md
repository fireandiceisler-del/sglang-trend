## 一句话判断

今天最明显的趋势不是“又多了一个 kernel”，而是 **SGLang 正在继续把推理系统的异步边界做细**：KV prefetch 的并行度必须随 batch 扩展，P/D 控制面不能阻塞 decode scheduler，Speculative Decoding 的 WAR fence 要落到真正的最后一次共享状态读取点，ragged decode 甚至开始按 KV 长度重排 batch。与此同时，DCP、HiCache、DSPARK、P/D 组合后暴露出的“逻辑索引 vs 物理索引”“target KV vs draft KV”语义正在成为新的 correctness 核心。

## 1. 今日结论

1. **Scheduler × Spec 的优化重点正在从“是否 overlap”转向“精确到 phase / buffer read boundary 的 overlap”。** #34816 已合入，让 DSPARK 在 verify 阶段发布 WAR read-done；#34890 进一步把 EAGLE v2 的 draft-extend 输入提前 staging，使 verify 后就能释放 scheduler，PR 报告 TP4、并发 128 下 decode throughput +36%，forward occupancy 65% → 94%。
2. **异步 prefetch 不天然比同步快。** #34847 展示了一个很典型的反例：固定 4-block grid 在 batch 增大后反而让 side-stream copy 成为 critical path；改成 one-block-per-request 后，BS=54 相对旧实现快 245.8%，并重新恢复为相对同步 swap-in 的 10%+ 正收益。
3. **Speculative Decoding 的“accept length”本质上也是 correctness / topology 指标。** #34846 中 DSpark draft MoE 因逻辑 expert ID 没映射到物理 expert slot，最终答案仍可由 target verify 保证正确，但平均 accept length 从 3.38 掉到 1.61，几乎把投机加速打没。
4. **P/D 的瓶颈正在从 KV bandwidth 扩展到 control plane。** #34865 修的是 decode scheduler 上同步 HTTP 请求造成的 5 秒级停顿；Issue #34815 则显示 PP8 prefill 即使吞吐能力不差，也可能因为 bootstrap / consensus round 出现约 30 秒 TTFT floor。
5. **DCP × HiCache × Spec × P/D 的可组合性仍未真正收口。** #34343 正在拆分 target KV 与 DSPARK draft KV 的 index semantics；DCP Q3 Roadmap 里 `DCP × DSpark × HiCache × PD Disagg` 仍是未完成项。

## 2. 重点 PR / Issue

### 2.1 [#34816](https://github.com/sgl-project/sglang/pull/34816) — DSPARK 在 verify 阶段发布 WAR read-done

**状态：已合入（2026-08-14）**  
**方向：Scheduler × Speculative Decoding**

#### 解决的问题

DSPARK 没有独立的 `draft_extend` phase：draft sampling 本身就在 verify CUDA Graph 中完成。原来的 `is_war_publish_phase()` 因此找不到合适的发布点，Scheduler 的 WAR barrier 会退化为“等整个 forward 完成”，导致 overlap scheduler 无法提前准备下一批请求。

#### 核心改动

- 对 DSPARK，把 `target_verify` 视为本 step 最后一次共享 buffer 读取的 phase。
- DeepSeek V4 attention backend 对 DSPARK verify 使用 `SharedReadBoundary.IN_REPLAY`，允许在 graph 内精确记录 read-done。
- `is_war_publish_phase()` 从仅覆盖 DFlash 扩展到 DSPARK。

#### 相关代码

- `python/sglang/srt/layers/attention/deepseek_v4_backend.py`
- Spec algorithm 的 WAR publish phase 判定逻辑

#### 工程影响

这个 PR 本身很小，但意义很大：**WAR fence 不应按“forward 函数结束”划分，而应按“共享 metadata 最后一次被 GPU 读取”划分。** 这正是 overlap scheduler 从粗粒度流水线走向数据依赖驱动调度的典型演进。

#### 面试启发

如果面试官问“为什么 CUDA Stream 已经异步了，CPU scheduler 还会被卡住”，可以回答：GPU 异步并不等于共享 host/device buffer 可以立刻重写。Scheduler 必须知道上一轮 GPU 对这些 buffer 的最后读取边界，否则会产生 WAR hazard；过早写会错，过晚 fence 又会损失 overlap。

### 2.2 [#34890](https://github.com/sgl-project/sglang/pull/34890) — EAGLE v2 把 draft-extend 输入提前 staging，verify 后即可释放 WAR fence

**状态：Open，窗口内新 PR**  
**方向：Scheduler × EAGLE / Speculative Decoding**

这是 #34816 背后的设计继续向 EAGLE v2 推进。

#### 解决的问题

EAGLE v2 的下一阶段 `draft_extend` 还会读取一批共享 CUDA Graph 输入，因此即使 target verify 已结束，Scheduler 仍不能安全覆盖这些 buffer，只能等待更晚的阶段。

#### 核心改动

在 verify launch 之前，把 draft-extend 后续需要的共享输入预先 staging / snapshot，使其不再依赖 scheduler 即将复用的共享 buffer。这样 verify 成为真正的最后一次共享读取边界，WAR read-done 可以更早发布。

#### PR 报告的性能数据

- EAGLE，TP4，concurrency=128：**decode throughput +36%**
- model forward occupancy：**65% → 94%**

> 注意：该 PR 仍处于 Open 状态，数据应视为作者当前 benchmark，而不是稳定 release 结论。

#### 相关代码

- `python/sglang/srt/layers/attention/deepseek_v4_backend.py`
- `python/sglang/srt/model_executor/runner/decode_cuda_graph_runner.py`
- `python/sglang/srt/speculative/eagle_draft_extend_cuda_graph_runner.py`
- `python/sglang/srt/speculative/eagle_worker_v2.py`
- `python/sglang/srt/speculative/spec_info.py`

#### 面试启发

这里非常适合解释 **snapshot、lifetime 与 synchronization 的区别**：

- `record_stream` 只能保证 allocator 不提前复用一块 tensor memory；
- snapshot/pre-staging 可以让后续 phase 不再依赖那块可变共享内存；
- event/fence 决定 Scheduler 何时可以覆盖共享 buffer。

三者解决的是不同问题。

### 2.3 [#34847](https://github.com/sgl-project/sglang/pull/34847) — HiSparse prefetch replay 从固定 grid 改为 one-block-per-request

**状态：Open，窗口内新 PR**  
**方向：KV Cache / HiSparse / P-D Decode**

#### 解决的问题

HiSparse 的 `copy_cache_planned_kernel` 会把 shared-index anchor 已经计算好的 miss plan 重放到 skip layer 的 device buffer。旧实现为了减少 SM 占用，固定只发 `num_blocks=4`，所有请求的 miss 通过这几个 warp round-robin 处理。

问题在于：总工作量随 `batch_size × misses_per_request` 增长，但并行度固定。batch 变大后，原本应该和 compute overlap 的 side-stream copy 反而越来越慢，skip layer 还必须等待它完成，最终 **prefetch 比同步 swap-in 更慢**。

#### 核心改动

- grid 改成 `num_blocks = num_reqs`；
- 每个 request 对应一个 block，只处理自己的 miss list；
- warp 在 block 内部再对该请求 miss 做 round-robin。

#### Benchmark

8× RTX PRO 6000、GLM-5.2 NVFP4、TP8、P/D decode、32K input / 4K output：

| BS | 同步 swap-in | 旧 prefetch | 新 prefetch | 新版 vs 同步 | 新版 vs 旧版 |
|---:|---:|---:|---:|---:|---:|
| 1 | 44.84 | 45.42 | 50.09 | +11.7% | +10.3% |
| 8 | 269.87 | 150.95 | 318.79 | +18.1% | +111.2% |
| 16 | 392.70 | 188.11 | 462.51 | +17.8% | +145.8% |
| 32 | 558.33 | 218.37 | 633.26 | +13.4% | +190.0% |
| 54 | 700.74 | 223.35 | 772.35 | +10.2% | +245.8% |

最重要的不是 245.8% 这个数字本身，而是：**旧 prefetch 从 BS≈2 开始已经输给同步路径**，说明固定 launch geometry 会让“异步优化”随着并发扩大而翻转成 regression。

#### 相关代码

- `python/sglang/kernels/jit/csrc/hisparse.cuh`
- `python/sglang/srt/managers/hisparse_coordinator.py`
- `test/registered/kernels/ops/kvcache/test_hisparse.py`

#### 面试启发

面试里可以用它回答“为什么异步 I/O/拷贝不一定更快”：异步只提供并行机会，如果 side stream 本身因为并行度不足变成长尾，主 stream 最终还是会在 event 上等它。需要分析 **producer/consumer 的临界路径，而不是只看有没有 overlap**。

### 2.4 [#34846](https://github.com/sgl-project/sglang/pull/34846) — DSpark draft MoE expert-location 映射错误导致 acceptance 崩塌

**状态：Open，窗口内新 PR**  
**方向：Speculative Decoding / EPLB / MoE**

#### 解决的问题

DSpark 复用了 DeepSeek NextN decoder layer。普通 MTP 为避免额外开销，NextN MoE 默认跳过 expert-location dispatch；但 DSpark 的 draft expert weight 会根据全局 expert-location metadata 放到重映射后的物理 slot。

于是出现语义错位：

`gate 输出 logical expert ID` → **未转换** → `直接索引 remapped physical slot`

Draft 实际执行的是错误 expert，target verify 最终仍可保证输出正确，但 draft 质量大幅下降。

#### 核心改动

- 给 NextN MoE 增加可选 expert-location dispatch；
- 普通 MTP 默认仍关闭，避免改变原有性能；
- 只在 `DSparkV4Stage` 打开 logical-to-physical expert 映射。

#### Benchmark

相同配置下：

- average accept length：**1.61 → 3.38**
- output throughput：**161.64 → 313.24 tok/s（约 +94%）**
- total token throughput：**576.49 → 1117.15 tok/s（约 +94%）**
- mean TPOT：**45.80 → 21.82 ms（约 -52%）**
- mean E2E：**78.0 s → 40.1 s**
- TTFT：4.95 s → 5.31 s，略有退化

#### 相关代码

- `python/sglang/srt/models/deepseek_v2.py`
- `python/sglang/srt/models/deepseek_v4_dspark.py`

#### 面试启发

这是一个非常好的 Spec 面试案例：**最终 accuracy 正确，不代表 speculative path 正确。** 因为 target model 会 reject 错误 draft，所以错误可能只表现为 accept length / TPOT / throughput 崩坏。排查投机解码必须同时看：

`draft correctness → acceptance → verify cost → end-to-end throughput`

而不能只看最终答案。

### 2.5 [#34865](https://github.com/sgl-project/sglang/pull/34865) — 把 Prefill parallel-info HTTP fetch 移出 Decode Scheduler 线程

**状态：Open，窗口内新 PR**  
**方向：P/D Disaggregation / Scheduler reliability**

#### 解决的问题

`CommonKVManager.try_ensure_parallel_info()` 名义上是 non-blocking probe，但内部直接执行同步：

```text
requests.get(..., timeout=5s)
```

调用链却位于 decode scheduler admission 路径：

```text
SchedulerDisaggregationDecodeMixin.process_decode_queue
  -> DecodePreallocQueue.pop_preallocated
  -> _resolve_pending_reqs
  -> _ensure_prefill_info
  -> try_ensure_parallel_info
```

一个不可达 Prefill endpoint 就可能把 decode scheduler 卡 5 秒；连续多个 retry / address 时，可形成数十秒停顿。更糟的是 health check 可能因此认为 decoder 已失效，Router 再把流量转走，形成级联过载。

#### 核心改动

- 使用小型 `ThreadPoolExecutor` 执行 blocking fetch；
- 每个 address 最多一个 in-flight fetch；
- scheduler loop 只轮询 async result，不等待网络；
- config mismatch 等真实错误仍回到 scheduler thread 抛出；
- in-flight fetch 不消耗 retry attempt。

#### 相关代码

- `python/sglang/srt/disaggregation/common/conn.py`
- `python/sglang/srt/disaggregation/decode.py`
- `test/registered/unit/disaggregation/test_parallel_info_nonblocking.py`

#### 工程影响

这是典型的推理系统控制面原则：**任何可能毫秒以上阻塞的网络控制操作，都不应该直接跑在 token scheduler 主循环里。**

#### 面试启发

P/D 不只是“Prefill GPU 把 KV 通过 RDMA 发给 Decode GPU”。完整设计还包括 bootstrap、metadata discovery、failure detection、retry、endpoint replacement 等 control plane；它们一旦和 scheduler hot path 耦合，就能把一个网络抖动放大成整个 decoder 的 ITL/availability 事故。

### 2.6 [#34815](https://github.com/sgl-project/sglang/issues/34815) — PP8 P/D Prefill 出现与负载无关的约 30s TTFT floor

**状态：Open Issue，窗口内值得重点观察**  
**方向：P/D Disaggregation × Pipeline Parallelism**

这个 Issue 的价值在于它说明：**吞吐足够，不代表 TTFT 正常。**

报告中的 Kimi-K3 P/D 对比里：

- PP8×TP1 Prefill TTFT p50：约 **31.1 s**
- TP8 reference：约 **2.33 s**
- 差距约 **13.4×**

但 PP8 本身并不是单纯算力不足：synthetic 8K 测试里 pure-prefill capacity 可以达到约 22.5K tok/s，甚至不差于 TP8 的约 20.4K tok/s。

Issue 的 timing breakdown 把问题指向 control path：bootstrap median 约 12.45 s，远高于 TP8 的毫秒级；怀疑 `event_loop_pp_disagg_prefill` 中的 PP consensus ring 对 bootstrap admission 和 KV release confirmation 做了多轮串行传递。

#### 面试启发

这正好区分两个概念：

- **capacity / throughput**：系统单位时间能处理多少 token；
- **critical-path latency**：一条请求为了拿到首 token 必须依次经过多少同步 round。

PP/P-D 组合时，控制消息如果按 stage 逐跳串行，即使所有 GPU 都很忙、总吞吐很高，也可能出现巨大的固定 TTFT floor。

### 2.7 [#34888](https://github.com/sgl-project/sglang/pull/34888) — TRTLLM MHA decode 按 sequence length 拆 ragged batch

**状态：Open，窗口内新 PR**  
**方向：Scheduler / Decode batching / Spec verify**

#### 背景

同一个 decode batch 中请求 KV 长度差异很大时，persistent attention kernel 的尾部会被最长 sequence 拖住。PR 在 GB300、Qwen3.5-397B-A17B-NVFP4 上观察到：保持 batch size、平均 context 和 draft 数量相近，仅把 context 从均匀 92K 改为 30K/70K/110K/170K 混合，steady decode step 从 49.7 ms 上升到 57.5 ms，约 +16%。

#### 核心改动

- 按 KV length 排序；
- 划分为若干等大小 group；
- 每组单独执行 TRTLLM MHA decode；
- 最后 scatter 回原 request 顺序；
- ordinary decode 和固定 q_len 的 speculative target verify 都支持。

#### Benchmark

- mixed-ISL speculative iteration：**57.485 → 51.639 ms（-10.17%）**
- q_len=1 attention：约 **-15.9%**
- q_len=6 attention：约 **-33.3%**
- uniform workload：约 +0.2%，基本持平

当前仍通过 `SGLANG_TRTLLM_MHA_DECODE_SEQ_LEN_SPLITS` opt-in；作者也发现拆成 4 组反而更差，说明 group 数需要权衡额外 launch 与 tail reduction。

#### 相关代码

- `python/sglang/srt/environ.py`
- `python/sglang/srt/layers/attention/trtllm_mha_backend.py`
- `test/registered/attention/unittests/dense/test_trtllm_mha.py`

#### 面试启发

Continuous batching 的 batch size 相同，不代表执行效率相同。对 attention 来说，**KV length distribution / raggedness** 也会决定 CTA 利用率和尾部等待。Scheduler 的 cost model 最终可能需要从“token 数”升级到“shape distribution”。

### 2.8 [#34343](https://github.com/sgl-project/sglang/pull/34343) — DCP + P/D + DSPARK 的 index-space 语义拆分继续推进

**状态：Open，过去 24 小时仍有活跃更新 / review**  
**方向：P/D × DCP × Speculative Decoding**

#### 核心问题

DCP 下 target KV 的 token index 会按 owner 做虚拟化 / relayout；但 DSPARK draft KV pool 是 replicated，期望的是未翻译的 row index。此前 target KV 和 draft KV 共用一套 `kv_indices`，导致同一个“index”在两个 pool 中表示不同物理含义，bootstrap thread 可能直接异常退出，最终请求表现为永久 hang。

#### 当前方案

- 把 DSPARK draft KV 独立成 `StateType.DSPARK_DRAFT_KV`；
- draft KV 按 row-verbatim 方式传输，不套 target KV 的 DCP index translation；
- 恢复 spec path 的 `kv_layer_ids` 以支持 PP×DCP layer matching；
- bootstrap 异常显式标记 session failure，避免后台线程死掉后前台无限等待；
- 对暂时不兼容的 NIXL / HiCache / Prefill-CP 组合提前 fail fast。

#### 面试启发

分布式缓存系统里最危险的 bug 往往不是“index 越界”，而是 **同一个整数在不同 component 中代表不同地址空间**。设计接口时最好显式区分 logical token id、DCP virtual slot、physical KV row、replicated draft row，而不是让一个 `kv_indices` 贯穿所有路径。

### 2.9 [#34889](https://github.com/sgl-project/sglang/pull/34889) — HiCache DCP index localization 从“每层一次”收敛到“每次 transfer 一次”

**状态：Draft / WIP**  
**方向：KV Cache / HiCache × DCP**

Kimi 一次 HiCache load 有 24 个 MLA layer，旧路径在每层 `load_to_device_per_layer()` 都做一次 widened logical index → physical row translation，导致一次 load 中出现 48 个 boolean-index kernel launch。WIP 方案把 localization 提到 transfer 级别，只做一次，再复用到各 layer。

目前 benchmark 还未补齐，因此今天只把它列为**值得观察的方向**，不做性能结论。

### 2.10 [#34876](https://github.com/sgl-project/sglang/pull/34876) — Decode Req Pool slot allocation 从 O(pool_size) 降为 O(need_size)

**状态：Open**  
**方向：P/D Decode Scheduler hot path**

`DecodeReqToTokenPool.alloc()` 以前从 `free_slots` 头部切片后重建剩余 list，池越大越慢；P/D decode 还有 `pre_alloc_size`，问题更明显。改成从 tail slice + delete 后，synthetic 16K pool、约 90% free 时：

- batch=1：约 28.5 μs → 0.34 μs
- batch=4：约 28.7 μs → 0.34 μs
- microbenchmark 提升约 **83–86×**

这还不是 E2E throughput 结论，但很典型：高并发 scheduler hot path 中，任何与“总容量”相关的 O(N) 操作都会随着资源池扩大逐渐暴露。

相关代码：`python/sglang/srt/disaggregation/decode.py`。

[DCP Q3 Roadmap #29736](https://github.com/sgl-project/sglang/issues/29736) 当前仍明确把下面几类组合列为未完全收口：

今天的 #34343、#34889 本质上都在填这张组合矩阵：一个解决跨 P/D 的 state/index 语义，一个减少 DCP×HiCache 的重复 index translation。

我的判断是：**接下来 SGLang 的高价值工作会越来越多地发生在 feature 交叉点，而不是单个 feature 内部。**

## 5. 今天最值得带去 AI Infra 面试的 6 个问题

1. **为什么 async prefetch 会比 sync copy 更慢？** 关注 launch geometry、side-stream critical path、event wait，而不是只回答“可以 overlap”。
2. **`record_stream`、CUDA Event、tensor snapshot 各自解决什么问题？** 分别是 allocator lifetime、execution ordering、mutable-buffer ownership / immutability。
3. **为什么 speculative decoding 最终 accuracy 正常，但性能可能完全坏掉？** Target verify 可以保 correctness，但 draft expert mapping / state mapping 错误会让 acceptance 崩掉。
4. **P/D disaggregation 为什么必须把 control plane 从 scheduler hot path 隔离？** 因为 metadata discovery / HTTP / retry 的秒级尾延迟会直接放大成 decoder 停顿和 health-check 误判。
5. **DCP 下为什么不能让 target KV 和 replicated draft KV 共用同一种 index？** 它们属于不同物理地址空间，translation 规则不同。
6. **Continuous batching 为什么不能只按 batch size 或 token count 做 cost model？** Ragged KV length 会改变 persistent attention 的 CTA occupancy 和 tail latency。
