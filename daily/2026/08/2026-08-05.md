## 1. DSPARK 支持 P/D 分离下的原生 Draft-KV 传输

**PR：[#33204 — DSPARK PD-disaggregation via native draft-KV transfer](https://github.com/sgl-project/sglang/pull/33204)**

### 解决的问题

DSPARK、P/D Disaggregation 与文件型 HiCache 原本不能顺畅组合。Prefill 节点虽然能够生成 target KV，但 Decode 节点运行 DSPARK 时还需要对应的 draft KV；只传 target KV 会破坏推测解码状态。

### 核心改动

- Prefill Engine 同样启用 `--speculative-algorithm DSPARK`；
- Prefill 阶段根据 target hidden states 构建 draft KV；
- P/D 传输同时携带 target KV 与 draft KV；
- 对 DSV4 / SWA 场景复用已有 KV 传输路径，而不是引入完整 hidden-row transfer 系统；
- Prefill 与 Decode 两侧必须使用一致的 DSPARK 配置。

### 工程影响

这是一个很有价值的架构信号：**推测解码状态正在成为 P/D 传输协议的一等数据**。以后做 P/D 设计时，不能只考虑普通 Attention KV，还要考虑：

- Draft KV 的格式和生命周期；
- Target/Draft 两套缓存的一致性；
- HiCache 命中和回填时是否同时恢复 speculative state；
- 异构 TP 下 Draft KV 如何重分片。

PR 报告在单用户场景中观察到约 **3–5×** 的 DSPARK 改善，但尚需更系统的端到端 benchmark 和 CI 验证。

### 建议精读

- `spec_info.py` 中 `build_disagg_draft_input`；
- P/D KV transfer 对 DSV4 / SWA draft KV 的打包方式；
- `FutureMap.resolve_future` 在 overlap 路径中的行为。

## 2. 修复 DSPARK 多 TP Rank 状态分歧

**PR：[#33614 — Fix Dspark state divergence across TP rank](https://github.com/sgl-project/sglang/pull/33614)**

### 解决的问题

TP > 1 时，每个 rank 默认可能独立完成以下决策：

- Draft Markov Chain 的 proposal token；
- Target Verify 的 `correct_len`、`bonus`、`cap_trim_lens`；
- Prefill 结束时的 `next_token_ids`。

SGLang 为避免同步开销，通常不会同步采样 token。一旦不同 rank 采样出不同 token 或接受长度，请求长度和 KV 状态就会逐步分叉，最终可能在后续 collective 中死锁。

### 核心改动

新增 `DsparkTpSync`，以 rank 0 为准广播：

- 每一步 Markov proposal token；
- Verify 阶段的接受长度和 bonus 信息；
- Prefill 进入 draft path 前的 next token。

同步同时覆盖 eager 与 CUDA Graph folded-sampling 路径，并在 DP Attention 下使用对应的 attention TP group。

### 性能与取舍

代价是每个 Decode Step 增加约 `gamma + 3` 次 `[batch_size]` 小 Tensor 广播。这里体现了一个典型分布式推理权衡：

> 省略同步可以减少延迟，但只要状态会影响 KV 提交、序列长度或后续 collective 顺序，就必须保证跨 rank 一致。

PR 的稳定性测试中，在双 DGX Spark、TP2、temperature=1 的负载下完成 42 个连续请求，共生成 21,504 token，未再出现死锁；当前 CI 尚未全部通过。

### 面试关联

可以把这个问题类比为复制状态机：proposal token 和 accept length 实际上是后续 KV 状态转换的“日志”。各 rank 若执行不同日志，即使每一步都局部合法，系统状态最终也会分叉。

## 3. Scheduler 的 WAR Fence 对齐 CUDA Graph 内部读边界

**PR：[#33587 — Align WAR fences with CUDA graph metadata reads](https://github.com/sgl-project/sglang/pull/33587)**

### 解决的问题

Overlap Scheduler 会在前一个 batch 尚在 GPU 上执行时准备下一个 batch。调度器准备新 batch 时会重写 request/attention metadata，因此必须等待上一轮 forward 完成最后一次读取。

此前 fence 粒度过粗：

- Decode 只能在整个 CUDA Graph replay 前后发布边界；
- Prefill 基本要等待整个 forward；
- 某些 SWA KV 写入仍会读取 live mapping，而不是本次 forward 的 metadata snapshot。

结果是 CPU Scheduler 无法充分与 GPU Forward 重叠。

### 核心改动

- Decode：把 `read_done` fence 推迟到 CUDA Graph metadata 初始化之后的正确位置；
- Target Verify：允许 speculative backend 声明是否支持提前释放 WAR fence；
- Prefill：通过 `SGLANG_ENABLE_PREFILL_WAR_READ_DONE=1` 开启更细粒度 fence；
- TRTLLM MHA SWA：在 metadata 准备阶段快照 cache write location，执行层只消费快照。

### 工程影响

核心思想是：

> 不必等待整个 GPU Forward 完成，只需等待 GPU 完成对“即将被 CPU 改写的数据”的最后一次读取。

这与数据库/并发系统里的生命周期管理很像。优化 Scheduler 时，真正困难的不是“多开一条 stream”，而是找出每块共享 metadata 的精确最后读位置。

PR 给出的 Nsight 结果显示，长 Prefill 下 Scheduler 操作可以基本完全隐藏在 Forward 内，但暂未给出统一数字化 benchmark。

## 4. HiCache 可观测性增强

**PR：[#32388 — Observability enhancement for HiCache](https://github.com/sgl-project/sglang/pull/32388)**

### 核心改动

新增或细化：

- 分层 Cache Hit Counter；
- Backup Token、Load-back Token；
- Write-back 策略下的 Dropped Token；
- 更准确的加载时间与内存占用统计；
- 基于实时计数计算带宽。

### 为什么重要

分层 KV Cache 的优化必须能够区分：

- GPU / CPU / SSD 各层命中率；
- 读回流量与后台写回流量；
- 缓存淘汰和丢弃是否制造写放大；
- 带宽不足究竟来自介质、传输、锁竞争还是调度。

没有分层指标，只看整体 TTFT/TPOT 很难定位瓶颈。该 PR 目前更偏工程可观测性，尚未给出性能 benchmark。

## 5. Decode CUDA Graph：移除每层临时分配

**PR：[#33063 — Stop allocating per-layer scratch inside decode CUDA graph](https://github.com/sgl-project/sglang/pull/33063)**

### 解决的问题

TRTLLM-MHA Decode 路径在每个 Attention Layer 中重复创建：

- multi-CTA KV counter buffer；
- 缺省 KV scale 对应的 `ones` Tensor。

这些分配在 CUDA Graph 捕获后会固化成重复的 Fill Kernel，还会打断相邻 kernel 的 PDL 依赖链。

### 核心改动

- 在 Backend 构造阶段持久化分配 counter buffer；
- 持久化一个 FP32 标量 Tensor，供没有 checkpoint KV scale 的层复用；
- Decode 和 Target Verify 共享这些持久缓冲区。

### Benchmark

Qwen3.5-397B-A17B-FP8、4×B200、TP4、batch size 1、输入 8192：

- 每个 Decode Step 减少 **45 次 kernel launch**；
- 每步减少约 **90 μs**；
- 相对 5.490 ms 的 Decode Step，约提升 **1.64%**。

这类优化说明：在低 batch Decode 下，小型 allocation/fill kernel 的固定开销仍然值得系统性清理。

## 架构观察

### 观察 1：P/D 的传输对象正在扩展

P/D 不再只是传普通 KV。未来协议可能同时承载：

- Target KV；
- Draft KV；
- DSA index cache；
- Hybrid model state；
- Cache tier metadata；
- Speculative accept/reuse state。

### 观察 2：Scheduler 优化进入“精确生命周期”阶段

大的 overlap 框架已经存在，近期工作更多是在细化：

- 哪个 Metadata 何时最后读；
- 哪个 Buffer 可跨层/跨 step 复用；
- CUDA Graph 内什么位置可以释放 CPU 写权限；
- Spec Verify 与普通 Decode 是否共享同一套同步协议。

### 观察 3：正确性优先于省略小通信

DSPARK 的 TP 分歧说明，小 Tensor 同步本身可能很便宜，但省略它造成的状态分叉代价极高。任何会影响 KV commit、request length 和 collective ordering 的值都应被视为分布式一致性状态。
