## P0：本日最重要变化

### 1. Spec admission 从固定 48 改为 CUDA Graph / 显存派生容量 — PR #34290

- PR：[Derive the speculative max_running_requests default from the decode CUDA-graph ladder](https://github.com/sgl-project/sglang/pull/34290)
- 状态：Open
- 方向：**Scheduler × Speculative Decoding**

**解决的问题**

开启 speculative decoding 后，五个算法 handler 都会把未显式设置的 `max_running_requests` 强行设成 `48`。这会让后续正常的 KV-capacity estimator 误以为是“用户显式指定”，从而完全跳过容量估算。结果是同一张 GPU、同一模型，仅仅打开 Spec，就可能从可运行 **4096 requests** 退化为 **48**；DP=8 时甚至只有每 worker 6 个请求。

**核心改动**

不再维护五份硬编码 `48`，而是统一从 SGLang 已经基于显存得到的 Decode CUDA Graph ladder 推导：

```text
max_running_requests
    = max(48, decode_cuda_graph_max_bs × attention_dp_size)
```

这里 `48` 只保留为历史下限；用户显式配置仍优先。这样 Scheduler admission 与 CUDA Graph capture 使用同一个硬件容量信号。

**性能 / 工程影响**

8×H200、ShareGPT 的端到端数据：

| 模型 / Spec | 并行 | 吞吐提升 |
|---|---:|---:|
| GLM-5.2-FP8 + MTP | TP8 | **2.375×** |
| Qwen3-8B + EAGLE3 | TP1 | **1.343×** |
| DeepSeek-V4 | TP4 | **1.11×** |

GLM accept length 仍约 2.98、Qwen 约 1.93，说明收益不是 draft 质量提升，而是此前 Scheduler 根本没有放足够多请求进来。

**相关代码**

- `python/sglang/srt/arg_groups/speculative_hook.py`
- Spec admission 的单元测试

**面试启发**

这是很典型的“局部 feature 默认值破坏全局 resource planner”问题。面试中如果被问“为什么 Spec 打开后吞吐反而低”，不要只看 acceptance rate / verify kernel，还要检查 **admission、batch size、KV capacity、CUDA Graph bucket 是否一致**。

### 2. NIXL P/D 支持 Prefill Pod/进程替换后的自动恢复 — PR #34289

- PR：[Fix NIXL P/D serving stall after prefill replacement](https://github.com/sgl-project/sglang/pull/34289)
- 状态：Open
- 方向：**Prefill/Decode Disaggregation**

**解决的问题**

生产环境里 Prefill 往往挂在稳定的 K8s Service / bootstrap 地址后面。Prefill 进程被替换后，IP/Service 地址可能不变，但 Decode 端缓存的 rank endpoint 仍指向旧进程。ZMQ PUSH 又可能继续静默排队，于是从 Decode 看起来只是“所有请求一直 timeout”，直到 Decode 自己重启。

本质问题是：**endpoint address 不是 process identity**。

**核心改动**

- 每个 Prefill 进程生成 `uuid4().hex` instance ID。
- `/health`、`/route`、`/query_dp_ranks` 返回 `X-SGLang-Disaggregation-Instance-ID`。
- Rust server 同样携带这一 process-generation 标识。
- heartbeat 发现地址没变但 instance ID 变化时，按 generation 失效 rank endpoint cache。
- NIXL 复用 endpoint 请求失败时，也会触发 fresh connection / topology snapshot 刷新。
- generation gate 防止多个恢复线程把新 endpoint 又被旧结果覆盖。

**性能 / 工程影响**

这是故障恢复路径而非 steady-state 性能 PR。2×RTX3090 的 NIXL A/B 中，旧版本 Prefill replacement 后持续卡死；补丁版在 heartbeat 检测到新 instance 后可以恢复，TP2 多 rank 场景也能独立恢复。

**相关代码**

- `python/sglang/srt/disaggregation/common/conn.py`
- `python/sglang/srt/disaggregation/decode.py`
- `python/sglang/srt/disaggregation/nixl/conn.py`
- `rust/sglang-server/src/api_server.rs`
- `rust/sglang-server/src/api_server/pd_bootstrap.rs`

**面试启发**

这是分布式系统经典的 **logical identity / incarnation（世代）** 问题。地址只回答“去哪儿发”，不能回答“对面还是不是原来的进程”。和 Raft term、lease epoch、connection generation 的思想非常接近。

### 3. PP + HiCache：L3 Prefetch readiness 纳入跨 Stage admission 共识 — PR #34287

- PR：[Fix PP HiCache prefetch readiness consensus](https://github.com/sgl-project/sglang/pull/34287)
- 状态：Draft
- 方向：**KV Cache × P/D × Scheduler**

**解决的问题**

在 PP disaggregated prefill 中，每个 PP stage 都可能独立执行 `check_prefetch_progress()`。KV bootstrap 已完成并不意味着每个 stage 的异步 L3 prefetch 都完成：Stage A 可能认为请求 ready 并加入 batch，而 Stage B 仍跳过它，于是不同 stage 选择了不同逻辑 batch，最终 PP proxy tensor 失同步甚至崩溃。

**核心改动**

没有额外塞一个 blocking all-reduce，而是复用已有的 **stage-by-stage bootstrap RID consensus**：

1. 每个 stage 先用自己的 HiCache readiness 过滤 candidate RID。
2. RID 沿 PP pipeline 逐 stage 求交集。
3. 只有被所有 stage 判定 ready 的请求才进入 `waiting_queue`。
4. 同时保持 RID 原顺序，failed RID 做稳定去重。

这点很关键：PP event loop 天生可能 skew，直接放一个 barrier-style collective 很容易把 correctness fix 变成 deadlock source。

**性能 / 工程影响**

无 steady-state benchmark；核心价值是正确性和组合能力。非 PP 路径保持原行为。

**相关代码**

- `python/sglang/srt/managers/scheduler_pp_mixin.py`
- `test/registered/unit/managers/test_pp_hicache_prefetch_consensus.py`

**面试启发**

要区分两类“ready”：**本地资源 ready** 与 **分布式系统全局可提交 ready**。在 pipeline 中，一个请求只有所有 stage 都拥有一致状态才真正可调度。这和分布式事务 prepare/commit、barrier-free consensus 都有相似思路。

### 4. DP Attention Scheduler：5 次 GPU→CPU 同步压成 1 次 — PR #34338

- PR：[Collapse the DP attention scheduler sync to a single D2H copy](https://github.com/sgl-project/sglang/pull/34338)
- 状态：Open
- 方向：**Scheduler**

DP-attention 的 scheduler metadata 本身只有几百字节，但此前消费时要经历两次 `.cpu()`、三个 min/max `.item()` 等多次 device sync。PR 改成一次把 TP0 row 拷到 CPU，min/max/list 都在 host 上完成。

4 DP rank 微基准：

- all-gather 本体：64.1 µs
- 原消费路径 5 sync：454.6 µs
- 新消费路径 1 sync：172.0 µs
- **每 scheduler step 节省约 282 µs，消费开销下降约 62%**

相关代码：

- `python/sglang/srt/managers/scheduler_components/dp_attn.py`
- `python/sglang/srt/batch_overlap/two_batch_overlap.py`

这里的系统性教训是：**小 tensor 不代表低成本，sync 次数常比 payload 大小更重要。**

### 5. EAGLE/NEXTN/EAGLE3 开始支持多 LoRA adapter 共 batch — PR #34337

- PR：[Support multi-adapter LoRA with EAGLE/NEXTN/EAGLE3 speculative decoding](https://github.com/sgl-project/sglang/pull/34337)
- 状态：Open
- 方向：**Speculative Decoding**

设计选择很值得注意：**LoRA 只作用于 target，draft 保持共享且不适配**。这不会破坏 sampling losslessness，因为最终 target verify 仍从适配后的 target distribution 采样；draft 变差只会影响 acceptance rate。

工程上还补齐了 target-verify 的 token count、MoE LoRA graph buffer 的 verify-width sizing、CUDA Graph 宽度断言，以及 draft 不应误用 target LoRA metadata 等边界。

Qwen3.5-35B-A3B + NEXTN 的数据说明了一个很重要的 trade-off：

- concurrency=1：LoRA + Spec 相比 LoRA no-spec **2.12×**
- concurrency=8：已经低于 no-spec
- concurrency=32：下降更明显

acceptance 基本没掉，因此高并发下的损失来自额外 draft/verify compute 与 batch regime，而非 adapter 把 draft 质量打坏。

相关代码：

- `python/sglang/srt/speculative/eagle_worker_v2.py`

- `python/sglang/srt/lora/lora_manager.py`

**面试启发**：Speculative Decoding 不是“acceptance 越高就一定越快”。要同时看并发度、target batch efficiency、draft/verify 占比和 Scheduler admission。

### 6. Overlap Scheduler 下异步 state capture 改为不可变快照 — PR #34319

- PR：[Snapshot async state-capture outputs before overlap](https://github.com/sgl-project/sglang/pull/34319)
- 状态：Draft
- 方向：**Scheduler × Spec / RL**

**问题**：Overlap scheduler 允许下一次 forward 在另一条 stream 上继续，而上一次 TopK state capture 正在 copy stream 做 D2H。`TopkCaptureOutput` 原来保存的是复用 device buffer 的 view；下一次 forward 可以在 D2H 读完前原地覆盖它。

`record_stream()` 在这里不够，因为它只能阻止 allocator 提前回收内存，**不能阻止持久 buffer 被 in-place mutation**。

**修复**：在 forward stream 上先 clone `out_cache_loc` 和 top-k device buffer，异步 copy 只读取 immutable snapshot。

B200、256 verify tokens / 40 MoE layers / Top-8 的代表 shape：新增 snapshot 中位数约 **18.96 µs**，现有 D2H 约 78.42 µs；只有启用 state capture 时付费。

相关代码：

- `python/sglang/srt/state_capturer/base.py`
- `test/registered/unit/test_state_capturer.py`

这是非常适合面试的 CUDA 并发题：**lifetime safety ≠ mutation safety**。Event、stream dependency、allocator lifetime、buffer ownership 是四个不同概念。

## 对 AI Infra 面试 / 项目实践的启发

1. **容量规划必须单一事实源（single source of truth）**：KV allocator、CUDA Graph ladder、Scheduler admission 各自维护阈值，迟早产生互相矛盾的容量边界。#34290 的价值远大于“把 48 改大”。
2. **P/D 的连接缓存必须带 process generation**：在容器化环境中，Service/IP 稳定但进程会更换。只缓存 endpoint 而没有 incarnation ID，是典型生产故障源。
3. **异步缓存不是只加一条 I/O pipeline**：HiCache L3 会把本来 deterministic 的 radix state 变成受异步完成顺序影响的分布式状态机；PP 下尤其需要把 local readiness 转成 global admission contract。
4. **Overlap scheduler 的核心难点是 ownership**：GPU stream overlap 之后，要逐一回答“谁能改 buffer、谁持有它、什么 event 证明读完、何时 allocator 才能复用”。`record_stream` 不能替代不可变快照。
5. **Spec 性能要看系统 regime，而不是单一 acceptance**：低并发 latency 优化和高并发 throughput 优化可能结论相反。面试时应主动拆成 draft cost、verify cost、accept length、batch size、admission 和 target utilization。
